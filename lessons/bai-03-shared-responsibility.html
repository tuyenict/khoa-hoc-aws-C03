Sau bài này bạn sẽ

  • Phát biểu chính xác Shared Responsibility Model: AWS lo Security OF the cloud, khách hàng lo Security IN the cloud.
  • Xác định ranh giới trách nhiệm thay đổi thế nào giữa dịch vụ IaaS (Amazon EC2), dịch vụ managed (Amazon RDS) và dịch vụ abstracted (Amazon S3, DynamoDB, Lambda).
  • Phân biệt 3 nhóm control: Inherited, Shared và Customer Specific.
  • Hiểu root user của tài khoản AWS, các tác vụ chỉ root user mới làm được và toàn bộ best practices bảo vệ root user.
  • Nắm các loại MFA AWS hỗ trợ, giới hạn 8 thiết bị MFA và cách giám sát việc dùng root user.
  • So sánh các AWS Support plans (Basic, Business Support+, Enterprise, Unified Operations và các gói cũ Developer/Business/Enterprise On-Ramp) để chọn đúng gói theo yêu cầu đề.

Shared Responsibility Model là gì?

Khi đưa workload lên AWS, bảo mật và tuân thủ (security and compliance) là trách nhiệm chung giữa AWS và khách hàng. Shared Responsibility Model giúp giảm gánh nặng vận hành cho khách hàng: AWS vận hành, quản lý và kiểm soát các thành phần từ hệ điều hành host, lớp ảo hóa (virtualization layer) cho tới bảo mật vật lý của các cơ sở (facilities) nơi dịch vụ chạy.

AWS tóm gọn sự phân chia này bằng hai cụm từ rất hay xuất hiện trong đề thi:

AWS – Security “OF” the Cloud

  • “AWS is responsible for protecting the infrastructure that runs all of the services offered in the AWS Cloud.”
  • Hạ tầng gồm hardware, software, networking và facilities chạy các dịch vụ AWS.
  • Bao gồm hạ tầng toàn cầu: Regions, Availability Zones, Edge Locations (học ở Bài 1).
  • Với dịch vụ managed: AWS còn lo cả OS, nền tảng (platform) và việc vá lỗi của chúng.

Khách hàng – Security “IN” the Cloud

  • “Customer responsibility will be determined by the AWS Cloud services that a customer selects.”
  • Dữ liệu khách hàng (customer data), quản lý định danh và quyền truy cập (IAM).
  • Guest OS, ứng dụng, cấu hình firewall (security group), cấu hình mạng – khi dùng IaaS như EC2.
  • Mã hóa phía client/server, bảo vệ traffic mạng (mã hóa, tính toàn vẹn, định danh).
Ví dụ đời thường

Thuê căn hộ trong một tòa chung cư: ban quản lý tòa nhà (AWS) chịu trách nhiệm móng, kết cấu, thang máy, bảo vệ cổng, hệ thống điện nước chung. Bạn (khách hàng) chịu trách nhiệm khóa cửa căn hộ, ai được giữ chìa khóa, đồ đạc bên trong. Nếu bạn để cửa mở và mất đồ, đó không phải lỗi của ban quản lý. Thuê căn hộ dịch vụ (dịch vụ managed) thì ban quản lý lo thêm dọn dẹp, sửa chữa nội thất, nhưng việc bạn giao chìa khóa cho ai vẫn do bạn quyết định.

Mẹo thi (Exam Tip) – Nhận diện nhanh
  • Câu chứa physical security, data center, hardware, hypervisor/virtualization layer, global infrastructure, decommissioning storage devices ⇒ trách nhiệm của AWS.
  • Câu chứa customer data, IAM users/roles/policies, security group rules, guest OS patching (EC2), encryption choice, application code ⇒ trách nhiệm của khách hàng.
  • Dữ liệu luôn luôn là trách nhiệm của khách hàng, kể cả với dịch vụ serverless.

Ranh giới trách nhiệm thay đổi theo loại dịch vụ

Điểm mấu chốt AWS nhấn mạnh: phần việc của khách hàng phụ thuộc vào dịch vụ được chọn, mức độ tích hợp dịch vụ đó vào môi trường IT, cùng các luật và quy định áp dụng. Vì vậy có sự linh hoạt và khách hàng kiểm soát được cách triển khai.

Infrastructure as a Service – ví dụ Amazon EC2

Theo AWS, một dịch vụ như Amazon EC2 được xếp vào nhóm Infrastructure as a Service (IaaS) và “requires the customer to perform all of the necessary security configuration and management tasks”. Khi triển khai một EC2 instance, khách hàng chịu trách nhiệm:

  • Quản lý guest operating system, bao gồm cập nhật và vá bảo mật (security patches).
  • Mọi phần mềm ứng dụng hoặc tiện ích khách hàng cài trên instance.
  • Cấu hình firewall do AWS cung cấp – security group – trên mỗi instance.

Abstracted services – ví dụ Amazon S3, Amazon DynamoDB

Với các dịch vụ abstracted như Amazon S3 và Amazon DynamoDB, AWS vận hành lớp hạ tầng, hệ điều hành và nền tảng; khách hàng chỉ truy cập các endpoint để lưu và lấy dữ liệu. Khách hàng vẫn chịu trách nhiệm:

  • Quản lý dữ liệu của mình, bao gồm các tùy chọn mã hóa (encryption options).
  • Phân loại tài sản (classifying assets).
  • Dùng công cụ IAM để cấp quyền phù hợp.

Ở giữa: dịch vụ managed (container/platform) – ví dụ Amazon RDS

Nhiều tài liệu đào tạo của AWS còn nêu một nhóm “ở giữa” – dịch vụ managed như Amazon RDS, Amazon ElastiCache, AWS Elastic Beanstalk: AWS lo OS và việc vá engine; khách hàng vẫn cấu hình mạng, quyền truy cập, tùy chọn mã hóa, sao lưu… Bảng dưới tổng hợp theo kiến thức thi phổ biến.

Bẫy thường gặp
  • “AWS is responsible for patching the guest OS on EC2” ⇒ sai. AWS chỉ vá hạ tầng; guest OS trên EC2 là việc của khách hàng (có thể tự động hóa bằng AWS Systems Manager Patch Manager – nhưng trách nhiệm vẫn của khách hàng).
  • “Because S3 is managed, AWS encrypts and classifies my sensitive data automatically, so I have no responsibility” ⇒ sai. Khách hàng vẫn quyết định quyền truy cập (bucket policy, IAM), phân loại dữ liệu (có thể dùng Amazon Macie) và tùy chọn mã hóa.
  • Security group có sẵn do AWS cung cấp, nhưng cấu hình rule là trách nhiệm của khách hàng. Mở port 22 ra 0.0.0.0/0 là lỗi của khách hàng.
Mẹo thi (Exam Tip)

Đề hỏi “Which option shifts the MOST security responsibility to AWS” hoặc “reduce operational overhead of patching” ⇒ chọn dịch vụ managed/serverless: tự cài MySQL trên EC2 → chuyển sang Amazon RDS / Aurora; chạy cron job trên EC2 → chuyển sang AWS Lambda + EventBridge Scheduler; tự quản lý file server → Amazon S3 / Amazon EFS / FSx.

Inherited, Shared và Customer Specific controls

Mô hình trách nhiệm chia sẻ cũng áp dụng cho IT controls (các biện pháp kiểm soát CNTT). Giống như trách nhiệm vận hành môi trường IT được chia giữa AWS và khách hàng, việc quản lý, vận hành và kiểm chứng (verification) các IT control cũng được chia sẻ. AWS giúp giảm gánh nặng vận hành control bằng cách quản lý các control gắn với hạ tầng vật lý.

Tài khoản AWS và root user

Khi tạo một AWS account, bạn bắt đầu với một định danh đăng nhập duy nhất có toàn quyền truy cập mọi dịch vụ và tài nguyên trong tài khoản. Định danh này gọi là AWS account root user. Thông tin đăng nhập của root user chính là địa chỉ email và mật khẩu dùng khi tạo tài khoản.

Khuyến nghị cốt lõi của AWS

“We strongly recommend that you don't use the root user for your everyday tasks.” Hãy tạo một administrative user cho công việc hằng ngày: với tài khoản đơn lẻ dùng IAM roles; với nhiều tài khoản trong AWS Organizations dùng IAM Identity Center (workforce users). Người dùng nên xác thực bằng temporary credentials thay vì long-term credentials (mật khẩu, access key của IAM user).

Best practices bảo vệ root user & MFA

Root user có đặc quyền cao nhất, nên AWS đưa ra 9 nhóm best practices để bảo vệ thông tin đăng nhập và account recovery mechanisms của nó.

  1. Secure your root user credentials – chỉ dùng cho các tác vụ bắt buộc; không chia sẻ mật khẩu, MFA, access key, CloudFront key pair hay signing certificate với bất kỳ ai không có nhu cầu kinh doanh chặt chẽ. Không lưu mật khẩu root trong công cụ phụ thuộc vào chính tài khoản AWS đó (mất mật khẩu thì cũng mất quyền vào công cụ). Việc truy cập nơi lưu mật khẩu nên cần ≥ 2 người và được log, giám sát.
  2. Use a strong root user password – mạnh và duy nhất (dùng password manager). AWS yêu cầu: 8–128 ký tự; có ít nhất 3 trong các loại: chữ hoa, chữ thường, số, ký tự đặc biệt; không trùng tên tài khoản hoặc email.
  3. Secure root sign-in with MFA – thêm yếu tố thứ hai ngoài email + mật khẩu. Đăng ký được tối đa 8 thiết bị MFA (kết hợp mọi loại). Mọi loại tài khoản (standalone, management, member) đều bắt buộc MFA cho root user; nếu chưa bật, phải đăng ký trong 14 ngày kể từ lần đăng nhập console đầu tiên.
  4. Don't create access keys for the root user – root có toàn quyền kể cả billing. Tác vụ root hiếm khi cần nên hãy làm trên console. Nếu thật sự cần CLI/SDK, dùng lệnh aws login để nhận credentials tạm thời, tự xoay vòng thay vì tạo access key dài hạn.
  5. Use multi-person approval for root sign-in – không để một người nắm cả mật khẩu và MFA. Ví dụ: nhóm admin A giữ mật khẩu, nhóm admin B giữ MFA; cần một người từ mỗi nhóm mới đăng nhập được.
  6. Use a group email address – email do doanh nghiệp quản lý, chuyển tiếp tới một nhóm người, để AWS liên hệ không bị chậm trễ khi một cá nhân nghỉ phép/nghỉ việc. Email root không dùng cho mục đích khác.
  7. Restrict access to account recovery mechanisms – quản lý hộp thư email root và số điện thoại liên hệ (hai kênh khôi phục). Mất hết MFA thì cần cả email và số điện thoại đã đăng ký còn dùng được. Không ai được nắm cả email lẫn số điện thoại – hai nhóm người quản lý hai kênh.
  8. Secure AWS Organizations root user credentials – management account bắt buộc MFA; member account nên xóa root credentials bằng centralized root access, hoặc ít nhất bảo vệ bằng MFA; có thể dùng SCP chặn hành động của root user ở member accounts.
  9. Monitor access and usage – cảnh báo mỗi khi root đăng nhập/sử dụng; có quy trình xác minh và leo thang (escalate) nếu nghi ngờ sự cố bảo mật.

Đáp án “share the root credentials with the operations team” hoặc “create root access keys for automation scripts” luôn sai.

Quản lý root tập trung & giám sát việc dùng root

Khi chuyển sang chiến lược nhiều tài khoản với AWS Organizations, mỗi tài khoản đều có root user riêng cần được bảo vệ. Tài khoản tạo tổ chức là management account; các tài khoản còn lại là member accounts (chi tiết ở Bài 6).

Centralized root access cho member accounts

  • Remove member account root user credentials – xóa mật khẩu, access key, signing certificate và hủy MFA của root ở member accounts. Tài khoản mới tạo trong Organizations mặc định không có root credentials. Member account khi đó không thể đăng nhập root hay tự khôi phục mật khẩu root (trừ khi bật account recovery).
  • Perform privileged tasks – management account hoặc delegated administrator cho IAM thực hiện một số tác vụ chỉ-root trên member account qua sts:AssumeRoot (phiên đặc quyền ngắn hạn), ví dụ: mở khóa S3 bucket hoặc SQS queue có policy deny-all.
  • Allow password recovery – khi thật cần root của member account, management account bật khôi phục, người giữ hộp thư email root reset mật khẩu; xong việc nên xóa lại root credentials.
  • SCP (Service Control Policy) – nếu member account vẫn còn root credentials, dùng SCP deny mọi hành động của root user ngoại trừ một số tác vụ chỉ-root.

Lưu ý

Nếu bạn làm đúng best practice xóa root credentials ở member accounts, các rule MFA (Config/Security Hub) có thể đánh giá các tài khoản đó là not applicable – không phải lỗi.

Mẹo thi (Exam Tip)

“Notify the security team whenever the root user signs in” với LEAST operational overhead ⇒ CloudTrail + EventBridge rule + SNS. “Prevent member accounts' root users from performing actions” ⇒ SCP (hoặc centralized root access để xóa hẳn root credentials). IAM policy không giới hạn được root user trong chính tài khoản đó.

Tóm tắt ghi nhớ

Key takeaways
  • AWS = Security OF the cloud: hardware, software, networking, facilities, global infrastructure (Regions, AZs, Edge Locations).
  • Khách hàng = Security IN the cloud: phụ thuộc dịch vụ chọn; dữ liệu và IAM luôn của khách hàng.
  • EC2 (IaaS): khách hàng vá guest OS, quản lý ứng dụng, cấu hình security group. S3/DynamoDB (abstracted): AWS lo hạ tầng, OS, platform; khách hàng lo dữ liệu, mã hóa, phân loại, IAM.
  • Inherited: physical & environmental. Shared: patch management, configuration management, awareness & training. Customer specific: service & communications protection, zone security.
  • Root user = email + mật khẩu tạo tài khoản, toàn quyền; không dùng hằng ngày, không tạo access key.
  • Tác vụ chỉ-root: đổi email/mật khẩu/access key root (standalone), đóng/mở lại account, khôi phục quyền IAM admin, bật IAM access vào Billing console, đăng ký seller RI Marketplace, bật S3 MFA Delete, gỡ bucket/SQS policy deny-all, đăng ký GovCloud.
  • MFA: bắt buộc cho root ở mọi loại tài khoản (14 ngày ân hạn); tối đa 8 thiết bị; ưu tiên passkey/security key (FIDO, phishing-resistant); SMS MFA đã ngừng.
  • Multi-account: xóa root credentials ở member accounts (centralized root access, sts:AssumeRoot), SCP chặn root; giám sát bằng CloudTrail + EventBridge + SNS, GuardDuty, Config, Security Hub, Trusted Advisor.
  • Support: Basic (miễn phí, chỉ account/billing) · Business Support+ ($29+, < 30 phút business-critical) · Enterprise ($5,000+, designated TAM, < 15 phút) · Unified Operations (< 5 phút). Legacy Developer/Business/Enterprise On-Ramp ngừng từ 1/1/2027.

Thuật ngữ (Glossary)

Shared Responsibility Model
Mô hình trách nhiệm chia sẻ – phân chia trách nhiệm bảo mật & tuân thủ giữa AWS và khách hàng.
Security OF the cloud
Bảo mật của đám mây – phần AWS chịu trách nhiệm: hạ tầng chạy mọi dịch vụ.
Security IN the cloud
Bảo mật trong đám mây – phần khách hàng chịu trách nhiệm, tùy dịch vụ được chọn.
Infrastructure as a Service (IaaS)
Hạ tầng như một dịch vụ – vd Amazon EC2; khách hàng làm mọi cấu hình bảo mật từ guest OS trở lên.
Abstracted service
Dịch vụ được trừu tượng hóa – vd S3, DynamoDB; AWS vận hành hạ tầng, OS, platform.
Guest operating system
Hệ điều hành khách – OS chạy bên trong máy ảo EC2, do khách hàng quản lý và vá.
Inherited Controls
Control được kế thừa – khách hàng kế thừa hoàn toàn từ AWS (physical & environmental).
Shared Controls
Control dùng chung – áp dụng cho cả lớp hạ tầng và lớp khách hàng (patch, configuration, training).
Customer Specific Controls
Control riêng của khách hàng – chỉ khách hàng chịu trách nhiệm (vd zone security).
AWS Artifact
Cổng báo cáo tuân thủ – tải báo cáo kiểm toán/chứng nhận của AWS.
AWS account root user
Người dùng gốc của tài khoản – định danh có toàn quyền, đăng nhập bằng email + mật khẩu tạo tài khoản.
Multi-factor authentication (MFA)
Xác thực đa yếu tố – thêm yếu tố thứ hai ngoài mật khẩu.
Passkey / Security key (FIDO)
Khóa truy cập / khóa bảo mật – MFA dùng mật mã khóa công khai, chống phishing.
TOTP
Mật khẩu dùng một lần theo thời gian – thuật toán của virtual MFA app và hardware token.
Phishing-resistant MFA
MFA chống lừa đảo – không thể bị đánh cắp bằng trang giả mạo (passkey, security key).
Temporary credentials
Thông tin xác thực tạm thời – do IAM role/STS cấp, tự hết hạn.
Account recovery mechanisms
Cơ chế khôi phục tài khoản – email và số điện thoại đăng ký của root user.
Multi-person approval
Phê duyệt nhiều người – tách người giữ mật khẩu và người giữ MFA.
Management account / Member account
Tài khoản quản lý / Tài khoản thành viên trong AWS Organizations.
Centralized root access
Quản lý root tập trung – xóa root credentials ở member accounts, thực hiện tác vụ đặc quyền từ management account.
Privileged task (sts:AssumeRoot)
Tác vụ đặc quyền – phiên root ngắn hạn trên member account.
Delegated administrator
Quản trị viên được ủy quyền – member account được giao quản trị một dịch vụ cho cả tổ chức.
MFA Delete
Xóa có MFA – S3 yêu cầu MFA khi xóa phiên bản object/tắt versioning; chỉ root bật được.
Support plan
Gói hỗ trợ – Basic, Business Support+, Enterprise, Unified Operations (và các gói cũ).
Technical Account Manager (TAM)
Quản lý tài khoản kỹ thuật – chuyên gia AWS được chỉ định, hướng dẫn chủ động (gói Enterprise trở lên).
Case severity
Mức độ nghiêm trọng của case – general guidance → business-critical system down.
Infrastructure Event Management (IEM)
Quản lý sự kiện hạ tầng – AWS hỗ trợ kiến trúc/scaling cho sự kiện lớn (ra mắt, khuyến mãi).
Concierge Support
Hỗ trợ tận tình về billing/account – có ở các gói Enterprise.

Câu hỏi luyện tập

A company runs a web application on Amazon EC2 instances that use an Amazon Linux AMI. A security audit finds that several instances are missing critical operating system security patches. According to the AWS shared responsibility model, who is responsible for applying these patches?
  1. AWS, because AWS manages the infrastructure that runs Amazon EC2.
  2. AWS, because the instances were launched from an AWS-provided AMI.
  3. The company, because it manages the guest operating system on its EC2 instances.
  4. AWS Support, but only if the company has an Enterprise Support plan.
Đáp án C. EC2 là IaaS: theo AWS, khách hàng quản lý guest operating system, bao gồm cập nhật và security patches, ứng dụng và security group. A sai: AWS chỉ chịu trách nhiệm hạ tầng (hardware, virtualization), không phải OS bên trong instance. B sai: AMI do AWS cung cấp chỉ là điểm khởi đầu; sau khi chạy, việc vá OS thuộc khách hàng. D sai: không gói Support nào chuyển trách nhiệm vá guest OS sang AWS (TAM chỉ tư vấn).
Một công ty chạy ứng dụng web trên các Amazon EC2 instance dùng Amazon Linux AMI. Một cuộc kiểm toán bảo mật phát hiện nhiều instance đang thiếu các bản vá bảo mật quan trọng của hệ điều hành. Theo AWS shared responsibility model (mô hình trách nhiệm chia sẻ), ai chịu trách nhiệm áp dụng các bản vá này?
  • AWS, vì AWS quản lý hạ tầng chạy Amazon EC2.Sai: AWS chỉ chịu trách nhiệm hạ tầng (phần cứng, lớp ảo hóa), không phải hệ điều hành bên trong instance.
  • AWS, vì các instance được khởi chạy từ AMI do AWS cung cấp.Sai: AMI của AWS chỉ là điểm khởi đầu; sau khi chạy, vá guest OS là việc của khách hàng.
  • Công ty, vì công ty quản lý guest operating system trên các EC2 instance của mình.Đúng: EC2 là IaaS – khách hàng quản lý guest OS, gồm cập nhật và security patch, cùng ứng dụng và security group.
  • AWS Support, nhưng chỉ khi công ty có gói Enterprise Support.Sai: không gói Support nào chuyển trách nhiệm vá guest OS sang AWS; TAM chỉ tư vấn.
A company hosts a MySQL database on a self-managed Amazon EC2 instance. The operations team spends many hours each month patching the operating system and the database engine. The company wants to reduce this operational overhead while keeping a MySQL-compatible relational database. What should a solutions architect recommend?
  1. Migrate the database to Amazon RDS for MySQL and configure a maintenance window for automatic patching.
  2. Use AWS Systems Manager Patch Manager to patch the EC2 instance and keep the self-managed database.
  3. Migrate the database to Amazon DynamoDB.
  4. Move the EC2 instance to a Dedicated Host so that AWS patches the operating system.
Đáp án A. Với Amazon RDS, AWS quản lý OS và vá database engine (trong maintenance window khách hàng chọn) ⇒ dịch chuyển trách nhiệm sang AWS và giảm overhead nhiều nhất. B sai: tự động hóa giúp được phần OS nhưng khách hàng vẫn chịu trách nhiệm vá OS và DB engine, overhead vẫn còn. C sai: DynamoDB là NoSQL, không tương thích MySQL. D sai: Dedicated Host chỉ là phần cứng chuyên dụng; guest OS vẫn do khách hàng vá.
Một công ty chạy database MySQL trên một Amazon EC2 instance tự quản lý. Nhóm vận hành mất nhiều giờ mỗi tháng để vá hệ điều hành và database engine. Công ty muốn giảm gánh nặng vận hành này nhưng vẫn giữ một database quan hệ tương thích MySQL. Solutions architect nên đề xuất gì?
  • Chuyển database sang Amazon RDS for MySQL và cấu hình maintenance window để vá tự động.Đúng: với RDS, AWS quản lý OS và vá DB engine trong maintenance window bạn chọn – chuyển trách nhiệm sang AWS, giảm overhead nhiều nhất mà vẫn là MySQL.
  • Dùng AWS Systems Manager Patch Manager để vá EC2 instance và giữ database tự quản lý.Sai: tự động hóa được phần OS nhưng khách hàng vẫn chịu trách nhiệm vá OS và DB engine, overhead vẫn còn.
  • Chuyển database sang Amazon DynamoDB.Sai: DynamoDB là NoSQL, không phải database quan hệ tương thích MySQL.
  • Chuyển EC2 instance sang Dedicated Host để AWS vá hệ điều hành.Sai: Dedicated Host chỉ là phần cứng chuyên dụng; guest OS vẫn do khách hàng vá.
Under the AWS shared responsibility model, which TWO of the following are the responsibility of AWS? (Select TWO.)
  1. Configuring security group rules for Amazon EC2 instances
  2. Physical security of the data centers that host AWS services
  3. Choosing and enabling server-side encryption for objects in Amazon S3
  4. Maintaining and patching the virtualization layer that runs Amazon EC2 instances
  5. Managing IAM user permissions in the company's AWS account
Đáp án B, D. “Security OF the cloud”: AWS bảo vệ hardware, software, networking và facilities – gồm bảo mật vật lý data center (Inherited Control) và lớp ảo hóa. A sai: security group do AWS cung cấp nhưng cấu hình rule là việc khách hàng. C sai: khách hàng quản lý dữ liệu “bao gồm tùy chọn mã hóa”. E sai: IAM luôn là trách nhiệm khách hàng.
Theo AWS shared responsibility model, HAI mục nào sau đây là trách nhiệm của AWS? (Select TWO – chọn hai.)
  • Cấu hình rule của security group cho các Amazon EC2 instanceSai: AWS cung cấp tính năng security group, nhưng cấu hình rule là trách nhiệm khách hàng.
  • Bảo mật vật lý của các data center chứa dịch vụ AWSĐúng: thuộc "security OF the cloud" – AWS bảo vệ cơ sở vật chất; khách hàng kế thừa hoàn toàn (Inherited Control).
  • Lựa chọn và bật mã hóa phía server (server-side encryption) cho các object trong Amazon S3Sai: khách hàng quản lý dữ liệu của mình, bao gồm các tùy chọn mã hóa.
  • Bảo trì và vá lớp ảo hóa (virtualization layer) chạy các Amazon EC2 instanceĐúng: lớp ảo hóa/hypervisor là hạ tầng do AWS vận hành – thuộc security OF the cloud.
  • Quản lý quyền của IAM user trong tài khoản AWS của công tySai: quản lý danh tính và quyền truy cập (IAM) luôn là trách nhiệm khách hàng.
A startup has just created a new AWS account. The founders have been signing in with the root user for all daily tasks and have created root user access keys for a deployment script. A solutions architect must improve the security of the account by following AWS best practices. Which combination of actions should the solutions architect take?
  1. Rotate the root user access keys every 30 days and store them in the deployment script's configuration file.
  2. Share the root user password with all founders through a team chat channel so that each founder can sign in when needed.
  3. Attach an IAM policy to the root user that denies all actions except billing.
  4. Enable MFA for the root user, delete the root user access keys, and create an administrative user (IAM Identity Center or IAM role) for daily tasks, with the deployment script using an IAM role.
Đáp án D. Đúng best practices: bật MFA cho root, không có access key root, tạo administrative user cho việc hằng ngày và dùng credentials tạm thời (IAM role) cho script. A sai: vẫn là access key dài hạn của root – AWS khuyến nghị không tạo. B sai: không chia sẻ credentials root; nên dùng multi-person approval và kênh lưu trữ an toàn.
