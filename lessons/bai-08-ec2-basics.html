Amazon EC2 là gì? Các thành phần cốt lõi

Amazon Elastic Compute Cloud (Amazon EC2) cung cấp năng lực tính toán theo nhu cầu, mở rộng được trên AWS Cloud. Bạn khởi chạy bao nhiêu máy chủ ảo cũng được, tự cấu hình bảo mật, mạng và lưu trữ; tăng năng lực (scale up) khi có tác vụ nặng hoặc lưu lượng tăng đột biến, rồi giảm lại (scale down) khi nhu cầu giảm.

Một EC2 instance là một máy chủ ảo trên AWS Cloud. Khi khởi chạy, instance type bạn chọn quyết định phần cứng của máy chủ host – mỗi loại có tỉ lệ compute, memory, network, storage khác nhau. Theo trang “What is Amazon EC2?”, EC2 có các tính năng cấp cao sau:

Instance types & instance families

Mỗi instance type cung cấp khả năng compute, memory, storage khác nhau và được gom vào một instance family theo các khả năng đó. Mỗi type có một hoặc nhiều size để bạn scale theo nhu cầu workload.

Tài liệu nêu một chi tiết quan trọng về cách EC2 chia tài nguyên của host: CPU, memory, instance storage được dành riêng cho từng instance; còn network và disk subsystem được chia sẻ giữa các instance trên cùng host. Khi mọi instance cùng dùng hết tài nguyên chia sẻ, mỗi instance nhận phần bằng nhau; khi tài nguyên rảnh, một instance có thể dùng nhiều hơn. Instance type có I/O cao được cấp phần tài nguyên chia sẻ lớn hơn và ít biến động hơn.

Bộ xử lý, hypervisor và virtualization

Intel & AMD (x86)

  • Intel: AES-NI (mọi instance current generation đều hỗ trợ), AVX/AVX2/AVX-512, Turbo Boost, DL Boost (VNNI).
  • AMD EPYC (chữ a): tối ưu chi phí và hiệu năng; hỗ trợ SME, TSME, SEV-SNP (mã hóa bộ nhớ).

AWS Graviton (Arm)

  • Họ chip Arm do AWS thiết kế, mang lại best price performance cho workload trên EC2 (chữ g).
  • Cần phần mềm/AMI hỗ trợ kiến trúc arm64 – AMI x86 không chạy được trên Graviton.

AWS Trainium & Inferentia

  • Trainium (Trn): chip chuyên cho training deep learning hiệu năng cao, tiết kiệm chi phí (PyTorch, TensorFlow).
  • Inferentia (Inf): tăng tốc inference ML với độ trễ thấp; dùng AWS Neuron SDK.
  • Hypervisor: EC2 hỗ trợ Xen (thế hệ cũ: M4, C4, R4, T2, I3…) và Nitro (hầu hết thế hệ hiện tại: M5+, C5+, R5+, T3, T4g…). Một số tính năng mới chỉ có trên Nitro-based instance (vd IMDS qua IPv6).
  • Virtualization type do AMI quyết định: HVM và PV. Mọi instance type current generation chỉ hỗ trợ HVM. HVM bắt buộc để dùng enhanced networking và GPU. Windows AMI luôn là HVM.
  • Muốn thử nhiều type? Tài liệu khuyên chạy benchmark ứng dụng của chính bạn – vì tính tiền theo giây nên thử rất rẻ. Gợi ý chọn type: EC2 instance type finder và AWS Compute Optimizer. Đổi instance type sau này được: với EBS-backed instance, stop instance rồi đổi.

Burstable performance instances (dòng T) và CPU credits

Nhiều workload phổ thông trung bình rất rảnh, chỉ thỉnh thoảng tăng vọt CPU. Burstable performance instances (T8i, T4g, T3a, T3 và T2 thế hệ trước) cho một mức baseline CPU, có thể burst vượt baseline khi cần. Tài liệu nêu T instance có thể tiết kiệm tới 15% so với M instance, nhỏ nhất chỉ 2 vCPU, 0,5 GiB memory.

  • 1 CPU credit = 1 vCPU × 100% × 1 phút (hoặc 1 vCPU × 50% × 2 phút…). Instance kiếm credit liên tục khi chạy dưới baseline và tiêu credit khi vượt baseline (tính ở mức mili-giây).
  • Ví dụ t3.nano: 2 vCPU, baseline 5% ⇒ kiếm 2 × 5% × 60 = 6 credit/giờ; tích lũy tối đa = credit kiếm được trong 24 giờ = 144 credit. t3.large kiếm 36 credit/giờ ⇒ baseline 30%.
  • Credit trên instance đang chạy không hết hạn. Khi stop: T2 mất hết credit; T3/T3a/T4g/T8i giữ credit 7 ngày.

Standard mode

  • Burst bằng credit đã tích lũy. Hết credit ⇒ CPU tụt dần về baseline, không burst được cho tới khi tích lũy lại.
  • Mặc định của T2; chỉ T2 standard có launch credits.
  • T3 trên Dedicated Host chỉ chạy được standard.

Unlimited mode

  • Hết credit tích lũy vẫn burst bằng surplus credits, duy trì CPU cao bao lâu cũng được.
  • EC2 tính trung bình CPU trong 24 giờ cuộn: nếu trung bình > baseline ⇒ trả thêm phí cố định theo vCPU-giờ.
  • Mặc định của T3, T3a, T4g, T8i.
Bẫy thường gặp với dòng T
  • Ứng dụng “chạy nhanh lúc đầu rồi chậm dần, CloudWatch CPUCreditBalance về 0” ⇒ instance T ở standard mode đã hết credit. Cách sửa: bật unlimited mode hoặc chuyển sang family có CPU cố định (M, C) nếu CPU cao liên tục.
  • Workload CPU cao suốt ngày mà vẫn dùng T unlimited ⇒ trả phí surplus thường xuyên, có thể đắt hơn M/C cùng cỡ. Dòng T chỉ hợp với CPU thấp–trung bình, có đỉnh ngắn.
Mẹo thi (Exam Tip) – chọn instance family
  • “In-memory database, real-time big data analytics, SAP HANA, large caches” ⇒ Memory optimized (R, X, U).
  • “Batch processing, video encoding, high-performance web servers, scientific modeling, gaming servers” ⇒ Compute optimized (C).
  • “High sequential/random I/O to local storage, NoSQL like Cassandra, data warehousing, millions of IOPS” ⇒ Storage optimized (I, D).
  • “Machine learning training / graphics rendering / GPU” ⇒ Accelerated computing (P, G, Trn, Inf). “Lowest cost ML inference” ⇒ Inferentia.
  • “Low average CPU with occasional spikes, dev/test, small websites, most cost-effective” ⇒ T3/T4g. “Best price performance, workload supports Arm” ⇒ Graviton.

Amazon Machine Images (AMI)

Một Amazon Machine Image (AMI) chứa phần mềm cần thiết để thiết lập và boot một EC2 instance, kèm một block device mapping chỉ định các ổ đĩa sẽ gắn vào instance. Bạn bắt buộc chọn AMI khi launch, và AMI phải tương thích với instance type đã chọn.

Nguồn AMI: AMI do AWS cung cấp (Amazon Linux 2023, Windows Server…), public AMI của cộng đồng, AMI người khác chia sẻ với bạn, hoặc AMI mua trên AWS Marketplace (có thể tính thêm phí phần mềm). Public AMI của Amazon hoặc đối tác đã xác minh được gắn nhãn Verified provider (owner alias amazon, aws-marketplace, aws-backup-vault). Tài liệu nhấn mạnh: dùng shared AMI là tự chịu rủi ro – hãy đối xử như code lạ và kiểm tra kỹ.

Chia sẻ AMI và AMI được mã hóa

  • Chỉ owner mới chia sẻ được. Chia sẻ với account ID (12 chữ số), organization hoặc OU mà không cần public. Người nhận chỉ launch được – không xóa, không chia sẻ lại, không sửa – nhưng có thể tạo AMI riêng từ instance của họ.
  • AMI là tài nguyên Region: share ở Region nào chỉ dùng được ở Region đó ⇒ muốn dùng Region khác thì copy rồi share.
  • Không cần share EBS snapshot đi kèm, nhưng phải share KMS key đã mã hóa snapshot. AMI có snapshot mã hóa bằng AWS managed key mặc định (aws/ebs) không chia sẻ được ⇒ copy AMI và re-encrypt bằng customer managed key, rồi cấp quyền key cho account đích.
  • Người launch AMI trả tiền instance; owner không bị tính phí khi người khác dùng AMI của mình.
  • Block public access for AMIs: cài ở cấp account cho từng Region; bật mặc định với account mới (và account cũ chưa từng có public AMI). Khi bật, mọi thao tác public AMI bị chặn – AMI đã public từ trước vẫn public. Dùng declarative policy của AWS Organizations để áp nhiều account/Region cùng lúc.

  • “Launch identical instances in another Region for DR” ⇒ Copy AMI sang Region đó (AMI ID ở Region đích sẽ khác).
  • “Share an encrypted AMI with another account” ⇒ snapshot phải mã hóa bằng customer managed KMS key, sửa key policy cho account đích, rồi thêm launch permission. Nếu đang dùng aws/ebs ⇒ copy + re-encrypt trước.
  • “Encrypt an existing unencrypted AMI” ⇒ copy AMI với tùy chọn encrypt (không có nút “encrypt in place”).
  • “Prevent anyone from making AMIs public across all accounts” ⇒ block public access for AMIs qua declarative policy của Organizations (hoặc SCP chặn ModifyImageAttribute).
  • “Prevent use of an outdated AMI without deleting it” ⇒ disable (chặn launch) hoặc deprecate (ẩn khỏi danh sách).

User data – bootstrap instance lúc khởi động

Khi launch, bạn có thể truyền user data cho instance để chạy các tác vụ cấu hình tự động hoặc chạy script sau khi instance khởi động – gọi là bootstrapping. Với kịch bản tự động hóa phức tạp hơn, tài liệu gợi ý dùng AWS CloudFormation.

Hai loại user data trên Linux

Shell script

  • Bắt đầu bằng #! + đường dẫn interpreter (thường #!/bin/bash).
  • Cách dễ và đầy đủ nhất nếu đã quen shell.

cloud-init directives

  • Dòng đầu bắt buộc #cloud-config; khai báo packages, runcmd, write_files…
  • Gói cloud-init cũng là thứ cấu hình .ssh/authorized_keys cho ec2-user.
  • Kết hợp cả hai bằng file MIME multi-part.

Golden AMI hay user data?

Golden AMI (nướng sẵn)

  • Cài sẵn OS patch, runtime, agent, ứng dụng vào AMI.
  • Boot nhanh – rất quan trọng với Auto Scaling phải scale-out gấp.
  • Mỗi lần đổi phần mềm phải build AMI mới (tự động bằng EC2 Image Builder).

User data (cấu hình lúc chạy)

  • Linh hoạt: một AMI chung, khác nhau ở tham số (môi trường, bucket, cluster name).
  • Boot chậm nếu cài nhiều gói; phụ thuộc kho phần mềm bên ngoài lúc khởi động.
  • Kết hợp tốt nhất: golden AMI + user data ngắn cho phần cấu hình động.
Mẹo thi (Exam Tip) – user data
  • “Instances take 15 minutes to install software at boot; Auto Scaling must respond faster” ⇒ tạo golden AMI chứa phần mềm cài sẵn, giữ user data cho cấu hình động (có thể kết hợp warm pool ở Bài 13).
  • “Run a script automatically when an instance first launches” ⇒ user data. “Run commands on a fleet of running instances” ⇒ Systems Manager Run Command, không phải user data.
  • “Script in user data needs to call S3” ⇒ gắn IAM role qua instance profile – không bao giờ chọn đáp án nhúng access key vào user data.

Instance metadata & IMDSv2

Instance metadata là dữ liệu về chính instance mà bạn dùng để cấu hình hoặc quản lý instance đang chạy. Nó được phục vụ bởi Instance Metadata Service (IMDS) chạy cục bộ trên mọi EC2 instance, chỉ truy cập được từ bên trong instance qua địa chỉ link-local.

Instance metadata gồm ba phần:

  • Metadata properties theo category: http://169.254.169.254/latest/meta-data/
  • Dynamic data sinh lúc launch, vd instance identity document (kèm chữ ký pkcs7 để bên thứ ba xác minh): …/latest/dynamic/
  • User data: …/latest/user-data (không có thì trả 404 - Not Found)

IPv6: http://[fd00:ec2::254]/latest/meta-data/ – phải bật riêng, chỉ trên Nitro-based instance trong subnet hỗ trợ IPv6. Dùng đường dẫn latest thay số version để không phải sửa code khi AWS phát hành build mới. Gọi IMDS không tốn phí.

IMDSv1 vs IMDSv2

IMDSv1 – request/response

  • Một lệnh GET đơn giản, không cần token.
  • Nếu ứng dụng có lỗ hổng SSRF, reverse proxy hoặc firewall cấu hình mở, kẻ tấn công có thể khiến server tự gọi 169.254.169.254 và lấy cắp credentials của IAM role.

IMDSv2 – session-oriented

  • Bước 1: PUT /latest/api/token với header X-aws-ec2-metadata-token-ttl-seconds (1 giây – 6 giờ).
  • Bước 2: mọi GET gửi kèm header X-aws-ec2-metadata-token. Token chỉ hợp lệ trên đúng instance sinh ra nó.
  • PUT chứa header X-Forwarded-For bị từ chối (chặn đi qua proxy).
  • Phản hồi PUT có hop limit (IP TTL) mặc định 1 ⇒ token không “bay” ra khỏi instance.

Thứ tự ưu tiên khi launch: (1) giá trị chỉ định lúc launch / trong launch template → (2) account-level defaults (đặt theo từng Region, không ảnh hưởng instance đã có) → (3) cấu hình AMI: đặt imds-support = v2.0 khi register/modify AMI thì instance launch từ AMI đó tự có HttpTokens=required và hop limit 2 (chỉ áp cho HttpTokens và hop limit). Bẫy & lưu ý vận hành
  • Metadata và user data không có xác thực/mã hóa – IMDSv2 chỉ chống truy cập gián tiếp, không biến user data thành nơi cất bí mật.
  • Chuyển sang required trước khi mọi phần mềm hỗ trợ IMDSv2 ⇒ ứng dụng/agent cũ dùng IMDSv1 sẽ hỏng. Các AWS SDK bản mới đều dùng IMDSv2 mặc định (vd AWS CLI ≥ 1.16.289, Boto3 ≥ 1.12.6).
  • IMDS bị throttle theo instance; dịch vụ link-local (DNS Route 53 Resolver, IMDS, NTP, Windows licensing) chung giới hạn 1024 packets/giây. Đừng gọi lấy credentials ở mọi transaction – hãy cache và retry với exponential backoff.
  • Container trên EC2 không lấy được token? Kiểm tra hop limit = 1 ⇒ tăng lên 2.
Mẹo thi (Exam Tip) – metadata
  • “Protect against SSRF stealing IAM role credentials from the metadata endpoint”, “require session tokens for metadata” ⇒ IMDSv2 required (HttpTokens=required), áp diện rộng bằng account default/SCP.
  • “Application needs to know its own instance ID / AZ / private IP at runtime” ⇒ đọc instance metadata (không cần gọi API EC2, không cần quyền IAM).
  • “Third party must verify that a request comes from a specific EC2 instance” ⇒ instance identity document + chữ ký.

  • Termination protection (DisableApiTermination): bật lên thì không terminate được qua console, CLI, API – chống xóa nhầm.

  • AWS khuyên reboot bằng EC2 (console/API) thay vì lệnh reboot trong OS. Stop/start là cách khắc phục phổ biến khi instance fail status check vì instance thường được dời sang host mới.

  • “Public IP changes every time the instance is stopped and started” ⇒ gắn Elastic IP (Bài 10).
  • “Data on instance store lost after stopping” ⇒ hành vi đúng thiết kế; dữ liệu cần bền ⇒ EBS/EFS/S3.
  • “Protect production instances from accidental termination” ⇒ termination protection (+ IAM/SCP chặn ec2:TerminateInstances). “Keep the root volume after termination” ⇒ DeleteOnTermination=false.

EC2 Hibernate – giữ nguyên RAM qua lần khởi động

Khi hibernate, EC2 báo hệ điều hành thực hiện suspend-to-disk: nội dung RAM được lưu xuống root EBS volume. Khi start lại: root volume về đúng trạng thái trước, RAM được nạp lại, các tiến trình đang chạy tiếp tục, data volume được gắn lại và instance giữ nguyên instance ID.

Ứng dụng nào mất nhiều thời gian bootstrap và “làm nóng” bộ nhớ (nạp cache lớn, JVM warm-up…) thì dùng hibernate để pre-warm: launch có bật hibernation → đưa về trạng thái mong muốn → hibernate → khi cần chỉ việc start là có ngay trạng thái đó.

Bẫy: hibernate ≠ stop ≠ reboot
  • Đề hỏi “preserve in-memory state / resume running processes quickly” ⇒ hibernate. Stop/start mất RAM; reboot cũng mất RAM (chỉ giữ instance store).
  • Instance root instance store không hibernate được; instance có RAM 256 GiB (vd r5.8xlarge) cũng không hibernate được (vượt 150 GiB).
  • Quên mã hóa root volume, hoặc quên bật hibernation lúc launch ⇒ phải launch instance mới.
Mẹo thi (Exam Tip) – hibernate
  • “Application takes a long time to load data into memory at startup; stop instances at night to save cost and resume quickly in the morning” ⇒ EC2 hibernation (encrypted EBS root đủ lớn, bật lúc launch).
  • “Long-running process on an instance must survive a stop” ⇒ hibernate giữ tiến trình; hoặc thiết kế lại ứng dụng stateless.

Tóm tắt ghi nhớ

Những điều phải nhớ
  • EC2 = instance + instance type + AMI + EBS/instance store + key pair + security group. On-Demand tính theo giây, tối thiểu 60 giây; chỉ tính phí instance khi running (và stopping nếu hibernate).
  • Tên type: series + generation + options . size (c7gn.xlarge). M/T = general, C = compute, R/X/U/z = memory, I/D = storage, P/G/Inf/Trn/F = accelerated, Hpc = HPC; g = Graviton, a = AMD, d = instance store, n = network.
  • Dòng T: CPU credit (1 vCPU × 100% × 1 phút), tích lũy tối đa 24 giờ; standard hết credit thì về baseline (mặc định T2), unlimited burst tiếp và trả phí surplus (mặc định T3/T3a/T4g/T8i). T2 mất credit khi stop, T3+ giữ 7 ngày.
  • AMI gắn với Region, OS, architecture, root volume type, virtualization. Copy sang Region khác (miễn phí, có thể mã hóa/đổi key); share với account/org/OU; AMI mã hóa bằng aws/ebs không share được ⇒ re-encrypt bằng customer managed key. Deprecate (ẩn) · disable (chặn launch) · deregister (xóa, snapshot vẫn còn). Block public access for AMIs bật mặc định cho account mới.
  • EBS-backed AMI: boot < 1 phút, stop được; S3-backed: boot < 5 phút, không stop được, end of life. Create image mặc định reboot; no-reboot không đảm bảo file system integrity.
  • User data: ≤ 16 KB, base64, chạy bằng root, chỉ lần boot đầu, sửa khi stopped, không nằm trong AMI, không chứa bí mật. Boot chậm ⇒ golden AMI (EC2 Image Builder).
  • IMDS tại 169.254.169.254 / [fd00:ec2::254]. IMDSv2: PUT lấy token (1 giây – 6 giờ), GET kèm token, hop limit mặc định 1 (container: 2), chặn X-Forwarded-For ⇒ chống SSRF. Ép bằng HttpTokens=required, account default theo Region, AMI imds-support v2.0, IAM/SCP condition key.
  • Reboot giữ host, IP, instance store; stop/start đổi host, đổi public IP, mất instance store; hibernate lưu RAM vào root EBS mã hóa (Linux < 150 GiB RAM, Windows ≤ 16 GiB, bật lúc launch, On-Demand/Spot); terminate xóa root volume mặc định, gỡ Elastic IP.

A company runs containers with Docker on Amazon EC2 instances. The instances are configured to require IMDSv2. Applications inside the containers use the AWS SDK and fail to retrieve the instance's IAM role credentials, while the same SDK works directly on the host. What is the MOST likely solution?
  1. Change the instance metadata options to allow IMDSv1 only.
  2. Attach an Elastic IP address to the instance so that containers can reach the IMDS.
  3. Store access keys for an IAM user in environment variables of each container.
  4. Increase the PUT response hop limit for the instance metadata to 2.
Đáp án D. Phản hồi PUT của IMDSv2 có hop limit mặc định 1; đi vào container tính thêm một hop nên token không tới được container. Tài liệu khuyến nghị tăng hop limit lên 2 trong môi trường container. A sai: quay lại IMDSv1 làm yếu bảo mật (SSRF), và không có tùy chọn “IMDSv1 only”. B sai: IMDS là địa chỉ link-local, Elastic IP không liên quan. C sai: dùng access key dài hạn là anti-pattern; trên ECS nên dùng task IAM role (Bài 34).
