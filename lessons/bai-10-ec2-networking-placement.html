Sau bài này bạn sẽ

  • Hiểu Security Group hoạt động thế nào: chỉ có rule allow, stateful nhờ connection tracking, tham chiếu security group khác làm nguồn (security group referencing) và các quota quan trọng.
  • Phân biệt private IPv4, public IPv4, IPv6 và Elastic IP address – địa chỉ nào giữ nguyên, địa chỉ nào đổi khi stop/start, và chi phí public IPv4.
  • Dùng Elastic Network Interface (ENI) cho management network, appliance, dual-homed instance và giải pháp failover “low-budget high availability”.
  • Chọn đúng placement group: cluster (độ trễ thấp), partition (hệ phân tán lớn, topology-aware), spread (ít instance quan trọng, tách phần cứng) – kèm các giới hạn hay thi.
  • Biết khi nào cần enhanced networking (ENA, ENA Express) và khi nào cần Elastic Fabric Adapter (EFA) cho HPC/ML tightly coupled.
Vị trí của bài trong Module 2 – Compute

Bài 8 đã dạy instance type, AMI, user data, IMDS (địa chỉ link-local 169.254.169.254), vòng đời và hibernate; Bài 9 dạy các phương thức mua (On-Demand Capacity Reservation được nhắc lại ở đây khi nói về cluster placement group). Bài này tập trung vào lớp mạng gắn trực tiếp với instance. Phần VPC, subnet, route table, internet gateway, NAT học ở Bài 20; so sánh chi tiết Security Group vs Network ACL, ephemeral ports, Flow Logs ở Bài 21; ELB ở Bài 12. Ở đây chỉ nhắc tới VPC/NACL ở mức đủ để hiểu security group và ENI.

Bức tranh tổng thể: một EC2 instance “nối mạng” ra sao?

Khi launch một instance vào một subnet của VPC, EC2 gắn cho nó một card mạng ảo (network interface) mang địa chỉ IP, được bảo vệ bởi một hoặc nhiều security group; tùy nhu cầu, bạn gắn thêm Elastic IP, thêm ENI phụ, bật enhanced networking/EFA và chọn placement group để ảnh hưởng tới vị trí vật lý. Đề SAA-C03 hỏi các mảnh này rải rác ở Domain 1 (bảo mật – security group) và Domain 3 (hiệu năng – placement group, EFA).

Ví dụ đời thường – một căn hộ trong chung cư

Instance là căn hộ. ENI là cửa ra vào có số nhà (private IP) và mã khóa riêng (MAC) – căn hộ luôn có cửa chính (primary ENI), có thể mở thêm cửa phụ ra hành lang kỹ thuật (secondary ENI). Security Groups – tường lửa ảo của EC2

Một security group đóng vai trò tường lửa ảo cho EC2 instance, kiểm soát traffic đi vào và đi ra. Inbound rules kiểm soát traffic tới instance, outbound rules kiểm soát traffic rời instance. Khi launch bạn chỉ định một hoặc nhiều security group; nếu không chỉ định, EC2 dùng default security group của VPC. Sau khi launch vẫn đổi được security group. Dùng security group không tốn thêm phí.

Đặc điểm cốt lõi (theo tài liệu)

  • Một instance gắn được nhiều security group, một security group gắn được cho nhiều instance. Khi quyết định cho traffic tới instance, EC2 đánh giá tất cả rule của tất cả security group gắn với instance – các rule được gộp (aggregate) thành một tập duy nhất.
  • Chỉ có rule allow, không có rule deny. Muốn chặn một IP cụ thể ⇒ không làm được bằng security group (dùng Network ACL – Bài 21, hoặc AWS WAF ở tầng ứng dụng).
  • Security group mới tạo: không có inbound rule (chặn mọi traffic vào cho tới khi bạn thêm rule) và có một outbound rule cho phép tất cả traffic ra. Bạn có thể xóa rule outbound đó; khi không còn outbound rule nào thì không traffic nào được đi ra.
  • Thêm/sửa/xóa rule tự áp dụng ngay cho mọi instance đang gắn security group đó (không cần restart).
  • Stateful: nếu instance gửi request ra, traffic phản hồi được phép đi vào bất kể inbound rules; ngược lại, phản hồi cho traffic inbound đã được allow được phép đi ra bất kể outbound rules.
  • Security group gắn ở mức network interface: mọi IP trên cùng một ENI chịu chung security group của ENI đó.
  • Mỗi rule được AWS gán một ID duy nhất (security group rule ID) để sửa/xóa qua API/CLI.
  • Security group thuộc về một VPC – chỉ dùng cho tài nguyên trong VPC đó (muốn dùng ở VPC khác phải tạo security group mới trong VPC đó).
  • Giới hạn: security group không chặn được DNS tới Route 53 Resolver (địa chỉ “VPC+2” hay AmazonProvidedDNS) – muốn lọc DNS dùng Route 53 Resolver DNS Firewall. Traffic tới các địa chỉ link-local dành riêng (IMDS 169.254.169.254, Time Sync 169.254.169.123…) cũng không bị security group hay NACL lọc.

Default security group

Mỗi VPC (default VPC hay VPC bạn tạo) đi kèm một security group tên default. Bạn sửa được rule nhưng không xóa được nó (lỗi Client.CannotDelete). AWS khuyến nghị tạo security group riêng cho từng tài nguyên/nhóm tài nguyên thay vì dùng default.

Default security group (của VPC)

  • Inbound: All traffic, source = chính security group này ⇒ các instance cùng gắn default SG nói chuyện với nhau mọi port.
  • Outbound: All traffic tới 0.0.0.0/0 (và ::/0 nếu VPC có IPv6).
  • Không nhận traffic từ Internet gateway hay NAT gateway (không có rule inbound từ ngoài).

Security group bạn mới tạo

  • Inbound: trống ⇒ chặn mọi traffic vào.
  • Outbound: All traffic tới mọi nơi (xóa được).
  • Bạn tự thêm rule theo nguyên tắc least privilege.

Security group referencing – dùng security group làm nguồn

Khi chỉ định một security group làm source/destination, rule áp dụng cho mọi instance gắn security group được tham chiếu; chúng giao tiếp bằng private IP của network interface, theo protocol/port đã chỉ định. Đây là cách “chuẩn” để cấu hình kiến trúc nhiều tầng mà không cần biết IP – đặc biệt hữu ích khi instance co giãn trong Auto Scaling group (IP thay đổi liên tục).

  • Tham chiếu được trong inbound rule nếu hai security group: cùng VPC, hoặc hai VPC có VPC peering, hoặc nối qua transit gateway. Trong outbound rule: cùng VPC hoặc qua peering.
  • Rule của security group được tham chiếu không được “gộp” vào security group tham chiếu – chỉ là “tập instance nguồn”.
  • Một rule tham chiếu security group tính là 1 rule, bất kể security group đó có bao nhiêu instance. Rule tham chiếu customer-managed prefix list tính bằng max entries của prefix list (vd max 20 ⇒ tính 20 rule).
  • Stale security group rule: rule tham chiếu security group ở VPC peer/shared VPC sẽ bị đánh dấu stale khi security group đó bị xóa hoặc peering bị xóa.
  • Giới hạn: nếu traffic giữa hai instance ở hai subnet đi qua một middlebox appliance (firewall trung gian), tham chiếu security group của instance kia không có tác dụng – phải dùng private IP hoặc CIDR subnet của instance kia làm source.

Stateful & connection tracking

Security group dùng connection tracking để theo dõi trạng thái kết nối – vì vậy mới “stateful”. Ví dụ trong tài liệu: inbound cho phép ICMP từ máy nhà bạn; phản hồi từ instance được coi là established connection nên vẫn đi ra được, kể cả khi outbound rule hạn chế ICMP. Với giao thức khác TCP/UDP/ICMP, chỉ IP và protocol number được theo dõi; nếu host bên kia gửi cùng loại traffic về trong 600 giây, security group coi đó là phản hồi và chấp nhận.

Bẫy thường gặp – “đã xóa rule mà vẫn SSH được”
  • Xóa rule SSH hẹp (vd /32) không ngắt phiên SSH đang mở vì kết nối đó được track. Muốn chặn ngay lập tức traffic đang diễn ra ⇒ thêm rule deny vào Network ACL của subnet (stateless – chặn cả kết nối đang có).
  • Đề cho “block a specific malicious IP address” ⇒ security group không có deny ⇒ đáp án là Network ACL (hoặc AWS WAF cho HTTP/HTTPS qua ALB/CloudFront).
  • Instance không ra được Internet dù route đúng? Kiểm tra outbound rule của security group (có thể đã bị xóa) và NACL – nhớ NACL stateless cần mở cả chiều về.

  • Launch vào default VPC ⇒ mặc định có public IP. Launch vào subnet của nondefault VPC ⇒ phụ thuộc thuộc tính auto-assign public IPv4 của subnet (mặc định không gán). Có thể ghi đè lúc launch, hoặc unassign sau khi launch.
  • Public IP bị release khi instance stop, hibernate, terminate, hoặc khi bạn gắn Elastic IP vào instance (khi gỡ EIP, instance nhận public IP mới).
  • Không cấp lại public IP mới nếu instance có secondary network interface, hoặc có secondary private IP đã gắn EIP. Bạn cũng không bật auto-assign public IPv4 được nếu thêm secondary ENI ngay lúc launch.
  • Dùng dynamic DNS trỏ vào public IP mới có thể mất tới 24 giờ để lan truyền ⇒ cần IP cố định thì dùng Elastic IP.
  • Public DNS hostname phân giải ra public IP/EIP khi hỏi từ ngoài mạng của instance, và ra private IP khi hỏi từ trong VPC. Hai instance ở hai VPC nói chuyện qua public IP thì traffic vẫn nằm trong mạng toàn cầu của AWS, không đi qua Internet công cộng.

Elastic IP – đặc điểm

  • Static – không đổi theo thời gian; là public IPv4; chỉ dùng trong một Region, không chuyển sang Region khác. Không có Elastic IP cho IPv6.
  • Quy trình: allocate vào account ⇒ associate với instance hoặc network interface. Gắn với instance = gắn với primary ENI của nó. Mỗi private IPv4 trên ENI gắn được một EIP.
  • Disassociate rồi associate sang tài nguyên khác được (nên đóng hết kết nối đang mở trước). EIP đã disassociate vẫn thuộc account cho tới khi bạn release.
  • Gắn EIP vào instance đang có public IPv4 ⇒ public IP cũ trả về pool, public DNS hostname đổi theo EIP.
  • Có thể gắn EIP với một network border group (nơi quảng bá CIDR); EIP chỉ dùng được trong network border group đó (liên quan Local Zones – Bài 1).
  • Các thao tác khác: chuyển EIP giữa các AWS account, tạo reverse DNS record (gửi email từ EC2), BYOIP (mang dải IPv4 của mình – EIP từ pool BYOIP không tính vào quota), cấp EIP liên tiếp từ pool Amazon VPC IPAM.

  2. Chỉ cần SSH bảo trì ⇒ dùng EC2 Instance Connect Endpoint (kết nối từ Internet mà instance không cần public IPv4).
  3. Chuyển instance sang private subnet + NAT gateway cho traffic ra (tài liệu đưa công thức so sánh: tổng chi phí NAT ÷ chi phí public IP < 1 ⇒ NAT rẻ hơn).

  6. Release các EIP không còn dùng – EIP nhàn rỗi vẫn bị tính tiền.
Mẹo thi (Exam Tip) – IP & Elastic IP

  • “Public IP changed after the instance was stopped and started” ⇒ đó là public IPv4 tự gán; giải pháp là Elastic IP.
  • “Mask the failure of an instance by rapidly remapping the address” ⇒ cụm từ nguyên văn mô tả Elastic IP.
  • “Need more than 5 Elastic IPs” ⇒ xin tăng Service Quotas (hoặc xem lại kiến trúc: load balancer, DNS).
  • “Reduce public IPv4 charges” ⇒ load balancer + private subnet, EC2 Instance Connect Endpoint, release EIP nhàn rỗi, IPv6.

Elastic Network Interface (ENI)

Một elastic network interface là thành phần mạng logic trong VPC, đại diện cho một card mạng ảo. Bạn tạo, cấu hình và gắn nó vào instance trong cùng Availability Zone. Thuộc tính của ENI đi theo nó khi được tháo ra và gắn sang instance khác – khi chuyển ENI, traffic được chuyển hướng từ instance cũ sang instance mới. (Console và API gọi tắt là “network interface”.)

Primary vs secondary network interface & cách gắn

  • Mỗi instance có một primary network interface (eth0, device index 0) – không tháo được. Bạn có thể gắn thêm secondary network interfaces; số ENI tối đa và số IP mỗi ENI phụ thuộc instance type.
  • Ba thời điểm gắn: hot attach (instance đang running), warm attach (instance stopped), cold attach (lúc launch). Secondary ENI tháo được khi running hoặc stopped.
  • ENI phải cùng AZ với instance; có thể nằm ở subnet khác, thậm chí VPC khác cùng account (miễn cùng AZ) ⇒ tạo instance multi-homed qua nhiều VPC. Không làm được với VPC của account khác.
  • Không thể gắn thêm ENI (kiểu NIC teaming) để tăng gấp đôi băng thông của instance.
  • Gắn nhiều ENI cùng subnet dễ gây asymmetric routing ⇒ nếu chỉ cần thêm IP, hãy thêm secondary private IPv4 vào primary ENI.
  • Amazon Linux và Windows Server tự nhận và cấu hình ENI mới; OS khác có thể phải tự bật interface và sửa route table.
  • Secondary ENI khi tháo/gắn mang theo primary & secondary private IPv4, EIP, IPv6.

Network cards

Đa số instance type có một network card. Các type hỗ trợ nhiều network card (vd c6in.32xlarge = 2, p4d.24xlarge = 4, p5.48xlarge = 32, trn1n.32xlarge = 16) cho hiệu năng mạng cao hơn – băng thông trên 100 Gbps và packet rate tốt hơn. Primary ENI phải ở network card index 0. Mỗi network card gắn được một EFA (hoặc EFA-only) – EFA cũng tính là một ENI.

Khi nào dùng nhiều ENI? (Multiple network interfaces scenarios)

Management network

  • eth0 nhận traffic public (SG cho 80/443 từ 0.0.0.0/0 hoặc từ load balancer).
  • eth1 ở subnet quản trị cùng AZ, SG chỉ cho SSH từ dải IP cho phép, private subnet hoặc virtual private gateway.

Network & security appliance

  • Load balancer, NAT server, proxy… thích có nhiều interface, mỗi interface có IP, SG, source/dest check riêng.

Dual-homed instance

  • Web server có ENI nối vào mạng mid-tier nơi app server ở; app server có ENI nối tiếp vào backend subnet của DB.
  • Qua 2 VPC cùng account: vượt CIDR chồng lấn không peering được; nối tài nguyên giữa nhiều VPC.

Low-budget high availability

  • Instance lỗi ⇒ tháo ENI gắn sang hot standby đã cấu hình sẵn. ENI giữ private IP, EIP, MAC ⇒ traffic chảy sang ngay, không cần sửa route table hay DNS.

Requester-managed ENI, managed ENI & prefix delegation

  • Requester-managed network interface: ENI do dịch vụ AWS tạo trong VPC của bạn thay bạn – vd cho RDS DB instance, NAT gateway, interface VPC endpoint (PrivateLink), ELB, Lambda, WorkSpaces. Bạn xem và gắn tag được nhưng không modify thuộc tính, attach/detach, gắn EIP, gán IP hay dùng nó khi launch instance. Xóa tài nguyên ⇒ dịch vụ tự detach và xóa ENI.
  • Managed network interface: do service provider (vd Amazon EKS Auto Mode) quản lý, trường Managed = true, không sửa trực tiếp.
  • Prefix delegation: gán cả một dải CIDR (prefix) IPv4/IPv6 cho ENI thay vì từng IP lẻ ⇒ launch dịch vụ nhanh hơn, tăng mật độ IP (vd nhiều pod/container trên một node).
Bẫy thường gặp – ENI
  • ENI là tài nguyên gắn với AZ: không gắn được cho instance ở AZ khác ⇒ failover bằng ENI không chống được sự cố cả AZ.
  • Thêm ENI không tăng băng thông. Muốn băng thông cao ⇒ instance type lớn hơn / có hậu tố “n”, enhanced networking, nhiều network card.
  • Instance NAT tự dựng (NAT instance) mà quên tắt source/destination check ⇒ không chuyển tiếp được traffic.
  • Không detach được ENI của NAT gateway / ELB / Lambda – đó là requester-managed.
Mẹo thi (Exam Tip) – ENI
  • “Software license tied to a MAC address; must fail over to a standby quickly” ⇒ secondary ENI chuyển sang standby.
  • “Separate management traffic from application traffic on the same instance” ⇒ thêm ENI thứ hai ở subnet quản trị với security group riêng.
  • “Host multiple websites/SSL certificates on one instance, each with its own IP” ⇒ secondary private IPv4 (mỗi IP có thể gắn một EIP).
  • “Instance acts as NAT / firewall / router” ⇒ disable source/destination check.

Placement Groups

Để đáp ứng nhu cầu workload, bạn launch một nhóm instance phụ thuộc nhau vào một placement group để ảnh hưởng tới vị trí phần cứng của chúng. Placement group là tùy chọn: nếu không dùng, EC2 cố gắng trải các instance của bạn ra nhiều phần cứng để giảm correlated failures. Tạo placement group miễn phí.

Cluster placement group

Nhóm logic các instance trong một AZ (không bị bó vào một rack). Instance trong cùng cluster PG có giới hạn throughput mỗi flow TCP/IP cao hơn và nằm cùng segment mạng high-bisection bandwidth. Khuyến nghị cho ứng dụng cần độ trễ mạng thấp, throughput cao, và khi phần lớn traffic là giữa các instance trong nhóm. Để có độ trễ thấp nhất và PPS cao nhất, chọn instance type hỗ trợ enhanced networking.

  • Không span nhiều AZ. Có thể span các VPC peered cùng Region.
  • Instance có enhanced networking: tới 10 Gbps single-flow trong cluster PG (ngoài PG: 5 Gbps). Traffic tới S3 cùng Region (qua public IP hoặc VPC endpoint) dùng được toàn bộ băng thông tổng hợp của instance. Traffic ra Internet hoặc qua Direct Connect về on-premises giới hạn 5 Gbps.
  • Throughput tối đa giữa hai instance bị giới hạn bởi instance chậm hơn.
  • Khuyến nghị: launch đủ số instance trong một launch request và dùng cùng một instance type. Thêm instance sau hoặc trộn type ⇒ tăng nguy cơ insufficient capacity error.
  • Gặp lỗi capacity khi nhóm đã có instance chạy ⇒ stop rồi start tất cả instance trong nhóm rồi thử lại (start có thể chuyển chúng sang phần cứng đủ chỗ cho toàn bộ).
  • Stop/start một instance thì nó vẫn ở trong placement group (start thất bại nếu không đủ capacity).
  • Muốn chắc chắn capacity ⇒ tạo On-Demand Capacity Reservation trong cluster placement group; zonal RI không giữ capacity riêng trong placement group được. Capacity Blocks không hỗ trợ placement group.
  • Hỗ trợ: instance current generation trừ burstable (T2…), Mac1, M7i-flex; và một số previous generation (A1, C3, C4, I2, M4, R3, R4).

Partition placement group

Giảm khả năng lỗi phần cứng tương quan cho ứng dụng. EC2 chia mỗi group thành các partition logic; mỗi partition có bộ rack riêng, mỗi rack có nguồn điện và mạng riêng; không hai partition nào dùng chung rack ⇒ một lỗi phần cứng chỉ ảnh hưởng một partition.

  • Dùng cho workload lớn, phân tán và có nhân bản: HDFS, HBase, Cassandra, Kafka (Hadoop).
  • Tối đa 7 partition mỗi AZ; có thể có partition ở nhiều AZ cùng Region. Số instance chỉ bị giới hạn bởi quota account (khác spread!).
  • EC2 cố gắng chia đều instance giữa các partition (không đảm bảo); bạn có thể launch vào partition cụ thể.
  • Visibility: thấy instance nào thuộc partition nào ⇒ chia sẻ cho topology-aware applications (HDFS, HBase, Cassandra) để quyết định nhân bản dữ liệu thông minh, tăng availability và durability.
  • Partition PG với Dedicated Instances: tối đa 2 partition. Capacity Reservation không giữ capacity trong partition PG.

Spread placement group

Nhóm instance mà mỗi instance đặt trên phần cứng riêng biệt. Khuyến nghị cho ứng dụng có số ít instance quan trọng cần tách rời nhau, giảm rủi ro hỏng đồng thời khi dùng chung thiết bị. Vì mỗi instance có phần cứng riêng, spread PG phù hợp trộn nhiều instance type hoặc launch dần theo thời gian.

  • Rack-level spread: có ở AWS Regions và Outposts; host-level spread: chỉ trên AWS Outposts.
  • Rack-level spread có thể span nhiều AZ cùng Region, tối đa 7 instance đang chạy mỗi AZ mỗi group. Ví dụ: Region có 3 AZ ⇒ tối đa 21 instance. Instance thứ 8 trong một AZ sẽ không launch được. Cần hơn 7/AZ ⇒ dùng nhiều spread placement group (không đảm bảo trải giữa các group, nhưng trải trong từng group).
  • Trên Outposts: rack-level spread chứa tối đa bằng số rack; host-level bằng số host.
  • Không hỗ trợ Dedicated Instances. Capacity Reservation không giữ capacity trong spread PG.
  • Không đủ phần cứng riêng biệt ⇒ request thất bại; EC2 bổ sung phần cứng theo thời gian, thử lại sau.

Precision time placement group (mới)

Đặt instance trên phần cứng có truy cập trực tiếp tới nguồn thời gian độ chính xác cao ⇒ dùng enhanced Amazon Time Sync Service (NTP cục bộ chính xác hơn), PTP Hardware Clock (đồng bộ cỡ micro giây, chỉ Linux), hardware packet timestamping (nano giây). Dùng cho database phân tán cần thứ tự giao dịch, dịch vụ tài chính cần timestamp chính xác. Có thể làm parent của cluster PG (--parent-group-id). Miễn phí.

Quy tắc chung của placement group

  • Một instance chỉ ở một placement group tại một thời điểm. Không merge được các placement group.
  • Muốn thêm/chuyển/gỡ instance khỏi placement group ⇒ instance phải ở trạng thái stopped (Actions › Instance settings › Modify instance placement, hoặc aws ec2 modify-instance-placement).
  • Không launch Dedicated Hosts vào placement group. Không launch Spot Instance cấu hình stop/hibernate khi bị interrupt vào placement group.
  • On-Demand Capacity Reservation và zonal RI khớp thuộc tính vẫn tự áp khi launch vào placement group (nhưng chỉ ODCR mới tạo được trong cluster PG).
  • Placement group chia sẻ được cho account khác (shared placement groups) qua AWS RAM.
Mẹo thi (Exam Tip) – Placement Groups
  • “HPC, tightly coupled, node-to-node, lowest latency, highest network throughput, MPI” ⇒ cluster placement group (+ EFA nếu có trong đáp án).
  • “Large distributed and replicated workload (Cassandra/HDFS/Kafka), hundreds of instances, isolate hardware failures, topology-aware” ⇒ partition placement group.
  • “Small number of critical instances, each on distinct hardware, reduce correlated failures” ⇒ spread placement group (nhớ giới hạn 7/AZ).
  • “Cluster placement group launch fails with insufficient capacity” ⇒ launch tất cả trong một request, cùng instance type; hoặc stop/start toàn bộ nhóm rồi thử lại; tạo ODCR trong cluster PG.
  • Cluster PG đánh đổi availability lấy hiệu năng: đề yêu cầu “highly available across AZs” thì cluster PG không phải câu trả lời.

Enhanced networking, ENA Express & Elastic Fabric Adapter

Enhanced networking dùng single root I/O virtualization (SR-IOV) – phương pháp ảo hóa thiết bị cho hiệu năng I/O cao hơn và CPU thấp hơn so với network interface ảo hóa truyền thống. Kết quả: băng thông cao hơn, packets per second (PPS) cao hơn và độ trễ thấp ổn định giữa các instance. Không tốn thêm phí.

Hai cơ chế enhanced networking

Elastic Network Adapter (ENA)

  • Tốc độ tới 100 Gbps trên instance hỗ trợ.
  • Mọi instance Nitro đều dùng ENA; cộng một số Xen-based: H1, I3, G3, m4.16xlarge, P3dn, R4.
  • Là lựa chọn mặc định hiện nay (current generation).

Intel 82599 Virtual Function (VF)

  • Tốc độ tới 10 Gbps.
  • Chỉ thế hệ cũ: C3, C4, D2, I2, M4 (trừ m4.16xlarge), R3.

ENA Express

ENA Express chạy trên công nghệ Scalable Reliable Datagram (SRD) của AWS: chia gói tin của mỗi flow ra nhiều đường mạng khác nhau, tự né đường tắc nghẽn, xử lý reorder và phần lớn retransmit ngay ở tầng mạng.

  • Tăng single-flow bandwidth từ 5 Gbps lên tới 25 Gbps trong cùng Region (vẫn không vượt giới hạn tổng của instance – vd instance 12,5 Gbps thì single-flow tối đa 12,5).
  • Giảm tail latency giữa các instance cùng AZ, nhất là khi mạng tải cao. Dùng được cả giữa các AZ trong cùng Region (trừ vài Region).
  • Điều kiện: cả hai instance gửi/nhận đều là type hỗ trợ và đều bật ENA Express; cùng Region; đường đi không qua middlebox; không dùng trong Local Zone. Không thỏa ⇒ tự quay về ENA thường.
  • Lúc mạng nhàn rỗi median latency có thể tăng nhẹ (vài chục micro giây) – ứng dụng cần PPS rất cao và tối ưu latency lúc không tắc nghẽn thì enhanced networking thường phù hợp hơn.

Elastic Fabric Adapter (EFA)

Một Elastic Fabric Adapter là network device gắn vào EC2 instance để tăng tốc ứng dụng AI, ML và HPC – đạt hiệu năng như cluster on-premises nhưng có tính co giãn của cloud. EFA cho độ trễ thấp và ổn định hơn, throughput cao hơn cho giao tiếp giữa các instance – yếu tố quyết định khi scale ứng dụng tightly coupled.

  • Tích hợp Libfabric; hỗ trợ NCCL, NIXL cho AI/ML và Open MPI 4.1+, Intel MPI 2019 Update 5+ cho HPC; AWS Neuron SDK (Trainium/Inferentia).
  • OS-bypass: ứng dụng (qua MPI/NCCL) gọi Libfabric API giao tiếp trực tiếp với EFA device, bỏ qua kernel/TCP-IP stack ⇒ giảm overhead. Có congestion control nhờ giao thức SRD.
  • Hỗ trợ RDMA read/write trên instance Nitro v4 trở lên; GPUDirect RDMA trên GPU NVIDIA.

Giới hạn của EFA – rất hay thành bẫy

  • EFA traffic không đi xuyên AZ hoặc VPC, và không routable (traffic IP thường qua ENA device của EFA interface vẫn routable bình thường) ⇒ các node HPC dùng EFA phải ở cùng AZ – thường kết hợp cluster placement group.
  • Một EFA mỗi instance (instance nhiều network card: một EFA mỗi card).
  • Không hỗ trợ trên AWS Outposts. Trên Windows, EFA device chỉ dùng cho ứng dụng AWS CDI SDK; ứng dụng khác thì EFA hoạt động như ENA.
  • EFA traffic giữa P4d/P4de/DL1 và instance type khác chưa được hỗ trợ.
  • Thực hành chuẩn (từ hướng dẫn “Get started with EFA”): security group của EFA phải cho phép mọi traffic inbound và outbound tới/từ chính security group đó (self-referencing) để các node trao đổi.
  • EFA là tính năng mạng tùy chọn, không tốn thêm phí.
Mẹo thi (Exam Tip) – Enhanced networking & EFA
  • “Higher bandwidth, higher PPS, lower latency, at no extra cost” ⇒ enhanced networking (ENA) trên instance type hỗ trợ.
  • “HPC with MPI / distributed ML training with NCCL, inter-node communication, OS-bypass, low-latency” ⇒ EFA + cluster placement group.
  • “Increase single TCP flow bandwidth between instances beyond 5 Gbps” ⇒ ENA Express (tới 25 Gbps) hoặc đặt trong cluster PG (10 Gbps).
  • EFA ⇒ nhớ “same AZ / same subnet-level” (không cross-AZ). Đáp án trải EFA cluster qua nhiều AZ là sai.

Ví dụ đời thường – tổ chức một đội bóng

Cluster PG là cho cả đội tập chung một sân để chuyền bóng nhanh nhất – nhưng sân ngập nước thì cả đội nghỉ. Partition PG là chia đội thành nhiều tổ, mỗi tổ tập ở một sân riêng (có điện, nước riêng), huấn luyện viên biết ai ở sân nào để xếp người dự bị hợp lý. Spread PG là giữ mấy cầu thủ ngôi sao ở các khách sạn khác nhau – ít người thôi, nhưng không bao giờ cùng ngộ độc một lúc. EFA là bộ đàm nội bộ nói thẳng với nhau không qua tổng đài (OS-bypass).

Tóm tắt ghi nhớ

Key takeaways
  • Security group: tường lửa ảo gắn ở network interface; chỉ allow; stateful; gộp rule của mọi SG; SG mới = không inbound, outbound all; default SG = inbound từ chính nó, outbound all, không xóa được; mặc định 5 SG/ENI (tới 16), 60 rule mỗi chiều.
  • Security group referencing (source = sg-xxx) cho kiến trúc nhiều tầng co giãn; dùng được qua peering/transit gateway (inbound).
  • Sửa rule không cắt kết nối đang được track; cần chặn ngay ⇒ NACL. SG không lọc DNS tới Route 53 Resolver ⇒ DNS Firewall.
  • Public IPv4 tự gán đổi khi stop/start/hibernate; private IPv4, IPv6, Elastic IP giữ nguyên. EIP: static, một Region, 5/Region, tính phí cả khi nhàn rỗi; mọi public IPv4 đều tính phí.
  • ENI: gắn với AZ; hot/warm/cold attach; primary không tháo được; mang private IP, EIP, MAC, SG ⇒ failover giá rẻ, management network, dual-homed; không tăng băng thông; NAT/firewall ⇒ tắt source/dest check; requester-managed ENI không detach được.
  • Cluster PG: 1 AZ, độ trễ thấp, 10 Gbps/flow, cùng type + 1 request. Partition PG: ≤ 7 partition/AZ, rack riêng, topology-aware (HDFS/Cassandra/Kafka). Spread PG: ≤ 7 instance đang chạy/AZ, mỗi instance một rack. Đổi placement ⇒ instance phải stopped; không merge; không Dedicated Host.
  • Enhanced networking (SR-IOV): ENA tới 100 Gbps (mọi Nitro), Intel 82599 VF tới 10 Gbps (đời cũ); miễn phí. ENA Express (SRD): single-flow 5 ⇒ 25 Gbps.
  • EFA: OS-bypass qua Libfabric cho MPI/NCCL; EFA traffic không cross-AZ/VPC, không routable; không Outposts; miễn phí ⇒ kết hợp cluster PG cho HPC/ML.

A research company runs a computational fluid dynamics (CFD) application on Amazon EC2. The application uses MPI, and the nodes exchange large amounts of data continuously during each simulation. The company needs the LOWEST possible inter-node latency and the highest network throughput. Which solution meets these requirements?

  2. Launch EFA-enabled instances of the same instance type in a cluster placement group in a single Availability Zone.
  3. Launch the instances in a partition placement group and attach two additional network interfaces to each instance.
  4. Launch burstable performance instances in an Auto Scaling group across multiple Availability Zones.
Đáp án B. Workload HPC tightly coupled dùng MPI ⇒ cluster placement group (cùng segment high-bisection bandwidth, 10 Gbps/flow) + EFA (OS-bypass qua Libfabric cho MPI); dùng cùng instance type giảm nguy cơ thiếu capacity. A sai: spread PG tách instance ra các rack và AZ khác nhau – tăng độ trễ, lại giới hạn 7 instance/AZ. C sai: partition PG để cô lập lỗi chứ không tối ưu độ trễ; gắn thêm ENI không tăng băng thông.
