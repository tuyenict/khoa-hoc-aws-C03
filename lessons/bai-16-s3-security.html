Sau bài này bạn sẽ

  • Viết được bucket policy cho các yêu cầu hay thi: ép HTTPS, chỉ cho phép từ VPC endpoint, chỉ trong AWS Organization, cross-account upload; hiểu vì sao AWS khuyên tắt ACL bằng S3 Object Ownership.
  • Nắm 4 thiết lập của S3 Block Public Access, các cấp áp dụng (Organization / account / bucket / access point) và cách S3 định nghĩa “public”.
  • Phân biệt SSE-S3, SSE-KMS, DSSE-KMS, SSE-C và client-side encryption; biết S3 Bucket Keys giảm tới 99% chi phí request KMS; thay đổi mới: SSE-C bị tắt mặc định từ 04/2026.
  • Thiết kế lưu trữ WORM với S3 Object Lock (Governance vs Compliance, legal hold, variable retention) và hiểu Glacier Vault Lock.
  • Chia sẻ có thời hạn bằng presigned URL; quản lý dataset dùng chung bằng S3 Access Points; cấu hình CORS cho ứng dụng web.
  • Biết dịch vụ nào giám sát bảo mật S3: IAM Access Analyzer, Macie, GuardDuty, AWS Config, CloudTrail data events, Trusted Advisor.

Ví dụ đời thường – két sắt ngân hàng

Bucket là phòng két của ngân hàng. Block Public Access là quy định “không bao giờ mở cửa cho khách vãng lai”, dù nhân viên lỡ ghi giấy phép. Bucket policy là danh sách ai được vào, từ cửa nào, giờ nào. Mã hóa là mỗi hộp đều khóa – SSE-KMS giống chìa khóa gửi ở phòng quản lý khóa riêng (KMS) có sổ ghi lại mỗi lần mượn. Object Lock là hộp niêm phong đến ngày hết hạn, kể cả giám đốc (root) cũng không phá được (Compliance mode). Presigned URL là vé vào cửa ghi tên một hộp, hết hạn sau vài giờ. Access Point là cửa riêng cho từng phòng ban với nội quy riêng.

Bucket policy, ACL và S3 Object Ownership

Bucket policy là resource-based policy gắn vào bucket – có phần tử Principal, dùng để cấp quyền cho chính account, account khác, dịch vụ AWS, hoặc (rất hạn chế) công khai. Kết hợp với IAM policy của user/role, đây là cơ chế kiểm soát truy cập chính của S3 hiện nay.

Disable ACLs – khuyến nghị số 1 trong “Security best practices”

S3 Object Ownership là thiết lập cấp bucket quyết định ai sở hữu object được upload và bật/tắt ACL (access control list). Mặc định là Bucket owner enforced: mọi ACL bị vô hiệu, bucket owner sở hữu mọi object, và quyền chỉ dựa trên policy (IAM policy, bucket policy, VPC endpoint policy, SCP, RCP).

  • Phần lớn use case hiện đại không cần ACL; AWS khuyên tắt ACL trừ khi phải kiểm soát quyền từng object riêng lẻ.
  • Sau khi tắt ACL: bucket chỉ nhận PUT không kèm ACL hoặc kèm bucket-owner-full-control; request kèm ACL khác bị lỗi 400 AccessControlListNotSupported.
  • Lợi ích lớn trong đề: bucket nhận object do nhiều account khác upload mà bucket owner vẫn sở hữu và quản lý được hết (trước đây object do account B upload thuộc về B ⇒ owner bucket A không đọc được).
  • Trước khi tắt ACL trên bucket cũ: rà bucket policy cho đủ mọi quyền cross-account đang cấp qua ACL; reset bucket ACL về mặc định.

Các mẫu bucket policy phải thuộc lòng

1) Ép mã hóa khi truyền (HTTPS only) – tài liệu khuyến nghị dùng điều kiện aws:SecureTransport và đặt CloudWatch alarm khi có truy cập HTTP; kiểm tra liên tục bằng AWS Config rule s3-bucket-ssl-requests-only.

{
  "Sid": "RestrictToTLSRequestsOnly",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::amzn-s3-demo-bucket", "arn:aws:s3:::amzn-s3-demo-bucket/*"],
  "Condition": { "Bool": { "aws:SecureTransport": "false" } }
}

2) Chỉ cho phép principal trong AWS Organization – dùng aws:PrincipalOrgID. Với Deny, nó chặn mọi principal ngoài tổ chức dù ACL hay policy khác lỡ cấp quyền (defense-in-depth).

{
  "Effect": "Deny", "Principal": "*", "Action": "s3:*",
  "Resource": ["arn:aws:s3:::amzn-s3-demo-bucket", "arn:aws:s3:::amzn-s3-demo-bucket/*"],
  "Condition": { "StringNotEquals": { "aws:PrincipalOrgID": "o-aa111bb222" } }
}

3) Chỉ cho phép truy cập qua VPC endpoint – điều kiện aws:SourceVpce (một endpoint cụ thể) hoặc aws:SourceVpc (cả VPC). Tài liệu: VPC endpoint giúp lưu lượng không đi qua Internet, và một VPC không có Internet Gateway giúp ngăn data exfiltration. Lưu ý: aws:SourceIp không dùng được với traffic đi qua VPC endpoint (IP là private) – khi đó dùng aws:SourceVpc/aws:SourceVpce.

{
  "Effect": "Deny", "Principal": "*", "Action": "s3:*",
  "Resource": ["arn:aws:s3:::amzn-s3-demo-bucket", "arn:aws:s3:::amzn-s3-demo-bucket/*"],
  "Condition": { "StringNotEquals": { "aws:SourceVpce": "vpce-1a2b3c4d" } }
}

4) Cross-account upload nhưng bucket owner phải có toàn quyền (bucket còn bật ACL) – điều kiện s3:x-amz-acl = bucket-owner-full-control. Với bucket đã Bucket owner enforced thì không cần nữa vì owner tự động sở hữu mọi object.

{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::amzn-s3-demo-bucket/*",
  "Condition": { "StringEquals": { "s3:x-amz-acl": "bucket-owner-full-control" } }
}

5) Các điều kiện khác hay gặp:

  • s3:x-amz-server-side-encryption / s3:x-amz-server-side-encryption-aws-kms-key-id – ép loại mã hóa hoặc một KMS key cụ thể (xem phần Mã hóa).
  • s3:ExistingObjectTag/<key> – chỉ cho đọc object có tag nhất định (ABAC trên object).
  • aws:SourceIp – giới hạn dải IP công khai (văn phòng công ty).
  • aws:MultiFactorAuthPresent – yêu cầu credential có MFA cho thao tác nhạy cảm (Bài 4).
  • s3:signatureAge – giới hạn tuổi chữ ký của presigned URL (xem phần Presigned URL).
  • Grant cho service principal: vd logging.s3.amazonaws.com ghi server access log; CloudFront Origin Access Control (OAC) đọc object để bucket không cần public (OAI là cách cũ, AWS hướng dẫn migrate sang OAC – chi tiết ở bài CloudFront).
Mẹo thi (Exam Tip) – Bucket policy
  • “Deny any request that is not sent over HTTPS” ⇒ bucket policy Deny + aws:SecureTransport = false.
  • “Only accounts in our organization can access the bucket”, “least operational overhead as accounts are added” ⇒ aws:PrincipalOrgID (không phải liệt kê từng account ID).
  • “Bucket must be accessible only from the VPC / EC2 in private subnets, traffic must not traverse the internet” ⇒ S3 gateway VPC endpoint + bucket policy aws:SourceVpce.
  • “Objects uploaded by partner accounts cannot be read by the bucket owner” ⇒ đặt Object Ownership = Bucket owner enforced (tắt ACL).
  • “Serve private S3 content only through CloudFront” ⇒ OAC + bucket policy cho service principal CloudFront, giữ Block Public Access bật.
Bẫy thường gặp – Bucket policy
  • Policy có "Principal": "*" + Allow không điều kiện ⇒ bucket public. Nếu Block Public Access đang bật (BlockPublicPolicy), lệnh PutBucketPolicy đó sẽ bị từ chối.
  • Deny theo aws:SourceVpce với "Principal": "*" có thể khóa luôn admin đang thao tác từ console/Internet – nên loại trừ role quản trị hoặc thử trên bucket test.
  • Resource phải đúng cấp: arn:aws:s3:::bucket cho s3:ListBucket, arn:aws:s3:::bucket/* cho s3:GetObject/PutObject. Viết lẫn là lỗi kinh điển.
  • Cross-account: account B muốn đọc bucket của A cần cả bucket policy của A cho phép và IAM policy trong B cho phép (Bài 5). Nếu object mã hóa SSE-KMS còn cần key policy cho B.

S3 Block Public Access

S3 Block Public Access (BPA) cung cấp các thiết lập cho access point, bucket, account và AWS Organizations để quản lý tập trung việc truy cập công khai. Mặc định bucket, access point và object mới không cho phép public; nhưng người dùng có thể sửa policy/ACL để mở – BPA ghi đè các policy và quyền đó, bất kể tài nguyên được tạo bằng cách nào.

Thứ tự ưu tiên giữa các cấp

  • S3 áp dụng tổ hợp chặt chẽ nhất giữa access point, bucket, account (và Organization). Ví dụ trong tài liệu: Organization bật BPA nhưng một bucket tắt BPA ⇒ bucket vẫn được bảo vệ. Ngược lại Organization tắt nhưng bucket bật ⇒ bucket vẫn được bảo vệ bởi setting cấp bucket.
  • Organization-level BPA (qua AWS Organizations S3 policy): gắn ở root hoặc OU, account thành viên tự kế thừa (cả account mới), ghi đè setting cấp account; thay thế việc phải duy trì SCP phức tạp để cấm tắt BPA. Theo dõi bằng CloudTrail.
  • Setting cấp bucket áp dụng cho mọi access point của bucket. Setting của access point chỉ đặt được lúc tạo, không sửa sau.
  • Gỡ một setting BPA ⇒ bucket/object có policy/ACL public sẽ public trở lại (BPA không sửa policy/ACL gốc).
  • BPA chỉ chặn quyền public đến từ policy/ACL gắn trực tiếp vào tài nguyên S3. AWS nhắc kiểm tra thêm identity-based policy của role và resource-based policy của tài nguyên liên quan (vd KMS key).

S3 hiểu “public” là gì?

  • ACL public: cấp bất kỳ quyền nào cho nhóm AllUsers hoặc AuthenticatedUsers (“Any authenticated AWS user” – tức mọi account AWS, không phải chỉ account của bạn).
  • Bucket policy: S3 giả định policy là public, rồi xét xem nó có đủ điều kiện non-public không. Non-public khi chỉ cấp cho giá trị cố định (không wildcard, không policy variable) của: principal cụ thể, aws:SourceIp (CIDR), aws:SourceArn, aws:SourceVpc, aws:SourceVpce, aws:SourceOwner, aws:SourceAccount, aws:userid, s3:DataAccessPointArn, s3:DataAccessPointAccount, hoặc aws:PrincipalOrgID.
  • Ví dụ trong tài liệu: "aws:SourceVpc": "vpc-*" (StringLike) vẫn là public; đổi thành StringEquals "vpc-91237329" ⇒ non-public.
  • aws:SourceIp với dải quá rộng (rộng hơn /8 với IPv4, hoặc /32 với IPv6, trừ dải private RFC1918) bị coi là public.
  • Access point có network origin = VPC luôn được coi là non-public.
Website tĩnh trên S3 thì sao?

Hosting static website bằng website endpoint của S3 cần bucket policy cho phép s3:GetObject với "Principal": "*" ⇒ phải tắt BlockPublicPolicy và RestrictPublicBuckets cho riêng bucket đó (và cấp account/Organization không được chặn). Cách an toàn hơn được khuyến nghị cho đề: đặt CloudFront + OAC phía trước, giữ bucket private và BPA bật đủ.

Mẹo thi (Exam Tip) – Block Public Access
  • “Ensure no S3 bucket in any account of the organization can ever be made public, including future accounts” ⇒ Organization-level Block Public Access (hoặc BPA cấp account + SCP cấm s3:PutAccountPublicAccessBlock – cách cũ).
  • “Prevent users who can edit bucket policies from making buckets public” ⇒ bật BlockPublicPolicy ở cấp account.
  • “Quickly identify buckets shared publicly or with external accounts” ⇒ IAM Access Analyzer for S3 (có nút block all public access một click; archive finding cho bucket chủ định public).
  • “Detect and auto-remediate public buckets continuously” ⇒ AWS Config rule s3-bucket-public-read-prohibited / s3-bucket-public-write-prohibited + remediation.

SSE-S3 – mặc định, không cần làm gì

  • S3 mã hóa object trước khi ghi xuống đĩa và giải mã khi bạn tải về. Mỗi bucket đều có default encryption = SSE-S3 trừ khi bạn đổi sang SSE-KMS hoặc DSSE-KMS.
  • Trạng thái mã hóa hiện trong CloudTrail, S3 Inventory, S3 Storage Lens (tỷ lệ % byte được mã hóa), console và header phản hồi API.
  • Đổi default encryption sang SSE-KMS không mã hóa lại object cũ ⇒ dùng S3 Batch Operations – Copy (copy đè lên chính nó) để chuyển hàng tỉ object hiện có sang SSE-KMS.

SSE-KMS – kiểm soát và audit key

S3 dùng cơ chế envelope encryption của AWS KMS: dữ liệu được mã hóa bằng data key, rồi data key được mã hóa bằng KMS key.

  • AWS managed key (aws/s3): S3 tự tạo trong account khi bạn upload object SSE-KMS lần đầu mà không chỉ định key. Không chia sẻ cross-account được (trừ khi uploader và người truy cập cùng account).
  • Customer managed key: bạn tạo, rotate, disable, viết key policy và audit. Bắt buộc khi cần chia sẻ dữ liệu SSE-KMS sang account khác. Nên dùng ARN đầy đủ của key – dùng alias thì KMS phân giải trong account của requester, có thể mã hóa nhầm bằng key của người upload.
  • KMS key phải cùng Region với bucket và phải là symmetric.
  • Mọi GET/PUT với object SSE-KMS phải dùng SSL/TLS và được ký (SigV4). Không gửi header mã hóa trong GET/HEAD object SSE-KMS – sẽ bị lỗi 400 Bad Request.
  • Encryption context: mặc định là ARN của object (hoặc ARN của bucket nếu bật Bucket Key); dùng để lọc CloudTrail và viết điều kiện key policy. Không đặt thông tin nhạy cảm vào context (không được mã hóa).
  • Bucket dùng làm đích của server access logging phải dùng SSE-S3 – nếu đặt SSE-KMS, log có thể được mã hóa bằng key mà bạn không truy cập được.
  • Dùng KMS key trong external key store thì bạn chịu trách nhiệm về tính sẵn sàng và độ bền của key material (shared responsibility thay đổi).
  • SSE-KMS chịu quota request/giây của AWS KMS (theo Region, có thể xin tăng) – workload hàng nghìn request/giây có thể bị throttling; đó là lý do có S3 Bucket Keys.

S3 Bucket Keys – giảm chi phí và tải KMS

  • Không có Bucket Key: S3 dùng một data key riêng cho mỗi object và gọi KMS cho mỗi request tới object mã hóa KMS.
  • Có Bucket Key: KMS sinh một bucket-level key ngắn hạn, S3 giữ tạm và dùng nó tạo data key cho object mới ⇒ giảm request Encrypt/GenerateDataKey/Decrypt tới KMS, giảm tới 99% chi phí request KMS. Bật bằng vài click, không sửa ứng dụng.
  • Tác dụng phụ: CloudTrail của KMS ghi ARN bucket thay vì ARN object và ít event hơn; IAM/key policy nào dùng ARN object làm encryption context phải đổi sang ARN bucket.
  • Chỉ áp dụng cho object mới; object cũ cần CopyObject. Không hỗ trợ DSSE-KMS. Dùng được với SRR/CRR.

DSSE-KMS – mã hóa hai lớp

DSSE-KMS áp dụng hai lớp AES-256 độc lập: lớp 1 bằng data key do AWS KMS sinh, lớp 2 bằng một key AES-256 riêng do S3 quản lý. Dùng khi tiêu chuẩn compliance bắt buộc mã hóa nhiều lớp và cần toàn quyền kiểm soát key. Đánh đổi: độ trễ cao hơn một chút, phí cao hơn SSE-KMS, không có Bucket Keys. Ép bằng bucket policy s3:x-amz-server-side-encryption = aws:kms:dsse.

SSE-C – khách hàng tự cung cấp key

  • Bạn gửi key trong mỗi request; S3 mã hóa/giải mã thay bạn nhưng không bao giờ lưu key. Bạn phải tự theo dõi key nào mã hóa object (version) nào – mất key = mất object.
  • Bắt buộc HTTPS: S3 từ chối request SSE-C qua HTTP; key lỡ gửi qua HTTP coi như bị lộ.
  • Không hỗ trợ trên S3 console (không upload, không sửa storage class/metadata của object SSE-C qua console). Dịch vụ AWS managed không giải mã native được object SSE-C.
  • Thay đổi 04/2026: SSE-C bị tắt mặc định cho mọi general purpose bucket mới và bucket hiện có trong account chưa từng có object SSE-C. Muốn dùng phải chủ động bật bằng PutBucketEncryption (đặt BlockedEncryptionTypes = NONE). Khi bị chặn, mọi PutObject/CopyObject/PostObject/multipart/replication chỉ định SSE-C bị lỗi 403 AccessDenied.

Client-side encryption

Bạn mã hóa dữ liệu trước khi gửi lên S3 và tự quản lý quy trình, key và công cụ (vd Amazon S3 Encryption Client). S3 chỉ lưu ciphertext. Chọn khi đề nói “data must be encrypted before it leaves the on-premises environment” hoặc “AWS must never have access to plaintext data or keys”.

Ép buộc mã hóa bằng policy

  • Ngày nay cách đơn giản hơn thường là đặt default encryption của bucket = SSE-KMS (object không chỉ định header sẽ tự mã hóa bằng key mặc định); policy deny dùng khi cần cưỡng chế và chặn key lạ.
Mẹo thi (Exam Tip) – Mã hóa
  • “Encrypt at rest with least operational overhead” ⇒ SSE-S3 (đã mặc định).
  • “Audit who used the key / control key rotation / separate permissions for key and data” ⇒ SSE-KMS với customer managed key.
  • “Share KMS-encrypted objects with another account” ⇒ customer managed key + key policy cho account kia (không dùng aws/s3).
  • “SSE-KMS costs are high / KMS throttling (ThrottlingException) with millions of objects” ⇒ S3 Bucket Keys.
  • “Regulation requires multi-layer (dual-layer) encryption” ⇒ DSSE-KMS.
  • “Company must manage keys outside AWS and supply them per request” ⇒ SSE-C; “encrypt before upload, AWS never sees plaintext” ⇒ client-side encryption.
  • “Encrypt existing unencrypted/SSE-S3 objects with KMS” ⇒ đổi default encryption + S3 Batch Operations Copy (dựa trên S3 Inventory).
Bẫy thường gặp – Mã hóa
  • User có s3:GetObject nhưng vẫn nhận AccessDenied ⇒ thiếu kms:Decrypt trên key (hay gặp trong cross-account, replication, Athena/Glue đọc bucket SSE-KMS).
  • Đổi default encryption không mã hóa lại object cũ.
  • SSE-C và client-side encryption không cho bạn audit qua CloudTrail KMS; SSE-S3 cũng không có audit key riêng.
  • “Mã hóa bằng KMS key ở Region khác” ⇒ không được; key phải cùng Region với bucket (replication CRR dùng key ở Region đích – Bài 15).

S3 Object Lock và Glacier Vault Lock – lưu trữ WORM

S3 Object Lock ngăn object bị xóa hoặc ghi đè trong một khoảng thời gian cố định, thay đổi được, hoặc vô thời hạn, theo mô hình WORM (write-once-read-many). Object Lock đã được Cohasset Associates đánh giá cho môi trường chịu quy định SEC 17a-4, CFTC và FINRA.

Nguyên lý: khóa theo từng object version

  • Thông tin khóa lưu trong metadata của từng object version. Khóa chỉ bảo vệ đúng version được chỉ định; không ngăn tạo version mới hoặc chèn delete marker lên trên.
  • PUT object trùng key với object đang bị khóa ⇒ tạo version mới; version cũ vẫn khóa theo cấu hình của nó. Ví dụ tài liệu: version cũ đang ở ngày 15 của retention 30 ngày, PUT version mới với 60 ngày ⇒ version cũ xóa được sau 15 ngày nữa.
  • Xóa object bị khóa:
    • DELETE kèm version ID (xóa vĩnh viễn) ⇒ 403 Access Denied.
    • DELETE thường (không version ID) ⇒ 200 OK, S3 chèn delete marker làm current version – dữ liệu version bị khóa vẫn còn nguyên.
  • Bật Object Lock: lúc tạo bucket (console: Advanced settings, hoặc --object-lock-enabled-for-bucket) hoặc trên bucket đã có (Properties ⇒ Object Lock, hoặc PutObjectLockConfiguration). Phải xác nhận rằng việc bật là vĩnh viễn.
  • Bucket có Object Lock không dùng làm đích server access log được. Replication bucket nguồn có Object Lock thì đích cũng phải bật Object Lock (Bài 15).

Governance mode vs Compliance mode

Governance mode

  • Hầu hết user không xóa/ghi đè version hay sửa cài đặt khóa được.
  • User có quyền đặc biệt s3:BypassGovernanceRetention và gửi header x-amz-bypass-governance-retention:true thì vượt qua được (console tự gửi header này).
  • Dùng để bảo vệ khỏi đa số người dùng nhưng vẫn cho admin linh hoạt; hoặc để thử nghiệm retention trước khi chuyển sang Compliance.

Compliance mode

  • Không ai xóa/ghi đè version được, kể cả root user.
  • Không đổi được mode, không rút ngắn được retention period (chỉ kéo dài được).
  • Cách duy nhất xóa trước hạn: xóa luôn AWS account.
  • Dùng cho dữ liệu phải tuân thủ quy định (tài chính, y tế, kiểm toán).

Retention period: fixed và variable

  • Fixed retention: chỉ định Retain Until Date. Có thể đặt cho từng version hoặc làm default retention của bucket (số ngày/năm, S3 cộng vào thời điểm tạo version). Setting riêng của version ghi đè default của bucket.
  • Variable retention (event hold): bật event hold + event hold duration; object được bảo vệ suốt khi hold còn bật; khi release, S3 đặt retain-until-date = thời điểm release + duration. Trong lúc hold bật, ngày này “trôi” theo thời gian (vd duration 1 năm, xem lúc 2027-01-01 ⇒ 2028-01-01). Giảm duration không kéo lùi được retain-until-date đã tính. Có thể kèm retain-until-date tối thiểu – S3 lấy ngày muộn hơn.
  • Use case variable retention: chưa biết ngày hết hạn lúc ghi – vd thời hạn tính từ sự kiện kinh doanh (hoàn tất hợp đồng, đóng tài khoản, giải quyết bồi thường) hoặc cửa sổ khôi phục cấu hình được chống ransomware.
  • Giới hạn min/max retention được phép bằng điều kiện s3:object-lock-remaining-retention-days trong bucket policy.
  • Quyền: s3:PutObjectRetention (đặt/kéo dài retention), s3:GetObjectRetention, s3:PutBucketObjectLockConfiguration, s3:BypassGovernanceRetention…

Legal hold

  • Bảo vệ giống retention period nhưng không có ngày hết hạn – tồn tại tới khi bị gỡ. Ai có s3:PutObjectLegalHold đều đặt/gỡ được.
  • Độc lập với retention: retention hết hạn mà legal hold còn ⇒ object vẫn được bảo vệ; gỡ legal hold khi retention còn hiệu lực ⇒ vẫn được bảo vệ tới hết retention.
  • Use case: chưa biết cần giữ bao lâu – vụ kiện, cuộc kiểm toán sắp tới, dự án đang dùng dataset.

Glacier Vault Lock (dịch vụ Glacier gốc dùng vault)

Glacier Vault Lock cho phép triển khai và cưỡng chế các control compliance (vd WORM, deny delete trước N ngày) cho một vault của Amazon Glacier bằng Vault Lock policy (ngôn ngữ IAM policy), rồi khóa policy để không ai sửa được nữa.

  1. Initiate – gắn Vault Lock policy vào vault ⇒ lock ở trạng thái in-progress và trả về lock ID.
  2. Kiểm thử trong 24 giờ – nếu policy không như ý, abort và làm lại. Quá 24 giờ mà chưa complete ⇒ lock ID hết hạn, policy bị xóa.
  3. Complete bằng lock ID ⇒ policy không thể sửa hay xóa nữa.
  • Vault Lock policy (bất biến, cho compliance) khác vault access policy (sửa thường xuyên, cho quyền tạm thời/không compliance). Dùng chung được: Vault Lock policy deny delete, access policy allow read cho đối tác.
  • AWS khuyên tạo vault, hoàn tất Vault Lock policy rồi mới upload archive.
  • Lưu ý hiện trạng: Amazon Glacier dạng vault (API gốc 2012) không còn nhận khách hàng mới; AWS khuyên dùng các S3 Glacier storage class trong S3 – khi đó WORM được làm bằng S3 Object Lock. Đề cũ vẫn có thể hỏi “Glacier vault lock” cho yêu cầu WORM trên archive.
Mẹo thi (Exam Tip) – Object Lock / Vault Lock
  • “WORM, SEC 17a-4, no one including the root user can delete for 7 years” ⇒ Object Lock – Compliance mode (retention 7 năm).
  • “Prevent deletion by most users, but allow a few administrators to delete/shorten retention” ⇒ Governance mode + s3:BypassGovernanceRetention cho admin.
  • “Retain objects indefinitely until litigation ends” ⇒ legal hold.
  • “Retention period starts when a contract ends (unknown at write time)” ⇒ variable retention (event hold).
  • “Protect backups/CloudTrail logs from ransomware or a compromised admin” ⇒ Versioning + Object Lock (thường kèm replication sang account riêng – Bài 15).
  • “Archive vault policy must be immutable” ⇒ Glacier Vault Lock (initiate ⇒ 24 giờ test ⇒ complete).
Bẫy thường gặp – Object Lock
  • “Object Lock ngăn mọi lệnh DELETE” ⇒ sai: DELETE không version ID vẫn thành công (tạo delete marker); chỉ version bị khóa là không mất.
  • Governance mode không đáp ứng yêu cầu “even the root user cannot delete” – phải là Compliance.
  • Compliance mode đặt nhầm 100 năm thì không rút ngắn được – AWS khuyên thử bằng Governance trước.
  • MFA Delete (Bài 14) chỉ yêu cầu thêm MFA khi xóa version; không phải WORM và không có thời hạn lưu giữ.

Giới hạn rủi ro của presigned URL

Presigned URL là bearer token – ai có URL đều dùng được. Các cách hạn chế theo tài liệu:

  • s3:signatureAge trong bucket/access point policy: deny nếu chữ ký cũ hơn N mili giây (ví dụ tài liệu: 600000 = 10 phút).
  • Network path: deny nếu không đến từ dải IP (aws:SourceIp – endpoint công khai) hoặc từ VPC/VPC endpoint (aws:SourceVpc/aws:SourceVpce). Đặt trên principal ký URL, trên bucket, hoặc cả hai.
  • Đặt expiration ngắn nhất có thể; ký bằng role có quyền tối thiểu.
Mẹo thi (Exam Tip) – Presigned URL
  • “Allow users without AWS credentials to download/upload a specific private object for a limited time” ⇒ presigned URL.
  • “Mobile/web clients upload large files directly to S3 without passing through the application servers” ⇒ backend sinh presigned PUT URL (kết hợp multipart nếu file lớn).
  • “Presigned URL expires earlier than configured” ⇒ URL được ký bằng credential tạm (role/instance profile/STS) – ký bằng credential có thời hạn dài hơn.
  • “Serve private content to many users via CDN with expiring links” ⇒ CloudFront signed URL/signed cookies + OAC, không phải S3 presigned URL (bài CloudFront).
Bẫy thường gặp – Presigned URL
  • “Tạo presigned URL hiệu lực 30 ngày” ⇒ không được; tối đa 7 ngày (SigV4).
  • Presigned URL không “mở public” bucket và không cần tắt Block Public Access.
  • Ai cầm URL cũng dùng được trong thời hạn – không gắn với danh tính người nhận. Muốn thu hồi sớm ⇒ revoke/vô hiệu credential đã ký (hoặc session của role).

S3 Access Points – quản lý truy cập dataset dùng chung

S3 Access Points là các network endpoint có tên gắn vào một nguồn dữ liệu (bucket, volume FSx for NetApp ONTAP / OpenZFS, hoặc S3 recovery point của AWS Backup). Mỗi access point có policy riêng, network control riêng (Internet hoặc chỉ VPC) và Block Public Access riêng. Thay vì một bucket policy khổng lồ phục vụ hàng trăm ứng dụng, mỗi ứng dụng/nhóm dùng một access point.

Cách hoạt động

  • Chỉ dùng cho thao tác trên object (GetObject, PutObject, ListBucket qua AP…) – không dùng để xóa bucket hay tạo replication configuration. Access point không làm đích replication được.
  • Để access point policy có hiệu lực, bucket cũng phải cho phép – hai cách: (khuyến nghị) ủy quyền toàn bộ kiểm soát cho access point bằng bucket policy với điều kiện s3:DataAccessPointAccount, hoặc lặp lại quyền trong bucket policy.
  • Resource trong access point policy có dạng arn:aws:s3:region:account:accesspoint/name/object/prefix/* (khác ARN bucket).
  • Policy access point chỉ áp dụng cho request đi qua access point đó; truy cập trực tiếp vào bucket vẫn theo bucket policy như cũ.
  • Điều kiện hữu ích: s3:AccessPointNetworkOrigin (VPC/Internet), s3:DataAccessPointArn, s3:DataAccessPointAccount. Ví dụ tài liệu: SCP deny s3:CreateAccessPoint khi network origin ≠ VPC ⇒ cả tổ chức chỉ tạo được access point nội bộ VPC; bucket policy deny mọi thao tác object không đi qua access point VPC.
  • Cross-account access point: account khác tạo access point trỏ tới bucket của bạn, nhưng giống CNAME DNS – không cấp quyền gì cho tới khi bucket owner cập nhật bucket policy. Bucket owner luôn giữ quyền kiểm soát cuối cùng.
  • Access point chỉ địa chỉ hóa theo virtual-hosted-style; có alias (hậu tố -s3alias) dùng thay tên bucket ở các ứng dụng chỉ nhận bucket name.
  • Biến thể liên quan: Multi-Region Access Points (một endpoint toàn cầu định tuyến tới bucket gần nhất, failover – Bài 15) và S3 Object Lambda Access Points (chạy Lambda biến đổi dữ liệu khi GET, vd che PII).
Mẹo thi (Exam Tip) – Access Points
  • “Hundreds of applications/teams share one bucket; the bucket policy is becoming too complex to manage” ⇒ S3 Access Points, mỗi team một access point policy.
  • “Data in the bucket must be accessible only from a specific VPC” ⇒ access point với VPC network origin (hoặc bucket policy aws:SourceVpce).
  • “Redact PII when an application reads objects, without storing a second copy” ⇒ S3 Object Lambda Access Point.

CORS – cho phép ứng dụng web khác domain gọi S3

Cross-origin resource sharing (CORS) định nghĩa cách ứng dụng web chạy trên trình duyệt ở một domain tương tác với tài nguyên ở domain khác. Trình duyệt mặc định chặn JavaScript gọi khác origin; S3 trả các header CORS khi bucket có CORS configuration phù hợp. CORS là cơ chế của trình duyệt, không thay thế quyền truy cập: ACL và policy vẫn áp dụng.

Hai kịch bản trong tài liệu

  1. Website tĩnh ở http://website.s3-website.us-east-1.amazonaws.com; JavaScript trên trang muốn gọi GET/PUT có xác thực tới API endpoint website.s3.us-east-1.amazonaws.com – hai origin khác nhau ⇒ bật CORS cho origin website.
  2. Host web font trên S3: trình duyệt bắt buộc preflight check khi tải font ⇒ cấu hình bucket chứa font cho phép origin cần thiết (hoặc mọi origin).

Mẹo thi (Exam Tip) – CORS

“A static website in bucket A loads images/fonts/JSON from bucket B (or calls the S3 API from JavaScript) and the browser shows a CORS error / ‘No Access-Control-Allow-Origin header’” ⇒ thêm CORS configuration trên bucket B cho origin của website A. Không phải sửa IAM, không phải tắt Block Public Access.

Tóm tắt ghi nhớ

Key takeaways
  • S3 mặc định private, ACL tắt (Bucket owner enforced), SSE-S3 bật sẵn (từ 05/01/2023), SSE-C bị chặn với bucket mới (từ 04/2026).
  • Bucket policy: ép HTTPS (aws:SecureTransport), giới hạn Organization (aws:PrincipalOrgID), VPC endpoint (aws:SourceVpce), mã hóa (s3:x-amz-server-side-encryption*). Cross-account cần cả bucket policy + IAM policy (+ KMS key policy).
  • Block Public Access: 4 setting (BlockPublicAcls, IgnorePublicAcls, BlockPublicPolicy, RestrictPublicBuckets), 4 cấp, áp dụng tổ hợp chặt nhất; Organization-level để bảo vệ cả account tương lai.
  • Mã hóa: SSE-S3 (đơn giản) · SSE-KMS (audit, key policy, cross-account cần customer managed key, quota KMS ⇒ Bucket Keys giảm tới 99%) · DSSE-KMS (hai lớp) · SSE-C (key theo request, HTTPS, không console) · client-side (AWS không thấy plaintext).
  • Object Lock cần versioning, bật rồi không tắt: Governance (bypass bằng s3:BypassGovernanceRetention + header) · Compliance (kể cả root không xóa được, chỉ kéo dài) · legal hold (không hạn) · variable retention (event hold). Glacier Vault Lock: initiate ⇒ 24 giờ ⇒ complete, bất biến.
  • Presigned URL: dùng quyền của người ký; console ≤ 12 giờ, CLI/SDK ≤ 7 ngày; hết sớm nếu credential tạm hết hạn; hạn chế bằng s3:signatureAge, IP, VPC.
  • Access Points: mỗi ứng dụng một endpoint + policy, VPC-only được, 10.000/account/Region, ủy quyền qua s3:DataAccessPointAccount. CORS: cấu hình trên bucket bị gọi tới, ≤ 100 rule.
  • Giám sát: Access Analyzer (chia sẻ ngoài), Macie (PII), GuardDuty (đe dọa), CloudTrail data events (ai làm gì), Config (tuân thủ cấu hình).

Mã hóa phía máy chủ với khóa do khách hàng cung cấp – key theo request, bắt buộc HTTPS.

Mã hóa phía client – mã hóa trước khi upload.

Mã hóa phong bì / Khóa dữ liệu – dữ liệu mã hóa bằng data key, data key mã hóa bằng KMS key.

Ngữ cảnh mã hóa – cặp key-value (mặc định ARN object/bucket) dùng làm AAD.

Khóa đối tượng / Ghi một lần, đọc nhiều lần.
Governance mode / Compliance mode
Chế độ quản trị / Chế độ tuân thủ – bypass được bằng quyền đặc biệt / không ai bypass được.

Variable retention / Event hold
Lưu giữ thay đổi được / Giữ theo sự kiện – ngày hết hạn = lúc release + duration.
Legal hold
Giữ pháp lý – khóa không thời hạn tới khi gỡ.
Glacier Vault Lock / Vault Lock policy
Khóa kho Glacier / Chính sách khóa kho – bất biến sau khi complete (24 giờ để kiểm thử).
Presigned URL
URL ký sẵn – quyền tạm thời tới một object, dùng credential của người ký.
Bearer token
Mã thông báo người cầm – ai có cũng dùng được.
S3 Access Point / Network origin
Điểm truy cập S3 / Nguồn mạng (Internet hoặc VPC).
S3 Object Lambda Access Point
Điểm truy cập biến đổi dữ liệu bằng Lambda khi đọc.
CORS
Chia sẻ tài nguyên khác nguồn gốc – AllowedOrigins/Methods/Headers, ExposeHeaders, MaxAgeSeconds.

Request kiểm tra trước – trình duyệt gửi OPTIONS trước request thật.

Sự kiện dữ liệu – log API cấp object (GetObject, PutObject, DeleteObject).

A company's security policy requires that all data sent to an Amazon S3 bucket be encrypted in transit. Some legacy clients still use HTTP. What should a solutions architect do to enforce this requirement?
  1. Enable default encryption with SSE-KMS on the bucket.
  2. Add a bucket policy statement that denies all S3 actions when the aws:SecureTransport condition key is false.
  3. Enable S3 Block Public Access on the bucket.
  4. Enable S3 Transfer Acceleration so that all requests use the accelerated endpoint.
Đáp án B. Tài liệu “Security best practices” khuyến nghị chỉ cho phép kết nối HTTPS (TLS) bằng điều kiện aws:SecureTransport trong bucket policy: Deny khi giá trị là false. A sai: SSE-KMS là mã hóa at rest, không chặn HTTP. C sai: BPA chặn quyền công khai, không liên quan giao thức. D sai: Transfer Acceleration tăng tốc truyền tải, không ép HTTPS.
Chính sách bảo mật của một công ty yêu cầu mọi dữ liệu gửi tới một Amazon S3 bucket phải được mã hóa khi truyền (in transit). Một số client cũ vẫn dùng HTTP. Solutions architect nên làm gì để bắt buộc thực thi yêu cầu này?
  • Bật default encryption với SSE-KMS trên bucket.Sai: SSE-KMS mã hóa dữ liệu at rest (khi lưu trữ), hoàn toàn không ngăn client gửi request qua HTTP không mã hóa.
  • Thêm một statement vào bucket policy để từ chối (deny) mọi thao tác S3 khi condition key aws:SecureTransport có giá trị false.Đúng: aws:SecureTransport = false nghĩa là request đi qua HTTP; Deny trong trường hợp này buộc mọi client phải dùng HTTPS (TLS), đúng yêu cầu mã hóa in transit.
  • Bật S3 Block Public Access trên bucket.Sai: Block Public Access chỉ chặn quyền truy cập công khai, không liên quan đến giao thức HTTP hay HTTPS.
  • Bật S3 Transfer Acceleration để mọi request đều dùng endpoint tăng tốc.Sai: Transfer Acceleration chỉ tăng tốc truyền tải qua edge location, không bắt buộc HTTPS và không chặn HTTP.
A financial company must store trade confirmations in Amazon S3 for 7 years to comply with SEC Rule 17a-4. No user, including the AWS account root user, can be allowed to delete or overwrite the records during this period. Which solution meets these requirements?
  1. Enable S3 Versioning and MFA Delete on the bucket.
  2. Enable S3 Object Lock in governance mode with a 7-year default retention period.
  3. Add a bucket policy that denies s3:DeleteObject for all principals, and use a lifecycle rule to expire objects after 7 years.
  4. Enable S3 Object Lock in compliance mode with a 7-year default retention period.
Đáp án D. Compliance mode: không user nào, kể cả root, xóa/ghi đè được version trong thời hạn lưu giữ; retention không rút ngắn được; Object Lock đã được Cohasset đánh giá cho SEC 17a-4. A sai: MFA Delete chỉ thêm bước MFA, root vẫn xóa được. B sai: governance mode cho phép user có s3:BypassGovernanceRetention xóa. C sai: bucket policy có thể bị root/admin sửa hoặc xóa – không phải WORM bất biến.
Một công ty tài chính phải lưu các xác nhận giao dịch trong Amazon S3 trong 7 năm để tuân thủ SEC Rule 17a-4. Không user nào, kể cả AWS account root user, được phép xóa hoặc ghi đè các bản ghi trong khoảng thời gian này. Giải pháp nào đáp ứng các yêu cầu này?
  • Bật S3 Versioning và MFA Delete trên bucket.Sai: MFA Delete chỉ thêm bước xác thực MFA khi xóa version; root user có MFA vẫn xóa được, nên không đảm bảo WORM.
  • Bật S3 Object Lock ở governance mode với thời hạn lưu giữ mặc định 7 năm.Sai: governance mode cho phép user có quyền s3:BypassGovernanceRetention (và root) xóa hoặc rút ngắn retention, vi phạm yêu cầu "không ai được xóa".
  • Thêm bucket policy từ chối s3:DeleteObject cho mọi principal, và dùng lifecycle rule để hết hạn object sau 7 năm.Sai: bucket policy có thể bị root/admin sửa hoặc xóa bất cứ lúc nào, nên không phải lưu trữ bất biến đạt chuẩn tuân thủ.
  • Bật S3 Object Lock ở compliance mode với thời hạn lưu giữ mặc định 7 năm.Đúng: compliance mode không cho bất kỳ ai, kể cả root, xóa/ghi đè version hay rút ngắn retention; Object Lock đã được đánh giá đáp ứng SEC 17a-4.
An application uses SSE-KMS with a customer managed key to encrypt millions of small objects in an S3 bucket.   • Tạo một customer managed key riêng cho mỗi prefix.Sai: số request KMS không giảm vì mỗi object vẫn gọi KMS, còn phát sinh thêm phí hàng tháng cho mỗi key.
