Sau bài này bạn sẽ

  • Phân biệt hai nhóm bài toán: hybrid storage (on-premises tiếp tục dùng storage, dữ liệu nằm trên AWS) và data transfer / migration (chuyển dữ liệu một lần hoặc định kỳ).
  • Chọn đúng loại AWS Storage Gateway: S3 File Gateway (NFS/SMB → S3), Volume Gateway cached vs stored (iSCSI → EBS snapshot), Tape Gateway (VTL → S3 Glacier), và biết tình trạng của FSx File Gateway.
  • Hiểu kiến trúc AWS DataSync: agent, location, task, task execution; khi nào cần agent, Basic vs Enhanced mode, kiểm tra toàn vẹn dữ liệu.
  • Biết khi nào phải chuyển dữ liệu offline bằng AWS Snowball Edge (Storage Optimized / Compute Optimized), các con số chính và lưu ý “không còn cho khách hàng mới”.
  • Thiết kế endpoint AWS Transfer Family (SFTP/FTPS/FTP/AS2) trên S3 hoặc EFS: endpoint type, Elastic IP cho allow list, identity provider, managed workflows.

AWS Storage Gateway: kiến trúc chung

AWS Storage Gateway kết nối một software appliance đặt tại chỗ với storage trên AWS Cloud, giúp môi trường IT on-premises tích hợp liền mạch và an toàn với hạ tầng lưu trữ AWS. Ứng dụng on-premises không cần sửa code: chúng vẫn nói NFS, SMB, iSCSI hay giao tiếp với thư viện băng từ như trước, còn gateway lo phần chuyển dữ liệu lên AWS.

Triển khai gateway ở đâu?

  • VM on-premises trên hypervisor VMware ESXi, Microsoft Hyper-V, Linux KVM hoặc Nutanix AHV.
  • Hardware appliance đặt mua qua đại lý (reseller) – dùng khi data center không có hạ tầng ảo hóa (vd chi nhánh nhỏ).
  • Amazon EC2 (AMI) hoặc VMware Cloud on AWS – dùng cho disaster recovery, data mirroring, hoặc cấp storage cho ứng dụng chạy trên EC2.
  • Sau khi triển khai, bạn activate gateway từ Storage Gateway console hoặc API, gateway được gắn với một AWS Region.

Hai vùng đĩa local: cache storage và upload buffer

Hầu hết loại gateway cần bạn cấp đĩa local cho VM với hai vai trò:

  • Cache storage – nơi lưu bền tạm thời dữ liệu đang chờ upload, đồng thời giữ dữ liệu vừa truy cập để đọc với độ trễ thấp. Khi ứng dụng đọc, gateway kiểm tra cache trước rồi mới lấy từ AWS. Với Volume Gateway cached, AWS khuyến nghị cache ≥ 20% kích thước file store hiện có và lớn hơn upload buffer.
  • Upload buffer – vùng staging chứa dữ liệu chuẩn bị upload, gửi lên AWS qua kết nối SSL/TLS mã hóa, rồi lưu mã hóa trong S3. (S3 File Gateway chỉ dùng cache.)

Gateway xác nhận ghi xong với ứng dụng ngay khi dữ liệu nằm an toàn trên đĩa local, rồi upload bất đồng bộ – đó là lý do ứng dụng cảm thấy độ trễ như storage local, đồng thời gateway “đệm” ứng dụng khỏi tắc nghẽn mạng.

Mẹo thi (Exam Tip) – nhận diện Storage Gateway
  • “On-premises applications” + “low-latency access to frequently used data” + “store data in AWS” ⇒ Storage Gateway (từ khóa local cache).
  • “NFS / SMB” + “objects in Amazon S3” ⇒ S3 File Gateway. “iSCSI” ⇒ Volume Gateway. “tape backup software / VTL” ⇒ Tape Gateway.
  • “No virtualization infrastructure at the branch office” ⇒ Storage Gateway hardware appliance.
  • “Disaster recovery: run gateway in AWS” ⇒ gateway trên EC2.

Amazon S3 File Gateway

Amazon S3 File Gateway cung cấp giao diện file vào Amazon S3: bạn lưu và lấy object trong S3 bằng giao thức file chuẩn NFS (v3 hoặc v4.1) và SMB (v2 và v3). Có thể hình dung nó như một “mount” của S3 bucket, kèm cache local trong suốt để đọc nhanh dữ liệu vừa dùng.

Cách hoạt động

  1. Triển khai & activate gateway (VM, hardware appliance hoặc EC2).
  2. Tạo file share và liên kết với một S3 bucket (có thể kèm prefix). Share dùng NFS hoặc SMB. Với SMB, gateway có thể join Microsoft Active Directory để xác thực người dùng Windows.
  3. Client mount share. Mỗi file ghi vào share trở thành một object trong S3, đường dẫn file = object key (ánh xạ 1:1). Object có sẵn trong bucket cũng hiện thành file.
  4. Gateway upload bất đồng bộ qua HTTPS, dùng multipart upload song song và byte-range download để tận dụng băng thông; điền header Content-MD5 để S3 từ chối và gateway gửi lại nếu checksum lệch.
  5. Metadata file (owner, quyền, timestamp) được lưu thành metadata của object S3. Object được mã hóa mặc định bằng SSE-S3 (có thể dùng AWS KMS).

Vì S3 không sửa được một phần object, nhiều thao tác file bình thường lại sinh ra object mới. Tài liệu AWS liệt kê:

  • Khi sửa file đã upload, gateway chỉ gửi phần dữ liệu mới/thay đổi, nhưng vẫn tạo phiên bản object mới.

Các điểm cần nhớ khác

  • Cache local giảm độ trễ và giảm phí data egress (đọc lại dữ liệu nóng không phải tải từ S3).
  • Nếu ứng dụng khác ghi thẳng object vào bucket (không qua gateway), gateway chưa biết ngay – cần refresh cache (API RefreshCache, có thể đặt lịch) để danh sách file trên share cập nhật.
  • Lưu được vào các lớp S3 Standard, S3 Standard-IA, S3 One Zone-IA, S3 Intelligent-Tiering; muốn xuống Glacier thì dùng S3 Lifecycle (đọc lại file đã ở Glacier phải restore trước).
  • Tích hợp IAM (role cho gateway ghi vào bucket), AWS KMS, CloudWatch metrics, CloudTrail audit.
Mẹo thi (Exam Tip) – S3 File Gateway
  • “Replace on-premises NAS / file server, store files as objects in S3, keep NFS/SMB access” ⇒ S3 File Gateway.
  • “On-premises database backups written to an SMB/NFS share must land in S3 and later move to Glacier” ⇒ S3 File Gateway + S3 Lifecycle.
  • “Files uploaded via the gateway must be analyzed by Athena / processed by Lambda” ⇒ S3 File Gateway (dữ liệu là object S3 đọc được), không phải Volume Gateway.
Bẫy thường gặp – S3 File Gateway
  • Đổi tên thư mục lớn trên share = ghi lại hàng triệu object ⇒ tốn phí PUT và có thể phí xóa sớm nếu object ở IA/Glacier.
  • Upload thẳng vào bucket rồi “không thấy file trên share” ⇒ cần RefreshCache, không phải lỗi quyền.
  • S3 File Gateway không phải giải pháp migration một lần tối ưu – migrate hàng loạt dùng DataSync.

Volume Gateway: cached volumes vs stored volumes

Volume Gateway cung cấp các storage volume được AWS hậu thuẫn mà server on-premises mount như thiết bị iSCSI (block storage). Bạn có thể chụp snapshot gia tăng của volume; snapshot được lưu trong S3 dưới dạng Amazon EBS snapshot, nên có thể khôi phục về gateway hoặc tạo EBS volume gắn vào EC2 (Bài 11).

Cached volumes

  • S3 là primary storage; chỉ giữ tập dữ liệu hay truy cập ở cache local.
  • Tiết kiệm lớn chi phí primary storage, giảm nhu cầu mở rộng storage on-premises.
  • Volume 1 GiB – 32 TiB; tối đa 32 volume/gateway, tổng 1.024 TiB (1 PiB).
  • Cache ≥ 20% file store hiện có, lớn hơn upload buffer.
  • Dữ liệu và snapshot lưu trong S3, mã hóa SSE, nhưng không truy cập được bằng S3 API / S3 console.
  • Snapshot ≤ 16 TiB có thể dùng làm nguồn tạo EBS volume mới.

Stored volumes

  • Toàn bộ dữ liệu ở local (DAS/SAN on-premises) ⇒ độ trễ thấp cho toàn bộ dataset.
  • Bất đồng bộ backup point-in-time snapshot lên S3 (EBS snapshot) – bản sao off-site bền, rẻ.
  • Volume 1 GiB – 16 TiB; tối đa 32 volume/gateway, tổng 512 TiB.
  • Có thể ánh xạ volume vào đĩa mới hoặc đĩa đã có dữ liệu.
  • Khôi phục: về volume on-premises, hoặc tạo EBS volume gắn vào EC2 cho DR.
  • Vẫn cần upload buffer (staging trước khi gửi qua SSL).
Mẹo thi (Exam Tip) – cached hay stored?
  • “Minimize on-premises storage, most data infrequently accessed, keep low-latency access to frequently accessed data” ⇒ cached volumes.
  • “Need low-latency access to the ENTIRE dataset” + “durable offsite backup in AWS” ⇒ stored volumes.
  • “iSCSI block storage + recover to Amazon EC2 for DR” ⇒ Volume Gateway → EBS snapshot → EBS volume.

Bốn khái niệm cốt lõi

  • Agent – VM appliance mà DataSync dùng để đọc/ghi storage trong quá trình truyền. Triển khai trên VMware ESXi, KVM, Nutanix AHV (dùng image KVM) hoặc Hyper-V; với storage trong VPC có thể chạy agent dạng EC2 instance. Có hai loại agent: cho task Basic mode và cho task Enhanced mode.
  • Location – mô tả nơi copy từ hoặc tới (vd một NFS export, một S3 bucket/prefix).
  • Task – định nghĩa một lần truyền: source location, destination location và tùy chọn (metadata, file đã xóa, quyền, filter, băng thông, lịch, mức kiểm tra).
  • Task execution – một lần chạy task, đi qua các pha chuẩn bị (prepare) → truyền (transfer) → kiểm tra (verify).

Khi nào cần agent?

Cần agent

  • Giữa storage on-premises và AWS.
  • Giữa Amazon EFS / FSx và storage ở cloud khác.
  • Giữa một số dịch vụ AWS khác account khi không bên nào là S3.
  • Giữa Region thương mại và AWS GovCloud (US) khi cả hai đầu là EFS/FSx.

Không cần agent

  • Giữa các dịch vụ AWS cùng account (cùng Region hoặc khác Region).
  • Giữa Amazon S3 và dịch vụ AWS khác khác account.
  • Giữa Amazon S3 và object storage ở cloud khác.
  • Commercial ↔ GovCloud khi một đầu là S3.

Truyền giữa Region bị tính phí data transfer OUT từ Region nguồn. Có thể gắn tối đa 4 agent Basic + 4 agent Enhanced vào một location để tăng tốc với hàng triệu file nhỏ, nhưng nhiều agent không tạo high availability: mọi agent của location phải online thì task mới chạy. Với dataset rất lớn, AWS khuyên chia thành nhiều task chạy song song, mỗi task một agent.

Tính năng hay được hỏi

  • Toàn vẹn dữ liệu: DataSync luôn kiểm tra toàn vẹn khi truyền, và có thể kiểm tra thêm cuối task (chỉ dữ liệu đã truyền hoặc toàn bộ dataset) bằng so sánh checksum và metadata.
  • Bảo mật: mã hóa TLS in transit; truy cập storage AWS bằng IAM role; hỗ trợ VPC endpoint để không đi Internet công cộng.
  • Lặp lại định kỳ: đặt lịch (schedule), chỉ truyền dữ liệu thay đổi kể từ lần trước, tùy chọn xóa ở đích những gì không còn ở nguồn.
  • Kiểm soát: filter include/exclude, giới hạn băng thông (không “ăn” hết đường truyền production), chọn metadata/quyền cần giữ.
  • File đang mở: copy được; nếu file bị ghi trong lúc truyền, pha verify phát hiện ⇒ chạy lại task. File bị khóa mà server không cho mở ⇒ bị bỏ qua và ghi log; DataSync không lock/unlock file.
  • Object archive: object ở lớp Glacier chưa restore sẽ bị bỏ qua – phải restore trước.
  • Use case chính: migrate dataset đang hoạt động, archive dữ liệu lạnh thẳng vào S3 Glacier Flexible Retrieval / Deep Archive để tắt hệ thống cũ, replicate sang S3 / EFS / FSx làm bản standby, đưa dữ liệu vào/ra để xử lý (ML, media, phân tích).
Mẹo thi (Exam Tip) – DataSync
  • “Migrate X TB from on-premises NFS/SMB NAS to Amazon EFS / FSx / S3”, “automate, verify data integrity, encrypted in transit”, “LEAST operational overhead” ⇒ AWS DataSync.
  • “Copy data between two EFS file systems / from S3 to FSx in another Region” ⇒ DataSync (không cần agent khi cùng account).
  • “Hadoop HDFS cluster migration to S3” ⇒ DataSync (HDFS location).
  • “Transfer must not consume all bandwidth during business hours” ⇒ DataSync + bandwidth limit / schedule.
  • “Transfer over Direct Connect privately” ⇒ DataSync với VPC service endpoint (PrivateLink).
Bẫy thường gặp – DataSync vs Storage Gateway
  • DataSync là công cụ di chuyển/đồng bộ – không phải nơi ứng dụng mount để đọc/ghi hằng ngày. Ứng dụng on-premises cần tiếp tục dùng file ⇒ Storage Gateway.
  • Kịch bản phổ biến của AWS: dùng DataSync để migrate dữ liệu hiện có, rồi S3 File Gateway cho truy cập liên tục từ on-premises vào dữ liệu đã migrate.
  • Nhiều agent trên một location ≠ HA. Agent offline ⇒ task không chạy được.

AWS Snowball Edge và chuyển dữ liệu offline

AWS Snowball Edge là thiết bị có sẵn storage và năng lực tính toán cho một số dịch vụ AWS. Nó có thể xử lý dữ liệu tại chỗ, chạy workload edge computing, và chuyển dữ liệu vào/ra AWS nhanh hơn Internet bằng cách gửi chính thiết bị qua đơn vị vận chuyển. Thiết bị là một hộp chắc chắn (rugged), có màn hình E Ink tự hiển thị nhãn gửi hàng.

Tình trạng dịch vụ (quan trọng khi đọc đề cũ)

Tài liệu AWS hiện ghi: “AWS Snowball Edge is no longer available to new customers.” Khách hàng mới được hướng tới AWS DataSync cho truyền online, AWS Data Transfer Terminal cho truyền vật lý an toàn (mang thiết bị lưu trữ tới địa điểm của AWS), hoặc giải pháp đối tác; với edge computing dùng AWS Outposts. Các thiết bị nhỏ hơn (Snowcone) và xe tải Snowmobile (100 PB) cũng đã ngừng. Tuy vậy, đề SAA-C03 vẫn có thể dùng Snow Family làm đáp án cho tình huống “băng thông hạn chế, hàng trăm TB–PB”, vì vậy bạn vẫn cần hiểu chúng.

Quy trình một job import

  1. Tạo job import trên console, chọn S3 bucket đích và KMS key. AWS gửi thiết bị tới bạn.
  2. Nhận thiết bị, cắm mạng, unlock bằng manifest + unlock code (Snowball Edge client / OpsHub).
  3. Copy dữ liệu bằng NFS hoặc S3 adapter (dữ liệu được mã hóa khi ghi lên thiết bị).
  4. Tắt thiết bị – nhãn E Ink tự đổi sang địa chỉ trả về; gửi qua đơn vị vận chuyển.
  5. AWS nhận thiết bị, nạp dữ liệu vào S3 bucket, sau đó xóa an toàn thiết bị theo chuẩn NIST.
Mẹo thi (Exam Tip) – Snow Family
  • “Hundreds of TB / petabytes” + “limited / slow network bandwidth” + “complete within weeks” ⇒ Snowball Edge Storage Optimized (nhiều thiết bị song song nếu cần).
  • “Process data at a remote location with no / intermittent connectivity (ship, mine, field)” ⇒ Snowball Edge Compute Optimized (hoặc AWS Outposts nếu có kết nối ổn định và cần hạ tầng AWS lâu dài).
  • Snowball nạp dữ liệu vào S3. Muốn dữ liệu vào Glacier ⇒ import vào S3 rồi dùng S3 Lifecycle chuyển xuống Glacier Flexible Retrieval / Deep Archive.
  • Đủ băng thông + thời gian ⇒ ưu tiên DataSync (online, tự động, kiểm tra toàn vẹn) thay vì vận chuyển thiết bị.

AWS Transfer Family: SFTP, FTPS, FTP, AS2 được quản lý

AWS Transfer Family là dịch vụ truyền file an toàn, fully managed, cho phép chuyển file vào/ra Amazon S3 hoặc Amazon EFS qua SFTP (version 3), FTPS, FTP, AS2 và truyền qua trình duyệt (web apps). Khách hàng, đối tác, đội nội bộ giữ nguyên client (OpenSSH, WinSCP, FileZilla, Cyberduck…), cấu hình xác thực và firewall – không có gì thay đổi phía họ, còn bạn không phải chạy server SFTP nào.

SFTP

SSH File Transfer Protocol

Qua SSH, mã hóa. Cổng 22 (mặc định), có thể thêm 2222, 22000. Dùng được trên endpoint public lẫn VPC.

FTPS

FTP qua TLS

Control channel cổng 21, data channel 8192–8200. Dùng được trên VPC endpoint internet-facing.

FTP

Không mã hóa

Chỉ cho mạng nội bộ: endpoint VPC internal (internet-facing chỉ cho SFTP và FTPS).

AS2

Applicability Statement 2

Giao thức B2B có sẵn bảo vệ dữ liệu: chuỗi cung ứng, thanh toán, tích hợp ERP/CRM, yêu cầu tuân thủ.

Identity provider – ai được đăng nhập?

  • Service managed: user và SSH public key lưu trong Transfer Family, mỗi user gắn IAM role và home directory (S3 prefix / thư mục EFS).
  • AWS Directory Service: xác thực bằng AWS Managed Microsoft AD hoặc AD on-premises qua AD Connector (Bài 7).
  • Custom identity provider: AWS Lambda hoặc Amazon API Gateway gọi tới IdP riêng (Okta, Azure AD, Cognito, database…), trả về IAM role, home directory, policy.

Tính năng bổ sung

  • Managed workflows (MFTW): serverless, tự chạy sau khi upload xong (hoặc upload dở) – copy, gắn tag, quét, lọc, nén/giải nén, mã hóa/giải mã; có theo dõi end-to-end để audit.
  • Transfer Family web apps: giao diện web được quản lý để người dùng nghiệp vụ tải lên/xuống S3, tích hợp S3 Access Grants.
  • Connectors (SFTP / AS2 connector): Transfer Family chủ động gửi/nhận file với server của đối tác.
  • Trả tiền theo sử dụng, không phí trả trước; dữ liệu trong S3 dùng ngay cho phân tích, báo cáo, audit, archive.
Mẹo thi (Exam Tip) – Transfer Family
  • “Partners upload files via SFTP, store in S3, no servers to manage” ⇒ AWS Transfer Family (không dựng EC2 chạy SFTP).
  • “Partners must allow list a static IP address” ⇒ endpoint VPC, internet-facing + Elastic IP; chặn IP lạ bằng security group.
  • “Authenticate SFTP users against the corporate Active Directory” ⇒ identity provider AWS Directory Service; IdP bên thứ ba ⇒ custom IdP (Lambda / API Gateway).
  • “EDI / B2B, AS2 protocol” ⇒ Transfer Family AS2.

Tóm tắt ghi nhớ

Những điều phải nhớ
  • Storage Gateway = appliance tại chỗ (VMware/Hyper-V/KVM/Nutanix, hardware appliance, EC2) + cache local; ứng dụng on-premises tiếp tục dùng storage, dữ liệu nằm ở AWS.
  • S3 File Gateway: NFS v3/4.1, SMB 2/3 ⇒ 1 file = 1 object, path = key, SSE-S3; đổi tên/quyền/append tạo object mới; dùng S3 Lifecycle để xuống Glacier. FSx File Gateway không còn cho khách hàng mới.
  • Volume Gateway (iSCSI): cached = S3 là bản chính, 32 TiB/volume, 1 PiB/gateway; stored = toàn bộ local, snapshot bất đồng bộ, 16 TiB/volume, 512 TiB/gateway; snapshot là EBS snapshot ⇒ EBS volume cho EC2.
  • Tape Gateway: VTL iSCSI (10 tape drive + 1 media changer), tape 100 GiB–15 TiB, 1.500 tape / 1 PiB; archive vào Glacier Flexible Retrieval (3–5 h) hoặc Deep Archive (~12 h).
  • DataSync: agent + location + task + task execution; TLS, verify checksum, schedule, chỉ truyền phần thay đổi, bandwidth limit, filter; không cần agent giữa dịch vụ AWS cùng account; tối đa 4 agent/location nhưng không HA.
  • Snowball Edge: Storage Optimized 210 TB, Compute Optimized 104 vCPU/416 GB/28 TB; mã hóa bắt buộc; cluster 3–16; nạp vào S3; không còn cho khách hàng mới (thay bằng DataSync / Data Transfer Terminal / Outposts).
  • Transfer Family: SFTP/FTPS/FTP/AS2/web ⇒ S3 hoặc EFS; endpoint Public / VPC internal / VPC internet-facing (Elastic IP tĩnh, security group); IdP service managed / Directory Service / custom (Lambda, API Gateway); managed workflows.

A company's on-premises Linux and Windows servers store documents on an aging NAS that is running out of capacity. The company wants to store the documents in Amazon S3 so that they can be analyzed with Amazon Athena, while the on-premises servers continue to access them over NFS and SMB with low latency for recently used files. Which solution meets these requirements with the LEAST operational overhead?
  1. Deploy Volume Gateway with cached volumes and mount the volumes over iSCSI.
  2. Deploy Amazon S3 File Gateway on premises and create NFS and SMB file shares backed by the S3 bucket.
  3. Use AWS DataSync to copy the NAS to Amazon S3 every hour and keep the NAS as the primary storage.
  4. Order Snowball Edge devices every month to move new documents to Amazon S3.
Đáp án B. S3 File Gateway cho truy cập NFS/SMB từ on-premises, lưu mỗi file thành object S3 (Athena đọc được ngay), có cache local cho dữ liệu vừa dùng. A sai: Volume Gateway là block iSCSI, dữ liệu trong S3 không truy cập được bằng S3 API ⇒ Athena không đọc được. C sai: NAS vẫn hết dung lượng, đồng bộ theo giờ tốn vận hành. D sai: Snowball dành cho chuyển khối lượng lớn một lần, không phải truy cập liên tục.
Các server Linux và Windows on-premises của một công ty lưu tài liệu trên một NAS đã cũ và sắp hết dung lượng. Công ty muốn lưu tài liệu trong Amazon S3 để có thể phân tích bằng Amazon Athena, trong khi các server on-premises vẫn tiếp tục truy cập chúng qua NFS và SMB với độ trễ thấp cho các file mới được dùng gần đây. Giải pháp nào đáp ứng các yêu cầu này với LEAST operational overhead (ít công sức vận hành nhất)?
  • Triển khai Volume Gateway với cached volumes và mount các volume qua iSCSI.Sai: Volume Gateway cung cấp block storage iSCSI, không phải NFS/SMB, và dữ liệu lưu trong S3 không truy cập được bằng S3 API nên Athena không đọc được.
  • Triển khai Amazon S3 File Gateway on-premises và tạo các NFS và SMB file share dựa trên S3 bucket.Đúng: S3 File Gateway cho truy cập NFS/SMB, lưu mỗi file thành một object S3 (Athena đọc trực tiếp được) và có cache local cho file dùng gần đây với độ trễ thấp.
  • Dùng AWS DataSync sao chép NAS sang Amazon S3 mỗi giờ và giữ NAS làm bộ lưu trữ chính.Sai: NAS vẫn là bộ lưu trữ chính nên vẫn hết dung lượng; vận hành đồng bộ theo giờ cũng tốn công hơn.
  • Đặt các thiết bị Snowball Edge mỗi tháng để chuyển tài liệu mới lên Amazon S3.Sai: Snowball dành cho chuyển dữ liệu lớn một lần (offline), không cung cấp truy cập NFS/SMB liên tục và tốn nhiều công vận hành.

  1. Create an AWS Transfer Family SFTP server with a custom identity provider that uses AWS Lambda, return an IAM role and home directory per user, and attach a managed workflow for post-upload processing.
  2. Create an AWS Transfer Family server with service-managed users and manually copy the users' SSH keys from the identity provider every day.
  3. Deploy Amazon S3 File Gateway and join it to the identity provider by using SMB.
  4. Run an SFTP server on Amazon EC2 with a custom PAM module and an S3 event-driven Lambda function for scanning.
