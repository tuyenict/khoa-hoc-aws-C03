Ví dụ đời thường – tòa chung cư

Network ACL là bảo vệ ở cổng khu nhà: có danh sách “cho vào / cấm vào” đánh số thứ tự, đọc từ trên xuống, khớp dòng nào làm theo dòng đó; và không nhớ mặt ai – bạn đi ra rồi quay lại vẫn bị kiểm tra lại từ đầu (stateless). Security group là lễ tân ở cửa từng căn hộ: chỉ có danh sách khách được mời (allow), và nhớ ai vừa đi ra để cho họ quay vào (stateful). Network Firewall là trạm an ninh soi chiếu hành lý ở cổng chính của cả khu đô thị, mở từng kiện hàng (deep packet inspection). Flow Logs là sổ ghi camera: ghi giờ, ai, đi đâu, được cho qua hay bị chặn – nhưng không ghi nội dung hành lý.

Stateful vs Stateless – khái niệm gốc của cả bài

Tài liệu NACL định nghĩa: NACL là stateless – thông tin về traffic đã gửi/nhận trước đó không được lưu. Nếu bạn tạo rule NACL cho phép một traffic inbound vào subnet, phản hồi của traffic đó không tự động được cho phép. Ngược lại, security group là stateful – thông tin traffic trước đó được lưu, nên nếu SG cho phép inbound thì phản hồi tự động được phép ra, bất kể outbound rule.

Một kết nối TCP thực ra có hai chiều

Khi người dùng mở https:// tới web server, client chọn một cổng nguồn tạm thời (ephemeral port, vd 50123) và gửi tới cổng đích 443 của server. Server trả lời từ cổng 443 về cổng 50123 của client. Vậy có hai “luồng”:

  • Request: client:50123 → server:443 (inbound với server).
  • Response: server:443 → client:50123 (outbound với server, đích là ephemeral port của client).

Với stateful (SG), bạn chỉ cần mở chiều request; firewall ghi nhớ kết nối và tự cho response đi. Với stateless (NACL), bạn phải viết hai rule: inbound cho port 443 và outbound cho dải ephemeral port của client.

Mẹo thi (Exam Tip)
  • Đề mô tả “inbound traffic is allowed but users receive timeouts”, “the security group allows port 443 … the network ACL allows inbound 443 … connection fails” ⇒ nghĩ ngay NACL thiếu outbound rule cho ephemeral ports (vì NACL stateless).
  • Đề hỏi “Which component is stateful?” ⇒ security group (và Network Firewall stateful engine). “Stateless” ⇒ network ACL (và stateless rule group của Network Firewall).
  • Sửa outbound rule của security group không ảnh hưởng tới response của kết nối inbound đã được cho phép – bẫy thường gặp khi đáp án gợi ý “add an outbound rule to the security group”.

  • “Allow traffic only from the load balancer” ⇒ security group của instance tham chiếu security group của ALB – không dùng NACL vì NACL chỉ có CIDR.
  • “Subnet-level”, “all instances in the subnet”, “explicit deny”, “rule number / order” ⇒ NACL. “Instance-level”, “reference another security group” ⇒ SG.

Network ACL chi tiết

Một network access control list (ACL) cho phép hoặc từ chối traffic inbound/outbound cụ thể ở cấp subnet. Bạn có thể dùng default network ACL của VPC hoặc tạo custom network ACL với rule tương tự security group để thêm một lớp bảo mật. Không có phí cho network ACL.

Liên kết NACL với subnet

  • Mỗi subnet bắt buộc phải gắn với một network ACL. Không gắn tường minh ⇒ subnet tự động gắn với default network ACL.
  • Một network ACL gắn được với nhiều subnet, nhưng một subnet chỉ gắn với một network ACL tại một thời điểm. Gắn NACL mới ⇒ liên kết cũ bị gỡ.
  • NACL được đánh giá khi traffic đi vào và rời khỏi subnet, không đánh giá traffic được route bên trong cùng một subnet. ⇒ Hai instance cùng subnet nói chuyện với nhau chỉ chịu security group.
  • Thêm/xóa rule ⇒ thay đổi tự áp dụng cho mọi subnet đang gắn, có hiệu lực sau một khoảng ngắn.

Bẫy thường gặp – NACL và các dịch vụ khác
  • ELB health check: nếu subnet của backend có NACL deny mọi traffic từ 0.0.0.0/0 hoặc từ CIDR của chính subnet, load balancer không health check được instance.

  • Quota 20 rule mỗi chiều (tăng tối đa 40 inbound + 40 outbound = 80, nhưng hiệu năng mạng có thể bị ảnh hưởng). Không thể dùng NACL để chặn hàng nghìn IP ⇒ dùng AWS WAF hoặc Network Firewall.

  • “Instances in the same subnet can communicate but not with another subnet” ⇒ kiểm tra NACL (NACL không lọc traffic trong cùng subnet).
  • Câu hỏi đưa bảng rule NACL và hỏi traffic nào được phép ⇒ đọc từ số nhỏ nhất, dừng ở rule khớp đầu tiên.

Ephemeral ports – chìa khóa để NACL không “làm gãy” kết nối

Ephemeral port là cổng nguồn tạm thời mà client khởi tạo request tự chọn; response quay về đúng cổng đó. Theo tài liệu, dải cổng do client chọn và phụ thuộc hệ điều hành của client. Vì NACL stateless, bạn phải mở dải này ở chiều trả về.

Hai tình huống cần nhớ

Instance trong VPC là server

  • Client ở Internet (vd Windows 10) gọi vào port 443.
  • NACL inbound: allow TCP 443.
  • NACL outbound: allow TCP tới dải ephemeral của client – với Windows 10 là 49152–65535.
  • Client đa dạng ⇒ thực tế mở 1024–65535.

Instance trong VPC là client

  • Instance Amazon Linux gọi ra https://repo… port 443 (tải bản vá).
  • NACL outbound: allow TCP 443.
  • NACL inbound: allow TCP tới dải ephemeral của chính instance – Amazon Linux 32768–61000.
  • Nếu đi qua NAT gateway: subnet của NAT cần mở 1024–65535.
Thực hành của AWS

Tài liệu gợi ý: để phục vụ mọi loại client gọi tới instance public, bạn có thể mở ephemeral port 1024–65535, rồi thêm rule DENY cho các port độc hại trong dải đó – nhớ đặt deny rule trước (số nhỏ hơn) allow rule dải rộng.

Mẹo thi (Exam Tip)
  • Đáp án đúng cho “web server behind NACL, users time out” thường là “Add an outbound rule to the network ACL that allows TCP ports 1024-65535 to 0.0.0.0/0”. Đáp án sai hay gặp: mở outbound port 443 (sai – response đi tới ephemeral port của client, không phải 443), hoặc sửa security group.
  • Instance private không tải được bản cập nhật dù có NAT gateway và route đúng ⇒ NACL của subnet private thiếu inbound ephemeral ports.

  • Reachability Analyzer: công cụ phân tích cấu hình tĩnh (không gửi gói tin thật). Cho hai tài nguyên trong VPC, nó trả về đường đi từng chặng nếu tới được, hoặc chỉ ra thành phần đang chặn – ví dụ rule NACL thiếu hoặc sai.
  • VPC Flow Logs: dữ liệu thực tế traffic đã ACCEPT hay REJECT (phần kế tiếp).
  • AWS Security Hub CSPM: AWS gợi ý dùng để kiểm tra instance có bị lộ ra mạng ngoài ý muốn không.
Mẹo thi (Exam Tip)

“Determine why two resources cannot connect without sending traffic” / “identify the misconfigured component” ⇒ Reachability Analyzer. “Analyze actual traffic / which requests were rejected / audit IP traffic” ⇒ VPC Flow Logs.

VPC Flow Logs

VPC Flow Logs là tính năng ghi lại thông tin về IP traffic đi vào và ra các network interface trong VPC. Dữ liệu được publish tới Amazon CloudWatch Logs, Amazon S3 hoặc Amazon Data Firehose. Đường đi + quyền để gửi log tới đích được gọi là subscription.

Flow Logs giúp bạn: chẩn đoán security group rule quá chặt; giám sát traffic tới instance; xác định hướng traffic tới/từ network interface. Dữ liệu được thu thập ngoài đường đi của traffic nên không ảnh hưởng throughput hay latency – tạo/xóa flow log không có rủi ro về hiệu năng mạng.

Tạo flow log ở đâu?

  • Ba cấp: VPC, subnet, hoặc network interface. Tạo ở cấp VPC/subnet ⇒ mọi network interface trong đó đều được giám sát, kể cả instance launch sau khi tạo flow log (AWS tự tạo log stream/file mới khi interface có traffic).
  • Tạo được cho network interface của dịch vụ AWS khác: Elastic Load Balancing, Amazon RDS, Amazon ElastiCache, Amazon Redshift, Amazon WorkSpaces, NAT gateways, transit gateways.
  • Khi tạo, bạn chỉ định: tài nguyên; loại traffic cần ghi – accepted, rejected hoặc all; và đích publish.
  • Sau khi tạo cần vài phút mới bắt đầu thu và publish; không thấy dữ liệu cho tới khi có traffic. Flow Logs không phải luồng thời gian thực.

Định dạng flow log record

Mỗi record đại diện cho một luồng IP (xác định bởi 5-tuple trên mỗi network interface) xảy ra trong một aggregation interval (còn gọi là capture window). Record là chuỗi các trường cách nhau bằng dấu cách. Default format gồm các trường version 2 theo thứ tự cố định và không sửa được; muốn thêm/bớt trường thì dùng custom format (chọn trường và thứ tự, ít nhất 1 trường).

Đọc record: SG hay NACL đã chặn?

Ví dụ (default format) – một luồng SSH (port 22, protocol 6) được chấp nhận:

2 123456789010 eni-1235b8ca123456789 172.31.16.139 172.31.16.21 20641 22 6 20 4249 1418530010 1418530070 ACCEPT OK

Tình huống kinh điển: bạn ping (ICMP, protocol 1) từ 203.0.113.12 tới instance 172.31.16.139. Security group cho phép ICMP inbound; NACL cho phép ICMP inbound nhưng không cho phép ICMP outbound. Flow log ghi hai record:

2 123456789010 eni-1235b8ca123456789 203.0.113.12 172.31.16.139 0 0 1 4 336 1432917027 1432917142 ACCEPT OK
2 123456789010 eni-1235b8ca123456789 172.31.16.139 203.0.113.12 0 0 1 4 336 1432917094 1432917142 REJECT OK
  • Inbound ACCEPT rồi response outbound REJECT ⇒ chỉ có thể là NACL (stateless) chặn chiều về. Security group stateful không bao giờ chặn response của request đã được cho phép.
  • Nếu chỉ thấy inbound REJECT ⇒ SG hoặc NACL chặn ngay từ chiều vào.

Giới hạn quan trọng (theo tài liệu)

  • Sau khi tạo, không đổi được cấu hình hay định dạng record (vd đổi IAM role, thêm/bớt trường) ⇒ phải xóa và tạo flow log mới.
  • Không bật flow log được cho VPC peer nếu VPC đó không thuộc account của bạn.
  • Xóa flow log chỉ dừng ghi log mới; dữ liệu cũ ở đích không bị xóa.
  • Traffic gửi tới secondary private IP vẫn hiện primary private IP trong dstaddr ⇒ cần trường pkt-dstaddr để thấy IP gốc.
  • Flow Logs chỉ ghi metadata của luồng, không ghi nội dung gói tin (payload). Cần nội dung để IDS/phân tích pháp chứng ⇒ Traffic Mirroring (sao chép gói tin từ ENI tới công cụ phân tích) hoặc Network Firewall.

Chi phí

Khi publish flow log, áp dụng phí data ingestion và archival của vended logs (theo bảng giá CloudWatch – mục Logs → Vended Logs), cộng phí lưu trữ ở đích. Có thể gắn cost allocation tag cho log group / bucket / delivery stream đích để theo dõi chi phí.

Mẹo thi (Exam Tip)
  • “Capture information about IP traffic / identify rejected connections / audit network traffic for compliance” ⇒ VPC Flow Logs.
  • “Analyze flow logs with SQL, low cost, long retention” ⇒ Flow Logs → S3 + Amazon Athena. “Alarm when rejected SSH attempts exceed a threshold” ⇒ Flow Logs → CloudWatch Logs + metric filter + alarm. “Stream to a third-party SIEM” ⇒ Data Firehose.
  • “Inspect packet payload / content” ⇒ không phải Flow Logs ⇒ Traffic Mirroring hoặc Network Firewall.
  • Amazon GuardDuty phân tích VPC Flow Logs (cùng CloudTrail, DNS logs) làm nguồn dữ liệu phát hiện mối đe dọa – bạn không cần tự bật flow log cho GuardDuty.
Bẫy thường gặp

Đáp án “modify the existing flow log to add the tcp-flags field” là sai – flow log không sửa được, phải tạo flow log mới với custom format. Đáp án “use flow logs to block malicious traffic” cũng sai – Flow Logs chỉ quan sát, không chặn.

AWS Network Firewall

AWS Network Firewall là dịch vụ tường lửa mạng stateful, được quản lý (managed) kèm khả năng intrusion detection and prevention (IDS/IPS) cho VPC. Nó lọc traffic ở biên (perimeter) của VPC: traffic đi tới/từ internet gateway, NAT gateway, hoặc qua VPN / Direct Connect. Engine stateful dùng IPS mã nguồn mở Suricata và hỗ trợ rule tương thích Suricata.

Network Firewall làm được gì mà SG/NACL không làm được?

  • Chỉ cho đi qua traffic tới các domain hoặc IP endpoint đã biết của dịch vụ AWS (vd Amazon S3) – lọc theo tên miền (domain list allow/deny).
  • Dùng danh sách tùy chỉnh các domain độc hại để giới hạn tên miền mà ứng dụng được truy cập.
  • Deep packet inspection traffic vào/ra VPC.
  • Nhận diện giao thức stateful: lọc HTTPS… bất kể port đang dùng.
  • TLS inspection (giải mã để kiểm tra traffic mã hóa – cần cấu hình riêng).

Tóm tắt ghi nhớ

Key takeaways
  • Stateful (SG) nhớ kết nối ⇒ response tự được phép. Stateless (NACL) không nhớ ⇒ phải mở rule cho cả chiều về (ephemeral ports).
  • SG: cấp instance, chỉ allow, đánh giá tất cả rule, tham chiếu được SG khác, 60 rule/chiều, 5 (→16) SG/ENI. NACL: cấp subnet, allow + deny, đánh giá theo số thứ tự tăng dần (1–32766), dừng ở rule khớp đầu, chỉ CIDR, 20 (→40) rule/chiều, 1 NACL/subnet.
  • Default NACL allow all (rule 100/101); custom NACL mới tạo deny all (chỉ còn rule *). Rule * không xóa được. NACL không lọc traffic trong cùng subnet.
  • Ephemeral ports: Linux 32768–61000; Windows Server 2008+ 49152–65535; ELB, NAT gateway, Lambda 1024–65535 ⇒ thực tế mở 1024–65535, đặt DENY số nhỏ hơn nếu cần.
  • Muốn chặn một IP ⇒ NACL deny (số nhỏ hơn allow). Cả SG lẫn NACL không lọc DNS Amazon, DHCP, IMDS, Time Sync ⇒ DNS Firewall / IMDSv2.
  • VPC Flow Logs: cấp VPC/subnet/ENI; ACCEPT/REJECT/ALL; đích CloudWatch Logs / S3 / Data Firehose; interval 10 phút (hoặc 1 phút); không real-time; không đổi cấu hình sau khi tạo; không ghi payload; không ghi DNS Amazon, IMDS, DHCP, ARP. Inbound ACCEPT + outbound REJECT ⇒ NACL.
  • Network Firewall: managed stateful firewall + IPS (Suricata), lọc domain, DPI; firewall endpoint trong firewall subnet riêng mỗi AZ; phải sửa route table (gồm IGW edge association); stateless engine → stateful engine; log tới S3/CloudWatch/Firehose; quản lý đa account bằng Firewall Manager.
  • Không gửi traffic mà muốn biết vì sao không kết nối được ⇒ Reachability Analyzer.

Câu hỏi luyện tập

A web application runs on Amazon EC2 instances in a public subnet. The instances' security group allows inbound TCP 443 from 0.0.0.0/0. A security engineer associates a new custom network ACL with the subnet and adds an inbound rule that allows TCP 443 from 0.0.0.0/0 and an outbound rule that allows TCP 443 to 0.0.0.0/0. Users now report that connections to the website time out. What should a solutions architect do to resolve the issue?
  1. Add an outbound rule to the security group that allows TCP 443 to 0.0.0.0/0.
  2. Add an inbound rule to the network ACL that allows TCP 1024-65535 from 0.0.0.0/0.

  • Trong network ACL của public subnet, chỉ cho phép inbound TCP 443 từ 0.0.0.0/0.Sai: inbound 443 chỉ cần khi có server HTTPS trong public subnet; nó không cho response từ Internet quay về NAT gateway ở ephemeral port.
  • Trong network ACL của public subnet, cho phép inbound TCP 1024-65535 từ 0.0.0.0/0.Đúng: response từ Internet quay về NAT gateway ở các port 1024–65535, nên NACL của public subnet phải cho phép inbound dải này.
