Tổng quan: CloudFront hoạt động thế nào?

Theo tài liệu AWS, Amazon CloudFront là web service tăng tốc phân phối nội dung web tĩnh và động (.html, .css, .js, ảnh, video, API…) tới người dùng thông qua mạng lưới data center toàn cầu gọi là edge location. Request của người dùng được định tuyến tới edge location có độ trễ thấp nhất; nếu nội dung đã có trong cache thì trả ngay, nếu chưa thì CloudFront lấy từ origin – nơi lưu bản gốc chính thức (S3 bucket, MediaPackage, HTTP server…).

Lợi ích tài liệu nêu rõ: request đi qua AWS backbone network thay vì nhảy qua hàng loạt mạng internet ⇒ giảm độ trễ (thời gian tới byte đầu tiên) và tăng tốc độ truyền; bản sao (object) được cache ở nhiều edge location ⇒ tăng reliability và availability; origin nhận ít request hơn ⇒ giảm tải origin.

Amazon CloudFront

Cache và phân phối nội dung tĩnh/động, video, API qua HTTP/HTTPS (cả WebSocket, gRPC) tại edge gần người dùng.

Điểm hiện diện

Bộ đệm biên khu vực

Tầng giữa POP và origin, cache lớn hơn, giữ object kém phổ biến lâu hơn ⇒ ít phải quay về origin.

CloudFront Functions & Lambda@Edge

Chạy code tại biên

Sửa request/response, redirect, xác thực token, chuẩn hóa cache key… ngay tại edge.

Bộ tăng tốc toàn cầu

2 static anycast IP đưa traffic TCP/UDP vào mạng AWS tại edge gần nhất rồi tới endpoint tối ưu ở các Region. Không cache.

Chống DDoS & tường lửa web

CloudFront và Global Accelerator được Shield Standard bảo vệ mặc định; gắn web ACL của WAF vào distribution (chi tiết ở bài Threat Protection).

Luồng xử lý một request

Theo trang “How CloudFront delivers content” và “How CloudFront works with regional edge caches”:

  1. Người dùng gửi request một object (ảnh, file HTML…). DNS định tuyến request tới POP phục vụ tốt nhất – thường là POP gần nhất về độ trễ.
  2. POP kiểm tra cache. Cache hit ⇒ trả object ngay.
  3. Cache miss ⇒ POP thường hỏi tiếp regional edge cache gần nhất. Có thì regional edge cache chuyển về POP; ngay khi byte đầu tiên tới, CloudFront bắt đầu chuyển cho người dùng và lưu vào cache POP.
  4. Không có ở cả hai tầng ⇒ CloudFront so request với cấu hình distribution, gửi tới origin (qua kết nối persistent). Object trả về được cache ở cả regional edge cache và POP – mọi POP trong khu vực dùng chung cache khu vực, tránh gọi origin nhiều lần.
Khi nào bỏ qua regional edge cache? (theo tài liệu)
  • Các proxy HTTP method PUT, POST, PATCH, OPTIONS, DELETE đi thẳng từ POP tới origin.
  • Request động (xác định lúc nhận request) đi thẳng tới origin.
  • Origin là S3 và regional edge cache tối ưu nằm cùng Region với bucket ⇒ POP gọi thẳng S3.
  • Regional edge cache có tính năng tương đương POP: invalidation xóa object ở cả hai tầng.

Origin Shield – tầng cache thứ ba

Origin Shield là tầng cache bổ sung, bật riêng cho từng origin và chọn một Region (nên chọn Region có độ trễ thấp nhất tới origin). Lợi ích: tăng cache hit ratio, giảm tải origin (gộp request trùng thành ít nhất một request), cải thiện hiệu năng mạng. Hữu ích khi viewer phân tán nhiều vùng địa lý, origin làm just-in-time packaging video live hay xử lý ảnh on-the-fly, origin on-premises bị giới hạn băng thông, hoặc dùng nhiều CDN. Không phù hợp với nội dung động/ít cache được. Origin Shield chạy trên hạ tầng regional edge cache, mỗi nơi dựng trên ít nhất 3 AZ, tự chuyển sang vị trí Origin Shield dự phòng khi vị trí chính lỗi. Ví dụ đời thường – chuỗi cửa hàng tiện lợi

Nhà máy (origin) ở một tỉnh. Nếu ai cũng phải tới tận nhà máy mua hàng thì xa và nhà máy quá tải. CloudFront giống chuỗi cửa hàng tiện lợi ở từng phường (POP) bày sẵn hàng bán chạy; phía sau có kho tổng khu vực (regional edge cache) chứa nhiều mặt hàng hơn; Origin Shield là một kho trung chuyển duy nhất trước cổng nhà máy – mọi kho khu vực thiếu hàng đều lấy qua đây, nhà máy chỉ phải xuất mỗi mặt hàng một lần. TTL là hạn sử dụng ghi trên bao bì: hết hạn thì cửa hàng phải hỏi lại nhà máy xem có lô mới không.

Định giá – các yếu tố đề hay khai thác

  • CloudFront tính phí data transfer out từ edge tới viewer và số HTTP/HTTPS request; giá khác nhau theo khu vực địa lý.
  • Data transfer từ AWS origin (S3, ELB, API Gateway) tới CloudFront luôn miễn phí ⇒ đặt CloudFront trước S3 thường rẻ hơn phục vụ trực tiếp từ S3 cho người dùng internet, và giảm số GET request tới S3.
  • Price class (kiến thức thi phổ biến): Price Class All (mọi edge, hiệu năng tốt nhất), Price Class 200 (bỏ bớt các vùng đắt nhất), Price Class 100 (chỉ các vùng rẻ nhất – Bắc Mỹ, châu Âu…) ⇒ đề hỏi “reduce CloudFront cost, users mainly in US/Europe” ⇒ chọn price class thấp hơn.

Distribution và Origin

Một distribution cho CloudFront biết lấy file từ origin nào và phân phối thế nào (log, HTTPS, cache, bảo mật…). CloudFront gán cho distribution một tên miền dạng d111111abcdef8.cloudfront.net và gửi cấu hình (không phải nội dung) tới tất cả edge location.

Các bước thiết lập (theo tài liệu)

  1. Chỉ định origin server – S3 bucket hoặc HTTP server của bạn (EC2, server tự quản lý… gọi là custom origin).
  2. Upload file (gọi là object) lên origin. Object S3 có thể public hoặc giữ private và kiểm soát truy cập.
  3. Tạo distribution: chọn origin, bật log, bật ngay khi tạo…
  4. CloudFront gán tên miền; bạn có thể thêm alternate domain name (CNAME) như www.example.com – trỏ bằng Route 53 alias record (Bài 24).
  5. CloudFront đẩy cấu hình tới mọi edge location/POP.

HTTPS: viewer protocol policy, origin protocol policy và chứng chỉ

  • Viewer protocol policy (trên cache behavior): HTTP and HTTPS · Redirect HTTP to HTTPS · HTTPS Only.
  • Origin protocol policy (chỉ custom origin): HTTP only · HTTPS only · Match viewer.
  • Muốn dùng chứng chỉ ACM cho HTTPS giữa viewer và CloudFront (alternate domain name) ⇒ phải request hoặc import chứng chỉ ở us-east-1 (N. Virginia). Chứng chỉ cho HTTPS giữa CloudFront và ELB origin thì ở Region nào cũng được (Region của load balancer).
  • Chứng chỉ phải bao phủ alternate domain name trong trường SAN (khớp chính xác hoặc wildcard cùng cấp). Chứng chỉ của origin không khớp origin domain ⇒ CloudFront trả 502 Bad Gateway.
  • Field-level encryption: mã hóa riêng từng trường nhạy cảm (vd số thẻ) ngay tại edge bằng public key, chỉ ứng dụng giữ private key mới giải mã được.
Bẫy thường gặp
  • Tạo chứng chỉ ACM ở ap-southeast-1 rồi không thấy trong danh sách khi gắn vào CloudFront ⇒ chứng chỉ cho CloudFront phải ở us-east-1.
  • Origin là S3 website endpoint thì không dùng được OAC – đề yêu cầu “bucket không public” + “dùng CloudFront” ⇒ origin phải là REST endpoint của bucket + OAC (dùng default root object hoặc CloudFront Function để xử lý index.html).

Origin group – origin failover

Cho kịch bản cần high availability, tạo origin group gồm hai origin: primary và secondary, rồi gán origin group cho cache behavior. Theo tài liệu:

  • Cache hit ⇒ trả object. Cache miss ⇒ gửi tới primary.
  • Primary trả mã lỗi bạn chọn làm tiêu chí failover – tổ hợp bất kỳ của 400, 403, 404, 416, 429, 500, 502, 503, 504 – hoặc không kết nối được (khi chọn 503) / timeout (khi chọn 504) ⇒ CloudFront gửi lại request đó tới secondary.
  • Mỗi request mới vẫn tới primary trước (không “dính” sang secondary).
  • Chỉ failover với GET, HEAD, OPTIONS; POST, PUT… không failover.
  • Mặc định CloudFront thử kết nối primary tối đa 30 giây (3 lần × 10 giây) rồi mới chuyển. Có thể giảm: connection timeout 1–10 s, connection attempts 1–3, origin response timeout 1–120 s (mặc định 30 s).
Mẹo thi (Exam Tip)
  • “Static website on S3 must be highly available across Regions” với CloudFront ⇒ origin group (primary S3 + secondary S3 ở Region khác, đồng bộ bằng CRR).
  • “Serve static and dynamic content from one domain” ⇒ một distribution, nhiều origin + nhiều cache behavior theo path pattern (vd /api/* → ALB, * → S3).
  • “Reduce load on the origin / improve cache hit ratio for global viewers” ⇒ tăng TTL, thu gọn cache key, bật Origin Shield.
  • Origin failover của CloudFront ở tầng HTTP (từng request); DNS failover của Route 53 ở tầng DNS (phụ thuộc TTL) – hai cơ chế khác nhau, có thể dùng cùng nhau.

Khóa origin: Origin Access Control (OAC), custom header, VPC origins

Dùng signed URL hay geo restriction ở CloudFront sẽ vô nghĩa nếu người dùng vòng qua CloudFront và gọi thẳng URL của S3 hoặc ALB. Vì vậy AWS khuyến nghị: bắt buộc người dùng truy cập qua CloudFront. Với S3 dùng Origin Access Control (OAC); với custom origin dùng custom header; với tài nguyên trong private subnet dùng VPC origins.

Bucket policy cho OAC

Cho phép service principal CloudFront đọc bucket, nhưng chỉ khi request thay mặt đúng distribution (điều kiện AWS:SourceArn) – ví dụ từ tài liệu:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontServicePrincipalReadOnly",
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::amzn-s3-demo-bucket/*",
    "Condition": { "StringEquals": {
      "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/EDFDVBD6EXAMPLE"
    } }
  }]
}
  • Cho phép upload qua CloudFront ⇒ thêm s3:PutObject (OAC hỗ trợ request động).
  • Object mã hóa SSE-KMS ⇒ thêm vào KMS key policy statement cho principal cloudfront.amazonaws.com với kms:Decrypt (và kms:Encrypt, kms:GenerateDataKey* nếu ghi), cùng điều kiện AWS:SourceArn.
  • Dùng OAC thì S3 Object Ownership phải là Bucket owner enforced (mặc định của bucket mới); cần ACL thì dùng Bucket owner preferred.
  • Signing behavior: Sign requests (recommended) = always; Do not sign requests = never (bucket phải public – dùng để tắt OAC hàng loạt); Do not override authorization header = no-override (chỉ ký khi viewer không gửi header Authorization).
  • Giữ S3 Block Public Access bật – bucket hoàn toàn private, chỉ CloudFront đọc được (đã học ở Bài 16).

Chuyển từ OAI sang OAC không gián đoạn

  1. Sửa bucket policy cho phép cả OAI và OAC (hai statement).
  2. Cập nhật origin của distribution sang OAC, chờ deploy xong tới mọi edge.
  3. Xóa statement OAI khỏi bucket policy.

Custom origin (ALB, EC2, server on-prem)

Custom origin phải truy cập được bằng HTTP/HTTPS chuẩn, nên tài liệu đề xuất:

  • Cấu hình origin custom header (vd X-Origin-Verify: <giá trị bí mật>) để CloudFront thêm vào mọi request tới origin; ứng dụng/ALB chỉ chấp nhận request có header đúng (với ALB: listener rule kiểm tra header, hoặc AWS WAF rule trên ALB).
  • Viewer protocol policy = HTTPS và origin protocol policy = Match viewer / HTTPS để header bí mật được mã hóa trên đường truyền; xoay vòng header định kỳ (thêm header mới ⇒ ứng dụng chấp nhận cả hai ⇒ bỏ header cũ).
  • Giới hạn Security Group của origin chỉ nhận traffic từ CloudFront managed prefix list com.amazonaws.global.cloudfront.origin-facing (IPv6: com.amazonaws.global.ipv6.cloudfront.origin-facing).

VPC origins – origin nằm hẳn trong private subnet

  • Dùng ALB, NLB hoặc EC2 trong private subnet làm origin; CloudFront kết nối qua ENI do dịch vụ quản lý trong subnet ⇒ CloudFront là điểm vào duy nhất, không cần ACL hay cơ chế tự chế để chặn truy cập trực tiếp.
  • VPC vẫn phải có internet gateway (chỉ để đánh dấu VPC nhận traffic internet, không dùng để định tuyến tới origin); subnet cần ít nhất 1 IPv4 trống.
  • Security Group của origin cho phép inbound từ managed prefix list hoặc từ security group dịch vụ CloudFront-VPCOrigins-Service-SG (chặt hơn – chỉ distribution của bạn).
  • Không hỗ trợ: Gateway Load Balancer, NLB có TLS listener, gRPC, Lambda@Edge origin request/response. Chia sẻ VPC origin cross-account qua AWS RAM.
Mẹo thi (Exam Tip)
  • “Users must not access S3 objects directly, only through CloudFront” ⇒ OAC + bucket policy cho cloudfront.amazonaws.com + AWS:SourceArn. Đáp án có OAI chỉ đúng khi không có OAC trong lựa chọn; OAC là bắt buộc nếu có SSE-KMS.
  • “Ensure the ALB only accepts traffic from CloudFront” ⇒ custom header bí mật (kiểm tra ở ALB rule / WAF) + Security Group dùng CloudFront managed prefix list; nếu được chọn kiến trúc mới ⇒ VPC origin (ALB internal).
  • “Least operational overhead to keep the origin private” ⇒ VPC origins thay vì tự dựng proxy/whitelist IP.

Cache behavior, cache key và TTL

Một cache behavior gom các thiết lập áp dụng cho một path pattern: origin đích, viewer protocol policy, allowed HTTP methods, cache policy, origin request policy, signed URL, nén, function association… Mỗi distribution có một default cache behavior với path pattern * (không đổi được) và luôn được xét sau cùng.

Path pattern – khớp đầu tiên thắng

  • Các behavior được so khớp theo thứ tự trong danh sách; khớp đầu tiên được áp dụng. Ví dụ thứ tự images/*.jpg → images/* → *.gif: request images/sample.gif khớp behavior thứ 2.
  • Ký tự đại diện: * = 0+ ký tự, ? = đúng 1 ký tự; path pattern phân biệt hoa thường, tối đa 255 ký tự; không xét query string/cookie.
  • Mỗi behavior trỏ tới một origin (hoặc origin group) ⇒ cần ít nhất số behavior bằng số origin muốn dùng.
  • Rủi ro bảo mật: nếu behavior đứng trước không yêu cầu signed URL còn behavior đứng sau có, file khớp cả hai sẽ bị truy cập không cần chữ ký.

Allowed HTTP methods

  • GET, HEAD · GET, HEAD, OPTIONS · GET, HEAD, OPTIONS, PUT, POST, PATCH, DELETE (cần cho form, API, upload, gRPC).
  • CloudFront chỉ cache response của GET, HEAD (và tùy chọn OPTIONS); các method khác luôn chuyển tới origin.
  • Bật đủ 7 method mà chỉ cần PUT ⇒ phải dùng OAC/bucket policy hoặc origin để chặn DELETE ngoài ý muốn.

Cache key, cache policy và origin request policy

Cache key là định danh duy nhất của mỗi object trong cache, quyết định một request có cache hit hay không. Mặc định gồm tên miền distribution + đường dẫn URL. Cache policy chỉ định thêm header, cookie, query string nào vào cache key, cùng các giá trị TTL và bật nén (Gzip/Brotli).

Cache key nhỏ

  • Ít biến thể ⇒ cache hit ratio cao ⇒ nhanh hơn, origin nhẹ hơn, rẻ hơn.
  • Managed policy CachingOptimized cho nội dung tĩnh/S3.
  • Dùng CloudFront Functions chuẩn hóa header/query string trước khi tạo cache key.

Cache key lớn

  • Thêm cookie/session ID, header User-Agent, mọi query string ⇒ mỗi người một bản ⇒ cache hit ratio thấp.
  • Chỉ thêm những giá trị thật sự làm nội dung khác đi.
  • Nội dung không cache (API) ⇒ managed policy CachingDisabled.

Origin request policy tách riêng: chọn header/cookie/query string được gửi tới origin nhưng không đưa vào cache key (vd origin cần biết CloudFront-Viewer-Country hay user-agent nhưng nội dung vẫn cache chung). Mọi giá trị trong cache key tự động được gửi tới origin.

TTL – object ở trong cache bao lâu?

Hết thời gian cache, request kế tiếp khiến CloudFront hỏi lại origin: origin trả 304 Not Modified nếu bản cache vẫn mới nhất, hoặc 200 OK kèm bản mới. Object ít được truy cập có thể bị evict sớm. Thời gian cache phụ thuộc Minimum / Default / Maximum TTL (trong cache policy) và header của origin:

max-age + s-maxageCloudFront dùng s-maxage (kẹp trong [Min, Max]); trình duyệt dùng max-age ⇒ cache ở edge lâu hơn ở trình duyệt.

  • Viewer gửi Cache-Control/Pragma trong GET không ép CloudFront quay về origin được – CloudFront bỏ qua.

  • Lỗi 4xx/5xx từ origin cũng được cache (error caching TTL, mặc định 10 giây); cấu hình được bằng custom error response (trang lỗi tùy biến, có thể lấy từ S3).

Xóa nội dung trước khi hết hạn: invalidation vs versioned file name

Invalidation

  • Xóa object khỏi cache POP và regional edge cache; request kế tiếp lấy bản mới từ origin.
  • 1.000 path đầu tiên mỗi tháng miễn phí (cộng dồn mọi distribution trong account), vượt thì tính phí theo path.
  • Path có wildcard (/images/*, /*) tính là 1 path dù xóa hàng nghìn file.
  • Không xóa được bản cache ở trình duyệt / proxy công ty.

Versioned file name (khuyến nghị khi cập nhật thường xuyên)

  • Đổi tên: app.v2.js, logo_2.png, cập nhật HTML trỏ tên mới.
  • Rẻ hơn (không trả phí invalidation), kiểm soát được cả cache trình duyệt.
  • Dễ roll forward / roll back, phân tích log theo tên file, phục vụ bản khác nhau cho người dùng khác nhau.
Mẹo thi (Exam Tip)
  • “Users still see the old version after updating files in S3” ⇒ create an invalidation (nhanh, một lần) hoặc dùng versioned object names (lâu dài, rẻ). Không phải “xóa distribution” hay “giảm TTL về 0 cho mọi thứ”.
  • “Low cache hit ratio” ⇒ bỏ bớt header/cookie/query string khỏi cache key, tăng TTL, gửi giá trị origin cần bằng origin request policy, bật Origin Shield.
  • “Serve stale content if the origin is down” ⇒ stale-if-error / TTL đủ dài + origin group.

Nội dung riêng tư: signed URL và signed cookie

Nội dung chỉ dành cho người dùng được phép (đã đăng nhập, đã trả tiền…) được bảo vệ bằng signed URL hoặc signed cookie. Ứng dụng của bạn xác thực người dùng rồi tạo URL/cookie được ký bằng private key; CloudFront dùng public key để kiểm tra chữ ký và thời hạn trước khi trả nội dung.

  1. (Khuyến nghị) Khóa origin để người dùng chỉ đi qua CloudFront – OAC cho S3, custom header cho custom origin.
  2. Tạo signer: trusted key group (khuyến nghị) chứa public key; gắn vào cache behavior qua Restrict viewer access = Yes.
  3. Ứng dụng kiểm tra quyền người dùng ⇒ trả về signed URL hoặc header Set-Cookie chứa signed cookie.
  4. CloudFront xác minh chữ ký (bị sửa ⇒ từ chối), kiểm tra policy (thời gian, IP) ⇒ trả object từ cache hoặc origin.

Signed URL

  • Hạn chế truy cập từng file riêng lẻ (vd file cài đặt ứng dụng, một bộ phim thuê).
  • Client không hỗ trợ cookie (custom HTTP client).
  • URL dài hơn, chứa tham số Expires/Policy, Signature, Key-Pair-Id.
  • Ưu tiên hơn cookie: request có signed URL thì CloudFront chỉ xét signed URL.

Signed cookie

  • Truy cập nhiều file bị hạn chế cùng lúc: mọi segment của video HLS, toàn bộ khu vực subscriber của website.
  • Không muốn đổi URL hiện có.
  • Không dùng được nếu URL gốc đã chứa tham số Expires, Policy, Signature, Key-Pair-Id, Hash-Algorithm (CloudFront tưởng là signed URL).

  • CloudFront signed URL/cookie: ký bằng key của trusted key group, đi qua edge cache, kiểm soát được thời gian bắt đầu, IP, wildcard. Đề nói “premium video to paying subscribers worldwide with low latency” ⇒ CloudFront signed cookie/URL + OAC.
  • Thêm query string vào URL sau khi ký ⇒ 403; query string phải nằm trong phần được ký.
Mẹo thi (Exam Tip)
  • “One downloadable file per customer, expires in 24 hours” ⇒ signed URL (canned policy đủ dùng).
  • “Members-only area with many files / HLS video, don’t change URLs” ⇒ signed cookies.
  • “Restrict access to users from the corporate IP range and only after a start date” ⇒ custom policy.
  • “Avoid using the root user to manage signing keys” ⇒ trusted key groups.

Geo restriction – chặn theo quốc gia

Geographic restriction (còn gọi geo blocking) ngăn người dùng ở một số vị trí truy cập nội dung của distribution – thường vì bản quyền phân phối hoặc yêu cầu pháp lý.

Tính năng geo restriction của CloudFront

  • Allow list (chỉ các nước được phép) hoặc Block list (cấm các nước).
  • Áp dụng cho toàn bộ distribution, mức quốc gia.
  • Bị chặn ⇒ HTTP 403 (Forbidden); có thể cấu hình trang lỗi tùy biến, cache lỗi (mặc định 10 giây).
  • Xác định vị trí bằng CSDL bên thứ ba, độ chính xác tổng thể 99,8%; không xác định được ⇒ vẫn phục vụ.

Dịch vụ geolocation bên thứ ba

  • Hạn chế một phần file của distribution, hoặc chi tiết hơn quốc gia (thành phố, mã bưu chính, tọa độ).
  • Ứng dụng tra IP người dùng ⇒ được phép thì tạo signed URL, không thì trả 403.
  • Khuyến nghị dùng S3 origin + OAC để không ai vòng qua.

Ví dụ trong tài liệu: chỉ có quyền phân phối ở Liechtenstein ⇒ allow list chỉ Liechtenstein; người dùng ở Monaco được DNS đưa tới edge ở Milan, edge thấy không được phép ⇒ trả 403. Trong standard log, request bị chặn có sc-status = 403 nhưng không phân biệt được bị chặn vì vị trí hay vì lý do khác.

Mẹo thi (Exam Tip)
  • “Prevent users in specific countries from accessing content distributed through CloudFront” ⇒ CloudFront geo restriction (block list/allow list) – ít vận hành nhất.
  • Phân biệt với Route 53 geolocation routing (Bài 24): Route 53 định tuyến người dùng tới endpoint khác nhau theo vị trí; CloudFront geo restriction chặn (403). Muốn chặn theo nước ở tầng ứng dụng với điều kiện phức tạp ⇒ AWS WAF geo match rule (bài Threat Protection).

AWS Global Accelerator

AWS Global Accelerator là dịch vụ global giúp tạo accelerator để cải thiện hiệu năng và availability cho ứng dụng có người dùng toàn cầu. Accelerator cấp static IP được quảng bá kiểu anycast từ mạng edge của AWS: traffic của người dùng vào mạng AWS tại edge location gần nhất, rồi đi trên AWS global network – được giám sát, không tắc nghẽn, dự phòng – tới endpoint tối ưu.

Standard accelerator vs custom routing accelerator

Standard accelerator

  • Định tuyến tới endpoint tối ưu dựa trên vị trí người dùng (geo-proximity), sức khỏe endpoint, weight, traffic dial.
  • Endpoint: ALB, NLB, EC2, Elastic IP ở 1 hoặc nhiều Region.
  • Có health check và failover tự động.
  • Use case: multi-Region, blue/green, A/B test, DR.

Custom routing accelerator

  • Ánh xạ tất định người dùng tới một EC2 + port cụ thể trong VPC subnet, theo logic ứng dụng của bạn.
  • Use case: VoIP (gán nhiều người gọi vào một media server), game multiplayer (ghép người chơi vào một game session).
  • Không health check, không failover; chỉ IPv4; luôn giữ client IP.

Cơ chế quan trọng

  • Kết thúc TCP tại edge: Global Accelerator terminate kết nối TCP của client ở edge location và gần như đồng thời mở kết nối TCP mới tới endpoint ⇒ response nhanh hơn, throughput cao hơn.
  • Health check: endpoint mới phải qua health check mới nhận traffic. Endpoint không khỏe ⇒ ngay lập tức chuyển kết nối mới sang endpoint khả dụng khác. Không còn endpoint khỏe nào ⇒ gửi tới tất cả endpoint. Health check cấu hình trong Global Accelerator (EC2/EIP) hoặc dùng health check của ALB/NLB.
  • Traffic dial (mỗi endpoint group): % traffic đã được hướng tới group đó mà group chấp nhận; ví dụ dial 50% cho us-east-1 ⇒ 100 request tới thì nhận 50, phần còn lại chuyển sang Region khác. Dùng cho performance test, nâng cấp stack, blue/green giữa các Region.
  • Endpoint weight (mỗi endpoint): giá trị 0–255, mặc định 128; tỉ lệ = weight / tổng weight trong group.
  • Client IP preservation: hỗ trợ cho ALB, EC2, NLB có security group; không hỗ trợ NLB không có security group và Elastic IP. Custom routing luôn giữ client IP.
  • Idle timeout cố định: 340 giây với TCP, 30 giây với UDP; kết nối đang mở vẫn tới endpoint cũ (kể cả unhealthy) cho tới khi idle timeout.
  • Bảo mật: che origin sau 2 static IP, được AWS Shield bảo vệ DDoS mặc định; kết nối tới ALB internal/EC2 private qua IP private trong VPC, không lộ ra internet. Security group và WAF rule cũ vẫn hoạt động.
  • Phản hồi ping (ICMP echo) tại edge – không đo được độ trễ thực tới endpoint bằng ping.

Tóm tắt ghi nhớ

Key takeaways
  • CloudFront = CDN: request ⇒ POP gần nhất (độ trễ) ⇒ regional edge cache ⇒ (Origin Shield) ⇒ origin. PUT/POST/… và request động bỏ qua regional edge cache. Data transfer từ AWS origin tới CloudFront miễn phí; price class giảm chi phí.
  • Distribution: nhiều origin + nhiều cache behavior theo path pattern (khớp đầu tiên thắng, default * cuối cùng). Chứng chỉ ACM cho viewer HTTPS phải ở us-east-1. Origin group failover theo mã HTTP, chỉ GET/HEAD/OPTIONS, mặc định 3 × 10 s.
  • OAC (thay OAI): service principal cloudfront.amazonaws.com + AWS:SourceArn; hỗ trợ SSE-KMS, PUT/DELETE, mọi Region; không dùng với S3 website endpoint. Custom origin ⇒ custom header + prefix list; private subnet ⇒ VPC origins.
  • Cache key nhỏ ⇒ cache hit ratio cao; cache policy (key + TTL) vs origin request policy (chỉ gửi tới origin). TTL mặc định: Min 0 · Default 86.400 s · Max 31.536.000 s; s-maxage cho CloudFront, max-age cho trình duyệt. Invalidation 1.000 path/tháng free, wildcard = 1 path; cập nhật thường xuyên ⇒ versioned file name.
  • Signed URL (một file, client không cookie) vs signed cookie (nhiều file, giữ URL); custom policy thêm thời điểm bắt đầu + IP + wildcard; dùng trusted key group (không cần root). Geo restriction: allow/block list theo quốc gia, cả distribution, trả 403.
  • CloudFront Functions: JS, viewer trigger, < 1 ms, triệu req/s, không mạng ⇒ header, redirect, rewrite, JWT, chuẩn hóa cache key. Lambda@Edge: Node.js/Python, 4 trigger, tới 30 s, có mạng/body/SDK.
  • Global Accelerator: 2 static anycast IP (2 network zone), listener TCP/UDP, endpoint group theo Region + traffic dial, endpoint weight 0–255 (mặc định 128), health check failover tức thì, client IP preservation (ALB, EC2, NLB có SG). Standard vs custom routing (VoIP/game, EC2 + port cụ thể). Không cache.

Thuật ngữ (Glossary)

Amazon CloudFront
Mạng phân phối nội dung (CDN) của AWS – cache và phân phối nội dung qua edge location.
Edge location / Point of Presence (POP)
Vị trí biên / Điểm hiện diện – nơi CloudFront cache nội dung gần người dùng.
Regional edge cache
Bộ đệm biên khu vực – tầng cache lớn giữa POP và origin.
Origin Shield
Lá chắn origin – tầng cache tập trung trước origin, gộp request, tăng cache hit ratio.
Distribution
Bản phân phối – cấu hình CloudFront: origin, cache behavior, tên miền, bảo mật.
Origin / Custom origin
Nguồn gốc nội dung / Origin tùy biến – nơi chứa bản gốc; custom origin là HTTP server (EC2, ALB, S3 website endpoint, on-prem).
Origin group (origin failover)
Nhóm origin – primary + secondary, chuyển khi primary trả mã lỗi đã chọn.
Alternate domain name (CNAME)
Tên miền thay thế – tên miền riêng thay cho *.cloudfront.net, cần chứng chỉ ACM ở us-east-1.
Origin Access Control (OAC)
Kiểm soát truy cập origin – CloudFront ký SigV4 khi gọi S3; bucket policy cho service principal CloudFront.
Origin Access Identity (OAI)
Danh tính truy cập origin (cũ) – cơ chế legacy, không hỗ trợ SSE-KMS, PUT/DELETE, Region mới.
VPC origin
Origin trong VPC – ALB/NLB/EC2 ở private subnet làm origin, CloudFront là điểm vào duy nhất.
Managed prefix list (CloudFront origin-facing)
Danh sách tiền tố IP do AWS quản lý – dải IP CloudFront dùng để gọi origin, dùng trong Security Group.
Cache behavior / Path pattern
Hành vi cache / Mẫu đường dẫn – bộ thiết lập áp dụng cho các URL khớp pattern; khớp đầu tiên thắng.
Cache key
Khóa cache – định danh object trong cache (URL + header/cookie/query string được chọn).
Cache hit ratio
Tỉ lệ trúng cache – phần trăm request được phục vụ từ edge.
Cache policy / Origin request policy
Chính sách cache / Chính sách request tới origin – quyết định cache key + TTL / giá trị chỉ gửi tới origin.
Minimum / Default / Maximum TTL
TTL tối thiểu / mặc định / tối đa – 0 / 86.400 / 31.536.000 giây mặc định.
Invalidation
Vô hiệu hóa cache – xóa object khỏi edge trước khi hết hạn; 1.000 path/tháng miễn phí.
Versioned file name
Tên file có phiên bản – đổi tên file khi cập nhật thay cho invalidation.
Signed URL / Signed cookie
URL có chữ ký / Cookie có chữ ký – cấp quyền truy cập nội dung riêng tư có thời hạn.
Canned policy / Custom policy
Chính sách dựng sẵn / tùy biến – chỉ thời hạn / thêm thời điểm bắt đầu, IP, wildcard.
Trusted key group
Nhóm khóa tin cậy – chứa public key để CloudFront xác minh chữ ký; không cần root user.
Geo restriction (geo blocking)
Giới hạn địa lý – allow/block list quốc gia cho cả distribution, trả 403.
Price class
Hạng giá – giới hạn tập edge location được dùng để giảm chi phí.
CloudFront Functions
Hàm siêu nhẹ tại biên – JavaScript, viewer request/response, dưới 1 ms.
Lambda@Edge
Hàm Lambda tại biên – Node.js/Python, 4 sự kiện, tới 30 s, có mạng.
Viewer request / Origin request / Origin response / Viewer response
Bốn sự kiện của CloudFront – điểm có thể gắn code trên đường đi request/response.
AWS Global Accelerator
Bộ tăng tốc toàn cầu – static anycast IP đưa traffic TCP/UDP vào backbone AWS.
Anycast IP
IP quảng bá từ nhiều vị trí – cùng một IP, client được đưa tới điểm gần nhất.
Standard / Custom routing accelerator
Bộ tăng tốc chuẩn / định tuyến tùy biến – tới endpoint tối ưu / tới EC2 + port cụ thể.
Listener / Endpoint group / Endpoint
Bộ lắng nghe / Nhóm điểm cuối theo Region / Điểm cuối – thành phần của accelerator.
Traffic dial
Núm điều chỉnh lưu lượng – % traffic một endpoint group chấp nhận.
Endpoint weight
Trọng số điểm cuối – 0–255, mặc định 128, chia traffic trong một group.
Network zone
Vùng mạng cô lập – mỗi static IP được phục vụ từ một zone riêng.
Client IP preservation
Giữ nguyên IP client – endpoint thấy IP gốc của người dùng.
BYOIP
Mang IP của bạn – dùng dải IPv4 riêng làm static IP của accelerator.
