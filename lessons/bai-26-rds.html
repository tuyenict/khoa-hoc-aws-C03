Sau bài này bạn sẽ

  • Giải thích Amazon RDS là gì, AWS lo phần nào và bạn lo phần nào; nhận diện 6 DB engine, các họ DB instance class và loại storage.
  • Phân biệt Multi-AZ DB instance (1 standby, đồng bộ, không phục vụ đọc, failover 60–120 s) với Multi-AZ DB cluster (writer + 2 reader, bán đồng bộ, đọc được, failover thường < 35 s).
  • Dùng read replica (bất đồng bộ, tối đa 15/primary, cùng hoặc khác Region, promote được) để scale đọc và làm DR; biết vì sao read replica không phải giải pháp high availability.
  • Nắm automated backup (retention 0–35 ngày, PITR, log 5 phút/lần), manual snapshot, storage autoscaling và giới hạn “không bao giờ thu nhỏ storage”.
  • Biết khi nào đặt RDS Proxy trước database (Lambda, nhiều kết nối ngắn, failover nhanh) và kết hợp với AWS Secrets Manager, IAM DB authentication.
  • Thiết kế encryption at rest bằng KMS – đặc biệt quy trình “mã hóa một DB đang chạy không mã hóa” mà đề rất hay hỏi.

Tổng quan: Amazon RDS là gì?

Theo tài liệu AWS, Amazon Relational Database Service (Amazon RDS) là web service giúp dựng, vận hành và mở rộng một CSDL quan hệ trên AWS Cloud dễ hơn. Nó cung cấp năng lực có thể thay đổi kích thước với chi phí hợp lý cho các CSDL chuẩn công nghiệp và tự quản lý các tác vụ quản trị CSDL thông thường. AWS khuyến nghị RDS là lựa chọn mặc định cho hầu hết workload CSDL quan hệ.

Các lợi ích tài liệu nêu: dùng DB engine quen thuộc; RDS lo backup, vá phần mềm, phát hiện lỗi và tự phục hồi; bật automated backup hoặc tự tạo snapshot; đạt high availability nhờ instance chính + instance phụ đồng bộ để failover; dùng read replica để scale đọc; kiểm soát truy cập bằng IAM và đặt DB trong VPC.

DB engine, instance class và storage

  • 6 DB engine của RDS: IBM Db2, MariaDB, Microsoft SQL Server, MySQL, Oracle Database, PostgreSQL. (Amazon Aurora có User Guide riêng – Bài 27.) Mỗi engine có tập tính năng khác nhau và hành vi điều khiển bởi DB parameter group.
  • DB instance class quyết định CPU và bộ nhớ: General purpose db.m* · Memory optimized db.z*, db.x*, db.r* · Compute optimized db.c* · Burstable db.t*. Ví dụ db.m7g.2xlarge = thế hệ 7, Graviton3, size 2xlarge. Đổi class (scale up/down) bất cứ lúc nào – scale dọc.
  • Storage dựa trên Amazon EBS (Bài 11): General Purpose SSD (gp2/gp3 – rẻ, đa dụng, dev/test và workload vừa) · Provisioned IOPS SSD (io1/io2 Block Express – I/O-intensive, độ trễ thấp và ổn định, khuyến nghị cho production) · Magnetic đã deprecated, không còn cho instance mới.
  • Thanh toán: On-Demand hoặc Reserved DB instances (cam kết 1/3 năm, giảm giá – đề hỏi “steady-state database running 24/7, reduce cost” ⇒ Reserved).

Multi-AZ deployment – tính sẵn sàng cao

Một Multi-AZ deployment là tùy chọn chạy DB trên nhiều Availability Zone: AWS tự tạo và duy trì một hoặc nhiều standby ở AZ khác và sao chép dữ liệu từ primary sang. Tài liệu chia làm hai kiểu: Multi-AZ DB instance deployment (1 standby) và Multi-AZ DB cluster deployment (2 standby đọc được).

Lợi ích tài liệu nêu: dư thừa dữ liệu và hỗ trợ failover; loại bỏ I/O freeze; giảm latency spike khi backup (backup lấy từ standby); và – chỉ với Multi-AZ DB cluster – phục vụ traffic đọc trên các instance phụ.

Kiểu 1 – Multi-AZ DB instance (một standby)

  • RDS tự tạo một standby replica ở AZ khác và sao chép synchronous replication – mỗi lần ghi được xác nhận khi đã ghi ở cả hai nơi ⇒ RPO gần bằng 0 khi một AZ hỏng.
  • Standby KHÔNG phục vụ đọc. Tài liệu nhấn mạnh: “The high availability option isn't a scaling solution for read-only scenarios”. Muốn đọc thêm ⇒ dùng read replica hoặc Multi-AZ DB cluster.
  • Đổi lại, write và commit latency có thể cao hơn Single-AZ do phải chờ sao chép đồng bộ; AWS khuyến nghị dùng Provisioned IOPS cho production.
  • MariaDB, MySQL, Oracle, PostgreSQL dùng công nghệ failover của Amazon; SQL Server dùng Database Mirroring (DBM) hoặc Always On Availability Groups.
  • Bật khi tạo DB, hoặc Modify một Single-AZ instance và chọn Multi-AZ – không cần tạo lại DB, không cần sửa ứng dụng vì endpoint giữ nguyên.

Failover diễn ra thế nào?

  1. RDS phát hiện sự cố trên primary (xem bảng nguyên nhân bên dưới) hoặc bạn chọn Reboot with failover.
  2. Standby được promote thành primary mới.
  3. RDS đổi bản ghi DNS (CNAME) của endpoint để trỏ sang instance mới. Ứng dụng phải kết nối lại – các kết nối cũ bị ngắt.
  4. RDS dựng lại standby mới ở AZ khác. Thời gian failover thường 60–120 giây; transaction lớn hoặc recovery dài có thể lâu hơn.

Kiểu 2 – Multi-AZ DB cluster (một writer + hai reader)

Theo tài liệu, Multi-AZ DB cluster là chế độ triển khai high availability bán đồng bộ (semisynchronous) với hai reader DB instance đọc được: 1 writer + 2 reader ở 3 AZ khác nhau trong cùng Region.

  • Semisynchronous replication: một thay đổi được commit khi có ít nhất một reader xác nhận đã nhận – không cần đợi mọi replica áp dụng xong ⇒ write latency thấp hơn Multi-AZ DB instance.
  • Reader vừa là đích failover tự động, vừa phục vụ đọc (qua reader endpoint). Khi writer gặp sự cố, RDS chọn reader có bản ghi thay đổi mới nhất.
  • Failover thường dưới 35 giây; hoàn tất khi cả hai reader đã áp dụng hết transaction còn tồn. Vì vậy replica lag (metric ReplicaLag) ảnh hưởng thời gian failover; RDS có flow control làm chậm ghi khi lag vượt ngưỡng (mặc định 120 s với MySQL).
  • Chỉ hỗ trợ RDS for MySQL và RDS for PostgreSQL (kiến thức phổ biến) trên các instance class có NVMe SSD cục bộ: db.c6gd, db.m5d, db.m6gd, db.r6gd, db.r8gd, db.x2iedn…
  • Backup là snapshot của cả cluster; retention 1–35 ngày; có thể restore cluster snapshot thành Single-AZ hoặc Multi-AZ DB instance.
  • Không phải Aurora – tài liệu cảnh báo “Multi-AZ DB clusters aren't the same as Aurora DB clusters”.

Read replica – mở rộng đọc và DR xuyên Region

Theo tài liệu, read replica là bản sao chỉ đọc của một DB instance. Bạn giảm tải cho primary bằng cách chuyển query đọc sang replica, nhờ đó scale out vượt giới hạn năng lực của một instance cho workload đọc nhiều.

Cách hoạt động

  1. Bạn chỉ định DB instance nguồn. RDS chụp snapshot của nguồn (nguồn Single-AZ bị I/O suspension khoảng 1 giây; nguồn Multi-AZ thì snapshot lấy từ standby nên không bị).
  2. RDS tạo instance chỉ đọc từ snapshot, rồi dùng cơ chế sao chép bất đồng bộ (asynchronous replication) gốc của engine để cập nhật mỗi khi primary thay đổi.
  3. Replica có endpoint DNS riêng; ứng dụng phải tự chỉ định endpoint replica cho query đọc (RDS không tự chia tải đọc/ghi).
  4. Do bất đồng bộ nên replica có thể trễ (replica lag) – đọc từ replica là eventually consistent.

Các quy tắc quan trọng (theo tài liệu)

  • Bắt buộc bật automated backup trên nguồn (backup retention ≠ 0) – kể cả khi replica làm nguồn cho replica khác.
  • Tối đa 15 read replica / primary (quota “Read replicas per primary”). Với RDS for Oracle AWS khuyên giữ ≤ 5 để giảm lag.
  • Replica của replica: được với MariaDB, MySQL và một số phiên bản PostgreSQL; không được với Db2, Oracle, SQL Server. Không hỗ trợ circular replication.
  • Không có auto scaling cho read replica – phải tự thêm/xóa (khác Aurora Replicas ở Bài 27).
  • Replica tính tiền như một DB instance bình thường. Không tính phí data transfer sao chép giữa nguồn và replica trong cùng Region; cross-Region thì có phí truyền dữ liệu.
  • Replica có thể dùng instance class / storage type khác nguồn (AWS khuyên bằng hoặc lớn hơn), và bản thân replica có thể bật Multi-AZ (độc lập với nguồn).
  • Writable: chỉ MySQL/MariaDB cho phép bật replica ghi được; PostgreSQL, Oracle, SQL Server, Db2 là bản sao vật lý, không ghi được trừ khi promote.
  • Oracle (mounted) và Db2 (standby) có chế độ replica không nhận kết nối – dùng cho DR cross-Region.
  • Xóa nguồn mà không xóa replica cùng Region ⇒ mỗi replica được promote thành standalone.

Promote read replica

Bạn có thể promote một read replica thành DB instance độc lập (đọc + ghi). Sau khi promote, quan hệ sao chép bị cắt vĩnh viễn – instance mới có dữ liệu tới thời điểm yêu cầu promote. Ứng dụng: disaster recovery khi primary/Region hỏng, tách DB để làm việc khác (vd chạy DDL dài trên bản sao rồi chuyển sang). Đây là thao tác thủ công – không phải failover tự động như Multi-AZ.

Cross-Region read replica

Tài liệu nêu ba mục đích: cải thiện disaster recovery, scale đọc tới Region gần người dùng, và di chuyển giữa các Region dễ hơn. Lưu ý:

  • Lag thường cao hơn do đường truyền giữa Region dài.
  • RDS chỉ đảm bảo tối đa 5 cross-Region read replica cho một nguồn (giới hạn ACL của VPC nguồn).
  • Muốn replica mã hóa ở Region khác ⇒ nguồn phải mã hóa, và chỉ định KMS key của Region đích (KMS key gắn với Region).
  • Mẹo giảm chi phí (MySQL/MariaDB): tạo 1 replica sang Region đích, rồi tạo các replica còn lại từ replica đó – chỉ trả phí truyền dữ liệu liên Region một lần.
  • Xóa nguồn của cross-Region replica: MySQL, MariaDB, Oracle, SQL Server, Db2 ⇒ replica được promote; PostgreSQL ⇒ replica chuyển trạng thái terminated, phải tự promote hoặc xóa.

Multi-AZ vs Read replica – bảng đề thi hay hỏi

Multi-AZ (DB instance)

  • Mục đích: high availability, failover tự động.
  • Sao chép đồng bộ; luôn khác AZ, cùng Region.
  • Standby không đọc được.
  • Failover tự động, endpoint giữ nguyên (DNS đổi).
  • Bật/tắt bằng Modify; engine upgrade áp dụng cho cả hai.

Read replica

  • Mục đích: scale đọc, báo cáo/analytics, DR.
  • Sao chép bất đồng bộ; cùng AZ, khác AZ hoặc khác Region.
  • Đọc được qua endpoint riêng; tối đa 15.
  • Không tự failover – promote thủ công.
  • Yêu cầu bật automated backup trên nguồn.
Mẹo thi (Exam Tip)
  • “Read-heavy workload”, “reporting queries slow down the production database”, “offload read traffic” ⇒ read replica (nếu đọc lặp lại cùng dữ liệu và cần độ trễ micro-giây ⇒ cân nhắc ElastiCache – Bài 29).
  • “Disaster recovery in another Region with RPO of minutes and read access in that Region” ⇒ cross-Region read replica (promote khi cần).
  • “RPO of seconds/near zero, RTO < 1 minute, cross-Region” thường là dấu hiệu của Aurora Global Database (Bài 27), không phải RDS replica.
  • Đáp án “dùng read replica để đạt high availability / automatic failover” ⇒ sai với RDS (read replica không tự failover).

Automated backup, snapshot và point-in-time recovery

RDS có hai cơ chế sao lưu: automated backup (RDS tự làm trong backup window, cho phép khôi phục về bất kỳ thời điểm nào trong retention period) và manual DB snapshot (bạn chủ động tạo, giữ tới khi tự xóa). Cả hai là storage volume snapshot của toàn bộ DB instance (không phải từng database), lưu trong Amazon S3.

Automated backup

  • RDS tạo snapshot hằng ngày trong backup window bạn chọn (hoặc RDS chọn) và upload transaction log lên S3 mỗi 5 phút ⇒ thời điểm khôi phục mới nhất (LatestRestorableTime) thường chỉ cách hiện tại vài phút.
  • Backup retention period: 0–35 ngày cho DB instance (0 = tắt automated backup); 1–35 ngày cho Multi-AZ DB cluster. Mặc định 7 ngày khi tạo bằng console, 1 ngày khi tạo bằng CLI/API.
  • Đổi retention từ 0 sang khác 0 (hoặc ngược lại) gây outage.
  • Snapshot đầu tiên là full, các lần sau incremental (chỉ phần thay đổi).
  • Backup chỉ chạy khi instance ở trạng thái available (vd không chạy khi storage_full); thời gian ở trạng thái stopped không tính vào retention.
  • Single-AZ có thể bị I/O suspension ngắn khi bắt đầu snapshot; Multi-AZ thì backup lấy từ standby nên tránh được latency spike.
  • Miễn phí backup storage bằng 100% tổng storage đã cấp phát trong Region; vượt mới tính phí.

Point-in-time recovery (PITR)

Bạn có thể khôi phục về bất kỳ giây nào từ earliest restorable time tới latest restorable time. Điểm cực kỳ quan trọng: restore luôn tạo DB instance MỚI (với endpoint mới) – instance nguồn không bị thay đổi. Instance mới dùng default parameter group / option group (đổi sau), và không thể giảm storage khi restore. Sau khi khôi phục, volume tiếp tục nạp block từ S3 ở nền nên hiệu năng có thể chưa tối đa ngay.

Manual DB snapshot

  • Do bạn tạo, không hết hạn; không bị xóa khi xóa DB instance. Quota: 100 manual snapshot / Region (adjustable; quota này không áp cho automated backup; backup do AWS Backup quản lý cũng không tính vào).
  • Khi xóa DB instance: nên tạo final snapshot; nếu không chọn Retain automated backups thì automated backup bị xóa theo instance.
  • Copy snapshot (automated hoặc manual) – kể cả sang Region khác (DR) và đổi KMS key khi copy; share manual snapshot cho account khác (snapshot mã hóa bằng AWS managed key thì không share được – phải dùng customer managed key).
  • Muốn lưu rất lâu ⇒ export snapshot sang S3 (định dạng Apache Parquet – kiến thức phổ biến) hoặc dùng AWS Backup với retention dài (Bài 19).

Storage auto scaling và các cách mở rộng RDS

Với workload khó dự đoán (ví dụ tài liệu: game mobile mới tăng người dùng rất nhanh), bật storage autoscaling để RDS tự tăng dung lượng khi sắp hết chỗ, không cần thao tác thủ công, không cần reboot, không downtime.

Khi nào RDS tự tăng storage? (cả 3 điều kiện)

  1. Dung lượng trống ≤ 10% storage đã cấp phát.
  2. Tình trạng thiếu chỗ kéo dài ít nhất 5 phút.
  3. Đợt storage modification trước đã tối ưu xong và có ít hơn 4 lần sửa storage trong 24 giờ qua.

Mỗi lần tăng thêm giá trị lớn nhất trong: 10 GiB · 10% storage hiện tại · mức tăng dự đoán cho 7 giờ tới (dựa trên metric FreeStorageSpace 1 giờ qua). Bạn đặt maximum storage threshold (tham số MaxAllocatedStorage) – phải lớn hơn storage hiện tại ít nhất 10% (khuyên ≥ 26% để tránh cảnh báo sắp chạm ngưỡng).

Bẫy thường gặp
  • RDS không bao giờ tự giảm storage, và bạn cũng không thể giảm allocated storage bằng Modify. Muốn nhỏ lại ⇒ tạo instance mới nhỏ hơn rồi migrate dữ liệu, hoặc dùng Blue/Green Deployment.
  • Autoscaling không ngăn hoàn toàn storage-full khi nạp dữ liệu cực lớn (giới hạn 4 lần/24 giờ) – vẫn nên cấp phát ban đầu hợp lý.
  • Tăng storage thủ công (hoặc khi restore) phải tăng ít nhất 10%; không dùng autoscaling với magnetic storage.

Amazon RDS Proxy

Theo tài liệu, Amazon RDS Proxy cho phép ứng dụng gom và chia sẻ kết nối DB (connection pooling) để scale tốt hơn; giúp ứng dụng chịu lỗi tốt hơn khi DB failover (tự kết nối tới standby mà vẫn giữ kết nối của ứng dụng); và cho phép ép xác thực IAM với client, trong khi proxy kết nối tới DB bằng IAM DB authentication hoặc thông tin lưu trong AWS Secrets Manager.

Vì sao cần proxy?

Mỗi kết nối DB tốn bộ nhớ và CPU (TLS handshake, xác thực, khởi tạo phiên…). Số kết nối tối đa phụ thuộc bộ nhớ của instance class – ví dụ MySQL trên db.t3.micro chỉ khoảng 60 kết nối mặc định. Ứng dụng mở/đóng kết nối liên tục (đặc biệt AWS Lambda: mỗi execution environment mở kết nối riêng, scale lên hàng trăm/hàng nghìn bản) dễ gây lỗi too many connections, hết RAM, DB quá tải.

  • Connection pooling: proxy giữ sẵn một pool kết nối tới DB và tái sử dụng ⇒ tránh overhead mở kết nối mới.
  • Multiplexing: tái sử dụng kết nối sau mỗi transaction – nhiều kết nối client dùng chung ít kết nối DB hơn.
  • Pinning: khi proxy không chắc tái sử dụng an toàn (vd thay đổi biến phiên, câu lệnh > 16 KB), nó giữ phiên trên một kết nối cố định tới hết phiên – giảm hiệu quả pooling.
  • Queue / throttle: kết nối chưa phục vụ được thì xếp hàng; vượt giới hạn bạn đặt thì từ chối (shed load) ⇒ DB không bị quá tải đột ngột.
  • Failover: proxy giữ cùng IP/endpoint, tự chuyển kết nối sang primary mới; client không bị ảnh hưởng bởi DNS propagation, DNS cache cục bộ, connection timeout. Chỉ các kết nối đang giữa transaction bị hủy. Với Multi-AZ DB cluster, proxy giúp giảm downtime khi minor version upgrade xuống ≤ 1 giây.
  • Serverless, high availability: hạ tầng proxy trải trên nhiều AZ, tự scale theo workload, tách biệt tài nguyên khỏi DB.
  • Hầu hết ứng dụng không cần sửa code – chỉ đổi endpoint sang endpoint của proxy.

Giới hạn & lưu ý (theo tài liệu)

  • Tối đa 20 proxy / account / Region (adjustable); mỗi proxy tối đa 200 secret Secrets Manager (≈ 200 user DB khác nhau); tối đa 20 endpoint bổ sung / proxy.
  • Proxy phải ở cùng VPC với DB và không thể publicly accessible (kể cả khi DB public). Không dùng được với VPC tenancy dedicated.
  • Với RDS DB instance có replication: proxy chỉ gắn với writer, không gắn vào read replica. Mỗi proxy gắn một DB instance đích; một DB có thể có nhiều proxy.
  • Engine: RDS for MySQL, MariaDB, PostgreSQL, SQL Server (và Aurora); proxy MySQL/MariaDB lắng nghe port 3306, PostgreSQL port 5432. Không dùng cho DB tự cài trên EC2.
  • TLS: proxy hỗ trợ TLS 1.0–1.3, dùng chứng chỉ ACM; có thể bật Require Transport Layer Security.
  • Hai kiểu IAM: Standard IAM auth (client → proxy bằng IAM, proxy → DB bằng secret) và End-to-end IAM auth (IAM tới tận DB, không cần secret).
Mẹo thi (Exam Tip)
  • “AWS Lambda functions connect to Amazon RDS; during traffic spikes the database runs out of connections / 'too many connections' errors” ⇒ RDS Proxy.
  • “Reduce application failover time” / “application should not depend on DNS propagation during failover” ⇒ RDS Proxy.
  • “Enforce IAM authentication for database access without changing the database's native password authentication” ⇒ RDS Proxy + Secrets Manager (standard IAM auth).
  • Tăng max_connections hay scale up instance chỉ là chữa triệu chứng, tốn tiền hơn và vẫn tốn RAM cho mỗi kết nối.

Bảo mật: mạng, xác thực, mã hóa

Bảo mật RDS gồm bốn lớp: mạng (VPC, private subnet, Security Group), xác thực (mật khẩu DB, Secrets Manager, IAM DB authentication, Kerberos), mã hóa khi truyền (SSL/TLS) và encryption at rest (AWS KMS). Quyền quản trị RDS (tạo, xóa, modify instance) do IAM policy kiểm soát; quyền trong database (SELECT, INSERT…) do engine kiểm soát.

IAM database authentication

  • Hỗ trợ MariaDB, MySQL, PostgreSQL. Thay vì mật khẩu, client dùng authentication token sinh bằng AWS Signature Version 4 (generate-db-auth-token).
  • Mỗi token có thời hạn 15 phút; chỉ dùng để xác thực lúc kết nối, không ảnh hưởng phiên đã thiết lập.
  • Lợi ích: traffic bắt buộc mã hóa SSL/TLS; quản lý truy cập tập trung bằng IAM; ứng dụng trên EC2 dùng instance profile (IAM role) thay vì lưu mật khẩu. IAM policy cần action rds-db:connect.
  • Lưu ý: cần thêm 300–1000 MiB bộ nhớ trên DB; không dùng custom Route 53 DNS để sinh token; CloudTrail/CloudWatch không log việc sinh token. Kết nối tần suất rất cao ⇒ cân nhắc RDS Proxy.

Quản lý mật khẩu master bằng Secrets Manager

  • Chọn Manage master credentials in AWS Secrets Manager khi tạo/modify: RDS tự sinh mật khẩu, lưu vào Secrets Manager và tự xoay vòng mỗi 7 ngày (mặc định, đổi được) – không cần sửa ứng dụng.
  • Secret được mã hóa bằng KMS key của Secrets Manager hoặc customer managed key (có thể tách khỏi key mã hóa DB). Truy cập secret kiểm soát bằng IAM, audit bằng CloudTrail.
  • Có thể ép bằng IAM condition key rds:ManageMasterUserPassword. Hạn chế: không hỗ trợ khi tạo read replica từ nguồn dùng tính năng này (trừ SQL Server, Db2), Blue/Green Deployments, RDS Custom.

Secrets Manager

  • Vẫn là mật khẩu DB, nhưng không hard-code.
  • Tự rotate (RDS-managed: 7 ngày).
  • Mọi engine.
  • Đề: “rotate database credentials automatically”.

IAM DB authentication

  • Không mật khẩu, token 15 phút.
  • Dùng IAM role của EC2/Lambda.
  • MariaDB, MySQL, PostgreSQL.
  • Đề: “no passwords stored, use IAM roles to connect”.

Encryption at rest với AWS KMS

  • Khi bật, RDS mã hóa AES-256: storage của instance, log, automated backup, read replica, snapshot. Giải mã trong suốt, ảnh hưởng hiệu năng tối thiểu, không cần sửa ứng dụng.
  • Chọn AWS managed key (aws/rds, mỗi Region một key) hoặc customer managed key. Sau khi tạo không đổi được KMS key của instance.
  • Oracle / SQL Server còn hỗ trợ Transparent Data Encryption (TDE), dùng được cùng RDS encryption.
  • Disable KMS key ⇒ DB mất quyền truy cập key, chuyển trạng thái inaccessible-encryption-credentials-recoverable (7 ngày để bật lại key), quá hạn thì không dùng được nữa.
Các giới hạn mã hóa đề rất hay bẫy
  • Chỉ bật mã hóa được khi tạo DB instance – không bật trên instance đang chạy; cũng không tắt được mã hóa.
  • Không tạo được snapshot mã hóa trực tiếp từ instance không mã hóa; không restore backup/snapshot không mã hóa thành instance mã hóa (trực tiếp).
  • Không có replica mã hóa của nguồn không mã hóa (và ngược lại).
  • Copy snapshot mã hóa sang Region khác ⇒ chỉ định KMS key ở Region đích.
  • Snapshot mã hóa bằng AWS managed key không share được cho account khác ⇒ dùng customer managed key và cấp quyền key cho account đích.

Quy trình mã hóa một DB đang chạy không mã hóa

Mã hóa khi truyền (in transit)

Client kết nối bằng SSL/TLS tới endpoint RDS (có thể ép bằng tham số như rds.force_ssl cho PostgreSQL/SQL Server hoặc require_secure_transport cho MySQL – kiến thức phổ biến). Dữ liệu sao chép giữa nguồn và read replica luôn được mã hóa, kể cả cross-Region, dù instance có mã hóa at rest hay không.

Mẹo thi (Exam Tip)
  • “An existing unencrypted RDS DB instance must be encrypted” ⇒ snapshot → copy snapshot with encryption → restore. Đáp án “Modify the DB instance and enable encryption” là sai.
  • “Application on EC2 must connect to RDS MySQL without storing credentials” ⇒ IAM database authentication + IAM role của EC2.
  • “Rotate the database password automatically every 30 days” ⇒ AWS Secrets Manager (RDS-managed secret hoặc rotation Lambda), không phải Systems Manager Parameter Store (không tự rotate).
  • “Only the application tier can reach the database” ⇒ DB trong private subnet, Security Group của DB chỉ cho phép inbound từ SG của app tier.

Tóm tắt ghi nhớ

Key takeaways
  • RDS = CSDL quan hệ managed cho Db2, MariaDB, SQL Server, MySQL, Oracle, PostgreSQL. AWS lo OS, patch, backup, HA, scaling; bạn lo query tuning, schema, Security Group, cấu hình. Không có quyền OS (cần thì EC2 / RDS Custom).
  • Multi-AZ DB instance: 1 standby, synchronous, không đọc được, failover tự động 60–120 s bằng đổi DNS; endpoint giữ nguyên. Multi-AZ DB cluster: writer + 2 reader / 3 AZ, semisynchronous, reader đọc được, failover < 35 s, MySQL/PostgreSQL.
  • Read replica: asynchronous, tối đa 15, cùng/khác AZ/Region, endpoint riêng, cần automated backup bật, không auto scaling, promote thủ công cho DR. Cùng Region không phí transfer; cross-Region có phí, KMS key ở Region đích.
  • Automated backup: retention 0–35 ngày (console 7, CLI 1), log lên S3 mỗi 5 phút, PITR tạo instance mới. Manual snapshot: giữ tới khi xóa, còn lại sau khi xóa DB, copy/share được, 100/Region.
  • Storage autoscaling: free ≤ 10%, ≥ 5 phút, < 4 lần/24 h; tăng max(10 GiB, 10%, dự đoán 7 h) tới maximum storage threshold. Không bao giờ giảm storage.
  • RDS Proxy: connection pooling + multiplexing serverless, failover nhanh không phụ thuộc DNS, IAM auth + Secrets Manager; cùng VPC, không public, chỉ gắn writer – đáp án chuẩn cho Lambda + RDS.
  • Bảo mật: IAM DB auth (MariaDB/MySQL/PostgreSQL, token 15 phút, SSL); Secrets Manager rotate master password (mặc định 7 ngày); encryption at rest chỉ bật khi tạo ⇒ DB đang chạy: snapshot → copy có mã hóa → restore.

A company runs its production order-processing application on an Amazon RDS for MySQL Single-AZ DB instance. The company requires the database to remain available with automatic failover if an Availability Zone becomes unavailable. The solution must require the LEAST operational overhead and no application code changes. What should a solutions architect do?
  1. Create a read replica in another Availability Zone and configure a Lambda function to promote it when the primary fails.
  2. Modify the DB instance to be a Multi-AZ DB instance deployment.
  3. Take hourly manual snapshots and restore the latest snapshot in another Availability Zone during an outage.
  4. Migrate the database to MySQL installed on two Amazon EC2 instances in different Availability Zones with native replication.
Đáp án B. Multi-AZ tạo standby đồng bộ ở AZ khác và tự failover bằng cách đổi DNS của endpoint – ứng dụng giữ nguyên endpoint, chỉ cần Modify instance. A sai: read replica bất đồng bộ (có thể mất dữ liệu), promote là thủ công/tự viết script, endpoint thay đổi ⇒ nhiều công vận hành. C sai: restore snapshot mất nhiều thời gian và mất tới 1 giờ dữ liệu, không phải failover tự động. D sai: tự quản lý DB trên EC2 tăng gánh nặng vận hành.

Giải pháp phải có LEAST operational overhead (ít công vận hành nhất) và không thay đổi mã nguồn ứng dụng. Solutions architect nên làm gì?

A company runs a write-intensive OLTP application on Amazon RDS for PostgreSQL. The company needs high availability across three Availability Zones, failover that typically completes in under 35 seconds, lower write latency than a Multi-AZ DB instance deployment, and the ability to serve read traffic from the standby instances. Which deployment option should the company choose?
  1. A Multi-AZ DB cluster deployment.
  2. A Multi-AZ DB instance deployment with two read replicas.
  3. A Single-AZ DB instance with automated backups and storage autoscaling.
  4. A Single-AZ DB instance with a cross-Region read replica.
Đáp án A. Multi-AZ DB cluster: 1 writer + 2 reader ở 3 AZ, sao chép semisynchronous (write latency thấp hơn Multi-AZ DB instance), reader đọc được và failover thường < 35 giây. B sai: failover thường 60–120 giây, write latency cao hơn, standby không đọc được (chỉ replica đọc). C sai: không có HA. D sai: không failover tự động, replica ở Region khác.
Một công ty chạy ứng dụng OLTP ghi nhiều trên Amazon RDS for PostgreSQL. Công ty cần high availability trên ba Availability Zone, failover thường hoàn tất dưới 35 giây, độ trễ ghi thấp hơn triển khai Multi-AZ DB instance, và khả năng phục vụ lưu lượng đọc từ các standby instance. Công ty nên chọn phương án triển khai nào?

  • Triển khai Multi-AZ DB instance kèm hai read replica.Sai: failover thường 60–120 giây, độ trễ ghi cao hơn và standby không phục vụ đọc.
  • Một Single-AZ DB instance với automated backup và storage autoscaling.Sai: Single-AZ không có high availability hay failover tự động.
  • Một Single-AZ DB instance với một cross-Region read replica.Sai: không có failover tự động và replica nằm ở Region khác, không đáp ứng HA trên 3 AZ.
A Java application connects to an Amazon RDS for MySQL Multi-AZ DB instance. During a recent Multi-AZ failover, the database became available in about 2 minutes, but the application kept failing for much longer because it continued to use cached DNS results and had to re-establish thousands of connections. The company wants to minimize application downtime during future failovers without major code changes. What should a solutions architect do?
  1. Increase the DB instance class to reduce failover time.
  2. Place an Amazon RDS Proxy in front of the DB instance and change the application to connect to the proxy endpoint.
  3. Create a read replica and configure the application to retry writes against the read replica.
  4. Create an Amazon Route 53 failover routing policy that points to the primary and standby IP addresses.
Đáp án B. Khi failover, RDS Proxy giữ nguyên endpoint/IP, tự chuyển kết nối sang primary mới, giữ các kết nối nhàn rỗi của ứng dụng ⇒ client không bị ảnh hưởng bởi DNS propagation hay DNS cache cục bộ; chỉ cần đổi endpoint. (Đặt JVM DNS TTL ≤ 60 s cũng giúp, nhưng không có trong lựa chọn.) A sai: class lớn hơn không sửa vấn đề cache DNS. C sai: read replica mặc định chỉ đọc, không nhận ghi; và replica bất đồng bộ nên có thể thiếu dữ liệu mới nhất. D sai: standby không có IP cố định để trỏ, không nhận kết nối, và RDS đã tự đổi DNS – thêm Route 53 không giải quyết cache ở client.
Một ứng dụng Java kết nối tới một Amazon RDS for MySQL Multi-AZ DB instance. Trong lần Multi-AZ failover gần đây, cơ sở dữ liệu sẵn sàng trở lại sau khoảng 2 phút, nhưng ứng dụng tiếp tục lỗi lâu hơn nhiều vì vẫn dùng kết quả DNS đã cache và phải thiết lập lại hàng nghìn kết nối. Công ty muốn giảm thiểu thời gian ngừng của ứng dụng trong các lần failover sau mà không thay đổi lớn về mã nguồn. Solutions architect nên làm gì?
  • Tăng DB instance class để giảm thời gian failover.Sai: instance class lớn hơn không giải quyết vấn đề DNS bị cache và việc tạo lại kết nối ở client.
  • Đặt một Amazon RDS Proxy trước DB instance và đổi ứng dụng sang kết nối tới endpoint của proxy.Đúng: RDS Proxy giữ nguyên endpoint, tự chuyển kết nối sang primary mới và giữ kết nối của ứng dụng ⇒ không bị ảnh hưởng bởi DNS cache; chỉ cần đổi endpoint.
