  • Dùng EventBridge Scheduler (one-time, cron, rate, time zone, flexible time window) thay cho scheduled rule (legacy) và cron trên EC2; biết vai trò của schema registry (schema discovery, code bindings).
  • Thiết kế state machine bằng Amazon States Language: các loại state (Task, Choice, Parallel, Map, Wait…), Retry / Catch, ba integration pattern (Request Response, .sync, .waitForTaskToken).
  • Chọn đúng Standard workflow (tới 1 năm, exactly-once, lịch sử 90 ngày) hay Express workflow (tối đa 5 phút, at-least-once / at-most-once, 100.000 execution/giây).

Kiến trúc hướng sự kiện: choreography và orchestration

Theo tài liệu EventBridge, event-driven architecture là cách xây dựng các hệ thống phần mềm loosely coupled làm việc cùng nhau bằng cách phát ra và phản ứng với các event. Kiến trúc này giúp tăng tính linh hoạt (agility) và xây dựng ứng dụng tin cậy, dễ scale.

Khi một nghiệp vụ gồm nhiều bước (đặt hàng → thanh toán → kho → giao hàng), có hai cách phối hợp các microservice:

Choreography (biên đạo)

  • Không có “nhạc trưởng”: mỗi service phát event khi việc của nó xong, các service khác tự đăng ký phản ứng.
  • Ghép lỏng tối đa – thêm consumer mới không cần sửa producer.
  • Khó nhìn toàn cảnh luồng, khó biết “đơn hàng đang ở bước nào”.
  • Công cụ: Amazon EventBridge (event bus), SNS (Bài 30).

Orchestration (điều phối)

  • Một state machine trung tâm gọi từng bước theo thứ tự, quyết định nhánh, retry, bù trừ khi lỗi.
  • Nhìn thấy trực quan từng execution, từng bước thành công/thất bại.
  • Phù hợp quy trình có thứ tự, có điều kiện, chờ người duyệt, chạy lâu.
  • Công cụ: AWS Step Functions.

Amazon EventBridge: event bus, rule và target

Amazon EventBridge là dịch vụ serverless dùng event để kết nối các thành phần ứng dụng, giúp xây dựng ứng dụng event-driven có khả năng scale. EventBridge cung cấp cách đơn giản, nhất quán để ingest, filter, transform và deliver event. Có hai cách xử lý event: event bus (nhiều nguồn → nhiều đích) và pipe (một nguồn → một đích).

Event, event bus, rule, target

  • Event: bản ghi JSON mô tả một thay đổi, có các trường source (vd aws.ec2), detail-type (vd EC2 Instance State-change Notification), account, region, time và detail (nội dung riêng).
  • Event bus: “router” nhận event và giao tới 0 hoặc nhiều target. Ba loại hay gặp:
    • Default event bus: có sẵn trong mỗi account, tự động nhận event từ các dịch vụ AWS (EC2 đổi trạng thái, S3, CodePipeline, Health…).
    • Custom event bus: bus bạn tạo cho event của ứng dụng riêng (gửi bằng PutEvents), thường tách theo domain/team.
    • Partner event bus: nhận event từ nhà cung cấp SaaS đối tác (vd Zendesk, Datadog, Shopify – kiến thức phổ biến) qua partner event source, không cần tự viết webhook.
  • Rule: gắn với một event bus, đánh giá event khi tới. Nếu event khớp event pattern của rule, EventBridge gửi event tới các target của rule (có thể transform trước khi gửi). Một event có thể khớp nhiều rule; mỗi rule có tối đa 5 target, các target chạy song song. Event không khớp rule nào ⇒ EventBridge bỏ qua.
  • Hai loại rule: rule khớp event pattern và rule chạy theo lịch (scheduled rule – nay là legacy, AWS khuyên dùng EventBridge Scheduler). Ngoài ra có managed rule do dịch vụ AWS tự tạo trong account (chỉ xóa bằng Force delete, xóa sẽ làm tính năng của dịch vụ đó ngừng chạy).

Ví dụ event pattern (theo tài liệu)

Rule trên default event bus bắt sự kiện EC2 instance chuyển sang trạng thái running rồi gọi một Lambda function:

{
  "source": ["aws.ec2"],
  "detail-type": ["EC2 Instance State-change Notification"],
  "detail": {
    "state": ["running"]
  }
}

Mỗi khi EC2 đổi trạng thái, EC2 (event source) tự gửi event vào default bus; EventBridge đối chiếu với rule, khớp thì gọi Lambda. Event pattern hỗ trợ khớp prefix, số, exists, anything-but, wildcard… (tối đa 30 rule chứa wildcard mỗi bus).

Target, retry và dead-letter queue

  • Target phổ biến: Lambda, Step Functions state machine, SQS, SNS, Kinesis Data Streams / Firehose, ECS task, CodePipeline, Systems Manager, một event bus khác (cùng/khác account hoặc Region), API destination (HTTPS endpoint bên ngoài).
  • Input transformer: đổi hình dạng event trước khi gửi tới target (chỉ lấy vài trường, ghép chuỗi…).
  • Retry policy: khi giao lỗi do lỗi có thể retry (target không sẵn sàng, mạng), EventBridge mặc định retry trong 24 giờ và tối đa 185 lần với exponential backoff + jitter. Hết lượt ⇒ event bị bỏ.
  • DLQ: gắn một SQS queue làm dead-letter queue cho target để không mất event giao thất bại.
  • Quyền gọi target: dùng resource-based policy của target (vd Lambda, SNS, SQS) hoặc IAM role mà EventBridge assume (vd Step Functions, Kinesis, ECS – kiến thức phổ biến).

Archive & replay

  • Archive: lưu event của một source bus (lọc được bằng event pattern), retention theo số ngày hoặc vô thời hạn (mặc định). Mã hóa AES-256 bằng AWS owned key. Một bus có thể có nhiều archive.
  • Replay: gửi lại event trong một khoảng thời gian về đúng source bus (có thể chỉ tới một số rule) – dùng để phục hồi sau lỗi hoặc kiểm thử tính năng mới trên dữ liệu thật. Tối đa 10 replay đồng thời mỗi account/Region; replay không xóa event khỏi archive; event replay có thêm trường replay-name.
  • Replay không bảo đảm thứ tự ban đầu (xử lý theo từng khoảng 1 phút). AWS khuyên chờ khoảng 10 phút trước khi replay để event kịp vào archive.

EventBridge Scheduler: lập lịch serverless

Amazon EventBridge Scheduler là bộ lập lịch serverless cho phép tạo, chạy và quản lý tác vụ từ một dịch vụ trung tâm. Scale cao: lên lịch hàng triệu tác vụ gọi tới hơn 270 dịch vụ AWS và hơn 6.000 API, không phải dựng máy chủ cron hay tự tích hợp nhiều dịch vụ.

Loại lịch và tính năng

  • One-time schedule: gọi target đúng một lần vào ngày giờ chỉ định (kèm time zone). Nên đặt ActionAfterCompletion để tự xóa lịch sau khi chạy (lịch đã chạy vẫn tính vào quota).
  • Recurring schedule: cron expression (vd 8:00 sáng thứ Hai) hoặc rate expression (vd mỗi 5 phút), có time zone, start/end date.
  • Flexible time window: cho phép lịch chạy trong một khoảng (vd 15 phút sau mốc) để dàn trải tải lên target khi không cần chính xác tuyệt đối.
  • Templated targets: thao tác phổ biến với SQS, SNS, Lambda, EventBridge PutEvents. Universal targets (UTP): gọi gần như mọi API AWS (vd ec2:StopInstances, ecs:RunTask).
  • Retry: giao at-least-once; cấu hình maximum age of event (tối đa 24 giờ) và maximum retries (tối đa 185). Event không giao được ⇒ DLQ là SQS queue (cùng hoặc khác account).
  • Execution role: Scheduler assume một IAM role để gọi API target (console tự tạo role; CLI/SDK/CloudFormation phải tạo sẵn). Mã hóa input bằng customer managed KMS key nếu cần.
  • Schedule group: nhóm lịch để gắn tag, quản lý (tối đa 500 group/Region).

AWS Step Functions: state machine và các loại state

Với AWS Step Functions, bạn tạo các workflow, còn gọi là state machine, để xây dựng ứng dụng phân tán, tự động hóa quy trình, điều phối microservices, tạo pipeline dữ liệu và machine learning. Mỗi bước trong workflow là một state; mỗi lần chạy workflow là một execution.

Khái niệm cốt lõi (theo tài liệu)

  • Amazon States Language (ASL): ngôn ngữ dựa trên JSON để định nghĩa state machine (StartAt, States, TimeoutSeconds…). Có thể thiết kế kéo-thả bằng Workflow Studio. Biến đổi dữ liệu bằng JSONata (khuyến nghị) hoặc JSONPath (cũ).
  • Flow states điều khiển luồng; Task states (còn gọi Actions) là đơn vị công việc do dịch vụ khác thực hiện.
  • Dữ liệu giữa các state là JSON: output của state này là input của state kế tiếp; có thể lưu vào variables. Giới hạn input/output mỗi task/state/execution: 256 KiB (dữ liệu lớn ⇒ lưu S3, truyền con trỏ).
  • Activities: worker chạy ngoài Step Functions (EC2, on-premises) poll lấy việc bằng GetActivityTask (chỉ Standard).
  • Redrive: chạy tiếp một execution Standard thất bại từ bước lỗi (trong 14 ngày sau khi kết thúc) thay vì chạy lại từ đầu.

Xử lý lỗi: Retry và Catch

  • Mặc định, một state báo lỗi sẽ làm thất bại toàn bộ execution. Task, Parallel và Map có thể khai báo Retry và Catch.
  • Retry (retrier): ErrorEquals, IntervalSeconds (mặc định 1), MaxAttempts (mặc định 3; 0 = không retry), BackoffRate (mặc định 2.0), MaxDelaySeconds, JitterStrategy (FULL/NONE). Mỗi lần retry tính là một state transition.
  • Catch (catcher): khi hết retry, chuyển sang state dự phòng (Next) – vd hoàn tiền, gửi thông báo, gợi ý username khác. Đây là nền tảng của mẫu saga pattern (kiến thức phổ biến).
  • Tên lỗi có sẵn: States.ALL (mọi lỗi, phải đứng một mình và ở cuối), States.TaskFailed (mọi lỗi trừ Timeout), States.Timeout, States.HeartbeatTimeout, States.Permissions, States.DataLimitExceeded…

Standard workflow vs Express workflow

Khi tạo state machine phải chọn Type: Standard (mặc định) hoặc Express. Cả hai định nghĩa bằng ASL, nhưng loại workflow không đổi được sau khi tạo (immutable).

Standard workflow

  • Chạy tối đa 1 năm – workflow dài, bền vững, auditable.
  • Exactly-once: mỗi task/state chạy đúng một lần (trừ khi khai báo Retry) ⇒ hợp với tác vụ không idempotent (khởi tạo EMR cluster, xử lý thanh toán).
  • Lịch sử execution xem qua API/console tới 90 ngày sau khi kết thúc (giảm còn 30 ngày được); tối đa 25.000 event lịch sử mỗi execution.
  • Tính tiền theo số state transition.
  • Hỗ trợ mọi pattern: .sync, .waitForTaskToken, Activities, Distributed Map, redrive.

Express workflow

  • Chạy tối đa 5 phút – workload khối lượng lớn, tần suất cao: IoT ingestion, xử lý/biến đổi streaming data, backend mobile.
  • Asynchronous Express: at-least-once (có thể chạy lại) ⇒ tác vụ phải idempotent. Synchronous Express: at-most-once, chờ xong rồi trả kết quả (gọi từ API Gateway, Lambda, StartSyncExecution).
  • Không lưu lịch sử trong Step Functions – phải bật CloudWatch Logs.
  • Tính tiền theo số execution, thời lượng và bộ nhớ.
  • Chỉ hỗ trợ Request Response; không có .sync, .waitForTaskToken, Activities, Distributed Map.

Amazon MQ: message broker cho ứng dụng đang dùng ActiveMQ / RabbitMQ

Amazon MQ là dịch vụ message broker được quản lý cho Apache ActiveMQ Classic và RabbitMQ; AWS lo việc setup, vận hành, bảo trì broker. Bạn có thể tạo broker mới dùng các protocol chuẩn công nghiệp, hoặc migrate broker sẵn có lên Amazon MQ mà không phải viết lại code messaging. Broker là khối xây dựng cơ bản của Amazon MQ.

Hai engine và protocol hỗ trợ

Amazon MQ for ActiveMQ

  • Protocol (bật TLS): OpenWire, AMQP, STOMP, STOMP over WebSocket, MQTT, MQTT over WebSocket. Ứng dụng Java dùng JMS API (kiến thức phổ biến).
  • Data store: KahaDB (không hỗ trợ JDBC, LevelDB).
  • Triển khai: single-instance hoặc active/standby.
  • Storage: EFS (mặc định, multi-AZ) hoặc EBS (single-AZ, chỉ mq.m5).
  • Có cross-Region data replication (CRDR): replica broker ở Region khác, failover qua API.

Amazon MQ for RabbitMQ

  • Protocol: AMQP 0-9-1 (bật TLS), dùng client của mọi ngôn ngữ RabbitMQ hỗ trợ.
  • Triển khai: single-instance (1 broker sau NLB, EBS) hoặc cluster deployment (3 node sau NLB, trải trên nhiều AZ).
  • Cluster: tự bật classic mirroring (ha-mode: all, ha-sync-mode: automatic) – dữ liệu nhân bản tới mọi node.
  • Quorum queues: queue nhân bản leader/follower ở các AZ khác nhau; xử lý tốt poison message.

Tóm tắt ghi nhớ

Key takeaways
  • Choreography (EventBridge – các service tự phản ứng với event) vs orchestration (Step Functions – state machine trung tâm điều khiển từng bước).
  • EventBridge: event bus (default nhận event dịch vụ AWS, custom, partner cho SaaS) → rule (event pattern, gắn với một bus) → tối đa 5 target chạy song song. Retry mặc định 24 giờ / 185 lần, hết thì bỏ ⇒ cấu hình DLQ (SQS). Archive & replay về source bus; cross-account bằng resource policy của bus (+ IAM role bên gửi); API destinations (connection, timeout 5 s); Pipes nối 1 nguồn → 1 đích có filter + enrichment.
  • EventBridge Scheduler (khuyến nghị thay scheduled rule legacy): one-time / cron / rate, time zone, flexible time window, retry ≤ 185 lần / ≤ 24 giờ, DLQ, 10 triệu lịch/Region, 270+ dịch vụ.
  • Schema registry: AWS / discovered / custom registry; schema discovery trên bus; OpenAPI 3 & JSONSchema Draft4; code bindings cho IDE.
  • Step Functions: state machine viết bằng ASL (JSON); state Task, Choice, Parallel, Map (Distributed tới 10.000 child song song), Wait, Pass, Succeed, Fail; Retry (1 s, 3 lần, backoff 2.0 mặc định) và Catch; payload ≤ 256 KiB. Pattern: Request Response, .sync, .waitForTaskToken (human approval).
  • Standard: ≤ 1 năm, exactly-once, lịch sử 90 ngày, tính theo state transition, có .sync/callback. Express: ≤ 5 phút, async at-least-once / sync at-most-once, 100.000 execution/s, log ra CloudWatch, tính theo execution + thời lượng + bộ nhớ. Loại workflow không đổi được.
  • Amazon MQ: ActiveMQ (OpenWire, AMQP, STOMP, MQTT, WebSocket; single-instance hoặc active/standby + EFS) và RabbitMQ (AMQP 0-9-1; single-instance hoặc cluster 3 node + NLB) – dùng để migrate ứng dụng broker sẵn có không sửa code.

  • Dùng Standard workflow với một Task state gọi batch:submitJob.sync.Đúng: pattern Run a Job (.sync) cho Step Functions tự chờ Batch job hoàn thành mà không cần code polling, và Standard chạy được nhiều giờ (tới 1 năm).
  • Dùng một Lambda function trong vòng lặp gọi DescribeJobs mỗi phút cho tới khi job hoàn thành.Sai: đây chính là tự viết code polling, trái yêu cầu.
  • Dùng một Parallel state với 2 triệu nhánh, mỗi nhánh một file.Sai: Parallel dành cho một số nhánh khác nhau được định nghĩa cố định, không dùng để lặp qua dữ liệu động khổng lồ.
  • Dùng Map state ở chế độ Distributed để đọc các object từ Amazon S3 và chạy song song các child workflow execution.Đúng: Distributed Map được thiết kế cho dataset lớn trên S3, chạy tới 10.000 child execution song song để xử lý hàng triệu file.
