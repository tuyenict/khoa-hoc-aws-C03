AWS Lambda: function, trigger và mô hình serverless

AWS Lambda là dịch vụ serverless compute: bạn chạy code mà không cần cấp phát hay quản lý máy chủ. Lambda tự quản lý toàn bộ hạ tầng bên dưới – bảo trì máy chủ, cấp phát dung lượng, scale và vá lỗi (patching) – để bạn chỉ tập trung vào logic ứng dụng.

Khái niệm cốt lõi

  • Function: đơn vị code bạn triển khai. Bạn viết một handler, chọn runtime (Node.js, Python, Java, .NET, Ruby… hoặc custom runtime) và cấu hình memory, timeout, quyền.
  • Trigger: dịch vụ/tài nguyên gọi function khi có sự kiện. Theo tài liệu, có thể nối với API Gateway, Amazon S3, Amazon SQS, EventBridge và hơn 200 dịch vụ AWS khác. Mỗi lần gọi chạy độc lập, không chia sẻ trạng thái, scale ngang theo nhu cầu.
  • Execution environment: môi trường cô lập, an toàn (dựa trên Firecracker microVM) nơi Lambda chạy code. Mặc định, mỗi môi trường xử lý một request tại một thời điểm; môi trường có thể được tái sử dụng (warm start) nhưng trạng thái không chắc còn giữa các lần gọi.
  • Execution role: IAM role mà function assume để gọi dịch vụ AWS khác (đọc S3, ghi DynamoDB…). Ngược lại, quyền cho dịch vụ khác gọi function (S3, SNS, EventBridge, API Gateway) nằm trong resource-based policy của function (tối đa 20 KB).
  • Giá: trả theo số request + GB-giây thời gian chạy (memory × thời lượng, làm tròn lên 1 ms). Không có phí khi không chạy – “scale to zero”.

Ví dụ đời thường – bếp nấu theo đơn

Lambda giống một bếp ăn thuê theo suất: bạn chỉ đưa công thức (code). Có đơn (event) thì bếp mở một quầy nấu (execution environment); nhiều đơn cùng lúc thì mở nhiều quầy song song (concurrency). Không có đơn thì không trả tiền thuê bếp. Quầy mới mở cần thời gian nhóm lò (cold start); quầy vừa nấu xong còn nóng thì nấu đơn sau nhanh hơn (warm start). Reserved concurrency là số quầy giữ riêng cho món quan trọng, provisioned concurrency là quầy đã nhóm lò sẵn chờ khách.

Mẹo thi (Exam Tip)
  • “Serverless”, “no servers to manage”, “run code in response to events”, “least operational overhead”, “pay only when code runs”, tác vụ ngắn (< 15 phút), tải thất thường ⇒ AWS Lambda.
  • “Process an image / file as soon as it is uploaded to S3” ⇒ S3 event notification → Lambda (async). Cần đệm, chống mất khi tải đột biến ⇒ S3 → SQS → Lambda (ESM).
  • Function cần quyền ghi DynamoDB ⇒ sửa execution role. S3/SNS bị “access denied” khi gọi function ⇒ thiếu resource-based policy (lambda:InvokeFunction) trên function.
Cập nhật mới trong tài liệu (ngoài phạm vi đề thi hiện tại)

Tài liệu Lambda hiện chia thành ba “compute primitive”: Lambda Event Functions (tên mới của Lambda function truyền thống – API, ARN, CreateFunction, Invoke không đổi), Lambda Web Functions (chạy web app/HTTP server, một môi trường phục vụ nhiều request) và Lambda MicroVMs (môi trường riêng cho từng user/job, sống tới 8 giờ). Ngoài ra có Durable Functions (workflow nhiều bước tới 1 năm) và Lambda Managed Instances (chạy trên hạ tầng của khách, timeout tới 90 phút cho async/ESM). Đề SAA-C03 vẫn dựa trên mô hình function truyền thống với giới hạn 15 phút – bài này dạy theo mô hình đó.

Memory, timeout và các giới hạn (quotas) quan trọng

Theo tài liệu, Lambda được thiết kế cho các tác vụ tính toán ngắn, không giữ và không phụ thuộc trạng thái giữa các lần gọi. Hiểu các quota giúp bạn loại nhanh đáp án sai: rất nhiều câu hỏi xoay quanh “việc này có vừa trong giới hạn Lambda không?”.

Memory quyết định cả CPU

  • Memory: 128 MB – 10.240 MB, bước 1 MB; mặc định 128 MB (cũng là mức thấp nhất – chỉ hợp với hàm đơn giản, chuyển tiếp event).
  • Lambda cấp CPU tỉ lệ thuận với memory. Tại 1.769 MB, function có tương đương 1 vCPU. Ở mức tối đa 10.240 MB được tới 6 vCPU (kiến thức phổ biến). Không có tùy chọn chỉnh CPU riêng – muốn thêm CPU thì tăng memory.
  • Theo tài liệu, memory là “đòn bẩy chính” điều khiển hiệu năng: hàm bị giới hạn bởi CPU, mạng hay bộ nhớ đều có thể nhanh lên đáng kể khi tăng memory (và đôi khi rẻ hơn vì chạy ngắn hơn). Công cụ chọn memory: AWS Compute Optimizer (gợi ý memory, chỉ x86_64) và AWS Lambda Power Tuning (mã nguồn mở, chạy bằng Step Functions).
  • Băng thông mạng mỗi execution environment: 625 Mbps (hàm ngoài VPC có thể xin tăng, scale theo memory tới 3.000 Mbps).

Timeout

  • Timeout: tối đa 900 giây (15 phút) mỗi lần gọi; mặc định 3 giây (kiến thức phổ biến, thấy trong log mẫu “Task timed out after 3.00 seconds”). Đây là giới hạn cứng, không xin tăng được (trừ Lambda Managed Instances mới).
  • Hàm vượt timeout bị dừng và môi trường bị reset. Với async, lỗi timeout được tính là function error và được retry.
  • Pha Init (chạy code ngoài handler) giới hạn 10 giây; quá thì Lambda thử Init lại ở lần gọi đầu với timeout của function. Giới hạn 10 giây không áp dụng với provisioned concurrency và SnapStart (init tới 15 phút).

Version và alias

  • Mỗi lần deploy code là ghi đè $LATEST. Publish tạo một version đánh số tăng dần, bất biến (code, runtime, memory, layers… bị khóa). Số version không bao giờ dùng lại.
  • Qualified ARN có hậu tố version (…:function:helloworld:42); unqualified ARN không hậu tố ⇒ gọi $LATEST.
  • Alias (vd PROD, BLUE) là con trỏ tới một version – event source chỉ cần trỏ tới alias, đổi version phía sau không phải sửa trigger. Alias có thể chia trọng số giữa 2 version để canary (kiến thức phổ biến).
  • Provisioned concurrency và SnapStart chỉ áp dụng trên version/alias, không dùng được với $LATEST.
Mẹo thi (Exam Tip)
  • Tác vụ chạy > 15 phút (transcode video dài, ETL nhiều giờ) ⇒ không dùng Lambda: chọn ECS/Fargate, AWS Batch, hoặc chia nhỏ thành nhiều bước bằng Step Functions (Bài 31).
  • “Function is CPU-bound and slow” ⇒ tăng memory (CPU tăng theo). Không có tham số “CPU” riêng.
  • Payload request > 6 MB (vd upload ảnh lớn qua API) ⇒ client upload thẳng lên S3 (presigned URL), Lambda xử lý qua S3 event.
Bẫy thường gặp
  • “Tăng timeout lên 30 phút” – không thể, 900 giây là trần.
  • Upload .zip qua S3 giúp vượt giới hạn 50 MB nén, nhưng không vượt được 250 MB giải nén. Dependency lớn (thư viện ML vài GB) ⇒ dùng container image (10 GB) hoặc mount EFS.
  • Đừng lưu dữ liệu cần giữ lâu trong /tmp hay biến toàn cục: Lambda hủy môi trường sau vài giờ kể cả khi function được gọi liên tục.

Gọi bất đồng bộ, retry, Destinations và DLQ

Với asynchronous invocation, bên gọi không chờ kết quả: Lambda đưa event vào hàng đợi bất đồng bộ của function và tự lo phần còn lại – retry, loại bỏ event quá hạn, và gửi destination khi thành công hoặc thất bại.

Retry mặc định (theo tài liệu)

  • Function error (lỗi code trả về, lỗi runtime, timeout): Lambda chạy lại thêm 2 lần – chờ 1 phút trước lần thứ 2 và 2 phút trước lần thứ 3.
  • Throttling (429) hoặc system error (5xx): Lambda trả event về hàng đợi và thử lại tới 6 giờ (mặc định), khoảng cách tăng theo cấp số nhân từ 1 giây tới tối đa 5 phút.
  • Cấu hình được: Maximum age of event (tối đa 6 giờ) và Retry attempts (0 – 2), trên function, version hoặc alias.
  • Event hết hạn hoặc hết lượt retry ⇒ Lambda bỏ (discard) event – trừ khi có on-failure destination hoặc DLQ.
  • Hàng đợi là eventually consistent ⇒ function có thể nhận cùng một event nhiều lần kể cả khi không lỗi ⇒ code phải idempotent.
  • Mẹo dừng khẩn cấp: đặt reserved concurrency = 0 ⇒ function không chạy nữa; với async, event mới đi thẳng vào DLQ / on-failure destination không retry.

Destinations – nơi nhận “biên bản” mỗi lần gọi

Concurrency: reserved và provisioned

Concurrency là số request mà function đang xử lý cùng một lúc. Mỗi request đồng thời cần một execution environment riêng; Lambda tự tăng số môi trường cho tới khi chạm quota concurrency của account – mặc định 1.000 cho tất cả function trong một Region.

Công thức tính (rất hay ra đề)

Concurrency = (số request trung bình mỗi giây) × (thời gian xử lý trung bình, giây)

Ví dụ tài liệu:
  100 req/s × 1    s   = 100
  100 req/s × 0,5  s   = 50
  200 req/s × 0,25 s   = 50
  5.000 req/s × 0,2 s  = 1.000   ← chạm đúng quota mặc định
  • Concurrency khác request per second. Ngoài concurrency, Lambda còn giới hạn RPS = 10 × concurrency quota (mặc định 10.000 RPS/account). Hàm rất ngắn (vd 20 ms, 30.000 RPS ⇒ concurrency chỉ 600) vẫn bị throttle vì vượt 10.000 RPS ⇒ phải xin tăng quota lên ≥ 3.000.
  • Vượt concurrency ⇒ request bị throttle (lỗi 429 TooManyRequestsException). Sync: bên gọi nhận lỗi; async: Lambda tự thử lại tới 6 giờ; ESM: poller chậm lại.
  • Concurrency scaling rate: mỗi function tăng tối đa 1.000 execution environment mỗi 10 giây (hoặc 10.000 RPS mỗi 10 giây), độc lập giữa các function.

Reserved concurrency

  • Reserved concurrency đặt đồng thời mức tối đa và tối thiểu cho function: phần này dành riêng cho nó, function khác không dùng được; function cũng không vượt quá mức này (throttle khi chạm trần).
  • Miễn phí. Dùng để: (1) bảo đảm function quan trọng luôn có capacity, (2) giới hạn function để không làm quá tải tài nguyên hạ nguồn (vd database chỉ chịu N kết nối), (3) đặt = 0 để tắt function.
  • Lambda luôn giữ 100 concurrency cho các function không reserved ⇒ với quota 1.000 chỉ reserve được tối đa 900 (quota 2.000 ⇒ 1.900).
  • Reserved concurrency không khởi tạo sẵn môi trường ⇒ vẫn có cold start.

Provisioned concurrency

  • Provisioned concurrency là số execution environment được khởi tạo trước (đã chạy xong Init), sẵn sàng phản hồi với độ trễ hai chữ số mili-giây ⇒ loại bỏ cold start cho phần lưu lượng nằm trong mức provisioned.
  • Tốn phí (tính liên tục, kể cả khi không có request). Phù hợp workload tương tác (web, mobile, API) nhạy độ trễ; pipeline bất đồng bộ thường không cần.
  • Cấu hình trên version hoặc alias (không phải $LATEST); event source phải trỏ đúng alias/version đó. Lambda cần 1–2 phút chuẩn bị và cấp tối đa 6.000 môi trường mỗi phút; chỉ dùng được khi cấp phát xong toàn bộ.
  • Vượt mức provisioned: nếu không đặt reserved ⇒ dùng tiếp concurrency chung (có thể cold start); nếu có reserved ⇒ bị throttle khi chạm reserved. Provisioned không được lớn hơn reserved.
  • Tự động hóa bằng Application Auto Scaling: scheduled scaling (lưu lượng dự đoán được, vd giờ hành chính) hoặc target tracking theo metric LambdaProvisionedConcurrencyUtilization (vd giữ 70%, chọn 10%–90%). Tài liệu khuyên cộng thêm 10% buffer so với đỉnh thường gặp.

Vòng đời execution environment, cold start và SnapStart

Mỗi execution environment trải qua ba pha: Init → Invoke → Shutdown. Khi chưa có môi trường sẵn, Lambda phải tải code, khởi động môi trường và chạy code khởi tạo – phần trễ thêm này gọi là cold start. Môi trường được tái sử dụng cho request sau gọi là warm start.

  1. Init – khởi động các extension, bootstrap runtime, chạy static code (code ngoài handler: import thư viện, tạo SDK client, mở kết nối DB). Giới hạn 10 giây. Thời gian Init được tính tiền.
  2. Invoke – chạy handler; toàn bộ pha bị giới hạn bởi timeout của function. Lỗi/timeout ⇒ Lambda reset môi trường (lần sau phải init lại).
  3. Freeze / thaw – xong request, môi trường bị “đóng băng” và giữ lại một thời gian; request mới tới thì “rã đông” và dùng lại: biến toàn cục, kết nối DB, nội dung /tmp còn nguyên.
  4. Shutdown – Lambda gửi sự kiện Shutdown cho extension (0 ms nếu không có extension, 500 ms với internal extension, 2.000 ms với external extension). Lambda vẫn hủy môi trường sau vài giờ để cập nhật runtime.
  • Theo tài liệu, cold start thường xảy ra ở dưới 1% số lần gọi, kéo dài từ dưới 100 ms tới hơn 1 giây; hay gặp ở môi trường dev/test (ít gọi) hơn production.
  • Giảm cold start bằng code: khởi tạo ngoài handler (tái sử dụng kết nối), chỉ import thứ cần dùng, giảm kích thước package, lazy-load tài nguyên ít dùng, tách function “to” thành nhiều function nhỏ.
  • Giảm cold start bằng cấu hình: provisioned concurrency (khởi tạo sẵn) hoặc SnapStart (khôi phục từ snapshot).

Lambda SnapStart

  • SnapStart: khi bạn publish một version, Lambda chạy Init một lần, chụp snapshot Firecracker microVM (trạng thái memory + disk của môi trường đã khởi tạo), mã hóa và cache nhiều bản sao. Khi gọi và khi scale, Lambda resume môi trường mới từ snapshot thay vì init từ đầu ⇒ startup từ vài giây xuống dưới 1 giây, thường không cần sửa code.
  • Runtime hỗ trợ: Java 11+, Python 3.12+, .NET 8+ (cả .zip và container image dựa trên base image AWS). Node.js, Ruby, OS-only runtime không hỗ trợ.
  • Không dùng chung với: provisioned concurrency, Amazon EFS, Amazon S3 Files, ephemeral storage > 512 MB. Chỉ trên published version và alias trỏ tới version (không $LATEST).
  • Giá: với runtime Java – không tốn thêm. Với Python/.NET – trả phí caching snapshot (tối thiểu 3 giờ, theo memory) và phí restoration mỗi lần khôi phục.
  • Lưu ý uniqueness: một snapshot dùng làm trạng thái ban đầu cho nhiều môi trường ⇒ giá trị “ngẫu nhiên/duy nhất” sinh ra trong Init (ID, secret, seed) sẽ bị trùng – phải sinh sau khi restore (dùng runtime hooks before-checkpoint / after-restore). Kết nối mạng mở trong Init cần kiểm tra lại; dữ liệu tạm (credential, timestamp) cần làm mới.

Provisioned concurrency

  • Môi trường luôn ấm sẵn – phản hồi hai chữ số ms.
  • Mọi runtime.
  • Trả tiền liên tục cho số môi trường provisioned.
  • Dùng khi yêu cầu độ trễ nghiêm ngặt mà SnapStart chưa đủ.

SnapStart

  • Resume từ snapshot – startup dưới 1 giây (tối ưu).
  • Java 11+, Python 3.12+, .NET 8+.
  • Java: miễn phí; Python/.NET: phí cache + restore.
  • Hiệu quả nhất khi gọi ở quy mô lớn; hàm ít gọi cải thiện ít hơn.
Mẹo thi (Exam Tip)
  • “Java (Spring Boot) function has multi-second cold starts; reduce startup latency at no additional cost” ⇒ SnapStart.
  • “Strict, predictable low latency for every request” ⇒ provisioned concurrency (có phí).
  • “Reuse database connections across invocations” ⇒ khởi tạo client/kết nối ngoài handler (static init) – kết hợp RDS Proxy khi concurrency cao.

Lambda trong VPC

Mọi function thực ra luôn chạy trong một VPC do Lambda sở hữu và quản lý (bạn không thấy) – VPC này có Internet. Khi function cần truy cập tài nguyên private trong VPC của bạn (RDS, ElastiCache, EC2, internal ALB…), bạn gắn function vào VPC bằng cách chọn private subnet và security group.

Hyperplane ENI – cách Lambda “cắm” vào VPC

  • Lambda tạo Hyperplane ENI trong các subnet bạn chọn. ENI gắn với một tổ hợp subnet + security group; các function khác dùng cùng tổ hợp sẽ dùng chung ENI ⇒ tài liệu khuyên dùng chung subnet/SG cho các function để tránh tạo ENI mới.
  • Mỗi Hyperplane ENI hỗ trợ tới 65.000 kết nối/port; vượt thì Lambda tự thêm ENI. ENI không cần tự cấu hình, không hiển thị để quản lý trực tiếp.
  • Function mới ở trạng thái Pending (không gọi được) trong lúc tạo ENI – có thể mất vài phút. Function idle 14 ngày ⇒ Lambda thu hồi ENI, function thành Inactive; lần gọi kế tiếp thất bại và function quay lại Pending tới khi có ENI.
  • Gỡ cấu hình VPC: Lambda cần tới 20 phút để xóa ENI (chỉ xóa khi không function/version nào khác dùng).
  • Quota ENI: 3.000 ENI mỗi VPC (chia sẻ với EFS và dịch vụ khác). Function không kết nối trực tiếp được VPC có dedicated tenancy (phải peer sang VPC default tenancy).

Quyền IAM cần có

  • Execution role cần quyền tạo/quản lý ENI: gắn managed policy AWSLambdaVPCAccessExecutionRole (console tự thêm) hoặc tự cấp ec2:CreateNetworkInterface, ec2:DescribeNetworkInterfaces, ec2:DescribeSubnets, ec2:DeleteNetworkInterface, ec2:AssignPrivateIpAddresses, ec2:UnassignPrivateIpAddresses trên "Resource": "*".
  • Các quyền EC2 này cũng vô tình cấp cho code của function ⇒ theo nguyên tắc least privilege, thêm Deny với điều kiện lambda:SourceFunctionArn để chặn code gọi EC2 API mà Lambda service vẫn quản lý được ENI.
  • Quản trị: condition key lambda:VpcIds, lambda:SubnetIds, lambda:SecurityGroupIds trong IAM policy cho CreateFunction/UpdateFunctionConfiguration – vd bắt buộc mọi function phải gắn VPC ("Null": {"lambda:VpcIds": "true"} ⇒ Deny).

Ra Internet và gọi dịch vụ AWS từ function trong VPC

  • Sau khi gắn VPC, function chỉ truy cập được những gì VPC đó cho phép – mất Internet mặc định.
  • Muốn ra Internet (gọi API bên thứ ba): đặt function trong private subnet có route 0.0.0.0/0 → NAT gateway nằm ở public subnet (public subnet route tới internet gateway). IPv6: route ::/0 → egress-only internet gateway.
  • Gắn function vào public subnet KHÔNG cho Internet và không cho public IP – ENI của Lambda không có public IP.
  • Chỉ cần gọi dịch vụ AWS (S3, DynamoDB, SQS, Secrets Manager…) mà không cần Internet ⇒ dùng VPC endpoint: gateway endpoint (S3, DynamoDB – miễn phí) hoặc interface endpoint (dịch vụ khác) – Bài 22. Rẻ hơn và riêng tư hơn NAT.
  • Tài liệu khuyên dùng ít nhất 2 AZ (chọn subnet ở nhiều AZ) và NAT gateway mỗi AZ để tăng tính sẵn sàng. Security group của function phải cho phép outbound; SG của DB cho phép inbound từ SG của function.
  • IPv6: bật Allow IPv6 traffic for dual-stack subnets – mọi subnet phải dual-stack; không hỗ trợ subnet IPv6-only.
Mẹo thi (Exam Tip)
  • “Lambda must access an RDS database in a private subnet” ⇒ cấu hình VPC cho function (private subnet + SG), SG của DB cho phép inbound từ SG của Lambda.
  • “After connecting to the VPC, the function can no longer reach the internet / third-party API” ⇒ NAT gateway trong public subnet + route từ private subnet của function.
  • “VPC-connected function must access S3 / DynamoDB privately, no internet, lowest cost” ⇒ gateway VPC endpoint.
  • “Many concurrent Lambda functions exhaust database connections” ⇒ RDS Proxy.
Bẫy thường gặp
  • Chọn public subnet cho function để “có Internet” – sai, ENI của Lambda không có public IP.
  • Gắn Elastic IP cho function – không làm được; muốn IP ra ngoài cố định (whitelist ở đối tác) ⇒ đi qua NAT gateway có Elastic IP.
  • Không cần gắn VPC chỉ để gọi S3/DynamoDB – function ngoài VPC đã gọi được dịch vụ AWS public. Chỉ gắn VPC khi cần tài nguyên private.

Layers, đóng gói và container image

Một Lambda layer là file .zip chứa code hoặc dữ liệu bổ sung – thường là thư viện phụ thuộc, custom runtime hoặc file cấu hình. Layer giúp tách thư viện khỏi code nghiệp vụ và dùng chung giữa nhiều function.

Vì sao dùng layer (theo tài liệu)

  • Giảm kích thước deployment package – thư viện để trong layer, package chỉ còn code nghiệp vụ.
  • Tách logic khỏi dependency – cập nhật thư viện độc lập với code và ngược lại.
  • Chia sẻ dependency giữa nhiều function – tạo một lần, gắn cho bao nhiêu function cũng được (cũng có thể chia sẻ sang account khác qua quyền của layer version).
  • Dùng được code editor trên console (package quá lớn thì không mở được editor).
  • Khóa phiên bản AWS SDK – runtime có SDK nhúng có thể đổi; đặt SDK vào layer để cố định version.

Cách hoạt động và giới hạn

  • Khi gắn layer, Lambda giải nén nội dung vào thư mục /opt trong execution environment; runtime có sẵn đường dẫn tới các thư mục con trong /opt.
  • Tối đa 5 layer mỗi function. Tổng code + mọi layer + custom runtime ≤ 250 MB giải nén.
  • Layer version là bản chụp bất biến, đánh số từ 1, mỗi version có ARN riêng (…:layer:my-layer:1); khi gắn phải chỉ rõ version.
  • Layer chỉ dùng với function đóng gói .zip. Function dạng container image phải đóng runtime + dependency vào image.
  • Với Go và Rust, tài liệu khuyên không dùng layer (binary đã chứa dependency; layer làm tăng cold start).

Tóm tắt ghi nhớ

Key takeaways
  • Lambda = serverless compute theo sự kiện, trả theo request + GB-giây; mỗi môi trường xử lý 1 request/lần; tác vụ phải ≤ 15 phút.
  • Ba kiểu gọi: sync (API Gateway, ALB, function URL – bên gọi retry), async (S3, SNS, EventBridge – Lambda retry 2 lần, event giữ tới 6 giờ), event source mapping (SQS, Kinesis, DynamoDB Streams, MSK, MQ – Lambda poll theo batch, at-least-once).
  • Giới hạn: memory 128–10.240 MB (CPU theo memory, 1.769 MB ≈ 1 vCPU), timeout 900 s, payload 6 MB sync / 1 MB async, env vars 4 KB, .zip 50 MB nén / 250 MB giải nén, image 10 GB, /tmp 512 MB–10 GB, 5 layer.
  • Destinations (on success / on failure → SQS, SNS, Lambda, EventBridge, S3) chứa cả response; DLQ (SQS/SNS) chỉ chứa event lỗi. Nguồn SQS ⇒ DLQ đặt trên queue.
  • Concurrency = RPS × thời gian xử lý. Quota 1.000/Region (RPS ≤ 10 × concurrency), scale 1.000 môi trường / 10 s mỗi function. Reserved = trần + dành riêng, miễn phí, giữ 100 cho unreserved, = 0 để tắt. Provisioned = khởi tạo sẵn trên version/alias, chống cold start, có phí, scale bằng Application Auto Scaling.
  • Cold start < 1% lời gọi; Init ≤ 10 s; khởi tạo client ngoài handler. SnapStart (Java 11+, Python 3.12+, .NET 8+, chỉ published version, không cùng provisioned concurrency/EFS) – Java miễn phí.
  • Lambda trong VPC: Hyperplane ENI dùng chung theo subnet + SG; cần AWSLambdaVPCAccessExecutionRole; mất Internet ⇒ private subnet + NAT gateway (public subnet không giúp gì); dịch vụ AWS ⇒ VPC endpoint; DB ⇒ RDS Proxy.
  • Layers: .zip giải nén vào /opt, version bất biến, chia sẻ thư viện; không dùng với container image.

Câu hỏi luyện tập

An AWS Lambda function reads customer records from an Amazon RDS for MySQL DB instance in a private subnet and then calls a third-party payment API on the public internet. After the function was configured to connect to the VPC, the database queries succeed but every call to the payment API times out. What should a solutions architect do to resolve the issue?
  1. Move the function's VPC configuration to a public subnet that has a route to an internet gateway.
  2. Assign an Elastic IP address to the Lambda function.
  3. Keep the function in private subnets, create a NAT gateway in a public subnet, and add a 0.0.0.0/0 route from the private subnets' route table to the NAT gateway.
  4. Create a gateway VPC endpoint for the payment API.
