Sau bài này bạn sẽ

  • Hiểu Amazon API Gateway là “cửa trước” (front door) của ứng dụng serverless, nắm các khái niệm resource, method, integration, deployment, stage.
  • Chọn đúng giữa REST API, HTTP API và WebSocket API dựa trên tính năng (API key, usage plan, caching, WAF, private endpoint, JWT authorizer, giao tiếp hai chiều).
  • Phân biệt ba endpoint type: edge-optimized, Regional, private, và biết khi nào dùng custom domain + Route 53.
  • Thuộc cơ chế throttling (token bucket, 10.000 RPS / burst 5.000 mỗi account mỗi Region, thứ tự áp dụng, 429) và usage plan + API key.
  • Cấu hình API caching (TTL mặc định 300 giây, tối đa 3.600 giây, chỉ GET mặc định, invalidate bằng Cache-Control: max-age=0).
  • Chọn authorizer phù hợp: IAM (SigV4), Cognito user pool, Lambda authorizer (TOKEN / REQUEST), JWT authorizer, kết hợp resource policy và AWS WAF; thiết kế các kiến trúc serverless hay thi.

Amazon API Gateway: “cửa trước” của ứng dụng

Amazon API Gateway là dịch vụ AWS để tạo, publish, bảo trì, giám sát và bảo mật các REST, HTTP và WebSocket API ở mọi quy mô. Theo tài liệu, API Gateway xử lý mọi việc liên quan tới việc nhận và xử lý tới hàng trăm nghìn lời gọi API đồng thời: quản lý lưu lượng (traffic management), ủy quyền và kiểm soát truy cập (authorization & access control), giám sát (monitoring) và quản lý phiên bản API.

API Gateway đóng vai trò front door để ứng dụng truy cập dữ liệu, logic nghiệp vụ hoặc chức năng ở back end: workload chạy trên Amazon EC2, code chạy trên AWS Lambda, bất kỳ web application nào, hoặc ứng dụng giao tiếp thời gian thực. Tài liệu nhấn mạnh: API Gateway cùng với AWS Lambda tạo thành phần “hướng ứng dụng” (app-facing) của hạ tầng serverless AWS.

Các khái niệm cốt lõi

  • Resource: một đường dẫn trong API, ví dụ /pets, /pets/{id}. Resource đặc biệt {proxy+} bắt mọi đường dẫn con – tài liệu khuyên dùng để giảm số resource (quota 300 resource/API).
  • Method: động từ HTTP gắn trên resource – GET, POST, PUT, PATCH, DELETE… Mỗi method có method request (xác thực, validate, tham số), integration request, integration response và method response.
  • Integration: back end thực sự xử lý request – Lambda function, HTTP endpoint, một action của dịch vụ AWS (vd SendMessage của SQS), tài nguyên private trong VPC (qua VPC link) hoặc mock.
  • Deployment: một snapshot của API tại một thời điểm. Sửa API xong phải deploy thì client mới thấy (REST API); HTTP API hỗ trợ automatic deployment.
  • Stage: “tên tham chiếu tới một deployment” – ví dụ dev, test, prod. Nhiều thiết lập vận hành (caching, throttling, logging, WAF, canary) được cấu hình theo stage.
  • Invoke URL mặc định có dạng https://{api-id}.execute-api.{region}.amazonaws.com/{stage}. Muốn URL dễ nhớ (https://api.example.com/myservice) thì dùng custom domain name.

Ví dụ đời thường – quầy lễ tân tòa nhà

API Gateway giống quầy lễ tân của một tòa văn phòng. Khách (client) không tự đi thẳng vào phòng ban (back end): lễ tân kiểm tra thẻ (authorizer), hạn chế số khách mỗi phút để thang máy không quá tải (throttling), trả lời ngay những câu hỏi lặp đi lặp lại như “giờ làm việc mấy giờ?” mà không cần gọi lên trên (caching), rồi chỉ đường tới đúng phòng (integration). Stage giống các tầng “dev”, “prod” – cùng tòa nhà nhưng mỗi tầng có quy định riêng.

Mẹo thi (Exam Tip)
  • “Expose Lambda functions as a RESTful API”, “serverless back end for a mobile app”, “least operational overhead” ⇒ API Gateway + Lambda (+ DynamoDB).
  • “Single entry point / front door for microservices”, “authentication, throttling, monitoring of API calls” ⇒ API Gateway (không phải ALB tự viết logic).
  • Ghi lại ai đã thay đổi cấu hình API ⇒ CloudTrail; ghi lại từng request của client ⇒ CloudWatch access logging; truy vết độ trễ end-to-end ⇒ X-Ray.

REST API, HTTP API và WebSocket API

API Gateway có ba “sản phẩm” API. REST API và HTTP API đều là API kiểu RESTful (dựa trên HTTP, client-server stateless, dùng các method chuẩn GET/POST/PUT/PATCH/DELETE). WebSocket API tuân theo giao thức WebSocket (RFC 6455) – stateful, full-duplex, định tuyến message theo nội dung.

Câu chốt của tài liệu: “REST APIs support more features than HTTP APIs, while HTTP APIs are designed with minimal features so that they can be offered at a lower price. Choose REST APIs if you need features such as API keys, per-client throttling, request validation, AWS WAF integration, or private API endpoints.”

WebSocket API – giao tiếp hai chiều

  • Khác REST API (nhận request – trả response), WebSocket API giữ kết nối lâu dài, cho phép back end chủ động gửi message (callback) tới client đang kết nối – phù hợp chat, bảng điều khiển thời gian thực, game nhiều người chơi, thông báo trực tiếp.
  • Route: message JSON được chuyển tới integration theo route key, là giá trị thu được khi đánh giá route selection expression (vd ${request.body.action}). Ba route định sẵn:
    • $connect – gọi khi client bắt đầu mở kết nối (chỗ thích hợp để xác thực, lưu connection ID vào DynamoDB).
    • $disconnect – gọi khi client hoặc server ngắt kết nối.
    • $default – khi không đánh giá được biểu thức hoặc không có route khớp (message không phải JSON cũng vào đây).
  • Back end gửi dữ liệu về client bằng: (1) route response của integration, hoặc (2) gửi POST tới @connections API kèm connection ID.
  • Mã đóng kết nối đáng nhớ: 1001 – client idle 10 phút hoặc chạm thời gian sống tối đa 2 giờ; 1008 – quá nhiều request từ một client; 1009 – message quá lớn.

Endpoint type: edge-optimized, Regional, private

Endpoint type là kiểu hostname của API, chọn theo việc phần lớn lưu lượng đến từ đâu. Đây là chủ đề rất hay ra đề vì nó gắn với CloudFront, VPC endpoint và custom domain.

Edge-optimized

  • Request đi tới CloudFront Point of Presence (POP) gần client nhất rồi mới vào Region của API (CloudFront distribution do API Gateway quản lý – bạn không thấy/không cấu hình được).
  • Phù hợp client phân tán toàn cầu.
  • Là endpoint mặc định của REST API.
  • Viết hoa tên HTTP header (vd Cookie); CloudFront sắp xếp cookie theo tên.
  • Custom domain áp dụng trên mọi Region; certificate ACM phải ở us-east-1 (kiến thức phổ biến, giống CloudFront).
  • Chỉ REST API.

Regional

  • Dành cho client cùng Region (vd EC2 trong cùng Region) hoặc API phục vụ ít client nhưng tải cao – giảm overhead kết nối.
  • Truyền header nguyên trạng.
  • Custom domain riêng từng Region; deploy cùng API ở nhiều Region với cùng custom domain + Route 53 latency-based routing / failover ⇒ API multi-Region.
  • Client toàn cầu nhưng muốn tự kiểm soát CloudFront (cache policy, WAF ở edge, Lambda@Edge) ⇒ Regional API + CloudFront distribution của riêng bạn.
  • REST và HTTP API (HTTP API chỉ có Regional).

Private

  • Chỉ gọi được từ trong VPC qua interface VPC endpoint (dịch vụ execute-api, chạy bằng AWS PrivateLink).
  • On-premises truy cập qua Direct Connect / VPN vào VPC. Lưu lượng không rời mạng Amazon.
  • Cần resource policy cho phép VPC/VPC endpoint (aws:SourceVpc, aws:SourceVpce).
  • Chỉ REST API; chỉ TLS 1.2; không chuyển thành edge-optimized được.

Private API – các best practice theo tài liệu

  • Dùng một VPC endpoint để truy cập nhiều private API – giảm số endpoint (và chi phí).
  • Associate VPC endpoint với API ⇒ API Gateway tạo bản ghi Route 53 alias, gọi API dễ hơn.
  • Bật private DNS trên endpoint để gọi API trong VPC mà không cần truyền header Host / x-apigw-api-id. Lưu ý: bật private DNS thì từ VPC không gọi được endpoint mặc định của các API public (muốn cả hai thì tắt private DNS và tạo private hosted zone riêng).
  • Giới hạn truy cập bằng điều kiện aws:SourceVpc / aws:SourceVpce trong resource policy; muốn “data perimeter” chặt nhất thì thêm VPC endpoint policy.

Custom domain name

  • Thay URL mặc định bằng tên dễ nhớ, kèm base path mapping (vd api.example.com/orders → API orders stage prod, api.example.com/users → API users). Cần certificate SSL/TLS trong ACM (hoặc import).
  • Tạo bản ghi DNS (Route 53 alias) trỏ custom domain tới endpoint của API. Có thể tắt endpoint mặc định (execute-api) để buộc client đi qua custom domain – gọi endpoint mặc định sẽ nhận 403.
  • Custom domain duy nhất trong một Region trên mọi account; hỗ trợ wildcard (*.example.com) cho kịch bản mỗi khách hàng một subdomain.
  • Có thể chuyển custom domain giữa edge-optimized và Regional; không chuyển public sang private được.
Mẹo thi (Exam Tip)
  • “Users around the world, reduce latency, REST API” ⇒ edge-optimized endpoint. Nếu đề thêm “need control over caching / custom CloudFront behaviors” ⇒ Regional endpoint + CloudFront của bạn.
  • “API must be accessible only from within the VPC / from on-premises over Direct Connect, not from the internet” ⇒ private REST API + interface VPC endpoint (execute-api) + resource policy.
  • “Multi-Region active-active API with the same domain name” ⇒ Regional API ở mỗi Region + custom domain + Route 53 latency / failover routing (Bài 24).

Stage và stage settings

  • Stage là tên tham chiếu tới một deployment. Thiết lập theo stage: cache (provision cache, TTL, encrypt), throttling (rate, burst), AWS WAF web ACL (có tùy chọn fail-close nếu web ACL không đánh giá được), client certificate (để back end xác minh request đến từ API Gateway), CloudWatch Logs (Off / Errors only / Errors and info), detailed metrics, custom access logging (tới CloudWatch Logs hoặc Firehose), X-Ray tracing.
  • Mỗi thiết lập stage có thể override theo method (vd tắt cache cho GET /pets, throttling riêng cho POST /orders).
  • Stage variables: cặp key/value theo stage (tối đa 100/stage) – dùng như biến môi trường, vd trỏ stage dev tới alias Lambda DEV, stage prod tới alias PROD (arn:...:function:orders:${stageVariables.lambdaAlias}).
  • Bật CloudWatch Logs cần khai báo một IAM role cho API Gateway (managed policy AmazonAPIGatewayPushToCloudWatchLogs). Tài liệu khuyên không bật data tracing cho production vì có thể ghi dữ liệu nhạy cảm vào log.

Canary release deployment (REST API)

  • Trên cùng một stage, lưu lượng được chia ngẫu nhiên giữa production release (bản gốc) và canary release (bản mới) theo phần trăm 0,0 – 100,0 bạn đặt; thường canary nhận phần nhỏ.
  • Canary có thể override stage variables, có log & metric riêng (log group hậu tố /Canary) để so sánh; có thể dùng stage cache.
  • Kết quả tốt ⇒ promote canary thành production; xấu ⇒ tắt canary (rollback). Đây là cách giảm rủi ro khi đổi API mà không cần tạo stage/URL mới.
Mẹo thi (Exam Tip)
  • “Send API requests directly to an SQS queue / Kinesis stream without managing compute”, “remove the Lambda function that only forwards data” ⇒ AWS service integration (AWS type) – API Gateway gọi thẳng dịch vụ.
  • “Expose a private service running behind an NLB/ALB in a VPC through API Gateway” ⇒ VPC link (private integration).
  • “Roll out a new API version to 10% of users and monitor” ⇒ canary release deployment trên stage (REST API). Phía Lambda tương đương là alias weighted routing (Bài 32).
  • “Separate dev / test / prod environments for the same API” ⇒ nhiều stage + stage variables trỏ tới Lambda alias khác nhau.

Throttling, usage plan và API key

Throttling và quota bảo vệ API (và back end) khỏi bị quá tải. API Gateway dùng thuật toán token bucket: mỗi request tiêu một token. Tài liệu nhấn mạnh throttle và quota đều áp dụng theo kiểu best-effort – là mục tiêu, không phải trần bảo đảm tuyệt đối.

Token bucket: rate và burst

  • Rate: số token được thêm vào bucket mỗi giây – tức tốc độ ổn định (steady-state) cho phép.
  • Burst: dung lượng của bucket – số request tối đa được xử lý “dồn” trong một khoảnh khắc trước khi API Gateway trả lỗi. Tài liệu định nghĩa: burst là “số request đồng thời mục tiêu tối đa API Gateway đáp ứng trước khi trả 429 Too Many Requests”.
  • Vượt cả rate và burst ⇒ client nhận 429 Too Many Requests; client nên retry có giới hạn tốc độ (exponential backoff).
  • Mặc định mỗi account, mỗi Region: 10.000 RPS (gộp chung REST, HTTP, WebSocket API) với bucket tối đa 5.000. RPS tăng được (Service Quotas / Support); burst do đội API Gateway quyết định theo RPS. Một số Region mới hơn: 2.500 RPS / burst 1.250.

Usage plan và API key (chỉ REST API)

  • Usage plan chỉ định ai được truy cập một hoặc nhiều stage/method đã deploy, kèm throttling (rate, burst) và quota (số request tối đa trong ngày/tuần/tháng) cho từng API key. Dùng để bán API như một sản phẩm theo gói (Free / Basic / Premium).
  • API key: chuỗi chữ-số 20–128 ký tự phân phát cho khách hàng (client gửi qua header x-api-key – kiến thức phổ biến). Một API key có thể thuộc nhiều usage plan, nhưng với mỗi stage chỉ thuộc một usage plan.
  • Throttling và quota áp dụng cho từng API key, cộng dồn trên mọi stage trong usage plan.
Bẫy thường gặp (tài liệu nhấn mạnh)
  • Không dùng API key để xác thực/ủy quyền. Người có API key hợp lệ cho một API trong usage plan có thể gọi mọi API trong plan đó; API key lại hay bị log trong header. Kiểm soát truy cập phải dùng IAM, Lambda authorizer hoặc Cognito user pool.
  • Không dựa vào usage plan / throttling để kiểm soát chi phí hay chặn truy cập – chúng là best-effort, client có thể vượt. Theo dõi chi phí bằng AWS Budgets, chặn/giới hạn request độc hại bằng AWS WAF (rate-based rule).
  • Throttle ở API Gateway không thay cho giới hạn ở back end: API 10.000 RPS vẫn có thể làm Lambda chạm quota concurrency (Bài 32) hoặc làm database quá tải ⇒ đặt stage throttling phù hợp sức chịu của back end.
Mẹo thi (Exam Tip)
  • “Offer the API to third-party developers with different request limits per customer / tiered plans” ⇒ usage plan + API key (REST API).
  • “Protect the back-end database from sudden traffic spikes coming through the API” ⇒ stage/method throttling trên API Gateway (+ đệm bằng SQS nếu chấp nhận xử lý bất đồng bộ).
  • Client nhận 429 ⇒ bị throttle (API Gateway hoặc Lambda) ⇒ retry với exponential backoff, xin tăng quota hoặc bật caching. Nhận 504 ⇒ back end vượt integration timeout 29 giây.

API caching

Bật API caching để cache response của back end trong một khoảng TTL (giây). Khi có request trùng, API Gateway trả kết quả từ cache thay vì gọi back end ⇒ giảm số lời gọi tới back end và giảm độ trễ. Caching chỉ có ở REST API.

Các điểm cần nhớ (theo tài liệu)

  • Bật cache theo stage: API Gateway tạo một cache instance riêng – mất tới khoảng 4 phút để tạo/xóa. Bạn chọn cache capacity; capacity lớn hơn ⇒ nhiều CPU, memory, băng thông hơn ⇒ hiệu năng tốt hơn nhưng đắt hơn. Các mức từ 0,5 GB tới 237 GB (kiến thức phổ biến – xem tham số cacheClusterSize).
  • Đổi capacity = xóa cache cũ, tạo cache mới ⇒ toàn bộ dữ liệu cache bị mất.
  • TTL mặc định 300 giây, tối đa 3.600 giây; TTL = 0 nghĩa là tắt cache. Response tối đa được cache: 1.048.576 byte (1 MB).
  • Khi bật cache cho stage, chỉ method GET được cache mặc định (vì an toàn). Method khác muốn cache phải override theo method. Mỗi method có thể override: bật/tắt cache, TTL, mã hóa cache (encrypt cache data – nên bật nếu response có dữ liệu nhạy cảm).
  • Cache key: chọn tham số (header, path, query string) làm khóa – response cho mỗi giá trị khóa được cache riêng. Ví dụ dùng type làm khóa: GET /users?type=admin và ?type=regular cache riêng; tham số không nằm trong khóa (vd department) thì bị bỏ qua khi tra cache.
  • Flush stage cache: xóa toàn bộ cache của stage (console / flush-stage-cache) – sau đó back end tạm thời chịu nhiều request hơn.
  • Invalidate từng mục: client gửi header Cache-Control: max-age=0 ⇒ lấy response mới từ back end và thay mục cache. Nên yêu cầu quyền IAM execute-api:InvalidateCache (“Require authorization”) – nếu không, bất kỳ client nào cũng có thể vô hiệu cache, làm tăng độ trễ. Request không có quyền có thể bị: FAIL_WITH_403, bỏ qua header + thêm cảnh báo, hoặc bỏ qua header.
  • Caching tính phí theo giờ theo kích thước cache, không thuộc Free Tier. Theo dõi hiệu quả bằng metric CacheHitCount và CacheMissCount. Caching là best-effort.
  • Tài liệu khuyên chạy load test 10 phút mô phỏng traffic thật (ramp up, ổn định, spike) để chọn capacity phù hợp.
Mẹo thi (Exam Tip)
  • “Many identical read requests, reduce load on back end / reduce latency, data changes infrequently” ⇒ bật API Gateway caching trên stage (REST API), chọn TTL phù hợp.
  • “Clients must be able to get fresh data on demand” ⇒ Cache-Control: max-age=0 + quyền execute-api:InvalidateCache.
  • Response chứa dữ liệu nhạy cảm/tuân thủ ⇒ bật Encrypt cache data. Response khác nhau theo user/tham số ⇒ đưa header/query đó vào cache key (tránh trả nhầm dữ liệu của người khác).
Bẫy thường gặp
  • Bật cache nhưng POST vẫn gọi back end – đúng, vì mặc định chỉ cache GET.
  • Cache key thiếu tham số quan trọng ⇒ client nhận dữ liệu sai của request khác. Ngược lại, quá nhiều tham số trong cache key ⇒ tỉ lệ hit thấp.
  • Không nhầm API Gateway cache với CloudFront cache: endpoint edge-optimized đi qua CloudFront nhưng distribution đó không cache response của bạn (kiến thức phổ biến); đừng dùng header X-Cache của CloudFront để kiểm tra API cache (tài liệu nêu rõ).

Kiểm soát truy cập: IAM, Cognito, Lambda authorizer, resource policy, WAF

API Gateway có nhiều cơ chế kiểm soát truy cập, thường kết hợp với nhau. Ba loại authorizer hay thi là IAM, Amazon Cognito user pool và Lambda authorizer; bổ sung bởi resource policy, VPC endpoint policy, AWS WAF, mutual TLS.

1. IAM authorization (AWS_IAM)

  • Đặt authorizationType = AWS_IAM trên method ⇒ caller phải ký request bằng SigV4 (hoặc SigV4a) với AWS credentials. IAM policy của caller cần execute-api:Invoke trên ARN dạng arn:aws:execute-api:{region}:{account}:{api-id}/{stage}/{METHOD}/{path}.
  • Phù hợp khi caller đã có AWS credentials: dịch vụ/ứng dụng nội bộ trên EC2/Lambda (dùng IAM role), user trong account khác (kết hợp resource policy), hoặc người dùng mobile có credentials tạm từ Cognito identity pool.

2. Amazon Cognito user pool authorizer (COGNITO_USER_POOLS)

  • Tạo authorizer kiểu COGNITO_USER_POOLS trỏ tới user pool (có thể ở account khác), gắn vào method. Client đăng nhập user pool, nhận ID token hoặc access token (JWT), gửi trong header Authorization. API Gateway tự xác minh token – không cần viết code.
  • ID token: ủy quyền theo claim danh tính của user. Access token: ủy quyền theo custom scope (OAuth 2.0) của resource server.
  • Muốn user Cognito lấy credentials IAM tạm thời rồi gọi API bằng IAM ⇒ dùng identity pool + AWS_IAM (chi tiết Cognito ở Bài 7).
  • Với HTTP API: dùng JWT authorizer native (Cognito user pool hoặc bất kỳ OIDC/OAuth 2.0 provider nào).

3. Lambda authorizer (trước đây gọi là custom authorizer)

  • API Gateway gọi một Lambda function của bạn; function nhận danh tính của caller và trả về IAM policy (Allow/Deny execute-api:Invoke) cùng principal ID (và tùy chọn context để chuyển thông tin cho back end). Không trả đủ thông tin ⇒ request thất bại.
  • Dùng cho cơ chế xác thực tùy chỉnh / bên thứ ba: OAuth, SAML, token tự phát hành, tra credential trong database, logic dựa trên tham số request.
  • Hai kiểu:
    • TOKEN authorizer: nhận danh tính trong bearer token (JWT, OAuth token) ở một header; hỗ trợ regex validation token trước khi gọi Lambda.
    • REQUEST authorizer: nhận danh tính từ tổ hợp header, query string, stage variables, $context ⇒ policy chi tiết hơn. Tài liệu khuyến nghị dùng REQUEST.
  • Authorization caching: API Gateway cache policy trả về để không gọi lại Lambda cho các request sau cùng danh tính (cache key: header token với TOKEN; tổ hợp identity source với REQUEST) – giảm độ trễ và chi phí. Cần đảm bảo policy cache được áp dụng đúng cho mọi resource/method. TTL cache authorizer mặc định 300 giây, tối đa 3.600 giây (kiến thức phổ biến).
  • Kết quả: Deny ⇒ 403; token thiếu/không hợp lệ ⇒ 401 Unauthorized. Lambda authorizer có thể ở account khác với API.

4. Resource policy, VPC endpoint policy, WAF và các cơ chế khác

  • Resource policy (REST API): JSON policy gắn trên API, cho phép/từ chối gọi API từ: principal của account khác (cross-account), dải IP / CIDR nguồn (aws:SourceIp), VPC hoặc VPC endpoint (aws:SourceVpc, aws:SourceVpce). Bắt buộc với private API. Dùng chung với IAM policy theo logic identity-based + resource-based.
  • VPC endpoint policy: policy trên interface endpoint – giới hạn endpoint đó được gọi API nào.
  • AWS WAF: gắn web ACL vào stage REST API để chống khai thác web phổ biến (SQL injection, XSS), chặn IP/quốc gia, rate-based rule chống flood (Bài 39).
  • Mutual TLS: client phải trình certificate (REST & HTTP API, dùng custom domain). Client-side SSL certificate do API Gateway sinh: back end xác minh request thực sự đến từ API Gateway.
  • CORS: cấu hình để trình duyệt từ domain khác gọi được API (REST dùng mock integration cho OPTIONS; HTTP API cấu hình CORS trực tiếp).

Các kiến trúc serverless hay thi

Ghép API Gateway với Lambda, DynamoDB, S3, SQS, Step Functions, Cognito và CloudFront tạo ra các mẫu kiến trúc serverless: không quản lý máy chủ, tự scale, highly available (các dịch vụ đều chạy trên nhiều AZ của Region), trả tiền theo mức dùng.

Mẫu 1 – Web/mobile back end đồng bộ

CloudFront + S3 (static website: HTML/JS/ảnh) → API Gateway (REST/HTTP, authorizer Cognito) → Lambda → DynamoDB. Bổ sung: bật API caching cho đọc nhiều, DAX nếu cần microsecond, DynamoDB global tables + Regional API ở nhiều Region cho multi-Region.

Mẫu 2 – Nhận request rồi xử lý bất đồng bộ (buffer)

API Gateway dùng AWS service integration ghi thẳng request vào SQS (hoặc Kinesis Data Streams) và trả 200/202 ngay; Lambda đọc queue theo batch (event source mapping) và ghi vào database. Lợi ích: decouple, chịu được đột biến, không mất request khi back end chậm/lỗi, vượt giới hạn 29 giây.

Mẫu 3 – Quy trình nhiều bước

API Gateway → Step Functions StartExecution (Standard workflow cho quy trình dài, Express cho khối lượng lớn ngắn – Bài 31). Client nhận execution ARN và kiểm tra trạng thái sau.

Mẫu 4 – Upload file lớn

Client gọi API → Lambda sinh S3 presigned URL → client upload thẳng lên S3 (tránh giới hạn 10 MB payload API Gateway và 6 MB payload Lambda) → S3 event kích hoạt Lambda xử lý.

Tóm tắt ghi nhớ

Những điều phải thuộc
  • API Gateway = front door cho REST, HTTP, WebSocket API; cùng Lambda tạo phần app-facing của serverless. Resource → method → integration; deployment = snapshot, stage = tên tham chiếu tới deployment.
  • REST API: đủ tính năng – API key, usage plan, per-client throttling, caching, request validation, WAF, resource policy, private endpoint, edge-optimized, canary, X-Ray. HTTP API: rẻ hơn, tối giản, có JWT authorizer, automatic deployment, chỉ Regional. WebSocket: hai chiều, $connect/$disconnect/$default, @connections, 2 giờ / idle 10 phút.
  • Endpoint: edge-optimized (mặc định REST, qua CloudFront POP, client toàn cầu), Regional (client cùng Region, hoặc tự đặt CloudFront, multi-Region với Route 53), private (chỉ từ VPC qua interface endpoint execute-api + resource policy, chỉ REST).
  • Integration: AWS_PROXY (Lambda proxy – khuyến nghị), AWS (gọi thẳng SQS/DynamoDB/Kinesis/Step Functions), HTTP(_PROXY), MOCK; VPC link tới NLB/ALB private.
  • Throttling: token bucket; 10.000 RPS + burst 5.000 mỗi account mỗi Region; thứ tự: usage plan → stage/method → account → AWS Regional; vượt ⇒ 429. Integration timeout 29 giây (504), payload 10 MB.
  • Caching (REST): theo stage, TTL 300 s mặc định, tối đa 3.600 s, chỉ GET mặc định, response ≤ 1 MB, invalidate bằng Cache-Control: max-age=0 + execute-api:InvalidateCache, tính phí theo giờ.
  • Authorizer: IAM/SigV4 (caller có AWS credentials, cross-account), Cognito user pool (user app, không code), Lambda authorizer TOKEN/REQUEST (IdP bên thứ ba, logic tùy chỉnh, có cache). API key ≠ xác thực.

A partner company's applications run on Amazon EC2 instances in the partner's AWS account. They must call a REST API that a company hosts in Amazon API Gateway in its own account. Requests must be authenticated with AWS credentials, and only the partner account should be allowed to invoke the API. Which solution meets these requirements?
  1. Distribute an API key to the partner and attach it to a usage plan.
  2. Set the methods to use AWS_IAM authorization, add an API Gateway resource policy that allows execute-api:Invoke for the partner account, and have the partner's IAM role sign requests with SigV4.
  3. Create a Cognito user pool for the partner's EC2 instances and use a Cognito user pool authorizer.
  4. Change the API to a private API and share the VPC endpoint with the partner.
Đáp án B. Caller có AWS credentials (IAM role trên EC2) ⇒ IAM authorization, request ký SigV4. Truy cập cross-account cần cả resource policy trên API cho phép account đối tác và IAM policy execute-api:Invoke phía đối tác.
