Container trên AWS: bức tranh tổng thể

Một container đóng gói code ứng dụng cùng runtime, thư viện và cấu hình vào một container image (định dạng Docker hoặc OCI – Open Container Initiative). Image chạy giống hệt nhau trên laptop, máy chủ on-premises hay trên AWS. Khi có hàng chục, hàng trăm container, ta cần một container orchestrator để đặt container lên máy, khởi động lại khi lỗi, cân bằng tải và scale.

Trên AWS, bài toán container được chia thành ba câu hỏi độc lập – đề thi SAA-C03 thường xoay quanh việc trả lời đúng từng câu:

  1. Lưu image ở đâu? ⇒ Amazon ECR (registry được quản lý).
  2. Ai điều phối (orchestration)? ⇒ Amazon ECS (orchestrator riêng của AWS, đơn giản) hoặc Amazon EKS (Kubernetes được quản lý, chuẩn mở).
  3. Container chạy trên hạ tầng nào? ⇒ EC2 instance bạn tự quản lý, AWS Fargate (serverless), ECS Managed Instances / EKS Auto Mode (EC2 nhưng AWS vận hành), hoặc máy on-premises (ECS Anywhere, EKS Hybrid Nodes / EKS Anywhere).

Amazon ECS: cluster, task definition, task, service

Amazon Elastic Container Service (ECS) là dịch vụ container orchestration được quản lý hoàn toàn, giúp triển khai, quản lý và scale ứng dụng container. ECS đã có sẵn cấu hình và best practice vận hành của AWS, tích hợp với ECR, Elastic Load Balancing, CloudWatch, IAM và công cụ bên thứ ba như Docker. Bạn chạy workload trên nhiều Region, cả on-premises, mà không phải quản lý control plane.

Ba lớp của Amazon ECS (theo tài liệu)

  • Capacity: hạ tầng nơi container chạy – Amazon ECS Managed Instances, EC2 instance trong AWS Cloud, Fargate (serverless), hoặc VM/máy chủ on-premises (ECS Anywhere).
  • Controller: triển khai và quản lý ứng dụng chạy trong container – chính là Amazon ECS scheduler.
  • Provisioning: công cụ để làm việc với scheduler – Console, AWS CLI, AWS SDK, AWS CDK (CDK provision qua CloudFormation), cùng Copilot CLI, Terraform…

Task definition – những tham số đáng nhớ

  • requiresCompatibilities: khai báo task tương thích với EC2, FARGATE, EXTERNAL, MANAGED_INSTANCES – ECS kiểm tra task definition có hợp lệ cho loại capacity đó không.
  • cpu, memory: ở cấp task (bắt buộc với Fargate) và/hoặc cấp container.
  • networkMode: network mode:
    • awsvpc – mỗi task có một elastic network interface (ENI) riêng, IP private riêng trong VPC và security group riêng theo task. Fargate luôn dùng awsvpc. Target group của ALB/NLB phải chọn target type ip (không phải instance).
    • bridge – (EC2) container dùng mạng ảo Docker trong instance; kết hợp dynamic host port mapping để nhiều task cùng service chạy trên một instance sau ALB.
    • host – (EC2) container dùng thẳng mạng của instance; mỗi port chỉ một task/instance.
    • none – không có mạng ngoài.
  • taskRoleArn (quyền cho code trong container) và executionRoleArn (quyền cho agent kéo image, ghi log, lấy secret) – xem phần IAM.
  • logConfiguration: Fargate hỗ trợ log driver awslogs (CloudWatch Logs), splunk, awsfirelens (FireLens – chuyển log tới dịch vụ AWS/partner).
  • secrets: tham chiếu Secrets Manager secret hoặc SSM Parameter Store parameter – giá trị được inject thành biến môi trường lúc task khởi động, không ghi cứng trong image hay task definition.
  • volumes: bind mount (ephemeral), Amazon EFS (lưu trữ bền vững, chia sẻ giữa nhiều task, nhiều AZ), Amazon EBS volume gắn cho task.

ECS service – scheduler, load balancing, kết nối giữa service

  • Service scheduler thay task không healthy khi container health check hoặc health check của target group thất bại: khởi động task thay thế trước (nếu maximumPercent cho phép), rồi mới dừng task lỗi. Task lỗi khởi động liên tục thì scheduler giãn tần suất thử lại (service throttle logic) để không lãng phí tài nguyên.
  • Hai scheduling strategy: REPLICA (duy trì desired count, trải đều theo AZ – mặc định) và DAEMON (đúng một task trên mỗi container instance – dùng cho agent log/monitoring; không dùng được trên Fargate). (kiến thức phổ biến)
  • Load balancer cho service (service trên Fargate hỗ trợ cả ba loại):
    • ALB – lưu lượng HTTP/HTTPS (layer 7); một service có thể gắn nhiều target group; hỗ trợ dynamic host port mapping (nhiều task của cùng service trên một instance); path-based routing để nhiều service dùng chung một listener port.
    • NLB – TCP/UDP (layer 4); UDP trên Fargate cần platform version 1.4 trở lên.
    • GWLB – đưa lưu lượng qua virtual appliance (firewall, IDS/IPS).
  • Kết nối service-to-service không cần load balancer: Service Connect (tự khám phá bằng tên ngắn + port chuẩn), service discovery (dùng Route 53 / AWS Cloud Map tạo namespace DNS), Amazon VPC Lattice (kết nối, bảo mật, giám sát service xuyên account/VPC – có tính phí).
  • Triển khai phiên bản mới: rolling update (mặc định, điều khiển bằng minimumHealthyPercent / maximumPercent, thường 100% / 200%), blue/green (ECS native hoặc qua AWS CodeDeploy), deployment circuit breaker tự rollback khi task mới không lên được. (kiến thức phổ biến)
Mẹo thi (Exam Tip)
  • “Long-running web application / microservice must always have N copies running and be load balanced” ⇒ ECS service (+ ALB). “Batch job that runs and then exits” ⇒ ECS task (RunTask, kích hoạt bằng EventBridge).
  • “Multiple containers / microservices behind a single ALB, routed by URL path” ⇒ ALB path-based routing tới nhiều target group / service.
  • “Each task needs its own security group” hoặc “tasks need their own IP address in the VPC” ⇒ network mode awsvpc.
  • “Containers need shared persistent storage across AZs” ⇒ Amazon EFS volume trong task definition (Fargate cũng hỗ trợ).
  • “Pass database credentials to containers securely” ⇒ tham chiếu Secrets Manager / Parameter Store trong mục secrets của task definition (không đặt trong image/biến môi trường plain text).

EC2 launch type vs AWS Fargate và capacity provider

ECS có hai cách cấu hình capacity: launch type (EC2, Fargate, External) và capacity provider. Tài liệu nói rõ: capacity provider là cách được khuyến nghị; launch type nên chỉ dùng để khai báo tính tương thích (requiresCompatibilities) trong task definition.

AWS Fargate – serverless compute cho container

  • Fargate cho phép chạy container không phải provision, cấu hình hay scale cluster EC2: không chọn loại server, không quyết định khi nào scale cluster, không tối ưu “xếp” task lên máy (cluster packing).
  • Bạn chỉ: đóng gói container, khai báo CPU & memory cấp task, định nghĩa networking và IAM policy, rồi chạy.
  • Cô lập: mỗi task Fargate có ranh giới cô lập riêng, không chia sẻ kernel, CPU, memory hay ENI với task khác. Tài liệu khuyên: workload yêu cầu cô lập nghiêm ngặt ⇒ dùng Fargate.
  • OS/kiến trúc: Linux (x86_64 hoặc ARM64/Graviton), Windows Server 2019/2022 Full & Core (chỉ x86_64).
  • Platform version: tổ hợp kernel + container runtime (Linux 1.4.0, 1.3.0; Windows). Task mới luôn chạy trên revision mới nhất – đã vá bảo mật. Khi revision có lỗ hổng, AWS tạo revision mới và retire task chạy trên revision cũ (bạn có thể nhận thông báo task retirement).
  • Lưu trữ: bind mount (ephemeral), EFS (bền vững), EBS volume. Ephemeral storage mặc định 20 GiB, mở rộng tới 200 GiB (kiến thức phổ biến).
  • Không hỗ trợ trên Fargate: privileged container, gpu, placementConstraints, links, ipcMode, dockerSecurityOptions, disableNetworking… Linux capability duy nhất được thêm là CAP_SYS_PTRACE.
  • SOCI (Seekable OCI) lazy loading: với platform 1.4.0 và image trong ECR có SOCI index, container khởi động sau vài giây kéo image, phần còn lại tải nền – tài liệu khuyên thử với image > 250 MiB (nén).

So sánh các lựa chọn capacity của ECS

EC2 (Auto Scaling group capacity provider)

  • Bạn chọn instance type, số lượng, quản lý capacity, AMI (ECS-optimized AMI), patch OS.
  • Cần khi dùng GPU, instance đặc thù, privileged container, DAEMON service, kiểm soát sâu host.
  • Tối ưu chi phí bằng Reserved Instances / Savings Plans / Spot khi tải ổn định, mật độ task cao.
  • Nhiều task chia chung kernel instance ⇒ không có cô lập task mặc định.

Fargate / Fargate Spot

  • Serverless, trả tiền theo vCPU + memory của task trong thời gian chạy.
  • FARGATE và FARGATE_SPOT capacity provider được ECS tạo sẵn trên mọi cluster.
  • Fargate Spot: chạy task chịu được gián đoạn với giá giảm, trên capacity dư; khi AWS cần lại ⇒ task bị gián đoạn với cảnh báo 2 phút.
  • Cô lập mạnh mỗi task; ít vận hành nhất.

ECS Managed Instances

  • Chạy trên nhiều loại EC2 (GPU, kiến trúc CPU riêng, mạng hiệu năng cao…) nhưng AWS lo provisioning, patching, scaling, bảo trì.
  • “Kết hợp sự đơn giản của Fargate với sự linh hoạt của EC2”.
  • Chỉ dùng qua capacity provider strategy.

External (ECS Anywhere)

  • Đăng ký máy chủ / VM on-premises làm external instance của cluster ECS.
  • Dùng cùng control plane ECS cho hybrid; yêu cầu dữ liệu phải ở lại data center.

Capacity provider và capacity provider strategy

  • Capacity provider được hỗ trợ: FARGATE, FARGATE_SPOT, Auto Scaling group (EC2 tự quản), ECS Managed Instances. Spot Fleet chỉ có dưới dạng capacity provider, không phải launch type.
  • Capacity provider strategy gắn vào service/task để chia task giữa các provider bằng base (số task tối thiểu chạy trên một provider) và weight (tỉ lệ phân bổ phần còn lại) – vd FARGATE base=2, weight=1 + FARGATE_SPOT weight=3 ⇒ 2 task nền on-demand, phần còn lại 75% chạy Spot. (base/weight: kiến thức phổ biến)
  • Một cluster có thể chứa mọi loại capacity provider, nhưng một strategy không trộn được các loại khác nhau (vd không trộn Fargate với Auto Scaling group trong cùng strategy).
  • Đổi compute cho service chỉ cần cập nhật capacity provider strategy (vd từ ASG sang Fargate). Không chuyển trực tiếp từ EC2 launch type sang Fargate launch type – phải dùng capacity provider tương ứng.
  • Với Auto Scaling group capacity provider, bật managed scaling ⇒ ECS tự tăng/giảm số EC2 theo nhu cầu task (Cluster Auto Scaling), và managed termination protection để không tắt instance còn task. (chi tiết managed scaling: kiến thức phổ biến)

Mạng của task Fargate – kéo image từ ECR

  • Task ở public subnet: phải gán public IP cho ENI của task (assignPublicIp: ENABLED) và có route ra Internet Gateway thì mới kéo được image.
  • Task ở private subnet: cần NAT gateway, hoặc – tốt hơn về bảo mật và chi phí data processing – tạo interface VPC endpoint cho ECR (com.amazonaws.region.ecr.api và .ecr.dkr) cùng S3 gateway endpoint (layer image lưu trên S3); thêm endpoint logs nếu dùng awslogs, secretsmanager/ssm nếu dùng secrets.
  • Có thể giới hạn task execution role chỉ được kéo image qua một VPC endpoint cụ thể bằng điều kiện aws:SourceVpce / aws:SourceVpc.
Mẹo thi (Exam Tip)
  • “No EC2 instances to manage / patch”, “serverless containers” ⇒ Fargate. Cần GPU, privileged, kiểm soát AMI/host, tối ưu chi phí bằng RI ⇒ EC2 launch type / ASG capacity provider (hoặc ECS Managed Instances nếu muốn AWS vận hành host).
  • “Fault-tolerant / interruptible batch containers at lowest cost, serverless” ⇒ Fargate Spot; trộn base trên FARGATE + weight trên FARGATE_SPOT để vừa rẻ vừa luôn có tối thiểu task.
  • “Tasks in private subnets cannot pull images (CannotPullContainerError)” ⇒ thêm NAT gateway hoặc VPC endpoints cho ECR (api + dkr) và S3 gateway endpoint.
  • “Strict isolation between workloads” ⇒ Fargate (mỗi task không chia sẻ kernel).
Bẫy thường gặp
  • Tạo target group kiểu instance cho service Fargate ⇒ sai; task awsvpc gắn với ENI nên phải là ip.
  • Fargate không hỗ trợ GPU (trên cả ECS lẫn EKS), privileged container, DAEMON service. Đề đòi những thứ này mà chọn Fargate là sai.
  • Fargate Spot phù hợp tác vụ chịu được gián đoạn; không chọn cho service “must not be interrupted”. EKS không hỗ trợ Fargate Spot.

Task IAM role, task execution role và container instance role

Đây là chủ đề bảo mật container được hỏi nhiều nhất. ECS có ba loại role phục vụ ba “người dùng” khác nhau: code ứng dụng trong container, agent của ECS/Fargate, và EC2 instance chạy container.

Task IAM role – quyền cho code trong container

  • Task IAM role (taskRoleArn): quyền trong role được cấp cho các container trong task, để code ứng dụng gọi dịch vụ AWS khác (đọc S3, ghi DynamoDB, gửi SQS…). Tài liệu: “The task role is required when your application accesses other AWS services, such as Amazon S3.”
  • Role phải có trust policy cho principal ecs-tasks.amazonaws.com; nên thêm điều kiện aws:SourceAccount / aws:SourceArn để chống confused deputy.
  • AWS SDK/CLI trong container tự lấy credential tạm thời qua container credential provider (endpoint nội bộ 169.254.170.2) – không cần access key trong code. Khi task có task role, SDK dùng độc quyền credential của task role, không kế thừa quyền của EC2 instance.
  • Lợi ích theo tài liệu:
    • Separation of concerns: không phải nhét quyền của mọi ứng dụng vào instance profile của EC2.
    • Auditability: credential mang ngữ cảnh taskArn ⇒ CloudTrail cho biết task nào đã dùng role.
    • Uniform credentials delivery: cùng cơ chế trên EC2, Fargate, Managed Instances, ECS Anywhere. Trên Fargate không có instance profile cho container ⇒ task role là cách duy nhất.
  • Best practice: mỗi task definition / service một role với quyền tối thiểu (least privilege).

Task execution role – quyền cho ECS agent / Fargate agent

  • Task execution role (executionRoleArn) cấp quyền cho container agent và Fargate agent gọi API AWS thay mặt bạn để khởi động task. Container không truy cập trực tiếp được các quyền này.
  • Dùng khi task cần:
    • Kéo image từ ECR private (kể cả ECR ở account khác).
    • Gửi log tới CloudWatch Logs bằng log driver awslogs.
    • Lấy Secrets Manager secret / SSM Parameter Store parameter được tham chiếu trong task definition (secretsmanager:GetSecretValue, ssm:GetParameters, kms:Decrypt nếu dùng customer managed key).
    • Private registry authentication (Docker Hub, Quay.io… qua repositoryCredentials lưu trong Secrets Manager).
  • Managed policy: AmazonECSTaskExecutionRolePolicy; tên role thường là ecsTaskExecutionRole.

ECS Service Auto Scaling và Cluster Auto Scaling

Container cần scale ở hai tầng: Service Auto Scaling thay đổi số task (desired count), còn Cluster Auto Scaling thay đổi số EC2 instance để có chỗ đặt task. Với Fargate chỉ cần tầng thứ nhất – AWS lo phần capacity.

Service Auto Scaling – dùng Application Auto Scaling

ECS dùng dịch vụ Application Auto Scaling để tăng/giảm desired count. ECS gửi metric CPU và memory trung bình của service lên CloudWatch (chu kỳ 1 phút). Các kiểu scaling được hỗ trợ:

KiểuCách hoạt độngKhi nào dùng

Scheduled scalingĐổi min/max/desired theo ngày giờ.Tải theo lịch biết trước (giờ hành chính, sự kiện).

Những điểm cần nhớ (theo tài liệu)

  • Cooldown: scale-out liên tục nhưng không quá đà; scale-in thận trọng – bị chặn tới khi hết cooldown, nhưng nếu alarm khác yêu cầu scale-out trong lúc đó thì scale-out ngay.
  • Có scaling policy đang hoạt động thì Service Auto Scaling có thể ghi đè desired count bạn đặt tay.
  • Tính toán dựa trên số task đang chạy thực tế chứ không phải desired count – tránh “runaway scaling” khi cluster không đủ tài nguyên đặt task.
  • Muốn scale về 0 khi không có việc ⇒ đặt minimum capacity = 0.
  • Trong lúc deployment, Application Auto Scaling tắt scale-in nhưng vẫn scale-out (trừ khi bạn suspend).
Mẹo thi (Exam Tip)
  • “ECS service must scale based on CPU / number of requests” ⇒ Service Auto Scaling target tracking (ECSServiceAverageCPUUtilization / ALBRequestCountPerTarget).
  • “Workers consume from SQS; scale with queue depth” ⇒ target tracking trên backlog per task.
  • “Tasks stuck in PROVISIONING / not enough EC2 capacity” ⇒ dùng ASG capacity provider với managed scaling (Cluster Auto Scaling) hoặc chuyển sang Fargate.
  • Đừng nhầm: EC2 Auto Scaling (Bài 13) scale instance; Service Auto Scaling scale task.

Amazon EKS: Kubernetes được quản lý

Amazon Elastic Kubernetes Service (EKS) là dịch vụ Kubernetes được quản lý hoàn toàn, loại bỏ độ phức tạp khi vận hành cluster Kubernetes. EKS certified Kubernetes-conformant ⇒ ứng dụng Kubernetes chạy được mà không phải refactor, dùng được tooling cộng đồng (kubectl, Helm, Argo CD…). EKS chạy trên AWS Cloud và cả data center của bạn (EKS Anywhere, EKS Hybrid Nodes).

Control plane do AWS quản lý

  • Mỗi cluster có control plane riêng, không chia sẻ giữa cluster hay account.
  • Control plane có ít nhất 2 API server instance và 3 etcd instance trải trên 3 Availability Zone trong một Region. Instance lỗi được thay tự động (có thể sang AZ khác) ⇒ có SLA cho API server endpoint.
  • Control plane giao tiếp với worker node qua requester-managed ENI trong VPC của bạn.
  • Quyền truy cập: kết hợp IAM (ai được gọi Kubernetes API) và Kubernetes RBAC; workload lấy quyền AWS qua IAM roles for service accounts / EKS Pod Identity.
  • Giá: trả phí theo cluster (theo mức hỗ trợ phiên bản Kubernetes – standard / extended support), cộng tiền EC2, EBS, Fargate… cho worker node; EKS Auto Mode có phí riêng cho instance nó quản lý. Savings Plans áp dụng được cho compute của EKS.

  • “Pods need AWS permissions” ⇒ IAM roles for service accounts (IRSA) / EKS Pod Identity – không gán quyền vào node role.
  • “Run Kubernetes on-premises with AWS-managed control plane” ⇒ EKS Hybrid Nodes; “fully on-premises Kubernetes supported by AWS” ⇒ EKS Anywhere.
  • “Cost-optimize stateless EKS workloads” ⇒ Spot managed node group nhiều instance type (+ Karpenter).

Amazon ECR: kho container image

Amazon Elastic Container Registry (ECR) là container image registry được AWS quản lý – an toàn, có khả năng mở rộng và tin cậy. ECR hỗ trợ private repository với quyền dựa trên IAM (resource-based) và cả ECR Public; lưu Docker image, OCI image và artifact tương thích OCI. ECR được xem là “phần mở rộng” của ECS và EKS.

Khái niệm cơ bản

  • Private registry: mỗi account có một private registry mặc định (theo Region), URL https://aws_account_id.dkr.ecr.region.amazonaws.com.
  • Repository: chứa các image cùng tên với nhiều tag / digest. Kiểm soát bằng IAM policy (identity-based) và repository policy (resource-based – vd cho account khác pull).
  • Authentication: Docker CLI không hiểu IAM ⇒ dùng aws ecr get-login-password | docker login --username AWS ... hoặc ECR credential helper. Authorization token có hiệu lực 12 giờ, phạm vi quyền đúng bằng IAM principal đã lấy token.
  • Mã hóa at rest: mặc định AES-256 (SSE-S3), tùy chọn KMS khi tạo repository (kiến thức phổ biến). Tag immutability: chặn ghi đè tag (vd v1.2.0) – đảm bảo image đã deploy không bị thay ngầm.
  • Giá: trả theo dung lượng lưu trữ, data transfer khi push/pull, và các tính năng opt-in (signing, replication).

  • Basic scanning không quét package ngôn ngữ (npm, pip, Maven…) và không quét liên tục – cần enhanced scanning.

AWS App Runner và cách chọn dịch vụ compute cho container

AWS App Runner là cách “nhanh, đơn giản, tiết kiệm” để đưa source code hoặc container image thành web application có scale và bảo mật trên AWS – không cần học công nghệ mới, không cần chọn dịch vụ compute hay cấu hình tài nguyên.

  • App Runner kết nối trực tiếp tới code repository hoặc image repository (ECR), cung cấp pipeline tích hợp & triển khai tự động: mỗi commit mới hoặc image mới ⇒ tự deploy.
  • Fully managed: load balancing, TLS, auto scaling (bạn đặt số instance tối thiểu/tối đa và tải tối đa mỗi instance), scale xuống khi ít request ⇒ chỉ trả tiền tài nguyên dùng.
  • Lưu ý cập nhật (theo tài liệu): App Runner không còn mở cho khách hàng mới; khách hàng hiện tại vẫn dùng bình thường. AWS khuyến nghị khách hàng mới dùng Amazon ECS Express Mode. Đề SAA-C03 vẫn có thể nhắc App Runner với ý nghĩa “cách đơn giản nhất để chạy web app/API container mà không cần kiến thức hạ tầng”.

Tóm tắt ghi nhớ

Những điều phải thuộc
  • ECS: task definition (blueprint JSON, có revision) → task (bản chạy, batch) / service (duy trì desired count, thay task lỗi, sau ALB/NLB) → trong cluster. Ba lớp: capacity – controller – provisioning.
  • Fargate: serverless, mỗi task cô lập (không chia kernel/ENI), awsvpc bắt buộc ⇒ target type ip; 0,25–32 vCPU, tới 244 GB; không GPU, không privileged. Fargate Spot: rẻ, cảnh báo 2 phút (chỉ ECS).
  • Capacity provider là cách khuyến nghị: FARGATE, FARGATE_SPOT (có sẵn mọi cluster), ASG (managed scaling = Cluster Auto Scaling), ECS Managed Instances.
  • Task IAM role = quyền cho code ứng dụng; task execution role = quyền cho agent kéo ECR, ghi CloudWatch Logs, lấy secret (AmazonECSTaskExecutionRolePolicy); container instance role = EC2 đăng ký cluster. Container không phải ranh giới bảo mật.
  • Service Auto Scaling (Application Auto Scaling): target tracking, step, scheduled, predictive, SQS backlog per task; metric 1 phút; scale-in tắt trong lúc deploy.
  • EKS: control plane ≥ 2 API server + 3 etcd trên 3 AZ, phí theo cluster; compute: managed node groups (ASG do EKS quản lý, On-Demand/Spot, tự drain), self-managed, Fargate (profile, chỉ private subnet, không DaemonSet/EBS/GPU), Auto Mode, Karpenter, Hybrid Nodes. Pod lấy quyền qua IRSA / Pod Identity.
  • ECR: token 12 giờ; lifecycle policy (thực thi trong 24 giờ); basic scan (OS, manual/on push) vs enhanced (Inspector, OS + language, continuous); replication cross-Region/account (≤ 25 đích, < 30 phút, chỉ image mới); pull through cache; tag immutability.
  • Private subnet không NAT ⇒ endpoint ecr.api + ecr.dkr + S3 gateway (+ logs, secretsmanager).

The company does not want to provision, patch, or scale any Amazon EC2 instances, and it needs each container to be placed behind an Application Load Balancer with its own security group.
