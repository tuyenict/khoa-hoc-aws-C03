Bức tranh phân tích dữ liệu trên AWS: data lake và data warehouse

Đề SAA-C03 hiếm khi hỏi sâu cú pháp SQL, nhưng rất hay hỏi chọn đúng dịch vụ phân tích cho một tình huống: “truy vấn ad-hoc log trên S3 rẻ nhất”, “BI trên petabyte dữ liệu có cấu trúc”, “chạy Spark tùy biến”, “tìm kiếm full-text”, “dashboard cho lãnh đạo”, “cấp quyền theo cột cho từng nhóm”. Bài này giúp bạn ghép đúng từ khóa với dịch vụ.

Data lake và data warehouse

Data lake

  • Kho tập trung chứa dữ liệu có cấu trúc, bán cấu trúc và phi cấu trúc (CSV, JSON, log, Parquet, ảnh…) ở định dạng gốc.
  • Trên AWS: lưu ở Amazon S3 (rẻ, bền 11 số 9, gần như vô hạn), metadata trong Glue Data Catalog, quyền bằng Lake Formation.
  • Schema-on-read: định nghĩa schema lúc đọc; nhiều engine (Athena, EMR, Redshift Spectrum, Glue) cùng đọc một bản dữ liệu.
  • Hợp với khám phá dữ liệu, ML, truy vấn ad-hoc, lưu trữ lâu dài giá rẻ.

Data warehouse

  • Gom dữ liệu từ nhiều hệ thống (tồn kho, tài chính, bán lẻ…) về một định dạng chung và lưu lâu dài (theo tài liệu Athena).
  • Trên AWS: Amazon Redshift – dữ liệu được nạp (load) vào bảng có schema rõ ràng (schema-on-write).
  • Tối ưu cho truy vấn phức tạp, join nhiều bảng rất lớn, báo cáo BI từ dữ liệu lịch sử.
  • Đây là OLAP – khác với OLTP (RDS/Aurora/DynamoDB phục vụ giao dịch).

Ví dụ đời thường – thư viện thành phố

S3 data lake là kho sách khổng lồ, nhận đủ loại sách, báo, tài liệu photo. Glue crawler là thủ thư đi qua từng kệ và ghi phiếu mục lục; Glue Data Catalog là tủ phiếu mục lục (chỉ có thông tin về sách, không chứa sách).   • “Hadoop / Spark / Hive / HBase / Presto”, “custom big data processing with full control” ⇒ Amazon EMR.
  • “Discover schema”, “central metadata catalog”, “serverless ETL” ⇒ AWS Glue (crawler + Data Catalog + ETL job).

Amazon Athena: SQL serverless trên S3

Amazon Athena là dịch vụ interactive query giúp phân tích dữ liệu trực tiếp trong Amazon S3 bằng SQL chuẩn (ANSI SQL). Chỉ vài thao tác trên console: trỏ Athena vào dữ liệu S3, định nghĩa bảng và chạy truy vấn ad-hoc, có kết quả trong vài giây. Athena SQL và Apache Spark trên Athena đều serverless – không có hạ tầng để dựng hay quản lý, bạn chỉ trả tiền cho truy vấn đã chạy; Athena tự scale, chạy song song nên nhanh cả với dữ liệu lớn.

Đặc điểm chính (theo tài liệu)

  • Phân tích dữ liệu có cấu trúc, bán cấu trúc và phi cấu trúc trên S3: CSV, JSON, hoặc định dạng cột Apache Parquet / Apache ORC (cùng Avro, log text… qua SerDe). Không cần nạp (load) hay gom dữ liệu vào Athena.
  • Tích hợp AWS Glue Data Catalog làm kho metadata bền vững cho dữ liệu S3 – tạo bảng một lần, dùng chung cho cả account và với các tính năng ETL/khám phá dữ liệu của Glue. Catalog của Athena tương thích Hive metastore: nếu đã có Hive metastore trên EMR, có thể chạy DDL trên Athena và truy vấn ngay mà không ảnh hưởng job EMR.
  • Tích hợp Amazon QuickSight để trực quan hóa; kết nối công cụ BI / SQL client qua JDBC / ODBC.
  • Ví dụ tài liệu nêu: chạy truy vấn nhanh trên web log để điều tra vấn đề hiệu năng của website.
  • Kết quả truy vấn được ghi vào một S3 query result location (cấu hình theo workgroup).
  • Giá: tính theo lượng dữ liệu quét mỗi truy vấn – khoảng 5 USD/TB ở nhiều Region, làm tròn lên tối thiểu 10 MB mỗi truy vấn. (con số giá: kiến thức phổ biến, xem trang Athena pricing). Vì vậy mọi kỹ thuật giảm dữ liệu quét = giảm tiền và tăng tốc.

Tối ưu chi phí & hiệu năng: partition + định dạng cột

1. Partitioning – chia dữ liệu theo khóa bất kỳ, phổ biến nhất là thời gian (year/month/day/hour) hoặc nguồn dữ liệu + ngày. Khi truy vấn có điều kiện partition trong WHERE, Athena chỉ quét dữ liệu của partition đó.

  • Hive-style partition: đường dẫn chứa cặp key=value, ví dụ s3://bucket/logs/year=2026/month=10/day=31/. Nạp partition mới vào bảng bằng MSCK REPAIR TABLE (chỉ chạy được với Hive-style; đường dẫn S3 nên viết chữ thường).
  • Non-Hive style (vd log CloudTrail, Firehose: data/2026/10/31/…) ⇒ thêm thủ công bằng ALTER TABLE ADD PARTITION.
  • Partition projection: với bảng có rất nhiều partition mà cấu trúc biết trước, Athena tính giá trị và vị trí partition từ thuộc tính bảng (trong bộ nhớ) thay vì tra metastore ⇒ giảm đáng kể thời gian truy vấn, khỏi phải quản lý partition.
  • Dữ liệu không partition + bucket rất nhiều object có thể chạm giới hạn GET request rate của S3 ⇒ lỗi S3 – partition dữ liệu để tránh. Athena hỗ trợ bảng Glue tới 10 triệu partition nhưng một lần quét đọc tối đa 1 triệu partition (dùng partition index).

2. Columnar storage format – Apache Parquet và ORC được tối ưu để truy xuất nhanh, có ba đặc tính khiến chúng hợp với Athena:

  1. Nén theo từng cột, thuật toán nén chọn theo kiểu dữ liệu của cột ⇒ tiết kiệm dung lượng S3, giảm I/O khi truy vấn.
  2. Predicate pushdown: Athena dùng thống kê của từng block (giá trị min/max) để quyết định đọc hay bỏ qua block ⇒ chỉ lấy block cần thiết.
  3. Splitting: chia việc đọc file cho nhiều reader ⇒ tăng song song.

Thêm vào đó, truy vấn chỉ chọn vài cột (SELECT col1, col2) thì Athena chỉ đọc các cột đó, không phải cả dòng như CSV/JSON.

Workgroup – tách tải, phân quyền, kiểm soát chi phí

  • Workgroup là tài nguyên IAM: dùng policy để quy định ai được chạy truy vấn trong workgroup nào; mỗi workgroup có lịch sử truy vấn và saved query riêng ⇒ tách team A / team B, hay báo cáo tự động / ad-hoc.
  • Enforce cấu hình cho mọi truy vấn: vị trí kết quả trên S3, expected bucket owner, mã hóa kết quả.
  • Data usage controls: per-query (truy vấn quét quá ngưỡng sẽ bị hủy) và per-workgroup (vượt ngưỡng theo giờ/ngày… ⇒ bắn SNS alarm).
  • Đẩy metric truy vấn lên CloudWatch, sự kiện trạng thái truy vấn lên EventBridge, gắn cost allocation tag; dùng capacity reservation (số DPU cố định) khi cần năng lực ổn định.
  • Mỗi account có workgroup primary (không xóa được); tối đa 1.000 workgroup/Region.

Athena Federated Query – SQL trên dữ liệu ngoài S3

  • Dùng data source connector để chạy SQL tại chỗ (query in place) trên nguồn quan hệ, NoSQL, object, tùy biến – ví dụ DynamoDB, Redshift, RDS MySQL/PostgreSQL, SQL Server, Oracle, DocumentDB, OpenSearch, CloudWatch Logs/Metrics, Timestream, MSK/Kafka, Redis, Google BigQuery, Snowflake, Teradata…
  • Athena gọi connector để xác định dữ liệu cần đọc, quản lý song song và đẩy điều kiện lọc xuống nguồn. Connector kiểu Athena data catalog chạy dưới dạng AWS Lambda function trong account của bạn (connector tùy biến viết bằng Athena Query Federation SDK); loại Glue Data Catalog federated connector dùng Glue connection và hỗ trợ quyền chi tiết qua Lake Formation.
  • Có thể dùng để join dữ liệu nhiều nguồn trong một câu SQL, hoặc dựng pipeline trích xuất dữ liệu nhiều nguồn và lưu vào S3. Không hỗ trợ ghi (INSERT INTO) vào nguồn federated.
Mẹo thi (Exam Tip)
  • “Reduce Athena query cost / improve performance” ⇒ chuyển sang Parquet/ORC + nén + partition theo cột hay lọc (thường là ngày) + gộp file nhỏ. Tăng “instance size” không phải là đáp án – Athena serverless.
  • “Analyze VPC Flow Logs / CloudTrail / ALB access logs stored in S3 with SQL, occasionally” ⇒ Athena (rẻ nhất, không cần cluster).
  • “Run SQL across S3 and DynamoDB / RDS without moving data” ⇒ Athena Federated Query.
  • “Limit how much data each team can scan”, “separate query history per team” ⇒ Athena workgroups với data usage controls.
  • “New partitions not showing in query results” ⇒ chạy MSCK REPAIR TABLE / ALTER TABLE ADD PARTITION, chạy lại crawler, hoặc dùng partition projection.
Bẫy thường gặp
  • Athena không phải database lưu dữ liệu – dữ liệu vẫn nằm trong S3; bảng Athena chỉ là metadata. Xóa bảng không xóa dữ liệu S3 (external table).
  • Athena hợp với truy vấn ad-hoc / tương tác; còn báo cáo BI phức tạp chạy liên tục, nhiều người dùng đồng thời, join rất nhiều bảng lớn ⇒ Redshift thường là lựa chọn tốt hơn.
  • Mỗi bảng Athena tương ứng một S3 prefix; để nhiều schema khác nhau dưới cùng prefix ⇒ truy vấn trả 0 kết quả hoặc lỗi. Mỗi bảng một prefix riêng.

AWS Glue: Data Catalog, crawler, ETL job

AWS Glue là dịch vụ data integration serverless giúp khám phá, chuẩn bị, di chuyển và tích hợp dữ liệu từ nhiều nguồn cho analytics, ML và phát triển ứng dụng. Glue kết nối hơn 70 nguồn dữ liệu, quản lý dữ liệu trong một data catalog tập trung, cho phép dựng – chạy – giám sát pipeline ETL trực quan để nạp vào data lake; dữ liệu đã lập danh mục có thể truy vấn ngay bằng Athena, EMR, Redshift Spectrum. Glue hỗ trợ ETL, ELT và streaming, có sẵn high availability, tính tiền pay-as-you-go.

Crawler xác định bảng và partition thế nào?

  • Bạn chỉ định Include path. Nếu phần lớn schema ở một cấp thư mục giống nhau, crawler tạo một bảng với nhiều partition thay vì nhiều bảng. Ví dụ s3://sales/year=2019/month=Jan/day=1… ⇒ 1 bảng sales với partition key year, month, day.
  • Muốn tách thành bảng riêng ⇒ khai báo mỗi thư mục gốc của bảng là một data store riêng trong crawler.
  • Crawler có thể chạy theo lịch; lần chạy sau chỉ bổ sung bảng/partition mới hoặc đã thay đổi. File nén nguyên khối (gzip) phải được tải về để đọc.
  • Với nguồn streaming (Kinesis, Kafka) thì định nghĩa bảng thủ công, không dùng crawler.

Job bookmark – xử lý tăng dần (incremental)

Job bookmark lưu trạng thái của lần chạy trước để không xử lý lại dữ liệu cũ – chạy job theo lịch thì chỉ xử lý dữ liệu mới, tránh trùng lặp ở đích. Áp dụng cho nguồn JDBC, transform Relationalize và một số nguồn S3 (JSON, CSV, Avro, XML, và Parquet/ORC từ Glue 1.0).

  • Với S3, bookmark dựa trên last modified time của object; với JDBC, dựa trên bookmark key (mặc định primary key tăng/giảm tuần tự).
  • Có thể rewind về lần chạy trước hoặc reset (aws glue reset-job-bookmark) để xử lý lại toàn bộ; Glue không xóa file đích khi rewind/reset.

Các tính năng khác hay xuất hiện

  • AWS Glue Studio – giao diện đồ họa (visual job editor) để kéo-thả luồng biến đổi, Glue tự sinh code và chạy trên engine Spark serverless.
  • AWS Glue DataBrew – công cụ chuẩn bị dữ liệu trực quan, không cần viết code để làm sạch và chuẩn hóa dữ liệu (dành cho analyst/data scientist).
  • FindMatches – ML có sẵn để khử trùng lặp và tìm bản ghi “gần giống nhau” mà không cần là chuyên gia ML.
  • Sensitive data detection – định nghĩa, phát hiện và xử lý dữ liệu nhạy cảm (PII) trong pipeline và data lake.
  • Streaming ETL – làm sạch/biến đổi dữ liệu streaming “in transit”, sẵn sàng phân tích trong vài giây.
  • AWS Glue Data Quality – kiểm tra chất lượng dữ liệu bằng rule (kiến thức phổ biến).
  • Engine chạy job: Spark (chính) và Python shell; Glue for Ray đã kết thúc hỗ trợ. Giám sát bằng job run insights, CloudTrail, Spark UI.
Mẹo thi (Exam Tip)
  • “Automatically discover the schema of data in S3 and make it queryable by Athena” ⇒ Glue crawler → Glue Data Catalog → Athena.
  • “Convert CSV/JSON in S3 to Parquet on a schedule, serverless” ⇒ Glue ETL job (hoặc Athena CTAS cho việc một lần; Firehose nếu dữ liệu đang streaming).
  • “ETL job reprocesses old files on every run” ⇒ bật job bookmark.
  • “Business analysts need to clean and normalize data without writing code” ⇒ Glue DataBrew.
  • “Replace self-managed Hive metastore” / “shared metadata for Athena, EMR and Redshift Spectrum” ⇒ Glue Data Catalog.
Bẫy thường gặp
  • Glue Data Catalog không lưu dữ liệu và không phải nơi chạy truy vấn – cần engine (Athena/EMR/Redshift Spectrum) để truy vấn.
  • Glue ETL là batch/micro-batch Spark: khởi động mất thời gian, không thay thế được Lambda cho xử lý từng sự kiện mili-giây; cũng không phải dịch vụ “real-time stream analytics” như Managed Service for Apache Flink.
  • Glue (serverless, tính theo DPU-giờ) và EMR (cluster, toàn quyền cấu hình) đều chạy Spark: đề nhấn “least operational overhead / serverless ETL” ⇒ Glue; nhấn “full control, custom frameworks, HBase, Presto…” ⇒ EMR.

AWS Lake Formation: quản trị và phân quyền data lake

AWS Lake Formation giúp quản trị tập trung, bảo mật và chia sẻ dữ liệu cho analytics và ML. Lake Formation quản lý fine-grained access control cho dữ liệu data lake trên S3 và metadata của nó trong Glue Data Catalog. Nó có mô hình quyền riêng bổ sung cho IAM: cơ chế grant / revoke đơn giản giống RDBMS, thực thi ở mức cột, hàng và ô trên các dịch vụ Athena, QuickSight, Redshift Spectrum, EMR, Glue. Theo tài liệu, quyền Lake Formation dễ quản lý thay cho tổ hợp S3 bucket policy + IAM policy phức tạp.

Tính năng chính

  • Nhập dữ liệu: đọc dữ liệu và schema từ MySQL, PostgreSQL, SQL Server, MariaDB, Oracle chạy trên RDS hoặc EC2, cũng như on-premises qua JDBC; hỗ trợ nạp bulk và incremental vào data lake (dùng các mẫu blueprint / workflow dựng trên Glue – tên “blueprint”: kiến thức phổ biến). Nguồn khác ⇒ viết Glue ETL job.
  • Lập danh mục: dùng Glue crawler; quản lý quyền theo tag (LF-TBAC).
  • Quyền ở mức database, bảng, cột, hàng, ô – áp dụng cho IAM user/role và user/group federated từ IdP ngoài (SAML).
  • Data filters: giới hạn truy cập theo tổ hợp cột + hàng ⇒ row-level và cell-level security để bảo vệ PII.
  • LF-Tags (LF-TBAC): gắn nhãn tùy biến lên database/bảng/cột (vd classification=confidential, domain=sales) rồi cấp quyền theo tag ⇒ thay hàng nghìn policy trên từng tài nguyên bằng vài tag logic; cách được khuyến nghị để scale quản trị.
  • Hybrid access mode: bật quyền Lake Formation dần dần cho một số database/bảng/người dùng mà không phá vỡ IAM/S3 policy hiện có của workload khác.
  • Audit: log truy cập dữ liệu đầy đủ qua CloudTrail – ai, truy cập dữ liệu nào, bằng dịch vụ nào, khi nào.
  • Federated catalog: đưa dữ liệu Redshift, DynamoDB, nguồn ngoài (BigQuery, MySQL…), S3 Tables vào Data Catalog để quản lý quyền tập trung mà không cần di chuyển dữ liệu.

Luồng kiểm tra quyền – credential vending

Chia sẻ cross-account

  • Chia sẻ database, bảng (có lọc cột), nhiều bảng hoặc “All Tables” cho account khác, Organization/OU, hoặc IAM principal ở account khác – vẫn giữ bảo vệ mức bảng/cột.
  • Lake Formation dùng AWS Resource Access Manager (RAM) để share. Cùng Organization ⇒ có hiệu lực ngay; khác Organization ⇒ RAM gửi lời mời, data lake admin bên nhận phải chấp nhận.
  • Hai phương pháp: LF-TBAC (khuyến nghị) và named resource. Athena và Redshift Spectrum bên nhận cần tạo resource link để đưa tài nguyên được chia sẻ vào truy vấn.
  • Mô hình phổ biến: một account “data lake” trung tâm, nhiều account “consumer” (phòng ban) truy vấn qua Lake Formation – không sao chép dữ liệu.
Mẹo thi (Exam Tip)
  • “Analysts may only see certain columns (e.g., hide PII) / rows (e.g., only their region) of tables in the S3 data lake, queried by Athena” ⇒ Lake Formation (column-level / data filters cho row & cell-level).
  • “Centrally manage permissions for thousands of tables” ⇒ LF-Tags (tag-based access control).
  • “Share Data Catalog tables with other accounts without copying data” ⇒ Lake Formation cross-account (dùng RAM), bên nhận tạo resource link.
  • “Build a secure data lake quickly, ingest from RDS” ⇒ Lake Formation (dựng trên Glue + S3).
Bẫy thường gặp
  • Lake Formation không phải nơi lưu dữ liệu riêng: dữ liệu vẫn ở S3, metadata vẫn ở Glue Data Catalog – Lake Formation là lớp phân quyền (authorization layer) phía trên.
  • IAM / S3 bucket policy chỉ kiểm soát được tới mức object/prefix; không thể ẩn một cột trong file Parquet – yêu cầu “column-level” trên data lake ⇒ Lake Formation (hoặc tách dữ liệu ra nhiều bảng, tốn công hơn).

Amazon Redshift: data warehouse, Serverless và Redshift Spectrum

Amazon Redshift là dịch vụ data warehouse fully managed, quy mô petabyte trên cloud. Bất kể kích thước dataset, Redshift cho hiệu năng truy vấn nhanh bằng chính các công cụ SQL và ứng dụng BI bạn đang dùng (JDBC/ODBC, query editor v2, Data API). Theo tài liệu Athena: chọn Redshift khi cần gom dữ liệu từ nhiều nguồn về định dạng chung, lưu lâu dài, dựng báo cáo nghiệp vụ phức tạp từ dữ liệu lịch sử, và chạy truy vấn có rất nhiều join giữa các bảng rất lớn trên dữ liệu có cấu trúc cao.

Kiến trúc provisioned cluster

  • Cluster gồm các node; mỗi cluster có một leader node và một hoặc nhiều compute node, chạy một Redshift engine và chứa một hoặc nhiều database.
  • Leader node: nhận truy vấn từ client, parse, lập kế hoạch thực thi, điều phối chạy song song trên compute node, tổng hợp kết quả trung gian rồi trả cho client. Bạn chỉ trả tiền compute node.
  • Compute node: chạy kế hoạch thực thi, trao đổi dữ liệu với nhau; mỗi compute node được chia thành nhiều slice (vd ra3.4xlarge: 4 slice/node). Đây là kiến trúc MPP + lưu trữ dạng cột (thuật ngữ MPP/columnar: kiến thức phổ biến).
  • Cluster single-node: leader và compute dùng chung một node – không khuyến nghị cho production. Cluster có ≥ 2 compute node thì dữ liệu mỗi node được mirror lên đĩa node khác để giảm rủi ro mất dữ liệu.
  • Cluster chạy trong VPC (cần cluster subnet group), kiểm soát truy cập bằng security group; có thể pause cluster (chỉ trả tiền backup storage), mua reserved node cho tải ổn định.

Amazon Redshift Serverless

  • Truy cập và phân tích dữ liệu không cần dựng, tinh chỉnh, quản lý cluster; tài nguyên được tự provision và capacity tự scale trong vài giây cho tải biến động/khó đoán.
  • Không tính phí khi data warehouse rảnh (idle) – chỉ trả khi đang dùng. Capacity đo bằng RPU (Redshift Processing Unit), tính theo giây (RPU: kiến thức phổ biến).
  • Tổ chức bằng namespace (database, user, dữ liệu) và workgroup (tài nguyên compute) ⇒ kiểm soát chi phí chi tiết. Backup: snapshot thủ công + recovery point tự động; có thể restore snapshot của provisioned cluster vào namespace serverless.

Nạp dữ liệu vào Redshift

  • Lệnh COPY từ S3 (song song, nhanh nhất cho batch), DynamoDB, EMR… – cũng là cách Amazon Data Firehose giao dữ liệu vào Redshift (ghi S3 rồi COPY – Bài 35). Ngược lại UNLOAD xuất kết quả ra S3 (UNLOAD: kiến thức phổ biến).
  • Streaming ingestion trực tiếp từ Kinesis Data Streams / MSK; zero-ETL integration từ Aurora/RDS/DynamoDB sang Redshift gần thời gian thực mà không cần tự dựng pipeline (zero-ETL: kiến thức phổ biến).
  • Glue ETL job ghi trực tiếp vào bảng Redshift; QuickSight và công cụ BI đọc từ Redshift.

Redshift Spectrum

  • Truy vấn hiệu quả dữ liệu có cấu trúc và bán cấu trúc trong file S3 mà không cần nạp vào bảng Redshift. Phần lớn xử lý diễn ra ở tầng Spectrum – các server Redshift chuyên dụng, độc lập với cluster; Redshift đẩy xuống các tác vụ nặng như lọc điều kiện và aggregation ⇒ ít tốn năng lực cluster; Spectrum có thể dùng hàng nghìn instance chạy song song.
  • Định nghĩa external schema / external table trong external data catalog: AWS Glue Data Catalog, catalog của Athena, hoặc Apache Hive metastore của bạn. Thay đổi catalog có hiệu lực ngay với mọi cluster.
  • Join bảng Spectrum với bảng Redshift cục bộ như bảng thường ⇒ mô hình “dữ liệu nóng trong Redshift, dữ liệu lịch sử lạnh trong S3”.
  • Nhiều cluster cùng truy vấn một dataset S3 mà không phải sao chép cho từng cluster – nhưng cluster và bucket S3 phải ở cùng Region.
  • Không hỗ trợ UPDATE trên external table; partition external table để tối ưu (optimizer bỏ qua partition không liên quan); có thể tạo materialized view trên bảng Spectrum. Tính phí theo dữ liệu quét (giống Athena – kiến thức phổ biến).
  • Lưu ý cập nhật: RA3/DC2 dùng Spectrum (fleet ngoài cluster); RG và Redshift Serverless có engine truy vấn data lake tích hợp chạy trên compute của chính chúng.

Scale, hiệu năng và khả năng phục hồi

  • Concurrency scaling: khi bật trên một WLM queue, Redshift tự thêm capacity cluster tạm để xử lý cả truy vấn đọc (dashboard) lẫn nhiều truy vấn ghi phổ biến (COPY, INSERT, DELETE, UPDATE, CTAS…) ⇒ hỗ trợ hàng nghìn user/truy vấn đồng thời, người dùng vẫn thấy dữ liệu mới nhất. Chỉ tính phí khi cluster concurrency-scaling đang chạy truy vấn (mỗi cluster tích lũy ~1 giờ credit miễn phí mỗi ngày – kiến thức phổ biến).
  • Elastic resize / classic resize để thêm bớt node hoặc đổi node type.
  • Snapshot: lưu trong S3 do Redshift quản lý, incremental. Automated: mặc định khoảng 8 giờ một lần hoặc mỗi 5 GB/node dữ liệu thay đổi (cái nào trước), retention mặc định 1 ngày, RA3/RG đặt 1–35 ngày (không tắt được). Manual: giữ vô thời hạn (kể cả khi xóa cluster) trừ khi đặt retention. Restore luôn tạo cluster mới, truy vấn được ngay trong khi dữ liệu tải nền. Tích hợp AWS Backup.
  • Cross-Region snapshot copy (tự sao snapshot sang Region khác cho DR; cluster mã hóa KMS cần snapshot copy grant) và tùy chọn Multi-AZ cho RA3 (kiến thức phổ biến).
  • Single-node gặp hardware failure thì không thay được node – phải restore snapshot.

Bẫy thường gặp

  • Redshift Spectrum cần một Redshift cluster (hoặc Serverless) – nếu đề không có Redshift và chỉ cần truy vấn ad-hoc S3 thì Athena rẻ và ít vận hành hơn.

Amazon EMR: Hadoop, Spark và big data có toàn quyền kiểm soát

Amazon EMR (tên cũ Elastic MapReduce) là nền tảng managed cluster giúp chạy các framework big data như Apache Hadoop và Apache Spark trên AWS để xử lý và phân tích lượng dữ liệu khổng lồ, đồng thời biến đổi và di chuyển dữ liệu lớn vào/ra S3, DynamoDB… Theo tài liệu Athena: dùng EMR khi chạy code tùy biến trên dataset cực lớn với Spark, Hadoop, Presto, HBase – ML, graph analytics, biến đổi dữ liệu, streaming… và cần toàn quyền cấu hình cluster và phần mềm cài trên đó.

Tầng lưu trữ

  • HDFS: hệ thống tệp phân tán, nhân bản dữ liệu trên nhiều instance – nhưng là ephemeral, bị thu hồi khi terminate cluster. Hợp cho cache kết quả trung gian, workload random I/O.
  • EMRFS / S3A (mặc định từ EMR 7.10): truy cập S3 như file system. Thực hành phổ biến: input/output ở S3, kết quả trung gian ở HDFS ⇒ dữ liệu bền vững độc lập với vòng đời cluster.
  • Local file system: instance store – chỉ tồn tại theo vòng đời EC2 instance.
  • Quản lý tài nguyên: YARN; framework xử lý: Hadoop MapReduce, Spark (in-memory, DAG); ứng dụng: Hive, Pig, Spark SQL/Streaming, MLlib, HBase, Presto/Trino, Flink…

Gửi việc và vòng đời cluster

  • Gửi việc bằng step (đơn vị công việc theo thứ tự: PENDING → RUNNING → COMPLETED; step lỗi ⇒ mặc định các step sau CANCELLED), hoặc SSH vào primary node dùng trực tiếp Spark/Hive…
  • Vòng đời: STARTING → BOOTSTRAPPING → RUNNING → WAITING → TERMINATING → TERMINATED (lỗi ⇒ TERMINATED_WITH_ERRORS, dữ liệu trên cluster bị xóa trừ khi bật termination protection).
  • Transient cluster: định nghĩa sẵn step, auto-terminate khi xong ⇒ tiết kiệm. Long-running cluster: chờ (WAITING) nhận thêm step / truy vấn tương tác, phải tự tắt.

Các tùy chọn triển khai

EMR on EC2

  • Toàn quyền: instance type, Spot, bootstrap action, SSH.
  • Tự chọn sizing, managed scaling.
  • Hợp với cluster lớn, ứng dụng đa dạng (HBase, Presto…).

EMR Serverless

  • Không cấu hình, tối ưu, bảo mật hay vận hành cluster; chạy Spark / Hive.
  • Tự xác định tài nguyên cho job, cấp phát rồi giải phóng khi job xong – tránh over/under-provision.
  • Pre-initialized capacity: “warm pool” worker để job khởi động trong vài giây.
  • Application → job run (mỗi job một runtime role IAM); nhiều AZ trong Region.

EMR on EKS

  • Chạy Spark job trên cluster EKS sẵn có, dùng chung hạ tầng Kubernetes với ứng dụng khác (kiến thức phổ biến).
Mẹo thi (Exam Tip)
  • “Migrate on-premises Hadoop / Spark / Hive jobs to AWS with minimal changes” ⇒ Amazon EMR.
  • “Reduce EMR cost for batch jobs” ⇒ Spot cho task node, On-Demand/Reserved cho primary & core; dữ liệu trên S3 (EMRFS); transient cluster tự terminate.
  • “Run Spark without managing clusters” ⇒ EMR Serverless (hoặc Glue nếu là ETL đơn giản).
  • “Data must persist after the cluster terminates” ⇒ lưu ở S3, không phải HDFS.
Bẫy thường gặp
  • Đặt core node trên Spot là rủi ro: Spot bị thu hồi ⇒ mất block HDFS và có thể làm job lỗi. Đáp án tối ưu chi phí an toàn là Spot cho task node.
  • EMR là cluster bạn phải chọn cấu hình – đề hỏi “least operational overhead” cho SQL đơn giản trên S3 thì Athena thắng EMR.

Amazon OpenSearch Service: tìm kiếm và log analytics

Amazon OpenSearch Service là dịch vụ managed giúp triển khai, vận hành và scale cluster OpenSearch – engine tìm kiếm và phân tích mã nguồn mở dùng cho log analytics, giám sát ứng dụng thời gian thực, clickstream và full-text search. Dịch vụ hỗ trợ OpenSearch và Elasticsearch OSS cũ (tới 7.10, bản mã nguồn mở cuối cùng) – vì thế tên cũ là Amazon Elasticsearch Service. AWS provision mọi tài nguyên, tự phát hiện và thay node hỏng, scale bằng một lệnh API.

Khái niệm và tính năng (theo tài liệu)

  • Domain = một cluster OpenSearch với instance type, số instance, storage do bạn chỉ định; mỗi EC2 instance là một node.
  • Scale: nhiều instance type (có Graviton), tới 1.002 data node, tới 25 PB storage gắn kèm.
  • Stability: phân bổ node trên 2 hoặc 3 AZ (Multi-AZ, có biến thể Multi-AZ with Standby); dedicated master node gánh việc quản lý cluster; automated snapshot để backup/restore.
  • Security: IAM access control, đặt domain trong VPC với security group, mã hóa at rest và node-to-node, xác thực OpenSearch Dashboards bằng Amazon Cognito, HTTP basic hoặc SAML; bảo mật mức index, document, field (fine-grained access control); audit log.
  • Tích hợp: OpenSearch Dashboards để trực quan; CloudWatch metric/alarm; CloudTrail; nạp dữ liệu streaming từ S3, Kinesis Data Streams, Data Firehose, DynamoDB (thường qua Lambda), CloudWatch Logs subscription; cảnh báo qua SNS; SQL cho công cụ BI.
  • Giá: theo giờ instance + dung lượng EBS; không tính phí truyền dữ liệu giữa các AZ trong domain Multi-AZ và giữa UltraWarm/cold với S3.

Amazon OpenSearch Serverless

  • Tùy chọn on-demand, serverless: không provision/cấu hình/tinh chỉnh cluster. Đơn vị là collection, chọn loại khi tạo (không đổi được): Time series (log analytics), Search (full-text), Vector search (semantic search, generative AI/RAG).
  • Kiến trúc tách indexing và search, lưu index trên S3 ⇒ scale ingest và query độc lập. Capacity đo bằng OCU – mỗi OCU = 6 GiB RAM + vCPU tương ứng; tự tăng/giảm trong giới hạn bạn đặt.
  • Giới hạn: không hỗ trợ cross-account access cho collection, không cross-Region search/replication, không plugin tùy biến; refresh interval ~10 giây; TLS 1.2 bắt buộc.
Ví dụ đời thường – mục lục cuối sách

CSDL như DynamoDB giống tra theo số trang (biết key là lấy ngay). OpenSearch giống mục lục chỉ mục từ khóa ở cuối sách (inverted index): gõ “áo khoác len đỏ” là ra mọi trang có các từ đó, xếp theo mức liên quan. Vì vậy mẫu kiến trúc phổ biến là DynamoDB lưu dữ liệu chính + DynamoDB Streams → Lambda → OpenSearch để có ô tìm kiếm full-text.

Mẹo thi (Exam Tip)
  • “Full-text search / fuzzy search / search box for product catalog” ⇒ OpenSearch Service (thường kèm DynamoDB/RDS là nguồn dữ liệu chính).
  • “Centralize logs (CloudWatch Logs, VPC Flow Logs, application logs) and visualize them in near real time” ⇒ Firehose / CloudWatch Logs subscription → OpenSearch + OpenSearch Dashboards.
  • “Retain months of logs in OpenSearch cost-effectively, still searchable” ⇒ UltraWarm (+ cold storage cho dữ liệu cũ hơn).
  • “Secure OpenSearch Dashboards login” ⇒ Amazon Cognito / SAML; “private access” ⇒ domain trong VPC.
  • “Avoid managing OpenSearch clusters”, “vector search for generative AI” ⇒ OpenSearch Serverless.
Bẫy thường gặp
  • OpenSearch không phải CSDL giao dịch chính (không ACID, không thay RDS/DynamoDB) – nó là index để tìm kiếm/phân tích.
  • Đề nhắc “Elasticsearch” hay “ELK stack” ⇒ chính là OpenSearch Service; “Kibana” ⇒ OpenSearch Dashboards.
  • Truy vấn SQL ad-hoc trên log lưu ở S3, không cần tìm kiếm full-text, không cần dashboard thời gian thực ⇒ Athena rẻ hơn duy trì domain OpenSearch.

Amazon QuickSight: BI, dashboard và SPICE

Amazon QuickSight là dịch vụ business intelligence (BI) serverless: kết nối nguồn dữ liệu, dựng dashboard tương tác, và nhúng analytics vào ứng dụng. Cập nhật: AWS đã phát triển QuickSight thành Amazon Quick (bộ dịch vụ AI gồm agent, research, automation…); phần BI nay mang tên Amazon Quick Sight, mọi API/SDK QuickSight cũ vẫn hoạt động. Đề SAA-C03 vẫn dùng tên QuickSight.

Khái niệm cần biết

  • Data source → dataset → analysis → dashboard: nguồn có thể là Athena, Redshift, RDS/Aurora, S3, OpenSearch, file upload, SaaS, database on-premises… (danh sách nguồn và chuỗi analysis → dashboard: kiến thức phổ biến). Dashboard là bản chỉ đọc của analysis, chia sẻ cho reader.
  • SPICE (Super-fast, Parallel, In-memory Calculation Engine): import dữ liệu vào bộ nhớ của QuickSight ⇒ truy vấn phân tích nhanh hơn, không phải chờ direct query, và dùng lại nhiều lần không tốn thêm – nguồn tính phí theo truy vấn (như Athena) chỉ bị tính khi tạo và khi refresh dataset. Ngược lại là direct query (truy vấn thẳng nguồn mỗi lần).
  • SPICE capacity cấp theo Region, dùng chung cho mọi người trong account tại Region đó; admin mua thêm hoặc trả bớt. Enterprise edition mã hóa SPICE at rest.
  • Row-level security (RLS) – Enterprise edition: gắn một permissions dataset (cột UserName/GroupName + giá trị được xem) để mỗi reader chỉ thấy các hàng khớp quy tắc (vd sales EMEA chỉ thấy EMEA). User/group không có rule ⇒ không thấy dữ liệu. Tối đa 999 rule/user. Có thêm column-level security (CLS: kiến thức phổ biến).
  • Người dùng/nhóm quản lý qua IAM Identity Center hoặc IAM federation; tính năng ML insights (anomaly detection, forecast) và hỏi đáp ngôn ngữ tự nhiên (Q / Quick) (kiến thức phổ biến).
Mẹo thi (Exam Tip)
  • “Interactive dashboards / BI visualizations for business users”, “embed dashboards in a web app” ⇒ QuickSight.
  • “Dashboard queries against Athena are slow and costly” ⇒ import vào SPICE và refresh theo lịch.
  • “Each regional manager sees only their region’s data in the same dashboard” ⇒ QuickSight row-level security (Enterprise). Nếu yêu cầu áp dụng cho mọi engine truy vấn data lake ⇒ Lake Formation data filter.

Tóm tắt ghi nhớ

Những điều phải thuộc
  • Data lake = S3 + Glue Data Catalog + Lake Formation (schema-on-read, mọi loại dữ liệu). Data warehouse = Redshift (OLAP, schema-on-write, join lớn, BI).
  • Athena: SQL serverless trên S3, trả theo dữ liệu quét ⇒ giảm chi phí bằng Parquet/ORC + nén + partition (Hive-style + MSCK REPAIR TABLE, hoặc partition projection); workgroup giới hạn dữ liệu quét/tách team; Federated Query qua connector (Lambda) cho DynamoDB, RDS, Redshift…; CTAS để đổi định dạng.
  • Glue: Data Catalog (1/account/Region, chỉ metadata), crawler (classifier → bảng/partition), ETL job Spark serverless (DPU), trigger/workflow, job bookmark (mặc định Disable) để xử lý tăng dần, Studio (visual), DataBrew (no-code), FindMatches.
  • Lake Formation: lớp quyền trên Data Catalog + S3; grant/revoke kiểu RDBMS mức database/bảng/cột/hàng/ô (data filters); LF-Tags; credential vending; cross-account qua RAM + resource link; audit CloudTrail.
  • Redshift: leader + compute node (slice), MPP, columnar; RA3/RG managed storage (scale compute/storage độc lập), DC2 < 1 TB; Serverless (không phí khi idle); Spectrum truy vấn S3 không cần nạp (cùng Region, chỉ đọc); concurrency scaling; snapshot tự động ~8 giờ/5 GB-node, retention 1–35 ngày, manual giữ vô hạn, cross-Region copy cho DR; nạp bằng COPY.
  • EMR: Hadoop/Spark/Hive/HBase/Presto; primary (điều phối), core (task + HDFS), task (chỉ tính toán ⇒ Spot); HDFS ephemeral, dữ liệu bền ở S3 (EMRFS); transient cluster auto-terminate; EMR Serverless (pre-initialized capacity), EMR on EKS.
  • OpenSearch: full-text search + log analytics + Dashboards; domain Multi-AZ, dedicated master; UltraWarm (S3, read-only, rẻ) & cold; bảo mật VPC/IAM/Cognito/FGAC; Serverless (collection time series/search/vector, OCU).
  • QuickSight (nay Amazon Quick Sight): BI dashboard, nhúng; SPICE in-memory (nhanh, giảm chi phí truy vấn nguồn); RLS (Enterprise).
