Sau bài này bạn sẽ

  • Phân biệt ba loại KMS key: customer managed key, AWS managed key, AWS owned key – ai kiểm soát key policy, ai rotate, có audit được không, có tốn tiền không.
  • Hiểu sâu envelope encryption ở cấp API (GenerateDataKey, Decrypt, data key, root key) và cơ chế phân quyền KMS: key policy (bắt buộc, mỗi key đúng một), IAM policy, grant, cross-account.
  • Nắm key rotation (tự động 90–2560 ngày, on-demand, manual bằng alias), quy trình xóa key (chờ 7–30 ngày) và multi-Region keys (cùng key ID + key material, mã hóa ở Region này giải mã ở Region khác).
  • Biết khi nào phải dùng AWS CloudHSM (HSM single-tenant, FIPS 140-3 Level 3, bạn tự quản lý user/key) và custom key store, thay vì KMS thông thường.
  • Chọn đúng nơi lưu bí mật/cấu hình: Secrets Manager (rotation tự động, replicate cross-Region) vs SSM Parameter Store (String/StringList/SecureString, Standard/Advanced tier); hiểu ACM (certificate public/private, regional, CloudFront cần us-east-1, managed renewal).

Bức tranh tổng thể: key, secret và certificate

Bảo vệ dữ liệu trên AWS xoay quanh ba loại “vật quý” khác nhau: encryption key (dùng để mã hóa dữ liệu at rest), secret (mật khẩu database, API key, OAuth token) và certificate (mã hóa in transit, chứng minh danh tính website). Mỗi loại có dịch vụ chuyên dụng. Chính tài liệu Secrets Manager khuyến nghị: AWS credentials ⇒ IAM; encryption key ⇒ AWS KMS; SSH key ⇒ EC2 Instance Connect; private key và certificate ⇒ AWS Certificate Manager; còn lại (credential DB, API key, token) ⇒ Secrets Manager.

AWS Key Management Service (KMS)

Dịch vụ quản lý khóa mã hóa

Tạo và kiểm soát KMS key; key material nằm trong HSM FIPS 140-3 Level 3, không bao giờ rời HSM ở dạng plaintext. Tích hợp hầu hết dịch vụ AWS (S3, EBS, RDS, DynamoDB…). SLA 99,999%.

AWS CloudHSM

HSM chuyên dụng (single-tenant) trên cloud

Cluster HSM nằm trong VPC của bạn; bạn toàn quyền quản lý user, key, thuật toán. Chuẩn PKCS #11, JCE, CNG/KSP; SSL offload, Oracle TDE, CA private key.

AWS Secrets Manager

Quản lý, truy xuất và xoay vòng bí mật

Thay credential hard-code bằng lời gọi API lúc runtime; rotation tự động (managed hoặc Lambda); replicate secret sang Region khác; mã hóa bằng KMS.

AWS Systems Manager Parameter Store

Kho cấu hình tập trung

Lưu tham số dạng String / StringList / SecureString theo cây thư mục; Standard tier miễn phí; tích hợp EC2 AMI, ECS, Lambda, CloudFormation, CodeBuild.

AWS Certificate Manager (ACM)

Quản lý chứng chỉ SSL/TLS

Cấp (miễn phí) hoặc import certificate X.509 cho ELB, CloudFront, API Gateway…; tự gia hạn certificate validate bằng DNS; certificate là tài nguyên regional.

AWS Private CA

Cơ quan cấp chứng chỉ riêng

Dựng CA nội bộ để cấp private certificate cho tài nguyên nội bộ (microservice, thiết bị, mTLS); certificate ký bởi Private CA có thể export dùng ở bất kỳ đâu trong PKI nội bộ.

Key material origin, alias và định danh

  • Key material origin: AWS_KMS (KMS tự sinh – mặc định), EXTERNAL (bring your own key (BYOK) – bạn import key material, tự chịu trách nhiệm độ bền của bản gốc, có thể đặt thời hạn hết hạn hoặc gọi DeleteImportedKeyMaterial để thu hồi ngay; key unusable cho tới khi import lại), AWS_CLOUDHSM / EXTERNAL_KEY_STORE (custom key store – phần CloudHSM).
  • Định danh: Key ID (vd 1234abcd-12ab-…, multi-Region bắt đầu bằng mrk-), Key ARN arn:aws:kms:<region>:<account>:key/<key-id>, Alias name alias/ExampleAlias (≤ 256 ký tự, tiền tố aws/ dành riêng cho AWS managed key), Alias ARN.
  • Alias có thể đổi sang trỏ KMS key khác bất cứ lúc nào ⇒ chìa khóa của manual rotation: ứng dụng gọi theo alias, bạn tạo key mới rồi trỏ alias sang.
  • Thao tác mã hóa (cryptographic operations) không làm được trên console KMS – chỉ qua SDK, CLI, Tools for PowerShell.

  • “Encrypt with the least operational overhead and no cost, no audit requirement” ⇒ để dịch vụ mã hóa mặc định bằng AWS owned key.
  • “Generate key material on-premises / keep a copy outside AWS / be able to revoke immediately” ⇒ import key material (BYOK, origin EXTERNAL).
  • “Key was scheduled for deletion by mistake” ⇒ CancelKeyDeletion trong waiting period (7–30 ngày), rồi enable lại key.

Envelope encryption và data key ở cấp API

Mã hóa dữ liệu thì dữ liệu được bảo vệ – nhưng lại phải bảo vệ key. Giải pháp: envelope encryption – mã hóa dữ liệu bằng một data key, rồi mã hóa data key bằng một key khác. Có thể lồng nhiều lớp, nhưng cuối cùng phải có một key ở dạng plaintext để mở mọi lớp – gọi là root key. Trong AWS, root key chính là KMS key, không bao giờ rời HSM của KMS ở dạng chưa mã hóa. Bài 16 đã xem cách S3 dùng cơ chế này; ở đây ta xem nó dưới góc nhìn ứng dụng tự mã hóa.

  • Data key là symmetric key dùng để mã hóa dữ liệu (kể cả dữ liệu lớn). Khác KMS key, data key được trả về cho bạn để dùng ngoài KMS (OpenSSL, AWS Encryption SDK…). KMS sinh, mã hóa, giải mã data key nhưng không lưu, không quản lý, không thực hiện mã hóa bằng data key.
  • GenerateDataKeyWithoutPlaintext: chỉ trả về bản đã mã hóa – dùng khi một thành phần chỉ chuẩn bị key trước, sẽ Decrypt lúc thật sự cần mã hóa.
  • GenerateDataKeyPair: sinh cặp key bất đối xứng được bảo vệ bởi một symmetric KMS key.
  • API Encrypt mã hóa trực tiếp bằng KMS key chỉ nhận lượng dữ liệu nhỏ – tối đa 4 KB (con số này: kiến thức phổ biến, không có trong trang đã đọc) ⇒ hợp cho mật khẩu, key nhỏ; dữ liệu lớn hơn phải dùng envelope encryption.
  • ReEncrypt: giải mã rồi mã hóa lại bằng KMS key khác ngay bên trong KMS, plaintext không lộ ra ngoài.

Lợi ích của envelope encryption (theo tài liệu)

  • Bảo vệ data key: data key đã mã hóa có thể lưu an toàn ngay cạnh dữ liệu.
  • Mã hóa cùng dữ liệu dưới nhiều key: chỉ cần mã hóa lại data key (nhỏ), không phải mã hóa lại toàn bộ dữ liệu lớn.
  • Kết hợp sức mạnh nhiều thuật toán: symmetric nhanh, ciphertext nhỏ; public key tách vai trò, quản lý key dễ hơn.
  • Giảm số lần gọi KMS ⇒ tránh throttling. Nếu vượt quota GenerateDataKey, tài liệu khuyến nghị data key caching của AWS Encryption SDK (với S3: S3 Bucket Keys – Bài 16).
Bẫy thường gặp
  • “Gửi file 500 MB lên KMS bằng Encrypt” – sai: KMS không mã hóa dữ liệu lớn trực tiếp; dùng GenerateDataKey + mã hóa cục bộ (Encryption SDK).
  • Rotate KMS key không re-encrypt dữ liệu và không rotate các data key đã sinh. Data key bị lộ ⇒ rotate KMS key không cứu được; phải mã hóa lại dữ liệu bằng data key mới.
  • Quota request KMS tính trên toàn bộ request trong account + Region, kể cả request S3/EBS… gọi thay bạn. ThrottlingException khi đọc/ghi nhiều object SSE-KMS ⇒ Bucket Keys, data key caching hoặc xin tăng quota (quota request điều chỉnh được, trừ custom key store).
  • Cross-account: KMS throttle account gửi request, không phải account sở hữu key.

Phân quyền KMS: key policy, IAM policy và grant

Key policy là resource policy của KMS key và là cách chính để kiểm soát truy cập. Mỗi KMS key phải có đúng một key policy. Khác biệt quan trọng nhất so với dịch vụ khác: không principal nào – kể cả root user hay người tạo key – có quyền với key nếu không được key policy, IAM policy hoặc grant cho phép rõ ràng (và không bị deny).

  • IAM policy một mình không đủ: nếu key policy không cho phép, IAM policy allow không có tác dụng. (IAM policy vẫn có thể deny mà không cần key policy cho phép.)
  • Default key policy có statement cho phép AWS account (root) ⇒ “bật” IAM policy: từ đó IAM policy trong account cấp được quyền dùng key. Thiếu statement này, chỉ key policy quyết định.
  • Key policy là Regional (khác IAM global): chỉ kiểm soát key trong cùng Region.
  • Nên tách vai trò: key administrators (quản lý: alias, policy, rotate, lên lịch xóa) và key users (Encrypt, Decrypt, GenerateDataKey…) – ý “separation of duties” hay gặp trong đề.
  • Condition key kms:ViaService giới hạn key chỉ được dùng khi request đến qua một dịch vụ cụ thể (vd chỉ qua S3 hoặc RDS ở một Region); kms:CallerAccount giới hạn theo account gọi (hai condition key này: kiến thức phổ biến). kms:RotationPeriodInDays giới hạn giá trị rotation period được phép đặt (có trong tài liệu rotation).

Grant – ủy quyền tạm thời

Grant cho phép principal (IAM identity hoặc service principal) dùng KMS key trong thao tác mã hóa, xem key, tạo/retire grant. Grant thường dùng cho quyền tạm thời: tạo, dùng, rồi xóa mà không phải sửa key policy hay IAM policy. Các dịch vụ AWS tích hợp KMS thường tạo grant thay bạn, dùng quyền, rồi retire ngay khi xong việc.

  • Mỗi grant áp dụng cho đúng một KMS key, chỉ allow (không deny), có thể cấp cho principal ở account khác.
  • Grant constraint: giới hạn theo encryption context (chỉ symmetric) hoặc SourceArn.
  • KMS theo mô hình eventual consistency – grant mới có thể mất vài giây (đôi khi vài phút) để có hiệu lực; dùng grant token để dùng quyền ngay. Xóa grant: retire (retiring principal) hoặc revoke (thường do key admin).
  • Quyền kms:CreateGrant nhạy cảm tương đương kms:PutKeyPolicy – người có nó có thể cho người khác dùng key.
Mẹo thi (Exam Tip)
  • “IAM user has kms:Decrypt in an IAM policy but gets AccessDenied” ⇒ kiểm tra key policy (đã có statement bật IAM policy / cho principal đó chưa).
  • “Share an encrypted EBS snapshot / RDS snapshot / AMI with another account” ⇒ mã hóa bằng customer managed key, sửa key policy cho account đích, rồi share snapshot.
  • “Temporary permission for a principal to use a key without changing policies” ⇒ grant.
  • “Key must only be usable through a specific AWS service” ⇒ condition kms:ViaService trong key policy.
  • “Separate key administrators from key users” ⇒ key policy với hai nhóm statement khác nhau.

Key rotation và Multi-Region keys

Ba cách xoay vòng key

Key rotation chỉ thay key material hiện hành (dùng cho mã hóa mới). KMS key vẫn là cùng một tài nguyên logic: key ID, ARN, Region, policy, quyền không đổi ⇒ ứng dụng và dịch vụ AWS không cần sửa. Khi giải mã, KMS tự chọn đúng phiên bản key material đã dùng để mã hóa.

  • Lý do rotate theo tài liệu: KMS key chủ yếu là wrapping key (key-encryption key) nên rủi ro “cạn key” rất thấp; rotate chủ yếu vì quy định, hợp đồng, compliance. Ưu tiên automatic → on-demand → manual.

Multi-Region keys

Multi-Region keys là các KMS key ở các Region khác nhau dùng thay thế nhau được: mỗi bộ key liên quan có cùng key material và cùng key ID (bắt đầu bằng mrk-), nên dữ liệu mã hóa ở Region này giải mã được ở Region khác mà không cần re-encrypt hay gọi KMS cross-Region.

  • Use case theo tài liệu: disaster recovery (giải mã dữ liệu backup ở Region dự phòng khi Region chính sự cố), global data management, distributed signing, ứng dụng active-active nhiều Region. Dùng với thư viện client-side: AWS Encryption SDK, AWS Database Encryption SDK (DynamoDB), S3 client-side encryption.
  • Không phải global: bạn tự tạo primary rồi replicate vào Region chọn (cùng partition); AWS không bao giờ tự replicate. Không thể chuyển đổi key single-Region ⇄ multi-Region; muốn chuyển phải re-encrypt bằng key mới.
  • Mỗi Region chỉ có một key (primary hoặc replica) của một bộ; đổi được primary Region. Không tạo được multi-Region key trong custom key store. AWS managed key luôn single-Region.
  • Phần lớn dịch vụ AWS vẫn xử lý multi-Region key như single-Region: ví dụ S3 Cross-Region Replication vẫn giải mã rồi mã hóa lại data key bằng key ở Region đích.
  • AWS khuyến nghị: đa số trường hợp dùng key single-Region (cô lập Region, chịu lỗi tốt); chỉ tạo multi-Region key khi cần mã hóa/ký client-side ở nhiều Region.
Mẹo thi (Exam Tip)
  • “Encrypt data in one Region and decrypt in another without re-encrypting / without cross-Region KMS calls”, “client-side encryption for DynamoDB global tables” ⇒ KMS multi-Region keys.
  • “Rotate keys yearly automatically with no code change” ⇒ bật automatic key rotation trên customer managed key.
  • “Rotate every 90 days” ⇒ automatic rotation với rotation period 90 (giá trị nhỏ nhất) – không cần Lambda + EventBridge tạo key mới.
  • Key asymmetric / HMAC / custom key store phải rotate ⇒ manual rotation bằng alias; key imported symmetric ⇒ on-demand rotation.

AWS CloudHSM và custom key store

Hardware security module (HSM) là thiết bị chuyên xử lý thao tác mật mã và lưu trữ key an toàn. AWS CloudHSM cho bạn các HSM single-tenant, general purpose, được kiểm định FIPS 140-2 Level 3 hoặc FIPS 140-3 Level 3 (với cluster ở FIPS mode), chạy trong VPC của bạn, độ trễ thấp. AWS lo phần cứng, provisioning, backup, bảo trì; còn key và user trên HSM thuộc toàn quyền của bạn.

  • E2E encryption, AWS không nhìn thấy: data plane được mã hóa đầu-cuối, không hiển thị với AWS ⇒ bạn tự quản lý user trên HSM (ngoài IAM). Đổi lại, bạn gánh nhiều trách nhiệm hơn dịch vụ managed (mất credential HSM thì AWS không khôi phục được key – kiến thức phổ biến).
  • Toàn quyền thuật toán & key: generate, store, import, export, quản lý và dùng key (session key, token key, symmetric, asymmetric). Hai chế độ cluster: FIPS (chỉ thuật toán được FIPS phê duyệt) và non-FIPS (mọi thuật toán CloudHSM hỗ trợ).
  • Chuẩn API công nghiệp: PKCS #11, Java Cryptographic Extension (JCE), Microsoft CNG / KSP ⇒ di chuyển ứng dụng mật mã/PKI on-premises lên cloud với ít thay đổi.
  • Cluster: tập HSM được CloudHSM tự đồng bộ; thao tác trên một HSM sẽ cập nhật sang các HSM khác. Cluster có 1–28 HSM (quota mặc định 6 HSM / account / Region). Thêm HSM ⇒ tăng hiệu năng; trải HSM qua nhiều AZ ⇒ dự phòng và high availability.
  • Theo dõi bằng Client SDK log, CloudTrail (API quản lý cluster), audit log của HSM và CloudWatch.

Use case của CloudHSM (theo tài liệu)

  • Compliance: HSM FIPS 140-2 Level 3, tuân thủ PCI DSS, PCI PIN, PCI-3DS.
  • Offload SSL/TLS cho web server: chuyển phần tính toán mật mã nặng của HTTPS sang HSM, private key nằm trong HSM.
  • Transparent Data Encryption (TDE): lưu master key TDE của Oracle trong HSM.
  • Bảo vệ private key của issuing CA và ký certificate; ký/xác minh tài liệu; HMAC/CMAC; sinh số ngẫu nhiên.
  • Kết hợp với KMS (custom key store) – key material single-tenant nhưng vẫn có tích hợp dịch vụ của KMS.
  • Nếu chỉ cần dịch vụ managed tạo và kiểm soát key ⇒ tài liệu khuyên dùng KMS; HSM cho thanh toán (payment HSM) ⇒ AWS Payment Cryptography.

  • “Offload SSL/TLS processing from web servers”, “Oracle TDE master key in HSM”, “PKCS #11 application migration” ⇒ CloudHSM.

AWS Secrets Manager: lưu trữ và xoay vòng bí mật

AWS Secrets Manager giúp quản lý, truy xuất và secret rotation cho database credential, application credential, OAuth token, API key… suốt vòng đời. Thay vì hard-coded credentials trong source code, ứng dụng gọi Secrets Manager lúc runtime để lấy credential. Khi bật rotation tự động, secret dài hạn được thay bằng secret ngắn hạn – và vì credential không còn nằm trong ứng dụng, rotate không cần sửa hay deploy lại ứng dụng.

Mã hóa và giá

  • Secret luôn được mã hóa bằng KMS: dùng miễn phí AWS managed key aws/secretsmanager, hoặc customer managed key (tính phí KMS). Muốn chia sẻ secret cross-account ⇒ dùng customer managed key + resource-based policy trên secret (kết hợp cross-account: kiến thức phổ biến).
  • Giá: trả theo số secret/tháng và số API call; không phí khởi tạo; không tính tiền secret đang chờ xóa. Rotation bằng Lambda tính thêm phí Lambda.
  • Mọi event ghi vào CloudTrail dưới dạng management event; có thể giám sát compliance bằng AWS Config rules (vd secret chưa bật rotation).

Replicate secret sang nhiều Region

  • Replica secret có cùng ARN trừ phần Region; Secrets Manager sao chép dữ liệu đã mã hóa + metadata (tag, resource policy). Mỗi replica có thể dùng KMS key riêng của Region đích.
  • Bật rotation trên primary ⇒ giá trị mới tự lan sang mọi replica, không phải quản lý rotation từng nơi.
  • Khi cần (vd failover DR), promote replica thành standalone secret. Use case: ứng dụng đa Region, độ trễ thấp, DR – ví dụ đi cùng Aurora Global Database hoặc RDS cross-Region read replica (có thể thêm cặp key/value chứa endpoint của Region).
Mẹo thi (Exam Tip)
  • “Store database credentials securely and rotate them automatically every 30 days”, “remove hard-coded passwords” ⇒ Secrets Manager với automatic rotation (RDS/Aurora: managed rotation, chọn “manage master user password in Secrets Manager”).
  • “Rotate third-party API keys” ⇒ Secrets Manager + Lambda rotation function tự viết.
  • “Multi-Region application / DR needs the same secret in another Region” ⇒ replicate secret (promote to standalone khi failover).
  • “Rotation Lambda times out connecting to Secrets Manager from a private subnet” ⇒ thêm VPC interface endpoint cho Secrets Manager (hoặc NAT gateway).
  • “Applications must never get an invalid credential during rotation” ⇒ chiến lược alternating users.

AWS Certificate Manager (ACM): certificate SSL/TLS

ACM gánh phần phức tạp của việc tạo, lưu trữ và gia hạn certificate SSL/TLS X.509 public và private cùng private key, để bảo vệ website và ứng dụng trên AWS. Certificate có thể do ACM cấp hoặc import từ CA bên thứ ba. Một certificate có thể bảo vệ một tên miền, nhiều tên miền cụ thể (SAN), wildcard hoặc kết hợp. Không tính phí thêm cho certificate SSL/TLS do ACM quản lý (public) – bạn chỉ trả cho tài nguyên chạy ứng dụng.

Những điểm phải thuộc

  • Certificate là tài nguyên Regional: muốn dùng cùng tên miền với ELB ở nhiều Region ⇒ request/import certificate ở mỗi Region (và validate lại tên miền ở mỗi Region). Không copy certificate giữa Region được.
  • CloudFront: certificate phải được request/import ở US East (N. Virginia) – us-east-1; ACM phân phối nó tới mọi edge location của distribution.
  • Domain validation: DNS validation (thêm CNAME do ACM cung cấp – mỗi SAN một record; Route 53 tạo hộ được) hoặc email validation. HTTP validation chỉ dùng trong quy trình tự động của CloudFront.
  • Wildcard *.example.com bảo vệ một cấp subdomain (login.example.com, test.example.com) – không bảo vệ apex example.com và không bảo vệ a.b.example.com. Muốn cả apex ⇒ thêm example.com vào SAN.
  • Mọi certificate public do ACM cấp được ghi vào Certificate Transparency log (không opt-out được). Private key của certificate được ACM mã hóa bằng KMS.

  • “Imported third-party certificate about to expire” ⇒ ACM không tự gia hạn certificate import – phải re-import; thiết lập cảnh báo qua EventBridge/CloudWatch.
  • “Internal microservices need private certificates / mTLS” ⇒ AWS Private CA (+ ACM).
  • “ALB in two Regions with the same domain” ⇒ request certificate trong từng Region.

Tóm tắt ghi nhớ

Những điều phải thuộc
  • 3 loại KMS key: customer managed (toàn quyền, rotate tùy chọn 90–2560 ngày, phí tháng + request, share cross-account được) · AWS managed (aws/<service>, rotate bắt buộc mỗi năm, xem được không sửa được, không cross-account) · AWS owned (không thấy, miễn phí, không audit).
  • Envelope encryption: GenerateDataKey ⇒ plaintext + encrypted data key; mã hóa cục bộ, lưu encrypted data key cạnh dữ liệu; giải mã gọi Decrypt. KMS không lưu data key. Encrypt trực tiếp chỉ cho dữ liệu nhỏ (4 KB).
  • Key policy: bắt buộc, mỗi key đúng một, Regional; không có key policy cho phép thì IAM allow vô hiệu. Grant: quyền tạm thời, chỉ allow, eventual consistency (grant token). Cross-account = key policy (account sở hữu) + IAM policy (account dùng).
  • Rotation: automatic (symmetric, AWS_KMS) · on-demand (cả imported) · manual bằng alias (asymmetric, HMAC, custom key store). Rotate không re-encrypt dữ liệu cũ; key ID không đổi.
  • Xóa key: waiting period 7–30 ngày (mặc định 30), Pending deletion, hủy được; không chắc ⇒ disable.
  • Multi-Region keys: cùng key ID (mrk-) + key material; mã hóa Region A, giải mã Region B; policy/alias/grant độc lập; không chuyển đổi được từ single-Region; không có trong custom key store.
  • CloudHSM: single-tenant, FIPS 140-2/140-3 Level 3, trong VPC, 1–28 HSM/cluster, nhiều AZ cho HA; user/key ngoài IAM; PKCS #11/JCE/CNG; SSL offload, Oracle TDE, CA key. CloudHSM key store = KMS + key trong HSM của bạn (chỉ symmetric, 1.800 req/s, không SLA).
  • Secrets Manager: credential/API key; rotation managed (RDS, Aurora, DocumentDB, Redshift) hoặc Lambda (create→set→test→finish), dày nhất 4 giờ; single user vs alternating users; staging label AWSCURRENT/AWSPENDING/AWSPREVIOUS; replicate cross-Region; 64 KB.
  • Parameter Store: String / StringList / SecureString; hierarchy; 100 version; Standard (10.000 param, 4 KB, miễn phí) vs Advanced (100.000, 8 KB, policies, shared, tính phí, không hạ cấp); không rotation; tham chiếu secret qua /aws/reference/secretsmanager/.
  • ACM: certificate public miễn phí, 198 ngày, regional; CloudFront ⇒ us-east-1; DNS validation ⇒ tự gia hạn (bắt đầu 45 ngày trước hạn); import ⇒ không tự gia hạn; dùng với ELB, CloudFront, API Gateway…; EC2 trực tiếp: ACME hoặc Nitro Enclaves; private cert ⇒ AWS Private CA.

A company stores sensitive data in Amazon EBS volumes and Amazon RDS databases. A new compliance policy requires the company to control who can use the encryption keys, to audit every use of the keys in AWS CloudTrail, and to rotate the key material every 180 days. The company wants to minimize operational overhead. Which solution meets these requirements?
  1. Use the AWS managed keys aws/ebs and aws/rds and change their rotation period to 180 days.
  2. Use AWS owned keys and enable CloudTrail data events for AWS KMS.
  3. Create AWS KMS customer managed keys, define key policies, and enable automatic key rotation with a rotation period of 180 days.
  4. Create customer managed keys and use an Amazon EventBridge scheduled rule with an AWS Lambda function that creates a new key every 180 days and re-encrypts all volumes.
Đáp án C. Customer managed key cho phép bạn viết key policy, audit qua CloudTrail, và bật automatic rotation với rotation period tùy chỉnh 90–2560 ngày – 180 ngày hợp lệ, không phải viết code. A sai: AWS managed key rotate cố định mỗi năm, không đổi lịch được, không sửa key policy được. B sai: AWS owned key không xem, không audit, không kiểm soát được. D sai: tự tạo key mới và re-encrypt là manual rotation nhiều vận hành – không cần thiết khi automatic rotation hỗ trợ chu kỳ tùy chỉnh.
Một công ty lưu dữ liệu nhạy cảm trên các Amazon EBS volume và cơ sở dữ liệu Amazon RDS. Công ty muốn giảm thiểu chi phí vận hành. Giải pháp nào đáp ứng các yêu cầu này?
  • Dùng các AWS managed key aws/ebs và aws/rds và đổi rotation period của chúng thành 180 ngày.Sai: AWS managed key do AWS rotate cố định mỗi năm, bạn không đổi được chu kỳ và cũng không sửa được key policy để kiểm soát ai dùng key.
  • Dùng AWS owned key và bật CloudTrail data events cho AWS KMS.Sai: AWS owned key nằm trong account của AWS, bạn không xem, không audit được trong CloudTrail và không kiểm soát quyền hay chu kỳ rotate.
  • Tạo AWS KMS customer managed key, định nghĩa key policy, và bật automatic key rotation với rotation period 180 ngày.Đúng: customer managed key cho bạn toàn quyền key policy, mọi lần dùng được ghi vào CloudTrail, và automatic rotation hỗ trợ chu kỳ tùy chỉnh 90–2560 ngày nên 180 ngày hợp lệ mà không phải viết code.

An application running on Amazon EC2 must encrypt files of up to 2 GB before storing them in an on-premises file system. The encryption keys must be protected by AWS KMS, and the application must minimize the number of calls to AWS KMS. What should a solutions architect recommend?

  2. Call the AWS KMS Encrypt operation and pass each file as the plaintext parameter.
  3. Upload each file to Amazon S3 with SSE-KMS, then download it to the on-premises file system.

Đáp án A. Đây là envelope encryption: KMS sinh data key (bản plaintext + bản đã mã hóa), ứng dụng mã hóa dữ liệu lớn cục bộ, lưu encrypted data key cạnh file; giải mã chỉ cần gọi Decrypt cho data key nhỏ. B sai: Encrypt chỉ nhận dữ liệu rất nhỏ (4 KB), không mã hóa file 2 GB. C sai: file tải xuống từ S3 đã được giải mã; SSE-KMS bảo vệ dữ liệu at rest trong S3, không phải trên file system on-premises.   • Gọi thao tác AWS KMS Encrypt và truyền mỗi file vào tham số plaintext.Sai: Encrypt chỉ nhận tối đa 4 KB dữ liệu, không thể mã hóa trực tiếp file 2 GB.

  2. Update the key policy of the customer managed key in Account A to allow Account B to use the key (for example, kms:Decrypt, kms:CreateGrant, kms:DescribeKey).
  3. Create an alias for the key in Account B that points to the key in Account A.

Hiện tại role trong Account B nhận lỗi AccessDenied từ AWS KMS. Solutions architect nên thực hiện HAI hành động nào? (Select TWO – chọn hai.)
  • Re-encrypt các snapshot bằng AWS managed key aws/ebs trong Account A rồi chia sẻ chúng.Sai: snapshot mã hóa bằng AWS managed key không chia sẻ cross-account được vì không thể sửa key policy của AWS managed key.

  • Tạo một alias cho key trong Account B trỏ tới key trong Account A.Sai: alias chỉ có hiệu lực trong account/Region của chính nó và không cấp bất kỳ quyền nào.
  • Gắn một IAM policy vào role trong Account B cho phép các KMS action cần thiết trên key ARN trong Account A.Đúng: account B còn phải ủy quyền cho role của mình qua IAM policy trỏ tới key ARN của Account A – kết hợp với key policy (B) mới đủ quyền.

  1. Create AWS KMS customer managed keys in the standard key store and restrict the key policy to the security team.

Đáp án D. CloudHSM cung cấp HSM single-tenant, FIPS Level 3, user/key do khách hàng quản lý (AWS không truy cập được). An application on Amazon ECS connects to an Amazon Aurora PostgreSQL database by using a username and password that are hard-coded in the application configuration. A security review requires that the credentials be removed from the code and rotated automatically every 30 days, with the LEAST operational overhead. Which solution meets these requirements?
  1. Store the credentials in AWS Secrets Manager, enable automatic rotation (managed rotation for the Aurora master user or a Secrets Manager rotation function for an application user), and retrieve the secret at runtime.
  2. Store the credentials as a SecureString parameter in AWS Systems Manager Parameter Store and configure a parameter policy to rotate it every 30 days.
  3. Store the credentials in an encrypted Amazon S3 object and create a cron job on an EC2 instance that changes the password monthly.
  4. Encrypt the credentials with AWS KMS and store the ciphertext in the ECS task definition environment variables.
Đáp án A. Secrets Manager được thiết kế để thay credential hard-code bằng lời gọi runtime và rotate tự động – Aurora có managed rotation cho master user, còn user ứng dụng dùng Lambda rotation function từ template sẵn. B sai: Parameter Store không có rotation; parameter policies chỉ hết hạn/xóa hoặc gửi thông báo. C sai: tự xây cơ chế rotate – nhiều vận hành. D sai: vẫn phải tự rotate, và giá trị trong task definition khó cập nhật.
Một ứng dụng trên Amazon ECS kết nối tới cơ sở dữ liệu Amazon Aurora PostgreSQL bằng username và password được hard-code trong cấu hình ứng dụng. Một đợt rà soát bảo mật yêu cầu loại bỏ credential khỏi code và tự động rotate chúng mỗi 30 ngày, với LEAST operational overhead (ít công vận hành nhất). Giải pháp nào đáp ứng các yêu cầu này?
  • Lưu credential trong AWS Secrets Manager, bật automatic rotation (managed rotation cho Aurora master user hoặc rotation function của Secrets Manager cho user ứng dụng), và lấy secret khi runtime.Đúng: Secrets Manager được thiết kế đúng cho việc thay credential hard-code bằng lời gọi runtime và hỗ trợ rotate tự động theo lịch, ít vận hành nhất.
  • Lưu credential dưới dạng SecureString parameter trong AWS Systems Manager Parameter Store và cấu hình parameter policy để rotate mỗi 30 ngày.Sai: Parameter Store không có tính năng rotation; parameter policy chỉ đặt hết hạn hoặc gửi thông báo, không đổi mật khẩu.
  • Lưu credential trong một Amazon S3 object được mã hóa và tạo cron job trên một EC2 instance để đổi mật khẩu hằng tháng.Sai: phải tự xây và duy trì cơ chế rotate cùng một EC2 instance, tốn nhiều công vận hành.
  • Mã hóa credential bằng AWS KMS và lưu ciphertext trong biến môi trường của ECS task definition.Sai: không có rotation tự động, và mỗi lần đổi mật khẩu phải cập nhật task definition rồi deploy lại.

A security engineer accidentally scheduled the deletion of an AWS KMS customer managed key that encrypts production Amazon S3 data. The deletion was scheduled 2 days ago with the default settings. Applications now fail when they try to read the data. What should the engineer do to restore access with the LEAST data loss?
  1. Create a new KMS key with the same alias and re-encrypt the objects.
  2. Cancel the key deletion during the waiting period, and then re-enable the key.
  3. Restore the key from the AWS KMS automatic daily backup.
  4. Nothing can be done; the data is permanently unrecoverable.
Đáp án B. Lên lịch xóa key bắt buộc waiting period 7–30 ngày (mặc định 30); trong lúc Pending deletion, key không dùng được cho thao tác mã hóa (vì vậy ứng dụng lỗi) nhưng hủy được. Sau khi cancel, key ở trạng thái disabled ⇒ enable lại là dùng được (trạng thái disabled sau khi hủy: kiến thức phổ biến). A sai: key mới không giải mã được ciphertext của key cũ (metadata gắn với từng key). C sai: KMS không có “backup key” để khôi phục. D sai: còn trong waiting period nên vẫn cứu được.

  • Khôi phục key từ bản backup tự động hằng ngày của AWS KMS.Sai: AWS KMS không có cơ chế backup key tự động để khôi phục.
