AWS CloudFormation: template và stack

CloudFormation giúp bạn mô hình hóa và thiết lập tài nguyên AWS để dành thời gian cho ứng dụng thay vì quản lý tài nguyên. Bạn tạo một template mô tả mọi tài nguyên mong muốn; CloudFormation lo việc cấp phát, cấu hình và xác định thứ tự phụ thuộc. Khi dùng template để tạo một stack, mọi tài nguyên được tạo; xóa stack thì mọi tài nguyên trong stack bị xóa theo.

Ba lợi ích chính theo tài liệu

  1. Đơn giản hóa quản lý hạ tầng – Web app gồm Auto Scaling group, load balancer, RDS: thay vì tạo và nối từng thứ bằng tay, một template tạo tất cả, quản lý như một đơn vị.
  2. Nhân bản hạ tầng nhanh – Mô tả tài nguyên một lần, tạo lại nhất quán, lặp lại được ở nhiều Region (phục vụ high availability / DR).
  3. Kiểm soát & theo dõi thay đổi – Template là file văn bản ⇒ quản lý phiên bản như source code (biết ai đổi gì, khi nào); cần quay lại thì dùng template phiên bản trước.

Template: định dạng và các section

Template là file YAML hoặc JSON, lưu với đuôi bất kỳ (.yaml, .json, .template, .txt). Mỗi resource có một logical ID duy nhất trong template, một Type (vd AWS::EC2::Instance) và các Properties. Sau khi tạo, resource có physical ID thật (vd i-0abc…).

CloudFormation hoạt động thế nào?

  • Quyền: CloudFormation gọi API dịch vụ thay bạn ⇒ bạn cần quyền tạo các tài nguyên đó (quản lý bằng IAM). Template có tạo IAM resource ⇒ phải xác nhận capability CAPABILITY_IAM / CAPABILITY_NAMED_IAM.
  • Thời gian triển khai phụ thuộc resource: database, load balancer, NAT gateway mất lâu nhất. Express mode kết thúc thao tác ngay khi cấu hình được áp dụng, không chờ resource ổn định – dành cho môi trường dev (và mặc định tắt rollback).
  • Rollback khi lỗi: tạo stack lỗi ⇒ xóa resource đã tạo; cập nhật lỗi ⇒ quay về trạng thái ổn định cuối cùng (UPDATE_ROLLBACK_COMPLETE).
  • Stack failure options – chọn Preserve successfully provisioned resources (CLI: --disable-rollback) để giữ resource đã tạo thành công, sửa lỗi rồi Retry / Update / Roll back, không phải làm lại từ đầu.

Drift detection – phát hiện thay đổi ngoài CloudFormation

Người dùng vẫn có thể sửa resource trực tiếp (vd đổi security group trên console EC2). Drift detection so sánh giá trị property thực tế với giá trị mong đợi theo template + parameter. Resource bị coi là drift nếu property bị đổi hoặc resource bị xóa.

  • Trạng thái stack: DRIFTED, IN_SYNC, NOT_CHECKED; trạng thái resource: MODIFIED, DELETED, IN_SYNC, NOT_CHECKED (resource không hỗ trợ drift).
  • Chỉ kiểm tra property được khai báo rõ trong template (không tính giá trị mặc định). Không tự kiểm tra nested stack (phải chạy riêng). Không kiểm tra KMSKeyId, mật khẩu, source code Lambda.
  • Drift detection chỉ phát hiện – không tự sửa. Xử lý: sửa resource về đúng template, hoặc cập nhật template / import resource.

Nested stack vs cross-stack reference

Nested stack

  • Tách cấu hình dùng chung (vd load balancer chuẩn) thành template riêng, gọi bằng resource AWS::CloudFormation::Stack + TemplateURL (S3).
  • Có root stack (cấp cao nhất) và parent stack (cha trực tiếp); nested stack lồng nhiều cấp được.
  • Cập nhật phải bắt đầu từ root stack; chỉ nested stack có thay đổi mới được update. Giúp vượt giới hạn 500 resource/template.
  • Dùng khi các thành phần có chung vòng đời, là tái sử dụng template.

Cross-stack reference (kiến thức phổ biến)

  • Stack A export giá trị trong Outputs (Export: Name); stack B dùng !ImportValue.
  • Các stack độc lập vòng đời, do nhóm khác nhau quản lý – vd stack network (VPC, subnet) dùng chung cho nhiều stack ứng dụng.
  • Không xóa được stack đang có export bị stack khác import; export name là duy nhất trong account/Region.
Mẹo thi (Exam Tip)
  • “Provision the same infrastructure consistently / repeatably in multiple environments or Regions”, “infrastructure in version control” ⇒ CloudFormation template (có Parameters/Mappings cho khác biệt từng môi trường).
  • “Keep the database / S3 data when the stack is deleted” ⇒ DeletionPolicy: Retain hoặc Snapshot.
  • “Prevent accidental updates to the production database during stack updates” ⇒ stack policy Deny Update:* cho logical ID đó. “Prevent the stack from being deleted” ⇒ termination protection.
  • “Detect resources changed manually outside CloudFormation” ⇒ drift detection.
  • “Serverless application template (Lambda + API Gateway + DynamoDB) with simplified syntax” ⇒ AWS SAM (là CloudFormation Transform: AWS::Serverless). Viết hạ tầng bằng ngôn ngữ lập trình (TypeScript, Python) ⇒ AWS CDK – sinh ra CloudFormation template (kiến thức phổ biến).

Change sets: xem trước thay đổi trước khi cập nhật stack

Khi cần sửa tài nguyên đang chạy trong stack, bạn update stack, không cần tạo stack mới rồi xóa stack cũ. Nhưng một số thay đổi nhỏ trên template có thể khiến CloudFormation xóa và tạo lại tài nguyên. Change set là bản tóm tắt các thay đổi đề xuất, cho bạn thấy tác động lên tài nguyên đang chạy (nhất là tài nguyên quan trọng) trước khi thực hiện. CloudFormation chỉ thay đổi stack khi bạn execute change set.

Quy trình dùng change set

  1. Create change set: gửi template đã sửa và/hoặc parameter mới. CloudFormation so sánh với stack hiện tại, chưa đổi gì trên stack.
  2. View change set: xem resource nào được Add / Modify / Remove, có Replacement không, so sánh trước–sau của property và tag.
  3. (Tùy chọn) Tạo thêm change set khác để so sánh phương án; tạo bao nhiêu cũng được.
  4. Execute change set muốn áp dụng. Sau khi execute, CloudFormation xóa mọi change set khác của stack (không còn hợp lệ). Có thể xóa change set để tránh bị execute nhầm.
  • Stack có nested stack: update root stack sẽ khởi động update trên mọi nested stack để xác định cái nào thay đổi; change set có thể bao gồm thay đổi của nested stack.
  • Drift-aware change set: tính đến trạng thái thực tế (đã drift) của resource khi tạo change set.
  • Update stack trên console cũng có phần “Preview your changes”: CloudFormation tạo change set để hiển thị preview.
Mẹo thi (Exam Tip)
  • “Review / preview the impact of changes to a production stack before applying them”, “determine whether the update will replace the RDS instance” ⇒ change set.
  • Change set ≠ drift detection: change set so sánh template mới với stack; drift so sánh stack với thực tế (thay đổi ngoài CloudFormation).
  • Change set ≠ stack policy: change set chỉ cho xem; stack policy mới chặn cập nhật lên resource được bảo vệ.

CloudFormation StackSets: một template, nhiều account và Region

StackSets mở rộng khả năng của stack: tạo, cập nhật hoặc xóa stack trên nhiều account và nhiều Region bằng một thao tác duy nhất. Từ một administrator account, bạn định nghĩa template rồi dùng nó làm cơ sở để cấp phát stack vào các target account ở các Region đã chọn. Đây là cách chuẩn để rải “baseline” (IAM role, Config rule, CloudTrail, VPC chuẩn…) cho cả tổ chức.

Hai mô hình quyền (permission model)

Self-managed permissions

  • Bạn tự tạo IAM role ở administrator account và từng target account để thiết lập quan hệ tin cậy (tên role thường dùng: AWSCloudFormationStackSetAdministrationRole / AWSCloudFormationStackSetExecutionRole, kiến thức phổ biến).
  • Triển khai được tới bất kỳ account nào bạn có quyền tạo IAM role, kể cả account không thuộc Organization.
  • Không có automatic deployment.

Service-managed permissions

  • Triển khai tới account do AWS Organizations quản lý; StackSets tự tạo IAM role thay bạn (cần bật trusted access).
  • Target theo OU; bật automatic deployment ⇒ account mới thêm vào OU tự nhận stack; chuyển account sang OU khác ⇒ stack được gỡ ở OU cũ và tạo theo OU mới.
  • Quản trị từ management account hoặc delegated administrator (member account được ủy quyền).
  • Không hỗ trợ template có macro/transform.

Tùy chọn khi chạy thao tác (operation options)

  • Maximum concurrent accounts: số (hoặc %) account chạy đồng thời. Thao tác chạy từng Region một theo Deployment order. Ví dụ tài liệu: 10 account, 2 Region, 50% ⇒ 5 account đầu ở Region 1, rồi 5 account tiếp, rồi mới sang Region 2. Phần trăm lẻ được làm tròn xuống.
  • Failure tolerance: số (hoặc %) stack được phép lỗi mỗi Region trước khi CloudFormation tự dừng. Vượt ngưỡng ⇒ thao tác FAILED và hủy ở các Region còn lại.
  • Region concurrency: Sequential (mặc định, từng Region theo thứ tự) hoặc Parallel (mọi Region cùng lúc).
  • Concurrency mode: ở chế độ Strict Failure Tolerance, maximum concurrent accounts tối đa bằng failure tolerance + 1.
  • Retain stacks khi xóa: stack tách khỏi StackSet, vẫn chạy và được quản lý tại target account.
  • Trạng thái stack instance: CURRENT (khớp StackSet), OUTDATED (thao tác lỗi/dừng), INOPERABLE, FAILED, SKIPPED_SUSPENDED_ACCOUNT…

  • “Deploy the same IAM roles / Config rules / resources to all accounts in the organization, including future accounts, with least operational overhead” ⇒ StackSets service-managed permissions + target OU/root + automatic deployment.
  • Account không thuộc Organization (vd account của đối tác) ⇒ chỉ dùng được self-managed permissions.
  • “Stop the rollout if more than N accounts fail” ⇒ failure tolerance; “roll out gradually” ⇒ maximum concurrent accounts thấp + Region sequential.
  • Muốn bỏ stack khỏi StackSet nhưng giữ tài nguyên ⇒ delete stack instances với Retain stacks.

AWS Elastic Beanstalk: chỉ cần upload code

Với Elastic Beanstalk, bạn xây dựng và deploy ứng dụng; Beanstalk cấp EC2 instance (hoặc EKS cluster), cấu hình load balancing, thiết lập health monitoring và tự động scale môi trường. Hỗ trợ Go, Java, .NET, Node.js, PHP, Python, Ruby và Docker (tự chọn ngôn ngữ và dependency). Không có phí riêng cho Beanstalk: chỉ trả tiền tài nguyên ứng dụng tiêu thụ.

Beanstalk có hai mode: Standard (chạy trực tiếp trên EC2, tiết kiệm khi chạy ít/nhỏ ứng dụng, hỗ trợ Windows) và Cluster (chạy container trên Amazon EKS, deploy và autoscaling nhanh hơn, tận dụng tài nguyên tốt hơn khi có nhiều environment). Đề SAA-C03 chủ yếu hỏi mode Standard. Bạn làm việc qua console, AWS CLI, EB CLI, GitHub Action, hoặc định nghĩa environment bằng CloudFormation/Terraform.

Web server tier vs worker tier

  • Queue autogenerated là standard queue và có dead-letter queue bật mặc định; dùng queue có sẵn thì tự cấu hình DLQ (có thể là FIFO, nhưng khi đó không có periodic task).
  • Periodic tasks: khai báo trong cron.yaml (name, url, schedule cron); Beanstalk dùng leader election qua bảng DynamoDB để chỉ một instance đẩy task vào queue.
  • Tham số worker: HTTP connections mặc định 50 (1–100), visibility timeout tới 43.200 giây, Max retries mặc định 10 (1–100), inactivity timeout mặc định 180 giây, retention mặc định 345.600 giây (4 ngày), tối đa 1.209.600 giây (14 ngày).
  • Worker tier scale theo CPU (CloudWatch + EC2 Auto Scaling); message chưa xử lý khi instance bị terminate sẽ trở lại queue. Nền tảng .NET on Windows Server không hỗ trợ worker tier.

AWS Systems Manager: managed node, SSM Agent và các tool

AWS Systems Manager (trước đây gọi là Amazon EC2 Systems Manager / Simple Systems Manager – nên viết tắt SSM) giúp bạn xem, quản lý và vận hành node tập trung, ở quy mô lớn trên AWS, on-premises và multicloud. Systems Manager quản lý máy từ xa, an toàn mà không cần đăng nhập vào server – tài liệu nói rõ: không còn cần bastion host, SSH hay remote PowerShell.

Điều kiện để một máy là “managed node”

  1. SSM Agent được cài trên máy (có sẵn trên nhiều AMI chính thức như Amazon Linux, Windows Server – kiến thức phổ biến). Máy on-premises/VM khác đăng ký bằng Hybrid Activation (activation code + ID).
  2. Quyền IAM: khuyến nghị bật Default Host Management Configuration (cấp quyền ở cấp account/Region cho mọi EC2 dùng IMDSv2 và SSM Agent ≥ 3.2.582.0, không cần instance profile), hoặc gắn instance profile có managed policy AmazonSSMManagedInstanceCore. Thêm CloudWatchAgentServerPolicy nếu chạy CloudWatch agent.
  3. Kết nối mạng ra ngoài: SSM Agent chủ động mở kết nối HTTPS 443 tới ssm, ssmmessages, ec2messages ⇒ không cần inbound rule. Subnet private không có internet/NAT ⇒ tạo interface VPC endpoint (AWS PrivateLink).

Run Command và Patch Manager: vận hành fleet ở quy mô lớn

Run Command

Run Command giúp quản lý cấu hình node từ xa, an toàn: tự động hóa tác vụ quản trị thường gặp và thay đổi cấu hình một lần (one-time) ở quy mô lớn. Dùng được từ console, CLI, Tools for PowerShell, SDK. Miễn phí khi dùng trên EC2. Ứng dụng tiêu biểu: cài/bootstrap ứng dụng, xây deployment pipeline, lấy log file khi instance bị gỡ khỏi Auto Scaling group, join instance vào Windows domain.

  • Lệnh được định nghĩa bằng Command document, vd AWS-RunShellScript, AWS-RunPowerShellScript, AWS-RunPatchBaseline (tên document: kiến thức phổ biến).
  • Chọn target bằng tag (Key=tag:Environment,Values=Production), resource group, hoặc danh sách instance ID. Tối đa 5 key, mỗi key 5 value; nhiều key ⇒ node phải thỏa tất cả.
  • Tích hợp EventBridge (Run Command vừa là nguồn event vừa là target của rule), ghi API qua CloudTrail; output có thể ghi vào S3 / CloudWatch Logs (kiến thức phổ biến).
  • API theo mô hình eventual consistency.

Patch Manager

Patch Manager tự động hóa việc vá managed node với cả bản cập nhật bảo mật và loại khác, cho hệ điều hành và ứng dụng (trên Windows Server chỉ ứng dụng do Microsoft phát hành).   • Patch baseline: quy tắc auto-approve patch sau N ngày kể từ khi phát hành, danh sách patch approved / rejected, lọc theo classification (Security, Bugfix…) và severity (Critical, Important…); với Linux có thể chỉ định repository tin cậy. Mỗi baseline cho một loại OS. AWS có predefined baseline (chỉ là ví dụ) – khuyến nghị tạo custom baseline.
  • Compliance do bạn định nghĩa qua baseline: node “compliant” = đã cài mọi patch có sẵn và được duyệt – không có nghĩa là “an toàn tuyệt đối”.

  • Báo cáo compliance dạng CSV vào S3 (một lần hoặc định kỳ); tích hợp Security Hub CSPM, AWS Config, CloudTrail, Organizations.

Tóm tắt ghi nhớ

Key takeaways
  • CloudFormation: template YAML/JSON (chỉ Resources bắt buộc; Parameters, Mappings, Conditions, Outputs, Transform…) → stack quản lý như một đơn vị; lỗi ⇒ rollback; DeletionPolicy Retain/Snapshot giữ dữ liệu khi xóa; stack policy chặn update ngoài ý muốn; drift detection phát hiện sửa tay; nested stack tái sử dụng, Export/ImportValue chia sẻ giữa stack. 500 resource/template.
  • Change set: xem trước Add/Modify/Remove và Replacement trước khi execute; không bảo đảm update thành công.
  • StackSets: một thao tác ⇒ stack ở nhiều account × Region; self-managed (tự tạo role, account bất kỳ) vs service-managed (Organizations, OU, automatic deployment cho account mới); max concurrent accounts, failure tolerance, sequential/parallel Region.
  • Elastic Beanstalk: upload code, Beanstalk lo EC2/ALB/ASG/health; không phí thêm; application → version (S3) → environment; web vs worker tier (SQS + sqsd, cron.yaml); deployment: All at once (nhanh, downtime), Rolling (giảm capacity), Rolling + additional batch (giữ capacity), Immutable (ASG mới, rollback an toàn), Traffic splitting (canary, ALB), Blue/green (Swap URLs, DB phải tách riêng).
  • Systems Manager: managed node = SSM Agent + quyền IAM (AmazonSSMManagedInstanceCore / DHMC) + đường ra 443 (hoặc VPC endpoint ssm, ssmmessages, ec2messages). Session Manager: không inbound port, không bastion, không SSH key, IAM + log S3/CloudWatch/CloudTrail. Run Command: lệnh one-time theo tag, concurrency (mặc định 50) & error threshold (mặc định 0). A company manages its production stack with AWS CloudFormation. An engineer needs to change a property of an Amazon RDS DB instance in the template. The company wants to know before the update whether the change will cause the DB instance to be replaced, and wants no changes made until the operations team approves. What should the engineer do?
  1. Run drift detection on the stack and review the resources with a MODIFIED status.
  2. Create a change set with the modified template, review the Replacement value for the DB instance, and execute the change set only after approval.
  3. Update the stack directly with the Preserve successfully provisioned resources option enabled.
  4. Apply a stack policy that allows Update:Replace on the DB instance.
Đáp án B. Change set tóm tắt các thay đổi đề xuất, cho biết resource nào bị Replacement (physical ID mới, mất dữ liệu), và CloudFormation chỉ đổi stack khi bạn execute. A sai: drift detection so sánh stack với thực tế (sửa tay ngoài CloudFormation), không xem trước template mới. C sai: update trực tiếp là thực hiện luôn; tùy chọn này chỉ giữ resource khi lỗi. D sai: stack policy dùng để chặn/cho phép update, không cho xem trước; và cho phép Replace càng nguy hiểm.
Một công ty quản lý stack production bằng AWS CloudFormation. Một kỹ sư cần thay đổi một thuộc tính của Amazon RDS DB instance trong template. Công ty muốn biết trước khi update liệu thay đổi có khiến DB instance bị thay thế (replace) hay không, và không muốn có bất kỳ thay đổi nào được thực hiện cho tới khi đội vận hành phê duyệt. Kỹ sư nên làm gì?
  • Chạy drift detection trên stack và xem lại các resource có trạng thái MODIFIED.Sai: drift detection so sánh stack hiện tại với cấu hình thực tế (bị sửa tay ngoài CloudFormation), không xem trước tác động của template mới.
  • Tạo một change set với template đã sửa, xem giá trị Replacement của DB instance, và chỉ execute change set sau khi được phê duyệt.Đúng: change set liệt kê thay đổi đề xuất kèm cột Replacement cho biết DB có bị thay thế không, và stack chỉ thay đổi khi bạn execute – khớp với quy trình phê duyệt.
  • Update stack trực tiếp với tùy chọn Preserve successfully provisioned resources được bật.Sai: update trực tiếp là thực hiện ngay, không có bước xem trước hay phê duyệt; tùy chọn này chỉ giữ resource khi update lỗi.
  • Áp dụng một stack policy cho phép Update:Replace trên DB instance.Sai: stack policy chỉ chặn/cho phép update, không cho xem trước; cho phép Replace càng làm tăng rủi ro mất dữ liệu.

A company runs a web application on AWS Elastic Beanstalk in a load-balanced environment. The company wants to deploy new versions with zero downtime. If a deployment fails, the existing instances must not be affected, and rollback must be fast and safe. Full capacity must be maintained during the deployment. Which deployment policy should be used?
  1. Immutable
  2. Rolling
  3. All at once
  4. Rolling with an additional batch
Đáp án A. Immutable khởi chạy một Auto Scaling group thứ hai với instance mới; instance cũ không bị đụng tới; lỗi ⇒ chỉ cần terminate instance mới – rollback nhanh và an toàn, capacity giữ nguyên. B sai: Rolling deploy lên instance hiện có và rút từng batch khỏi phục vụ (giảm capacity); lỗi phải redeploy thủ công. C sai: All at once gây downtime. D sai: giữ được capacity nhưng vẫn deploy lên instance hiện có, rollback là redeploy thủ công.
Một công ty chạy ứng dụng web trên AWS Elastic Beanstalk trong một môi trường load-balanced. Công ty muốn triển khai phiên bản mới mà không có downtime. Nếu triển khai thất bại, các instance hiện có không được bị ảnh hưởng, và rollback phải nhanh và an toàn. Phải duy trì đầy đủ capacity trong suốt quá trình triển khai. Nên dùng deployment policy nào?
  • ImmutableĐúng: Immutable khởi chạy instance mới trong một Auto Scaling group tạm thời, instance cũ không bị đụng tới; nếu lỗi chỉ cần terminate instance mới – rollback nhanh, an toàn và giữ đủ capacity.
  • RollingSai: Rolling deploy lên chính các instance hiện có và rút từng batch khỏi phục vụ nên giảm capacity; lỗi thì phải redeploy thủ công.
  • All at onceSai: All at once deploy lên tất cả instance cùng lúc, gây downtime và ảnh hưởng toàn bộ instance nếu lỗi.
  • Rolling with an additional batchSai: giữ được capacity nhưng vẫn deploy lên instance hiện có, nên lỗi sẽ ảnh hưởng chúng và rollback là redeploy thủ công.
