Chiến thuật giải một câu hỏi tình huống

Mỗi câu SAA-C03 gần như đều có cấu trúc: bối cảnh (công ty đang chạy gì) → vấn đề / yêu cầu mới → ràng buộc (“MOST cost-effective”, “LEAST operational overhead”, “without changing the application code”…) → câu hỏi. Kỹ năng quan trọng nhất là đọc đúng ràng buộc, vì distractor thường đúng về kỹ thuật nhưng vi phạm ràng buộc.

  1. Đọc câu hỏi cuối trước (dòng chứa “Which solution…?”) để biết đề hỏi gì: chọn dịch vụ, chọn cấu hình, hay chọn bước tiếp theo.
  2. Gạch chân từ khóa yêu cầu: highly available, fault tolerant, decouple, real-time, millisecond latency, encrypted, least privilege, serverless…
  3. Gạch chân ràng buộc ưu tiên (xem bảng dưới). Đây là “trọng tài” khi hai phương án cùng đúng.
  4. Loại trừ phương án sai rõ ràng: dịch vụ không làm được việc đó, vi phạm giới hạn (vd Lambda > 15 phút), làm thủ công khi đề yêu cầu tự động, phải sửa code khi đề cấm sửa code.
  5. So hai phương án còn lại theo ràng buộc ưu tiên; chọn phương án dùng managed service và ít thành phần nhất nếu cả hai đều đúng.
  6. Nếu vẫn phân vân quá 2 phút: chọn tạm một đáp án, đánh dấu Flag for review rồi đi tiếp (kiến thức phổ biến về giao diện thi).

Decision guide “AWS Fargate or AWS Lambda?”

AWS Lambda

  • Function chạy theo event; tối đa 15 phút mỗi lần gọi (durable functions điều phối workflow tới 1 năm).
  • Memory 128 MB – 10 GB, CPU tỉ lệ theo memory (tới 6 vCPU); package 250 MB unzipped, container image 10 GB.
  • Concurrency mặc định 1.000/Region (tăng được); scale 1.000 môi trường mỗi 10 giây cho mỗi function.
  • Tính tiền theo request + GB-giây; free tier 1 triệu request và 400.000 GB-giây/tháng ⇒ rẻ với tải thấp, thất thường.
  • Cold start: giảm bằng provisioned concurrency, SnapStart. Truy cập RDS với concurrency cao ⇒ RDS Proxy.

AWS Fargate

  • Serverless cho container (ECS/EKS); không giới hạn thời gian chạy ⇒ hợp tác vụ dài, process liên tục, kết nối bền.
  • CPU 0,25 – 32 vCPU, memory tới 244 GiB, chọn độc lập.
  • Mọi ngôn ngữ đóng gói được vào container; ephemeral storage tới 200 GiB.
  • Tính tiền theo giây (tối thiểu 1 phút) cho vCPU + memory đã cấp; có Fargate Spot ⇒ kinh tế hơn với tải cao, ổn định.
  • Cả hai đủ điều kiện Compute Savings Plans (giảm tới 66%).
Mẹo thi (Exam Tip)
  • “Processing takes 30–60 minutes” hoặc “long-running” ⇒ không chọn Lambda (giới hạn 15 phút) ⇒ Fargate / ECS, AWS Batch, hoặc chia nhỏ bằng Step Functions.
  • “Strict ordering” + decouple ⇒ SQS FIFO (hoặc SNS FIFO cho fan-out có thứ tự); EventBridge không đảm bảo thứ tự.
  • “Route events from a SaaS partner / to another AWS account based on event content” ⇒ EventBridge.
  • “Send the same message to multiple independent consumers” ⇒ SNS fan-out → nhiều SQS queue.

Mẫu 1 – 3-tier web app có tính sẵn sàng cao

3-tier architecture (một dạng multi-tier architecture) chia ứng dụng thành tầng web (presentation), tầng ứng dụng (application/logic) và tầng dữ liệu (data). Reference architecture “Web Application Architecture on AWS” mô tả cách host một ứng dụng web cổ điển: dùng nhiều Availability Zone cho high availability, Application Load Balancer để phân phối traffic, và managed services cho database, cache, shared storage. Đây là kiến trúc “nền” của rất nhiều câu hỏi D1, D2, D3.

11 bước của reference architecture (theo tài liệu AWS)

  1. Route 53 định tuyến traffic từ web client theo đường dẫn cho nội dung tĩnh và động (Bài 24).
  2. CloudFront (CDN) giảm độ trễ khi phân phối nội dung tĩnh (Bài 25).
  3. Amazon S3 lưu nội dung tĩnh và bản backup (Bài 14).
  4. AWS WAF bảo vệ ứng dụng khỏi các kiểu tấn công web phổ biến (Bài 39).
  5. AWS Certificate Manager (ACM) đơn giản hóa quản lý chứng chỉ SSL/TLS (Bài 38).
  6. Internet-facing ALB phân phối traffic tới web server trải trên nhiều AZ (Bài 12).
  7. NAT gateway trong mỗi public subnet cho EC2 ở private subnet ra Internet (Bài 20).
  8. Internal ALB phân phối traffic tới application server trải trên nhiều AZ.
  9. Amazon RDS đơn giản hóa quản trị tầng database (Bài 26).
  10. Nếu truy cập DB đọc nhiều, thêm tầng cache Amazon ElastiCache (Bài 29).
  11. Nếu các server cần file dùng chung, dùng Amazon EFS (Bài 17).

Bẫy thường gặp với 3-tier
  • Một NAT gateway cho mọi AZ là single point of failure (và tốn phí cross-AZ). Reference architecture đặt NAT gateway trong mỗi public subnet.
  • Read replica không phải giải pháp HA của RDS (bất đồng bộ, phải promote) – HA là Multi-AZ. Ngược lại, Multi-AZ standby của RDS (kiểu instance) không phục vụ đọc.
  • Đặt web server ở public subnet với public IP không sai về kỹ thuật, nhưng phương án “instance ở private subnet sau ALB” luôn an toàn hơn.
  • ALB là Layer 7 (path/host routing, HTTP); cần IP tĩnh, TCP/UDP, cực nhiều kết nối ⇒ NLB.

  • “Users sign in with social identity providers” ⇒ Cognito user pool; “temporary AWS credentials to upload directly to S3” ⇒ Cognito identity pool hoặc presigned URL.

Mẫu 3 – Event-driven & decoupled pipeline

Task 2.1 của Exam Guide yêu cầu “designing event-driven, microservice, and/or multi-tier architectures” và “determining the AWS services required to achieve loose coupling”. Trong event-driven architecture, thành phần phát ra event mà không cần biết ai xử lý; bên nhận phản ứng độc lập. Có năm mẫu con bạn cần nhận ra ngay trong đề.

3a. Queue-based load leveling – đệm tải bằng SQS

Producer gửi job vào SQS; worker (EC2 ASG, ECS/Fargate, Lambda) lấy job theo tốc độ của mình. Hàng đợi hấp thụ đỉnh tải, worker hỏng thì message vẫn còn (tối đa 14 ngày). Reference architecture “Autoscaling Asynchronous Job Queues” mô tả đúng mẫu này cho tác vụ nền (tạo tài liệu, ETL, inference):

3b. Fan-out – SNS → nhiều SQS

Một event (vd “đơn hàng mới”) cần được nhiều hệ thống độc lập xử lý (thanh toán, kho, email, analytics). Publish lên SNS topic, mỗi hệ thống có SQS queue riêng subscribe vào topic ⇒ mỗi bên xử lý theo tốc độ riêng, lỗi một bên không ảnh hưởng bên khác; dùng subscription filter policy để mỗi queue chỉ nhận loại message nó cần (Bài 30). Muốn route theo nội dung phức tạp, nguồn SaaS hoặc cross-account ⇒ EventBridge (Bài 31).

3c. S3 event → xử lý tự động

Upload ảnh/tài liệu lên S3 ⇒ S3 Event Notification (hoặc EventBridge) gọi Lambda tạo thumbnail, trích xuất metadata, chạy Rekognition/Textract… Khi lượng file lớn hoặc xử lý chậm, chèn SQS giữa S3 và worker để đệm (Bài 15, Bài 37).

3d. Orchestration – Step Functions & mẫu Saga

Khi quy trình có nhiều bước, cần retry, rẽ nhánh, chờ phê duyệt của người, hoặc bù trừ (rollback) khi một bước lỗi ⇒ AWS Step Functions. Reference architecture “Serverless Architecture for Global Applications” dùng Saga pattern với Step Functions để điều phối giao dịch phân tán theo hướng eventual consistency; “Invoking Asynchronous External APIs” dùng Step Functions cho callback từ dịch vụ bên thứ ba chạy lâu (Bài 31).

3e. Streaming – Kinesis → Firehose → S3 → Athena

Mẹo thi (Exam Tip) – nhận diện mẫu event-driven
  • “Orders are lost when the processing tier fails / traffic spikes overwhelm the backend” ⇒ chèn SQS giữa hai tầng; scale worker theo độ sâu hàng đợi (vd metric backlog per instance).
  • “Process each message exactly once, in order” ⇒ SQS FIFO (exactly-once processing, theo message group).
  • “Messages that fail repeatedly must be isolated for analysis” ⇒ dead-letter queue.
  • “Coordinate multiple Lambda functions with retries, error handling, and a manual approval step” ⇒ Step Functions (không phải chuỗi Lambda gọi nhau).
  • “Ingest streaming data and store in S3 in Parquet with least operational overhead” ⇒ Data Firehose (record format conversion).
Ví dụ đời thường

SQS giống quầy lấy số ở ngân hàng: khách (message) xếp hàng, giao dịch viên (worker) gọi số khi rảnh; đông khách thì mở thêm quầy. SNS giống loa phát thanh: một thông báo, mọi phòng ban cùng nghe. EventBridge giống tổng đài phân luồng: đọc nội dung cuộc gọi rồi chuyển đúng bộ phận, kể cả sang công ty đối tác. Step Functions là người quản lý dự án cầm checklist: bước nào xong, bước nào lỗi phải làm lại, bước nào chờ sếp ký.

Bẫy thường gặp với multi-Region
  • Multi-AZ ≠ multi-Region. Đề chỉ yêu cầu “highly available” ⇒ Multi-AZ là đủ và rẻ hơn; chỉ chọn multi-Region khi đề nói Region outage, DR cross-Region, hoặc người dùng toàn cầu cần độ trễ thấp.
  • Replication liên tục không thay thế backup: xóa nhầm/hỏng dữ liệu sẽ được replicate sang Region kia. Vẫn cần point-in-time backup, S3 versioning.
  • RDS cross-Region read replica (không phải Aurora) promote mất vài phút và có reboot; cần RPO giây, RTO < 1 phút ⇒ Aurora Global Database.
  • Ghi ở nhiều Region với dữ liệu quan hệ cần nhất quán mạnh ⇒ không dùng “write local” của DynamoDB (last writer wins) mà dùng write global.

Bẫy tâm lý trong phòng thi
  • Sa lầy vào một câu dài 5 phút – chính câu đó có thể là câu unscored. Flag và đi tiếp.
  • Đổi đáp án theo cảm giác ở lượt 2: chỉ đổi khi phát hiện một ràng buộc đã đọc sót.
  • Chọn đáp án “xịn nhất” thay vì đáp án “đủ và khớp ràng buộc”: multi-Region active-active khi đề chỉ cần Multi-AZ, Shield Advanced khi đề chỉ hỏi SQL injection…
  • Bỏ sót từ phủ định: “Which option will NOT…”, “…without…”.

Tóm tắt ghi nhớ

Những điểm phải nhớ
  • Đề thi: 65 câu (50 tính điểm + 15 unscored ẩn), multiple choice (1 đúng/4) và multiple response (≥ 2 đúng/≥ 5), scaled score 100–1.000, đậu 720, chấm bù trừ, đoán sai không bị trừ. D1 30% · D2 26% · D3 24% · D4 20%.
  • Quy trình giải: đọc câu hỏi cuối → gạch từ khóa yêu cầu → gạch ràng buộc (least operational overhead, most cost-effective, without code change…) → loại trừ → chọn managed & ít thành phần → flag nếu > 2 phút.
  • 3-tier: Route 53 → CloudFront + WAF + ACM → ALB internet-facing → web ASG (private) → internal ALB → app ASG → RDS Multi-AZ + ElastiCache; S3 cho tĩnh, EFS cho file chung, NAT mỗi AZ; tầng web stateless.
  • Serverless: S3 + CloudFront (OAC) → Cognito → API Gateway → Lambda (≤ 15 phút, 128 MB–10 GB) → DynamoDB; dài/nặng ⇒ Fargate (không giới hạn thời gian, tới 32 vCPU/244 GiB); nhiều kết nối RDS ⇒ RDS Proxy.
  • Event-driven: SQS (pull, ≤ 14 ngày, long polling 20 s) đệm tải; SNS fan-out (push, filter policy); EventBridge (rule, cross-account, SaaS, không thứ tự, retry 24 giờ/185 lần); Step Functions điều phối/saga; Kinesis → Firehose → S3 → Athena.
  • Multi-Region: Route 53 (latency, health check, ARC) hoặc Global Accelerator (anycast, traffic dial); write global = Aurora Global DB (≤ 5 Region phụ, < 1 s, promote < 1 phút); write local = DynamoDB global tables (last writer wins); write partitioned = S3 replication hai chiều. Replication không thay backup.
  • DR: backup & restore (giờ) → pilot light (DB chạy, app tắt) → warm standby (thu nhỏ nhưng chạy) → multi-site (gần 0). Chọn mức vừa đủ theo RPO/RTO.
  • Tài liệu ôn: AWS Decision Guides (so sánh dịch vụ có tiêu chí), Reference Architecture Diagrams (sơ đồ có bước đánh số), Exam Guide (task statements).

Câu hỏi không tính điểm – 15 câu thử nghiệm ẩn trong đề.
Scaled score / Compensatory scoring
Điểm quy đổi 100–1.000 (đậu 720) / chấm điểm bù trừ – không cần đậu từng domain.
Distractor
Phương án gây nhiễu – hợp lý, đúng chủ đề nhưng không khớp ràng buộc.
Flag for review
Đánh dấu để xem lại câu hỏi trong giao diện thi.
Process of elimination
Phương pháp loại trừ các phương án sai trước khi chọn.
AWS Decision Guides
Hướng dẫn ra quyết định – so sánh có cấu trúc giữa các dịch vụ AWS.
Reference architecture
Kiến trúc tham chiếu – sơ đồ mẫu có các bước đánh số do AWS công bố.
Multi-tier / 3-tier architecture
Kiến trúc nhiều tầng / ba tầng: presentation (web), application (logic), data.
Internet-facing / Internal load balancer
Load balancer hướng Internet / nội bộ giữa các tầng.
Single point of failure (SPOF)
Điểm lỗi đơn lẻ – thành phần hỏng thì cả hệ thống ngừng.
Serverless web app
Ứng dụng web phi máy chủ – S3/CloudFront, API Gateway, Lambda, DynamoDB, Cognito.
Event-driven architecture
Kiến trúc hướng sự kiện – thành phần phát và phản ứng với event, ghép lỏng.
Queue-based load leveling
Cân bằng tải bằng hàng đợi – SQS đệm đỉnh tải, worker xử lý theo tốc độ riêng.
Fan-out
Phát tán một message tới nhiều đích – SNS → nhiều SQS.
Orchestration / Choreography
Điều phối tập trung (Step Functions) / phối hợp phi tập trung qua event (EventBridge) – kiến thức phổ biến.
Saga pattern
Mẫu giao dịch phân tán có bù trừ – mỗi bước có thao tác hoàn tác khi bước sau lỗi.
CQRS
Tách luồng lệnh ghi và truy vấn đọc (Command Query Responsibility Segregation).
Event sourcing
Lưu trạng thái dưới dạng chuỗi sự kiện.
Eventual consistency
Nhất quán cuối cùng – dữ liệu đồng bộ sau một khoảng trễ.
Multi-site active/active
Đa địa điểm cùng hoạt động – mọi Region đều phục vụ traffic.
Read local / Write global / Write local / Write partitioned
Đọc tại chỗ / Ghi tập trung / Ghi tại chỗ / Ghi phân vùng theo khóa.
Last writer wins
Bản ghi sau cùng thắng – cách DynamoDB global tables giải quyết xung đột.
Traffic dial
Núm chỉnh % traffic cho mỗi endpoint group của Global Accelerator.
Data plane / Control plane
Mặt phẳng dữ liệu (phục vụ thời gian thực, sẵn sàng cao hơn) / mặt phẳng điều khiển (cấu hình).
Keyword → service mapping
Ánh xạ từ khóa đề sang dịch vụ – phản xạ làm bài.

Câu hỏi luyện tập

A company runs a web application on a single Amazon EC2 instance in a public subnet. The application stores session data in memory and uses a MySQL database installed on the same instance. The company wants the application to be highly available and to tolerate the failure of an Availability Zone with minimal changes to the application code. Which solution meets these requirements?
  1. Create a larger EC2 instance, take hourly EBS snapshots, and copy the snapshots to another Availability Zone.
  2. Place EC2 instances in an Auto Scaling group across two Availability Zones behind an Application Load Balancer, move the database to Amazon RDS for MySQL Multi-AZ, and store session data in Amazon ElastiCache.
  3. Place EC2 instances in an Auto Scaling group in one Availability Zone behind a Network Load Balancer and create an RDS read replica in another Availability Zone.
  4. Rewrite the application as AWS Lambda functions and migrate the database to Amazon DynamoDB global tables.
Đáp án B. Đây là mẫu 3-tier HA: ASG trải 2 AZ sau ALB, DB tách ra RDS Multi-AZ (failover tự động), session đưa ra ElastiCache để tầng web stateless – thay đổi code tối thiểu (đổi chuỗi kết nối DB và session store). A sai: vẫn một instance, snapshot chỉ là backup, không HA. C sai: ASG chỉ một AZ; read replica không phải giải pháp HA (bất đồng bộ, phải promote). D sai: viết lại toàn bộ ứng dụng – trái yêu cầu “minimal changes”, và multi-Region là thừa.
Một công ty chạy ứng dụng web trên một Amazon EC2 instance duy nhất trong public subnet. Ứng dụng lưu dữ liệu session trong bộ nhớ và dùng cơ sở dữ liệu MySQL cài trên cùng instance đó. Công ty muốn ứng dụng có tính sẵn sàng cao (highly available) và chịu được sự cố của một Availability Zone, với thay đổi tối thiểu đối với code ứng dụng. Giải pháp nào đáp ứng các yêu cầu này?
  • Tạo một EC2 instance lớn hơn, chụp EBS snapshot mỗi giờ và copy snapshot sang một Availability Zone khác.Sai: Vẫn chỉ có một instance (single point of failure); snapshot chỉ là backup, không mang lại HA khi AZ lỗi.
  • Đặt các EC2 instance trong một Auto Scaling group trải trên hai Availability Zone phía sau Application Load Balancer, chuyển cơ sở dữ liệu sang Amazon RDS for MySQL Multi-AZ, và lưu dữ liệu session trong Amazon ElastiCache.Đúng: Mẫu 3-tier HA – ASG trên 2 AZ sau ALB, RDS Multi-AZ failover tự động, session đưa ra ElastiCache để tầng web stateless; code chỉ đổi chuỗi kết nối DB và session store.
  • Đặt các EC2 instance trong một Auto Scaling group ở một Availability Zone phía sau Network Load Balancer và tạo RDS read replica ở một Availability Zone khác.Sai: ASG chỉ ở một AZ nên không chịu được AZ lỗi; read replica sao chép bất đồng bộ và phải promote thủ công, không phải giải pháp HA.
  • Viết lại ứng dụng thành các AWS Lambda function và di chuyển cơ sở dữ liệu sang Amazon DynamoDB global tables.Sai: Viết lại toàn bộ ứng dụng trái yêu cầu thay đổi tối thiểu, và global tables đa Region là thừa so với yêu cầu chịu lỗi AZ.
A startup is building a new web application with a single-page front end and a REST API. Traffic is expected to be very low most of the time with unpredictable spikes during marketing campaigns. Users must sign in with email or with their social media accounts. The company has a small team and wants the solution with the LEAST operational overhead. Which architecture should a solutions architect recommend?
  1. Host the front end and API on Amazon EC2 instances in an Auto Scaling group behind an Application Load Balancer, and use Amazon RDS for user accounts.
  2. Deploy the front end and API as containers on Amazon EKS with managed node groups, and use AWS IAM Identity Center for user sign-in.
  3. Host the front end on Amazon EC2, use Amazon API Gateway with AWS Lambda for the API, and store user passwords in AWS Secrets Manager.
  4. Host the front end in Amazon S3 behind Amazon CloudFront, use Amazon Cognito user pools for sign-in, and use Amazon API Gateway with AWS Lambda and Amazon DynamoDB for the API.
Đáp án D. Mẫu serverless web app: S3 + CloudFront cho front-end tĩnh, Cognito user pool (email + social login), API Gateway + Lambda + DynamoDB – tất cả tự co giãn, trả theo mức dùng (gần 0 khi ít traffic), không có server để quản lý. A sai: EC2/ASG/RDS phải vá OS, trả tiền cả lúc nhàn rỗi. B sai: EKS nhiều công vận hành; IAM Identity Center dành cho nhân viên truy cập AWS account/ứng dụng doanh nghiệp, không phải khách hàng đăng nhập bằng mạng xã hội. C sai: vẫn có EC2; Secrets Manager không phải hệ thống quản lý người dùng.
Một startup đang xây dựng ứng dụng web mới với front end dạng single-page và một REST API. Lưu lượng dự kiến rất thấp hầu hết thời gian, với các đợt tăng đột biến không dự đoán được trong các chiến dịch marketing. Người dùng phải đăng nhập bằng email hoặc bằng tài khoản mạng xã hội. Công ty có đội ngũ nhỏ và muốn giải pháp có LEAST operational overhead (ít gánh nặng vận hành nhất). Solutions architect nên đề xuất kiến trúc nào?
  • Host front end và API trên các Amazon EC2 instance trong Auto Scaling group phía sau Application Load Balancer, và dùng Amazon RDS cho tài khoản người dùng.Sai: EC2/ASG/RDS phải vá OS và quản lý server, lại tốn tiền cả lúc nhàn rỗi; còn phải tự xây chức năng đăng nhập mạng xã hội.
  • Triển khai front end và API dưới dạng container trên Amazon EKS với managed node group, và dùng AWS IAM Identity Center cho việc đăng nhập của người dùng.Sai: EKS tốn nhiều công vận hành; IAM Identity Center dành cho nhân viên truy cập AWS account/ứng dụng doanh nghiệp, không phải khách hàng đăng nhập bằng mạng xã hội.
  • Host front end trên Amazon EC2, dùng Amazon API Gateway với AWS Lambda cho API, và lưu mật khẩu người dùng trong AWS Secrets Manager.Sai: Vẫn còn EC2 phải quản lý; Secrets Manager lưu secret của ứng dụng, không phải hệ thống quản lý/đăng nhập người dùng.
  • Host front end trong Amazon S3 phía sau Amazon CloudFront, dùng Amazon Cognito user pool cho việc đăng nhập, và dùng Amazon API Gateway với AWS Lambda và Amazon DynamoDB cho API.Đúng: Kiến trúc serverless hoàn toàn – tự co giãn theo đột biến, trả theo mức dùng (gần 0 khi ít traffic), Cognito hỗ trợ sẵn email và social login, không có server để quản lý.
An e-commerce company publishes an event every time an order is placed. The payment service, the inventory service, and the shipping service must each process every order event independently. If one service is unavailable for several hours, it must not lose any events and must not affect the other services. Which solution meets these requirements?
  1. Publish the order events to an Amazon SNS topic, and subscribe a separate Amazon SQS queue for each service to the topic.
  2. Send the order events to a single Amazon SQS standard queue that all three services poll.
  3. Publish the order events to an Amazon SNS topic and subscribe each service's HTTPS endpoint directly to the topic.
  4. Write the order events to an Amazon S3 bucket and have each service list the bucket every minute.
Đáp án A. Fan-out SNS → SQS: mỗi service có queue riêng, nhận bản sao của mọi event; message được lưu trong queue (tối đa 14 ngày) khi service ngừng vài giờ, và lỗi của một service không ảnh hưởng service khác. B sai: một queue chung ⇒ mỗi message chỉ được một consumer xử lý, không phải cả ba. C sai: SNS không lưu message; endpoint HTTPS ngừng vài giờ có thể mất event sau khi hết retry. D sai: polling S3 là tự chế, nhiều công, không có cơ chế đánh dấu đã xử lý.
Một công ty thương mại điện tử phát ra một event mỗi khi có đơn hàng được đặt. Service thanh toán, service kho hàng và service vận chuyển đều phải xử lý mọi event đơn hàng một cách độc lập. Nếu một service không khả dụng trong vài giờ, nó không được mất bất kỳ event nào và không được ảnh hưởng tới các service khác. Giải pháp nào đáp ứng các yêu cầu này?
  • Publish các event đơn hàng lên một Amazon SNS topic, và cho mỗi service một Amazon SQS queue riêng subscribe vào topic đó.Đúng: Fan-out SNS → SQS – mỗi service nhận bản sao của mọi event trong queue riêng; message được lưu trong queue (tối đa 14 ngày) khi service ngừng, và lỗi của service này không ảnh hưởng service khác.
  • Gửi các event đơn hàng vào một Amazon SQS standard queue duy nhất mà cả ba service cùng poll.Sai: Với một queue chung, mỗi message chỉ được một consumer xử lý, nên không phải cả ba service đều nhận được mọi event.
  • Publish các event đơn hàng lên một Amazon SNS topic và subscribe trực tiếp HTTPS endpoint của từng service vào topic.Sai: SNS không lưu trữ message lâu dài; endpoint HTTPS ngừng vài giờ có thể mất event sau khi hết số lần retry.
  • Ghi các event đơn hàng vào một Amazon S3 bucket và cho mỗi service list bucket mỗi phút.Sai: Polling S3 là cách tự chế, tốn công, không có cơ chế đánh dấu event đã xử lý.
A company has a web tier that accepts document conversion requests and a processing tier of Amazon EC2 instances that converts the documents. During peak hours, the processing tier is overwhelmed and some requests are dropped. Outside peak hours, most processing instances are idle. The company wants to ensure no requests are lost and to optimize costs. What should a solutions architect do?
  1. Increase the size of the processing instances and purchase Reserved Instances for them.
  2. Use an Application Load Balancer between the web tier and the processing tier with sticky sessions.
  3. Have the web tier send requests to an Amazon SQS queue, and run the processing tier in an Auto Scaling group that scales based on the number of messages in the queue.
  4. Have the web tier publish requests to an Amazon SNS topic that the processing instances subscribe to with HTTP endpoints.
Đáp án C. Queue-based load leveling: SQS giữ request an toàn khi tầng xử lý quá tải; ASG scale theo độ sâu hàng đợi (vd backlog per instance) – đông thì thêm instance, vắng thì giảm, tiết kiệm chi phí (giống reference architecture “Autoscaling Asynchronous Job Queues”). A sai: instance to hơn vẫn có giới hạn, và RI cho tài nguyên nhàn rỗi ngoài giờ là lãng phí. B sai: ALB không đệm request; sticky session không giải quyết quá tải. D sai: SNS push không lưu message, instance bận vẫn có thể làm rơi request.
Một công ty có tầng web nhận yêu cầu chuyển đổi tài liệu và một tầng xử lý gồm các Amazon EC2 instance thực hiện chuyển đổi. Vào giờ cao điểm, tầng xử lý bị quá tải và một số yêu cầu bị rơi. Ngoài giờ cao điểm, phần lớn instance xử lý nhàn rỗi. Công ty muốn bảo đảm không yêu cầu nào bị mất và tối ưu chi phí. Solutions architect nên làm gì?
  • Tăng kích thước các instance xử lý và mua Reserved Instance cho chúng.Sai: Instance lớn hơn vẫn có giới hạn khi đột biến, và mua RI cho tài nguyên nhàn rỗi ngoài giờ là lãng phí.
  • Dùng một Application Load Balancer giữa tầng web và tầng xử lý với sticky session.Sai: ALB không đệm (buffer) request; sticky session không giải quyết quá tải hay mất request.
  • Cho tầng web gửi yêu cầu vào một Amazon SQS queue, và chạy tầng xử lý trong Auto Scaling group scale dựa trên số lượng message trong queue.Đúng: SQS giữ yêu cầu an toàn khi tầng xử lý quá tải (không mất request), ASG scale theo độ sâu hàng đợi – đông thì thêm, vắng thì giảm instance để tiết kiệm.
  • Cho tầng web publish yêu cầu lên một Amazon SNS topic mà các instance xử lý subscribe bằng HTTP endpoint.Sai: SNS đẩy (push) message mà không lưu trữ; instance bận vẫn có thể làm rơi request.
A global gaming company runs its player profile service in us-east-1 and eu-west-1. Players must be able to read and write their profiles with single-digit millisecond latency from the Region closest to them, and the service must keep running if an entire Region becomes unavailable. Which TWO actions should a solutions architect take? (Select TWO.)
  1. Store the profiles in an Amazon RDS for MySQL database with a cross-Region read replica.
  2. Store the profiles in Amazon DynamoDB global tables with replicas in both Regions.
  3. Use an Amazon CloudFront distribution with a cache behavior for the profile API to cache write requests.
  4. Use Amazon Route 53 simple routing with one record that points to the us-east-1 endpoint.
  5. Use Amazon Route 53 latency-based routing with health checks that point to the API endpoints in both Regions.
Đáp án B, E. Đây là mẫu multi-Region active-active, write local: DynamoDB global tables cho phép đọc và ghi ở mọi Region (xung đột theo last writer wins), độ trễ mili-giây; Route 53 latency-based routing + health check đưa người chơi tới Region gần nhất và tránh Region hỏng. A sai: read replica chỉ cho đọc, ghi vẫn phải về Region chính; promote mất vài phút. C sai: CloudFront không cache được request ghi. D sai: simple routing một Region – không active-active, không failover.
Một công ty game toàn cầu chạy service hồ sơ người chơi ở us-east-1 và eu-west-1. Người chơi phải đọc và ghi hồ sơ với độ trễ mili-giây một chữ số từ Region gần họ nhất, và service phải tiếp tục chạy nếu toàn bộ một Region không khả dụng. Solutions architect nên thực hiện HAI hành động nào? (Select TWO.)
  • Lưu hồ sơ trong cơ sở dữ liệu Amazon RDS for MySQL với một cross-Region read replica.Sai: Read replica chỉ cho đọc, mọi thao tác ghi vẫn phải về Region chính; khi Region chính lỗi phải promote mất vài phút.
  • Lưu hồ sơ trong Amazon DynamoDB global tables với replica ở cả hai Region.Đúng: Global tables cho phép đọc và ghi ở mọi Region với độ trễ mili-giây một chữ số, và Region còn lại vẫn hoạt động khi một Region lỗi.
  • Dùng một Amazon CloudFront distribution với cache behavior cho profile API để cache các request ghi.Sai: CloudFront không cache được request ghi; ghi vẫn phải tới backend.
  • Dùng Amazon Route 53 simple routing với một record trỏ tới endpoint ở us-east-1.Sai: Simple routing chỉ trỏ một Region – không active-active, không tự failover khi us-east-1 lỗi.
  • Dùng Amazon Route 53 latency-based routing với health check, trỏ tới API endpoint ở cả hai Region.Đúng: Latency-based routing đưa người chơi tới Region có độ trễ thấp nhất, và health check tự loại bỏ Region bị lỗi.
A financial services company runs a relational database workload on Amazon Aurora PostgreSQL in us-east-1. A new regulation requires a disaster recovery plan in another Region with an RPO of a few seconds and an RTO of less than 1 minute. Reads from the DR Region should be possible during normal operations. Which solution meets these requirements?
  1. Convert the cluster to an Amazon Aurora Global Database with a secondary cluster in the DR Region, and promote the secondary cluster during a disaster.
  2. Use AWS Backup to copy daily snapshots of the Aurora cluster to the DR Region and restore them during a disaster.
  3. Export the database to Amazon S3 every hour and enable S3 Cross-Region Replication to the DR Region.
  4. Create a second Aurora cluster in the DR Region and use AWS DMS full-load tasks once a day to copy the data.
Đáp án A. Theo whitepaper DR, Aurora Global Database dùng hạ tầng chuyên dụng, replicate sang Region phụ với độ trễ điển hình dưới 1 giây (RPO giây) và có thể promote Region phụ nhận read/write trong chưa đầy 1 phút (RTO); cluster phụ phục vụ đọc bình thường. B sai: snapshot hằng ngày ⇒ RPO tới 24 giờ, restore mất lâu. C sai: RPO 1 giờ, phải import lại. D sai: full load một lần/ngày ⇒ RPO 24 giờ.
Một công ty dịch vụ tài chính chạy workload cơ sở dữ liệu quan hệ trên Amazon Aurora PostgreSQL ở us-east-1. Một quy định mới yêu cầu kế hoạch khôi phục thảm họa ở một Region khác với RPO vài giây và RTO dưới 1 phút. Trong vận hành bình thường, phải có thể đọc dữ liệu từ Region DR. Giải pháp nào đáp ứng các yêu cầu này?
  • Chuyển cluster thành Amazon Aurora Global Database với một secondary cluster ở Region DR, và promote secondary cluster khi có thảm họa.Đúng: Aurora Global Database sao chép sang Region phụ với độ trễ điển hình dưới 1 giây (RPO giây), promote trong chưa đầy 1 phút (RTO), và cluster phụ phục vụ đọc trong lúc bình thường.
  • Dùng AWS Backup để copy snapshot hằng ngày của Aurora cluster sang Region DR và restore khi có thảm họa.Sai: Snapshot hằng ngày cho RPO tới 24 giờ, restore mất lâu, và không đọc được ở Region DR lúc bình thường.
  • Export cơ sở dữ liệu sang Amazon S3 mỗi giờ và bật S3 Cross-Region Replication sang Region DR.Sai: RPO tới 1 giờ và phải import lại dữ liệu khi thảm họa, RTO vượt xa 1 phút.
  • Tạo một Aurora cluster thứ hai ở Region DR và dùng các task full load của AWS DMS mỗi ngày một lần để copy dữ liệu.Sai: Full load mỗi ngày một lần cho RPO tới 24 giờ, không đạt yêu cầu vài giây.
A company collects clickstream data from its website at a rate of several thousand events per second. The data must be stored in Amazon S3 in Apache Parquet format within a few minutes of arrival so that analysts can run SQL queries on it. The company wants the solution with the LEAST operational overhead. Which solution meets these requirements?
  1. Send the events to an Amazon SQS queue and use a fleet of EC2 instances to convert the events to Parquet and write them to S3 every few minutes.
  2. Write the events directly to an Amazon RDS database and run a nightly export job to Amazon S3.
  3. Send the events to Amazon Kinesis Data Streams and write a custom consumer application on EC2 that converts the data and stores it in Amazon Redshift.
  4. Send the events to Amazon Data Firehose with record format conversion to Parquet, deliver them to Amazon S3, and query the data with Amazon Athena.
Đáp án D. Firehose là dịch vụ managed để nạp streaming data vào S3 (near real-time, theo buffer), có sẵn chuyển đổi định dạng sang Parquet (dùng schema trong Glue Data Catalog); Athena truy vấn SQL serverless trên S3 – không có server nào để quản lý. A sai: tự viết code chuyển đổi và quản lý EC2. B sai: RDS không hợp làm đích ingest clickstream tốc độ cao; export hằng đêm vi phạm “within a few minutes”. C sai: consumer tự viết trên EC2 nhiều công vận hành và đích là Redshift chứ không phải S3 Parquet.
Một công ty thu thập dữ liệu clickstream từ website với tốc độ vài nghìn event mỗi giây. Dữ liệu phải được lưu trong Amazon S3 ở định dạng Apache Parquet trong vòng vài phút kể từ khi đến để các nhà phân tích có thể chạy truy vấn SQL. Công ty muốn giải pháp có LEAST operational overhead (ít gánh nặng vận hành nhất). Giải pháp nào đáp ứng các yêu cầu này?
  • Gửi các event vào một Amazon SQS queue và dùng một nhóm EC2 instance để chuyển đổi event sang Parquet rồi ghi vào S3 mỗi vài phút.Sai: Phải tự viết code chuyển đổi và quản lý nhóm EC2 – gánh vận hành lớn.
  • Ghi các event trực tiếp vào một cơ sở dữ liệu Amazon RDS và chạy job export hằng đêm sang Amazon S3.Sai: RDS không phù hợp làm đích ingest clickstream tốc độ cao, và export hằng đêm vi phạm yêu cầu "trong vòng vài phút".
  • Gửi các event vào Amazon Kinesis Data Streams và viết một ứng dụng consumer tùy chỉnh trên EC2 để chuyển đổi dữ liệu và lưu vào Amazon Redshift.Sai: Consumer tự viết trên EC2 tốn công vận hành, và đích là Redshift chứ không phải S3 dạng Parquet.
  • Gửi các event vào Amazon Data Firehose với tính năng record format conversion sang Parquet, giao vào Amazon S3, và truy vấn dữ liệu bằng Amazon Athena.Đúng: Firehose là dịch vụ managed nạp streaming data vào S3 gần real-time, có sẵn chuyển đổi sang Parquet; Athena truy vấn SQL serverless – không có server nào để quản lý.
A media company needs to transcode uploaded video files. Each transcoding job takes between 20 and 90 minutes and needs 4 vCPUs and 16 GB of memory. The jobs are packaged as a container image. Uploads are sporadic, and the company does not want to manage servers or clusters of EC2 instances. Which compute option should a solutions architect choose?
  1. AWS Lambda functions triggered by Amazon S3 event notifications, configured with 10 GB of memory.
  2. An Amazon EC2 Auto Scaling group of compute optimized instances with a minimum capacity of two instances.
  3. Amazon ECS tasks on AWS Fargate, started for each upload (for example, by an Amazon EventBridge rule on the S3 upload event).
  4. Amazon Lightsail instances that run the container image.
Đáp án C. Theo decision guide “Fargate or Lambda?”, Fargate chạy container không giới hạn thời gian, chọn được CPU (tới 32 vCPU) và memory (tới 244 GiB) độc lập, không cần quản lý server; EventBridge rule có thể chạy ECS task khi có file mới. A sai: Lambda tối đa 15 phút mỗi lần gọi – job 20–90 phút sẽ bị dừng. B sai: phải quản lý EC2 và trả tiền cho tối thiểu 2 instance kể cả khi không có upload. D sai: Lightsail vẫn là server tự quản, không tự co giãn theo job.
Một công ty truyền thông cần transcode các file video được tải lên. Mỗi job transcode mất từ 20 đến 90 phút và cần 4 vCPU cùng 16 GB bộ nhớ. Các job được đóng gói dưới dạng container image. Việc tải lên diễn ra rời rạc, và công ty không muốn quản lý server hay cluster EC2 instance. Solutions architect nên chọn phương án compute nào?
  • Các AWS Lambda function được kích hoạt bởi Amazon S3 event notification, cấu hình 10 GB bộ nhớ.Sai: Lambda chạy tối đa 15 phút mỗi lần gọi, job 20–90 phút sẽ bị dừng giữa chừng.
  • Một Amazon EC2 Auto Scaling group gồm các instance compute optimized với capacity tối thiểu hai instance.Sai: Phải quản lý EC2 (trái yêu cầu) và trả tiền cho tối thiểu 2 instance kể cả khi không có upload.
  • Các Amazon ECS task trên AWS Fargate, được khởi chạy cho mỗi lần tải lên (ví dụ bằng một Amazon EventBridge rule bắt sự kiện upload lên S3).Đúng: Fargate chạy container không giới hạn thời gian, chọn CPU/memory linh hoạt (đủ 4 vCPU/16 GB), không cần quản lý server và chỉ trả tiền khi task chạy.
  • Các Amazon Lightsail instance chạy container image.Sai: Lightsail vẫn là server phải tự quản lý, chạy thường trực và không tự co giãn theo job.
A company processes loan applications in several steps: validate the application, run a credit check by calling a third-party API, wait for a human underwriter to approve, and then create the account. If account creation fails, previous steps must be compensated (for example, the credit hold must be released). Each step is implemented as an AWS Lambda function. The company wants built-in retries, error handling, and visibility into each execution with the LEAST custom code. What should a solutions architect use?
  1. Have each Lambda function invoke the next function directly and store progress in Amazon DynamoDB.
  2. An AWS Step Functions state machine that orchestrates the Lambda functions, uses a wait-for-callback task for the human approval, and uses Catch states to run compensating steps.
  3. An Amazon SQS FIFO queue between each pair of Lambda functions.
  4. An Amazon EventBridge rule for each step that matches the output of the previous step.
Đáp án B. Quy trình nhiều bước có retry, xử lý lỗi, chờ con người và bù trừ (saga) là trường hợp kinh điển của Step Functions: Retry/Catch có sẵn, task token chờ callback, lịch sử từng execution trực quan. A sai: Lambda gọi nhau là “chuỗi tự chế”, phải tự viết retry, bù trừ, theo dõi trạng thái. C sai: SQS chỉ đệm message, không có logic điều phối, không chờ phê duyệt. D sai: choreography qua EventBridge không cho cái nhìn tập trung và phải tự xây logic bù trừ.
Một công ty xử lý hồ sơ vay vốn qua nhiều bước: xác thực hồ sơ, kiểm tra tín dụng bằng cách gọi API của bên thứ ba, chờ chuyên viên thẩm định (con người) phê duyệt, rồi tạo tài khoản. Nếu tạo tài khoản thất bại, các bước trước đó phải được bù trừ (ví dụ phải giải phóng khoản giữ tín dụng). Mỗi bước được triển khai dưới dạng một AWS Lambda function. Công ty muốn có sẵn cơ chế retry, xử lý lỗi và khả năng quan sát từng lần thực thi với LEAST custom code (ít code tự viết nhất). Solutions architect nên dùng gì?
  • Cho mỗi Lambda function gọi trực tiếp function kế tiếp và lưu tiến trình trong Amazon DynamoDB.Sai: Lambda gọi nhau là chuỗi tự chế, phải tự viết retry, bù trừ và theo dõi trạng thái – nhiều code.
  • Một AWS Step Functions state machine điều phối các Lambda function, dùng task wait-for-callback cho bước phê duyệt của con người, và dùng Catch để chạy các bước bù trừ.Đúng: Step Functions có sẵn Retry/Catch, task token chờ callback cho phê duyệt thủ công, mẫu saga bù trừ và lịch sử từng execution trực quan – ít code nhất.
  • Một Amazon SQS FIFO queue giữa mỗi cặp Lambda function.Sai: SQS chỉ đệm message, không có logic điều phối, không hỗ trợ chờ phê duyệt hay bù trừ.
  • Một Amazon EventBridge rule cho mỗi bước, khớp với output của bước trước đó.Sai: Choreography qua EventBridge không cho cái nhìn tập trung về từng execution và phải tự xây logic bù trừ.
A company is deploying a three-tier web application on AWS. The web tier runs on EC2 instances behind an internet-facing Application Load Balancer, and the database tier runs on Amazon RDS. The security team requires protection against common web exploits such as SQL injection, and requires that the database be reachable only from the application tier. Which TWO actions meet these requirements? (Select TWO.)
  1. Associate an AWS WAF web ACL with managed rule groups for SQL injection with the Application Load Balancer.
  2. Enable Amazon GuardDuty to block SQL injection requests.
  3. Place the RDS DB instance in a public subnet and restrict access with a network ACL that allows the company's office IP range.
  4. Place the RDS DB instance in private subnets and configure its security group to allow inbound database traffic only from the security group of the application tier instances.
  5. Enable encryption at rest on the RDS DB instance with AWS KMS.
Đáp án A, D. AWS WAF gắn vào ALB (hoặc CloudFront) với managed rule SQL injection chặn tấn công lớp 7 (A). DB ở private subnet, security group tham chiếu security group của app tier ⇒ chỉ app tier kết nối được, kể cả khi ASG thay instance/IP (D). B sai: GuardDuty phát hiện mối đe dọa, không chặn request web. C sai: DB ở public subnet và mở cho IP văn phòng trái yêu cầu “only from the application tier”. E sai: mã hóa at rest là tốt nhưng không giải quyết SQL injection hay kiểm soát truy cập mạng.
Một công ty đang triển khai ứng dụng web ba tầng trên AWS. Tầng web chạy trên các EC2 instance phía sau một Application Load Balancer internet-facing, và tầng cơ sở dữ liệu chạy trên Amazon RDS. Đội bảo mật yêu cầu bảo vệ trước các kiểu tấn công web phổ biến như SQL injection, và yêu cầu cơ sở dữ liệu chỉ có thể truy cập được từ tầng ứng dụng. HAI hành động nào đáp ứng các yêu cầu này? (Select TWO.)
  • Gắn một AWS WAF web ACL với các managed rule group chống SQL injection vào Application Load Balancer.Đúng: AWS WAF gắn vào ALB với managed rule SQL injection chặn các tấn công web lớp 7 trước khi tới ứng dụng.
  • Bật Amazon GuardDuty để chặn các request SQL injection.Sai: GuardDuty chỉ phát hiện mối đe dọa từ log, không chặn request web.
  • Đặt RDS DB instance trong public subnet và giới hạn truy cập bằng network ACL cho phép dải IP văn phòng công ty.Sai: DB ở public subnet và mở cho IP văn phòng trái yêu cầu chỉ tầng ứng dụng mới truy cập được.
  • Đặt RDS DB instance trong các private subnet và cấu hình security group của nó chỉ cho phép traffic cơ sở dữ liệu inbound từ security group của các instance tầng ứng dụng.Đúng: Private subnet cộng security group tham chiếu security group của app tier bảo đảm chỉ tầng ứng dụng kết nối được, kể cả khi ASG thay instance/IP.
  • Bật mã hóa at rest cho RDS DB instance bằng AWS KMS.Sai: Mã hóa at rest bảo vệ dữ liệu lưu trữ, không chống SQL injection hay kiểm soát truy cập mạng.
